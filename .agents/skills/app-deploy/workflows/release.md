# Cut a release

Run when cutting, shipping or releasing a kendex version. Read [§ Release kendex](../SKILL.md#release-kendex) for the version, [§ Major tag](../SKILL.md#major-tag) and [§ Secrets](../SKILL.md#secrets) before step 1.

Before collation, run `tools/release-previous-tag`. It prints the newest published stable `vX.Y.Z` release tag and fetches it from `origin`. Use that tag for the file comparison with `HEAD`. Stop if the lookup, fetch or comparison fails.

1. From a clean index and working tree, set `COMMIT_GUARDS_CHANGELOG_COLLATE=1` in the environment and run `.agents/skills/commit-guards/scripts/changelog-entries --collate`. It folds the program fragments into `CHANGELOG.md`'s `Unreleased` under their sections. A nonzero exit halts the release: fix the cause before retrying.
2. Bump the workspace `version` in `Cargo.toml` and the version in `crates/app/tauri.conf.json`. Both must equal the tag minus the `v`, or the update feed no-ops or loops. Move the collated entries under a new `## [<version>] - <date>` heading, leaving an empty `## [Unreleased]` above it. The collator writes no link footer: point `[Unreleased]:` at `compare/v<version>..HEAD` and add `[<version>]: https://github.com/vanillagreencom/kendex/releases/tag/v<version>` above the previous version's line.
3. Commit with `COMMIT_GUARDS_CHANGELOG_COLLATE=1`. That declaration makes `CHANGELOG.md` count as the entry for the version bump under `crates/`; the `commit-msg` lane refuses the commit without it. The committed release branch fixes this release's changelog entries. Later queue fragments stay for the next release only when their kinds fit the collated version. An Added fragment needs a minor or major; a Breaking fragment needs a major. Merge with the github skill's `pr-merge`. Read `gh pr view <PR> --json state,mergeCommit,headRefOid`. Require `state` to be `MERGED` and record `mergeCommit.oid` as the release commit. This is the merged commit, including the new commit from a squash merge. Fetch `origin main` and `refs/pull/<PR>/head`. Require `git merge-base --is-ancestor <mergeCommit.oid> origin/main` to pass. The release workflow reads `changelog.d` at this proven collation head and requires that it contain only `changelog.d/README.md`. Run `.agents/skills/commit-guards/scripts/changelog-entries --release <mergeCommit.oid>` to check the installed code's release level. Stop on a failed read, ancestry check or changelog check. If the queue or release check names an incompatible entry and required level, re-collate the unpublished release with those entries at the correct version. Commit the inputs cleanly before step 1 and repeat step 2. Select the correction pull request's merge commit. Record the requested tag, pull request number and merged commit, then start the release workflow on `main`:

   ```sh
   gh workflow run release.yml --repo vanillagreencom/kendex --ref main -f tag="v<version>" -f release_commit="<mergeCommit.oid>" -f release_pr="<PR>"
   ```

   Keep the returned run URL. If the CLI returns no URL, find the `workflow_dispatch` run on `main` with that tag and source commit in its title. Watch it with `gh run watch <RUN_ID> --repo vanillagreencom/kendex --exit-status` through the orch job runner. The workflow builds the selected merged commit, which excludes later main changes, and creates its version tag. Fetch it with `git fetch origin tag v<version>`. Require `git rev-parse v<version>^{commit}` to equal the recorded commit. A failed fetch, failed read or different commit halts the release. Retry failed jobs in the same run. Before a fresh dispatch, inspect `gh release view v<version>` if publication may have completed; do not make a published stable release a draft again. A fresh retry uses the same tag and commit. The workflow never moves an existing version tag.

4. Read the selected version's section from `CHANGELOG.md` at the recorded release commit. Set the draft's description to that program section through the existing GitHub release editor, then review and publish it. Keep its version, date, migration instructions and links. Include no catalog package entries. Publishing is what makes the version "latest" for self-update.

   After publishing, the lane sends `published v<version> at <SHA>` to its overseer with `lane-mail notice`, `<SHA>` as [§ Major tag](../SKILL.md#major-tag) defines it. The overseer relays the notice with `lane-mail notice --item overseer --to owner`. The Jarvis session reads it while it holds that overseer's mailbox ([The Jarvis session hold](../../../../skills/slack/README.md#the-jarvis-session-hold)). The notice reaches the owner when no Jarvis session runs.

   The major tag then moves per [§ Major tag](../SKILL.md#major-tag).

5. Once the release is published, bump the per-release pins `packaging/README.md` § Per release lists: `version` and the checksums in the Homebrew formula and cask, and `pkgver` and `sha256sums` in the Arch recipes where they are not already current. The pin bump writes no changelog fragment: the [release standard](../../../../changelog.d/README.md#release-standard) keeps recipe pins out of the release notes. Landing that bump on `main` is the push that runs the two publishers below.

Distro packaging runs itself once the recipes reach `main`: `.github/workflows/publish-aur.yml` (`tools/publish-aur`) pushes the four Arch packages `kendex`, `kendex-bin`, `kendex-git` and `kendex-cli-git` to the AUR, and `.github/workflows/publish-homebrew.yml` (`tools/publish-homebrew`) pushes the formula and cask to the Homebrew tap. Both run on every push to `main` touching their recipes, their tools or their workflow. The AUR publisher defers a package whose pinned downloads are not up yet and lands it when the release is published; the Homebrew push does not check, so a Homebrew version bump must not reach `main` before its release is published (`packaging/README.md` § Publishing).
