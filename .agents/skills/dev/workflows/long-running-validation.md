# Long-running validation

Read [Long-Running Validation](../SKILL.md#long-running-validation) before starting, polling or resuming validation.

`.agents/skills/orch/scripts/dev-validate-run --worktree [WORKTREE_PATH] --run-id [RUN_ID]` starts the run the round's admission named, `[RUN_ID]` being the id the admission step of [dev-implement.md § 5. Validate](dev-implement.md#5-validate) minted. It starts the admitted directory as `orch-runtime validate start` does: it resolves the mode from the project's declaration, records the run's mode and job on the round's admitted `validate` entry, launches the run's job and prints the `state=started` line; when the run ends, the runtime closes that entry with the run's verdict and sends this lane its end notice, mail on the lane's channel. The bare start without `--run-id`, `.agents/skills/orch/scripts/dev-validate-run --worktree [WORKTREE_PATH]`, is the ad-hoc route for a delegation that carries no admission: the runtime mints the id and records the run files. Both routes bound the command with `DEV_VALIDATE_TIMEOUT_SECS`, detach it so the run outlives the shell that launched it, print the run directory first and the verdict last, and resume through the same `--wait --run-dir` poll. The validation command contract is in orch's `references/artifact-checks.md` § Validation command output. The wait's cap is that setting plus the kill grace and one poll interval; never choose any of those numbers yourself. Full contract: `dev-validate-run --help`.

Every harness row below plans without a spawned harness child, a harness process a tool starts in this session: no row names such a child's sign-in as proven, so a lane that needs a second agent takes the harness's own subagent route, which runs in the lane's session.

- **Claude Code.** Run the BARE command `.agents/skills/orch/scripts/dev-validate-run --worktree [WORKTREE_PATH] --run-id [RUN_ID]` in the foreground, never piped or chained, under the harness's maximum command timeout; it starts the run detached and then blocks until the verdict. A run that outlasts that timeout comes back cut off or moved to the background: read the `run-dir=` value off the `state=started` line in the output it returned or in the output file the harness names, and take the foreground poll `.agents/skills/orch/scripts/dev-validate-run --wait --run-dir [RUN_DIR]` as the turn's next step, under the same timeout because one call runs for up to nine minutes, repeating for as long as it exits 3 and prints `state=running`. Never end the turn while the run is still running and never wait for a completion notice: a subagent whose turn has ended is not woken when the run ends, the runtime's end notice reaches the lane's mailbox and never that subagent, and the harness can kill a background shell on a low-memory heuristic that fires with free memory to spare. Neither loses the verdict, because the sentinel is on disk. The verdict is the `validate=` value on the `state=done` line: `pass`, `FAILING`, or `no-verdict` for a timeout or unavailable host check, which [dev-implement.md § 5. Validate](dev-implement.md#5-validate) routes; the log holds command output and never an exit status. `state=timeout` and `state=lost` are both failed validations. A tool-started `claude -p` is the spawned child this workflow forbids: its sign-in is unproven. Then resume the tail.
- **Codex.** Start `.agents/skills/orch/scripts/dev-validate-run --worktree [WORKTREE_PATH] --run-id [RUN_ID]` with `exec_command`; while a call returns a `session_id`, hold it inside the turn with empty `write_stdin` polls on it, and a return that carries an `exit_code` ended the command. A session that printed `state=started` and then ended without a verdict line or an exit-2 refusal resumes with `.agents/skills/orch/scripts/dev-validate-run --wait --run-dir [RUN_DIR]` the same way, repeated while it exits 3 and prints `state=running`; a refusal routes by [dev-implement.md § 5. Validate](dev-implement.md#5-validate) and is never resumed. The calls and their limits are [codex-runtime.md § Validation wait](../../orch/references/codex-runtime.md#validation-wait). Once the run has started, never end the turn before its verdict: Codex starts no turn when the run ends, and nothing wakes a hosted Codex lane. Read the verdict as Claude Code does, then resume the tail. A tool-started `codex exec` is the spawned child this workflow forbids: its sign-in is unproven. For every other long command, hold its job-runner completion inside the turn through the Codex row in [waiter-launch.md § Completion](../../orch/references/waiter-launch.md#completion).
- **Pi.** Pi sets no default foreground timeout. A foreground ceiling comes from the host or an explicit tool timeout. Start `.agents/skills/orch/scripts/dev-validate-run --worktree [WORKTREE_PATH] --run-id [RUN_ID]` through `bg_task action: "spawn"` with `notifyOnExit: true`. Keep the task id and the `run-dir=` value from the task log's `state=started` line. Read the task log on its exit wake and interpret the verdict as Claude Code does. If the task ends without a verdict, resume `.agents/skills/orch/scripts/dev-validate-run --wait --run-dir [RUN_DIR]` through the same background mechanism, repeating while it prints `state=running` and exits 3. Resume the completion tail after reading the verdict. A Pi background child that starts this run needs a `bgTaskTimeoutMs` deadline that covers its work before the run plus `DEV_VALIDATE_TIMEOUT_SECS`, because the deadline counts from the child's launch; otherwise the deadline kills it before its completion tail. A Pi process a tool starts is the spawned child this workflow forbids: its sign-in is unproven. For other long commands, follow the [Long-Running Validation](../SKILL.md#long-running-validation) command-routing rule.
- **A host whose agent warden kills detached jobs**, on any harness: add `--attached` to the start command and run it in the foreground, under a harness timeout above the `cap-secs=` value on its `state=started` line. The route fits only a harness whose call can outlast that cap. The run then stays inside the agent's own process tree and writes the same run directory, sentinel and record, which `orch-runtime dev-return --text write` takes as it takes a detached run. A harness that cuts the call off kills only the parent, and the warden then reaps the child before its verdict: the run ends as `state=lost`, a failed validation. The `--wait --run-dir` resume above holds only on a host without such a warden. An `--attached` run is never memory-capped: with `ORCH_VALIDATE_MEMORY_MAX` set, its runner line says `memory-cap=unavailable cause=attached`.
