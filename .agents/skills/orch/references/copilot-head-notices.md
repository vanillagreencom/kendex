# Copilot head notices

The overseer applies these rules to the three Copilot head notices [review-pr-comments.md](../workflows/review-pr-comments.md) § 7.2 sends as a `lane-notice`, and to the review call's own `copilot-fallback` ([gates.md § Copilot requests](gates.md#copilot-requests)). They also apply to a head a pr-watch `awaiting-stale` or `refresh-ready` line names. Both events are in [oversee-events.md § Event kinds](oversee-events.md#event-kinds). The first line of a notice § 7.2 sends is its kind, then `PR #[N] head [SHA]`; read the review call's notice by [gates.md § Copilot requests](gates.md#copilot-requests). Every approval below is one `approve-head` request, run from the trusted consumer checkout as `.agents/skills/orch/scripts/orch-runtime op --item [ITEM] --request [PATH]` on the owning item's record; a pull request no lane owns takes a dedicated item, made once with `.agents/skills/orch/scripts/orch-runtime state init --item [ITEM]` and reused for that pull request. `[PATH]` holds:

```json
{"op":"approve-head","repo":"[OWNER/REPO]","pr":[N],"head":"[SHA]","body_file":"[BODY_PATH]","hold_copilot":true}
```

`head` is the SHA the notice or the `pr-watch` line names, as printed, and `repo` the repository the `pr-watch` line leads with, or for a notice the owning lane's repository. The runtime reads the pull request's live head with the fleet's `ORCH_OVERSEER_REVIEW_TOKEN_FILE` credential, approves only when that head starts with `head`, and binds the review to the full head it read. `ORCH_OVERSEER_REVIEW_LOGIN` names the app whose approval of that head confirms the attempt. A `head-moved` refusal approves nothing and writes no `use1` row, since the new head takes its own route. An `approval-setting-unread` refusal means the private env file sets the token file, the login or `GH_HOST` in a form only a shell reads, which the runtime passes over; write it there as a plain value. The runtime records the attempt on the item before the POST and answers `result.status`: `confirmed` permits the `use1` row; `finished` approves nothing; `refused` approves nothing and clears the attempt, its `reason` naming why: `post-failed` where GitHub refused the POST, `not-started` where the POST never started, `not-landed` where a complete read of the pull request's reviews after a lost answer found no approval from the app at the head. Once that cause is gone, an app permission granted or a failing service back, the same request posts again. `unknown` means the POST's answer was lost and the reviews could not be read whole: repeat the same request, which reads them back first and posts again only after a complete read finds no approval.

Every fallback approval below sets `hold_copilot` to `true`. Proved-render consumer refresh approval and `copilot-declined-unchanged` set it to `false`. The hold waits in the call while Copilot's work runs on the head, up to `ORCH_COPILOT_HOLD_SECS`. On `finished`, that work ended inside the hold: approve nothing, write no `use1` row and repeat the request on the same head, which then checks the review replies Copilot's review left. A failed check-run read approves nothing. Work still running at the bound permits approval only after the runtime rechecks the exact original live head. A `review-replies` refusal approves nothing, writes no `use1` row and wakes the lane to answer what `github.sh check-review-replies [N]` names: a `suppressed-entry` is a finding Copilot wrote only in a review body, which no thread carries.

While the lane status file's `Review:` line reads `pending` for that pull request ([review-pr.md](../workflows/review-pr.md) § 1), every rule below, § Fallback approval included, approves nothing, requests no Copilot review and wakes no lane: the lane's own review is still running on a pull request [start-worktree.md](../workflows/start-worktree.md) § 2.1 opened early. The verdict line [submit-pr.md](../workflows/submit-pr.md) § 2 step 1 writes in its place, once the push carrying the review's fix round lands, ends the hold. That step then routes the pushed head once by [review-pr-comments.md](../workflows/review-pr-comments.md) § 7.2, which re-delivers what the hold held: a head Copilot read takes its notice, and any other head the review call's `request` route ([gates.md § Copilot requests](gates.md#copilot-requests)); a request that call sends restarts pr-watch's quiet period with its request event, so a held `awaiting-stale` line rises again.

- `copilot-declined-unchanged` → when the notice lists every thread `github.sh pr-threads [N]` gives with `author` `copilot-pull-request-reviewer` and each reply holds at that head, and lists each body finding with the comment answering it, post one comment saying why each decline holds, then approve the head at once as the overseer's app with `approve-head`, with no Copilot re-review. Otherwise direct the lane on what does not hold and approve nothing.
- `copilot-fallback` → approve the head as the app with `approve-head`, `hold_copilot` `true`, when the lane's own review of it passed with no open blocker; otherwise wake the lane with what its review left open. On the review call's own notice ([gates.md § Copilot requests](gates.md#copilot-requests)), judge the lane's review from the lane status file the notice names, in the lane's worktree. Its `cause=off` does not say the repository's `PR_COPILOT_REQUESTS` reads `off` now. On approving a head whose notice ends in `cause=refused exit=N`, also send one notice naming the pull request, the head and that cause to the Jarvis session while one runs: a spent Copilot budget is one cause of that refusal, and a request that keeps failing for another reason then reaches a person. Its `cause=no-files` takes [§ Fallback approval](#fallback-approval)'s `no-files` route.
- `copilot-approved-on-rerequest` → Copilot approved the head; approve nothing.

## Consumer refresh approval

A `pr-watch` `refresh-ready` line takes this route immediately, including when no lane owns the pull request. Apply this route before fallback approval for the refresh identity below. Re-read the pull request and require the refresh identity the consumer's base-checkout settings declare, read from the base checkout's settings files [gates.md § Gate-mode routing](gates.md#gate-mode-routing) names, never from the caller's environment: head branch `REVIEW_GATE_REFRESH_BRANCH` exactly, author `REVIEW_GATE_REFRESH_AUTHOR` and author type `Bot`. A consumer that declares no identity has no refresh route here. Read its current full head. Require that head to start with the line's SHA. From the trusted consumer checkout, read its own CI render proof:

```bash
env -u GH_REPO -u GITHUB_REPOSITORY .agents/skills/orch/scripts/refresh-ci-proof [N] [FULL_HEAD_SHA] --repo [OWNER/REPO]
```

The reader selects only jobs from a `pull_request` run on that exact head in the consumer repository. The run must link the target pull request and head. The job log must name the current diff on its `base-rev:` and `head-rev:` lines. The reader fetches and verifies the target head and base through github's `git-https-auth` helper. It keeps the trusted checkout's files, refs and `FETCH_HEAD` unchanged. It gets that diff from harness-ci's `harness-only` range output and uses its pull-request merge base. Repeated range records from render-reach and the classifier must agree; conflicting or missing records refuse proof. It checks the live head, base SHA and base branch again after reading the evidence. GitHub's run links identify the pull request; their base SHA is not execution evidence. The run's workflow path must be an unchanged consumer workflow. It excludes `HARNESS_CI_REFRESH_CALLER`, read from the installed harness-ci library, from proof sources. That mutable caller cannot prove its own ownership. Among those trusted jobs, the latest GitHub Actions `Classify the diff` check and its job must complete successfully. A newer failed or pending trusted check refuses the proof. The reader accepts the Actions log's control bytes into a private parser buffer with gh's raw-output option. It requires `class: class=render measured=true` in the job log. Its `render-verifier:` version must equal the `Engine version: kendex X` version in the refresh pull request body. It permits no changed workflow path except the adopted caller. The trusted classifier's render proof owns that caller's validation. Require the CI aggregate to pass on the same head. On reader exit `0`, approve that head as the overseer's app with `approve-head`. The runtime also runs the review-reply check. Record the approval as a fallback Use 1 row.

The proved-render branch starts no internal review, GitHub agent review or Copilot wait. The catalog already reviewed the rendered packages. The reader refuses with one `cause=`: `ci-proof-missing`, `class-not-render`, `engine-mismatch` or `workflow-changed`. Each refusal grants no render approval. `class-not-render`, `engine-mismatch` and `workflow-changed` enter [Fallback approval](#fallback-approval) immediately from this `refresh-ready` line. That procedure applies the consumer's review route and requires review before approval. `ci-proof-missing`, a failed aggregate or a moved head grants no approval. The approval, stale-approval dismissal and thread-resolution rules still control merging.

## Fallback approval

Before every approval POST, `approve-head` runs `github.sh check-review-replies [N]` for the target repository. It posts only when the reader exits `0` with `review-replies: pass head=` equal to the full head the runtime bound. Every other result refuses as `review-replies`; run the same reader from the trusted checkout to read its findings before the request is repeated.

An `awaiting-stale` line means no approval reached the head within the quiet period. A `refresh-ready` line enters here after [Consumer refresh approval](#consumer-refresh-approval) reads a completed classifier result that cannot prove render. A pending review line takes the hold above before either branch here. When the owning lane's own review of that head passed with no open blocker, approve the head as the overseer's GitHub App with `approve-head`, `hold_copilot` `true`, whose approval the base's rules count like Copilot's, and send one notice naming the pull request and the head, to the Jarvis session while one runs. No ruleset or setting changes. Otherwise, use the [Copilot request owner](gates.md#copilot-requests), with `[PR_NUMBER]` set to `[N]` and `[REVIEW_BASE_CHECKOUT]` bound per that reference. Route its answer before any review wait. On a `fallback` answer a consumer workflow can still request Copilot on that head, so the fallback approval above sets `hold_copilot` to `true`. On `fallback cause=refresh`, review that head from the consumer checkout with the reviewer skill, then approve it with `approve-head`, `hold_copilot` `true`, when the review leaves no open blocker, recording a fallback Use 1 row, or otherwise approve nothing and send one owner notice naming the pull request, the head and the open blockers. Otherwise wake the lane with what its review left open. A head that a `copilot-declined-unchanged` notice names takes that notice's rule instead.

On `fallback cause=no-files`, send no further Copilot request. When the owning lane's review of that head passed with no open blocker, use the existing fallback approval with `hold_copilot` `true`. When the head's workflow state tier is `micro`, the lane ran no internal review: approve nothing and wake the lane to take [micro.md § Escape](../workflows/micro.md#escape) through `/orch small [ISSUE_ID]`, with one internal review round before the fallback approval. The overseer reviews nothing itself on this branch.

## Use 1 rows

Each head approved through a notice above, by the overseer or by Copilot, or through the fallback approval is one `use1` append to the fleet log, written as [oversee-events.md § Judgement rules](oversee-events.md#judgement-rules) directs, with `text` `PR #[N] head [SHA]` and `outcome` `declined-unchanged`, `fallback`, or `approved-on-rerequest` for Copilot's approval. The fallback approval is outcome `fallback`. `oversee-report` counts these rows in its Use 1 line.
