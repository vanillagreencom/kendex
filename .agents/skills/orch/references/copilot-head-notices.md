# Copilot head notices

The overseer applies these rules to the three Copilot head notices a lane sends as a `lane-notice`: [review-pr-comments.md](../workflows/review-pr-comments.md) § 7.2 sends each kind, [gates.md § Copilot requests](gates.md#copilot-requests) sends `copilot-fallback` on a refused request, an error-review result routes through [gates.md § Copilot requests](gates.md#copilot-requests), and under `PR_COPILOT_REQUESTS=off` the lane's `approval-wait` sends `copilot-fallback` itself, once per head. They also apply to a head a pr-watch `awaiting-stale` or `refresh-ready` line names. Both events are in [oversee-events.md § Event kinds](oversee-events.md#event-kinds). Each notice's first line is its kind, then `PR #[N] head [SHA]`; a `copilot-fallback` that answers no Copilot review then ends with its `cause=` field. Every approval below is `overseer-approve [N] [SHA] --body-file [PATH] --repo [OWNER/REPO]`, with the SHA the notice or the `pr-watch` line names, as printed, and `[OWNER/REPO]` the repository the `pr-watch` line leads with, or for a notice the owning lane's repository: it re-reads the pull request's head, approves only when that head starts with the SHA, and binds the review to the full head it read. On its `head-moved` refusal the overseer writes no `use1` row, since the new head takes its own route; `overseer-approve --help` holds its token file and every refusal.

Before any approval below, run the one reader of review bodies at that head from `[REVIEW_BASE_CHECKOUT]`, bound per [gates.md § Gate-mode routing](gates.md#gate-mode-routing):

```bash
env -u GH_REPO -u GITHUB_REPOSITORY .agents/skills/github/scripts/github.sh -C [REVIEW_BASE_CHECKOUT] check-review-replies [N]
```

Approve only on exit `0` whose `head=` starts with the SHA. Any other result approves nothing, writes no `use1` row and wakes the lane with the lines it printed, or on exit `2` its first stderr line: a `suppressed-entry` is a finding Copilot wrote only in a review body, which no thread carries.

While the lane status file's `Review:` line reads `pending` for that pull request ([review-pr.md](../workflows/review-pr.md) § 1), every rule below, § Fallback approval included, approves nothing, requests no Copilot review and wakes no lane: the lane's own review is still running on a pull request [start-worktree.md](../workflows/start-worktree.md) § 2.1 opened early. The verdict line [submit-pr.md](../workflows/submit-pr.md) § 2 step 1 writes in its place, once the push carrying the review's fix round lands, ends the hold. That step then routes the pushed head once by [review-pr-comments.md](../workflows/review-pr-comments.md) § 7.2, which re-delivers what the hold held: a head Copilot read takes its notice, and any other head an exact-head request, whose request event restarts pr-watch's quiet period so a held `awaiting-stale` line rises again.

- `copilot-declined-unchanged` → when the notice lists every thread `github.sh pr-threads [N]` gives with `author` `copilot-pull-request-reviewer` and each reply holds at that head, and lists each body finding with the comment answering it, post one comment saying why each decline holds, then approve the head at once as the overseer's app with `overseer-approve`, with no Copilot re-review. Otherwise direct the lane on what does not hold and approve nothing.
- `copilot-fallback` → approve the head as the app with `overseer-approve` when the lane's own review of it passed with no open blocker; otherwise wake the lane with what its review left open. A first line ending in `cause=off` is `approval-wait`'s, with the full head; the lane status file its second line names, in the lane's worktree, holds the review state to judge. A first line ending in `cause=error` means Copilot answered the error-review retry with another error; the lane status path under it holds the review state to judge. A first line ending in `cause=refused exit=N` means the lane's Copilot request exited nonzero, a spent budget or a failed call alike: on that approval also send one notice naming the pull request, the head and that cause with the `copilot-request-refused` line under it, to the master while one runs. A request that keeps failing for a reason other than the budget then reaches a person.
- `copilot-approved-on-rerequest` → Copilot approved the head; approve nothing.

## Consumer refresh approval

A `pr-watch` `refresh-ready` line takes this route immediately, including when no lane owns the pull request. Apply this route before fallback approval for the refresh identity below. Re-read the pull request and require the refresh identity the consumer's committed settings declare: head branch `REVIEW_GATE_REFRESH_BRANCH` exactly, author `REVIEW_GATE_REFRESH_AUTHOR` and author type `Bot` (`approval-wait --help` § Refresh review route). A consumer that declares no identity has no refresh route here. Read its current head and base. Require that head to start with the line's SHA. Run `kendex source refresh` once from the consumer checkout. A failed source refresh grants no approval. Then run the default-branch classifier against those commits and require a passing render proof with `change_class=render`. Require its CI aggregate to pass on that same head. Then approve that head as the overseer's app with `overseer-approve`. The review-reply check above still applies. Record the approval as a fallback Use 1 row.

This route starts no internal review, GitHub agent review or Copilot wait. The catalog already reviewed the rendered packages. A non-render result, a failed proof, a failed aggregate or a moved head grants no refresh approval. A consumer whose committed `REVIEW_GATE_REFRESH_REVIEW` is `overseer` routes its refresh head's later `awaiting-stale` line to the overseer, through § Fallback approval's `fallback cause=refresh`, never to Copilot. The approval, stale-approval dismissal and thread-resolution rules still control merging.

## Fallback approval

An `awaiting-stale` line means no approval reached the head within the quiet period. A pending review line takes the hold above before either branch here. When the owning lane's own review of that head passed with no open blocker, approve the head as the overseer's GitHub App with `overseer-approve`, whose approval the base's rules count like Copilot's, and send one notice naming the pull request and the head, to the master while one runs. No ruleset or setting changes. Otherwise, use the [Copilot request owner](gates.md#copilot-requests), with `[PR_NUMBER]` set to `[N]` and `[REVIEW_BASE_CHECKOUT]` bound per that reference. Route its answer before any review wait; a `fallback` answer sent no request and leaves no Copilot review to wait for. On `fallback cause=refresh` the consumer routes its declared refresh head to the overseer: review that head from the consumer checkout with the reviewer skill, then approve it with `overseer-approve` when the review leaves no open blocker, recording a fallback Use 1 row, or otherwise approve nothing and send one owner notice naming the pull request, the head and the open blockers. Otherwise wake the lane with what its review left open. A head that a `copilot-declined-unchanged` notice names takes that notice's rule instead.

## Use 1 rows

Each head approved through a notice above, by the overseer or by Copilot, or through the fallback approval is one `use1` append to the fleet log, written as [oversee-events.md § Judgement rules](oversee-events.md#judgement-rules) directs, with `text` `PR #[N] head [SHA]` and `outcome` `declined-unchanged`, `fallback`, or `approved-on-rerequest` for Copilot's approval. The fallback approval is outcome `fallback`. `oversee-report` counts these rows in its Use 1 line.
