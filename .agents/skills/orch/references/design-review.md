# Design review

Read at a `lane-long` event, at each `heartbeat`, before a recurring fix delegation, before the overseer files a fix item, and before an overseer answer changes a running item's Requirements or Done-when. The review closes a patch chain at its cause, and the lane builds the item's Done-when on the approved design. The overseer reads and directs; it implements nothing.

## The lane-long counts

The `lane-long` line and the `lane status` reply carry the same five counts, read from the lane's workflow state and its worktree. Each is a string of digits, or `unread`.

| Count | What it counts | `unread` where |
|-------|----------------|----------------|
| `review_rounds` | One for a recorded `first_panel`, plus `rereview_cycles`, plus `pr_comment_review.iterations` | only as the line below the table says |
| `fix_receipts` | The `stages` entries of kind `fix` | the record holds no `stages` list |
| `validation_runs` | The runs listed in the lane's `tmp/validation-runs` inventory under its `mail_root` | the inventory is missing or not in its `dev-validate-runs-v1` form |
| `restacks` | The record's `restacks` | only as the line below the table says |
| `repeated_class_rounds` | The later patch commits in `pr_comment_review.patched_causes` that repeat an earlier patch's cause, or share its location or owner key | no patch is recorded |

All five read `unread` for a parked lane, for a lane whose record or worktree cannot be read, and where a field holds a shape the count cannot read.

## Inputs and actions

| Input | Action |
|-------|--------|
| Before a proposed fix delegation: a matched class's `observed_count >= 2` in the reply of `orch-runtime state findings query` | After disposition and the previous round's closure, read this route before `begin-round`, a prune or a delegation time. Carry the same query reply, its prior coverage and exact sources included, in the lane's ask or status, the design ruling and the next delegation. A ruling that covers those sources is reused; a later source is new evidence. A failed record or query, or coverage that reads unknown, takes the widened read below and stays unknown. A count starts no pause, fix, validation retry or cap extension. |
| Before an overseer answer narrows, widens or replaces a running item's Requirements or Done-when | Write a short table naming each input class and each owner the changed requirement reaches, with each outcome on main, on the branch and under the proposed change. Check the proposed answer against the table. Post the table on the item before sending the answer. |
| A `lane-long` line with `repeated_class_rounds >= 1` or `review_rounds >= 3` | Start the read and the brief in this pass. A count alone starts no pause. |
| `heartbeat`: for each `running` lane, `.agents/skills/orch/scripts/orch-runtime lane status --item [ITEM]` | The reply carries the lane-long line's five counts, `review_rounds`, `fix_receipts`, `validation_runs`, `restacks` and `repeated_class_rounds`, each a string of digits or `unread`, beside `stage`, `stage_start`, `post_pr_stop` and the lane's state. Apply the `lane-long` row above to the counts, and the next row to an `unread` count or a refused read. Skip an item whose latest `design-review` or `long-reason` ruling records the counts this read shows; a `long-reason` ruling from this read names them as `rounds=[review_rounds] repeated=[repeated_class_rounds]`. Where neither the counts nor the widened read shows a trigger, record nothing. |
| A count is `unread`, or the read refused | Widen the read to the lane's `patched_causes`, with the command in [finding-disposition.md § Recurrence](../../reviewer/references/finding-disposition.md#recurrence), and to its pull request timeline under [oversee-events.md § Event kinds](oversee-events.md#event-kinds). Start the review if that read shows the trigger facts; a read that shows nothing takes the cause-naming step of the `lane-long` handler. No missing record blocks or adds a wait. A parked lane's stopped disk keeps that handler's rule. |
| A repeated class whose cause lies outside the item's goal and can land apart | File it once to its owner, with the item linked, and take it out of the lane's fix set. Work the goal needs continues in the lane. A round cap is the point where the overseer rules on this split, never the end of work the goal needs; the ruling names each separated item. |
| Before filing a fix item | Select recent activity from fleet-log `ruling` rows whose text starts `filed ` and from item `cycle` rows whose `at` falls in the last 24 hours. For each selected item, read its `filed ` ruling from the fleet log, the archives under [workflow-state.md § Recording policy](../schemas/workflow-state.md#recording-policy) and [§ Prune](../schemas/workflow-state.md#prune) included, whatever its age. Match the selected item to the filed item the ruling's text names. [File one item alone](oversee-events.md#file-one-item-alone) writes the filed item's Location files and defect-class rule into that ruling. A prior filing or merged fix concerns the same mechanism when its ruling names a Location file in common and the same rule every site breaks; `cycle` rows supply timing only. Run this review on that mechanism instead of filing a second patch item. File the approved outcome and requirements through that route's `description` and `recommendation` fields, post the complete brief through Record below, and carry it in the lane directive before implementation. |
| The read shows a legitimate cause: a large migration, a long validation or a real multi-round review | End the review with one `ruling` whose text starts `long-reason` and names the cause. The lane continues. Age or a round count alone never proves a patch chain. |
| The read shows a patch chain | The overseer decides to pause and records its reason, then applies § Patch-chain actions in order. |
| Neither holds | Name the cause under the `lane-long` handler and record one `ruling` whose text starts `long-reason`. Keep that handler's cause list and its Fix the source route. |

## Patch-chain actions

| Step | Action |
|------|--------|
| Brief | Write one page in five parts: the item's Done-when; the defect class and its cause, as the rule every site breaks; the options, including cutting surface the Done-when does not require; the chosen design and what it deletes; what stays out of scope. Keep it in tracker or `tmp/` content. |
| Pause | A local overseer may first run one one-shot `reviewer-arch` review through [oversee-events.md § Judgement rules](oversee-events.md#judgement-rules). Send one directive carrying the completed brief and either that verdict or the Second opinion instruction below. The directive tells every paused lane to finish the current round, start no further fix round, complete any requested Second opinion, then return the supplied or produced verdict for approval. A mailbox lane puts that verdict in its single approval `lane-mail ask`, then runs `lane-mail wait` for the matching answer; that wait is the only mailbox wait this review adds. A cloud session lane posts the verdict and the pause reason under `## Lane status` in its pull request body and ends its turn ([skill-rules.md § Lane mail](skill-rules.md#lane-mail)), and the overseer reads that body. Send the directive through [oversee-lanes.md § Talking to a lane](oversee-lanes.md#talking-to-a-lane): `lane-mail send --directive` for a mailbox lane, `orch-runtime send` for a session lane. With no current lane, take the filing row above and carry the complete brief in its lane's directive before implementation. |
| Second opinion | A lane whose directive carries the review instruction runs one one-shot `reviewer-arch` review, in its own lane per [SKILL.md § The Cycle](../SKILL.md#the-cycle), Item work stays in lanes. The overseer revises the brief once for the review's blockers. A failed or empty review yields `second-opinion=unread`, and the overseer goes on without another review. |
| Approve and resume | Answer a mailbox lane's ask with the approved brief through `lane-mail send --re`. For a cloud session lane, send the approved brief as its next directive. The next round builds that design. |
| Record | Post the brief as a tracker comment on the item. Append one fleet-log `ruling` under [oversee-events.md § Judgement rules](oversee-events.md#judgement-rules) whose text starts `design-review rounds_before=[review_rounds] repeated=[repeated_class_rounds]` and names the brief, the pause reason, the second opinion, the overseer's decision and any separated item. Write an `unread` count as `unread`. |

A `lane-long` event with neither a `design-review` nor a `long-reason` ruling for its item is a finding for the owner's audit, which the missing row identifies. No gate reads it.
