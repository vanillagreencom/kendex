# Design review

Read at a `lane-long` event and before the overseer files a fix item. The outcome is a patch chain closed at its cause, with the lane building the item's Done-when. The overseer reads and directs; it implements nothing.

## Inputs and actions

| Input | Action |
|-------|--------|
| `lane-long` line: `repeated_class_rounds >= 1` or `review_rounds >= 3` | Start the read and brief in this pass. A count starts no pause by itself. |
| A count is `-`, `unread`, missing or unreadable | Widen the read to the lane's `patched_causes`, using the command in [Finding disposition § Recurrence](finding-disposition.md#recurrence), and its pull request timeline under [Oversee events § Event kinds](oversee-events.md#event-kinds). Start the review if that read shows the trigger facts. A read that shows nothing takes the existing cause-naming step. No missing record blocks or adds a wait. Keep that handler's rule for a parked lane's stopped disk. |
| Before filing a fix item | Select recent activity from fleet-log `ruling` rows whose text starts `filed ` and from item `cycle` rows. Keep activity whose `at` falls in the last 24 hours. For each selected item, read its `filed ` ruling from the fleet log, including rows in the existing prune archives under [Recording policy](../schemas/workflow-state.md#recording-policy) and [Prune](../schemas/workflow-state.md#prune). Match the selected item to the filed item named in the ruling's text. Read that ruling regardless of its age or whether retention removed it from the active log. [File one item alone](oversee-events.md#judgement-rules) writes the filed item's Location file(s) and defect-class rule in the ruling. A prior filing or merged fix concerns the same mechanism when that ruling names a Location file in common and the same rule every site breaks. Cycle rows supply timing only. Run this review on that mechanism instead of filing a second patch item. File the approved outcome and requirements through that route's existing `description` and `recommendation` fields. Post the complete brief through Record below and carry it in the lane directive before implementation. |
| Read shows a legitimate cause: a large migration, long validation or a real multi-round review | End the review with one `ruling` whose text starts `long-reason` and names the cause. The lane continues. Age or round count alone never proves a patch chain. |
| Read shows a patch chain | The overseer decides to pause and records its reason. Apply the actions below in order. |
| Neither trigger holds | Name the cause under the existing `lane-long` handler. Record one `ruling` whose text starts `long-reason`. Keep its cause list and Fix the source route. |

## Patch-chain actions

| Step | Action |
|------|--------|
| Brief | Write one page with five parts: the item's Done-when; the defect class and cause as the rule every site breaks; options, including cutting surface the Done-when does not require; the chosen design and what it deletes; what stays out of scope. Keep it in tracker or `tmp/` content. |
| Pause | A local overseer may first run one one-shot `reviewer-arch` review through [Oversee events § Judgement rules](oversee-events.md#judgement-rules). Send one directive carrying the completed brief and either that verdict or the Second opinion instruction below. The directive tells every paused lane to finish the current round, start no further fix round, complete any requested Second opinion, then return the supplied or produced verdict for approval. A mailbox lane puts that verdict in its single approval `lane-mail ask`, then calls `lane-mail wait` for the matching answer. That existing wait is the only mailbox wait this review adds. A cloud lane posts the verdict and pause reason under `## Lane status` in its pull request body and ends its turn, per [Lane mail](skill-rules.md#coordination). The overseer reads that body. Use `lane-mail send --directive` through [Talking to a lane](oversee-lanes.md#talking-to-a-lane), which routes a Claude cloud lane's directive through its session channel. With no current lane, use the filing action above and carry the complete brief in its lane's directive before implementation. |
| Second opinion | A lane whose directive carries the review instruction runs one one-shot `reviewer-arch` review under [SKILL.md § The Cycle, Item work stays in lanes](../SKILL.md#the-cycle). The overseer revises the brief once for the review's blockers. A failed or empty review yields `second-opinion=unread`; the overseer proceeds without another review. |
| Approve and resume | The overseer answers a mailbox lane's ask with the approved brief through `lane-mail send --re`. For a cloud lane, send the approved brief as the next session directive. The next round builds that design. Record `recurrence: structural-close` on each item it closes, per [Finding disposition § Recurrence](finding-disposition.md#recurrence), for `dev-round-write` to accept. |
| Record | Post the brief as a tracker comment on the item. Append one fleet-log `ruling` under [Oversee events § Judgement rules](oversee-events.md#judgement-rules). Its text starts `design-review rounds_before=[review_rounds] repeated=[repeated_class_rounds]` and names the brief, the pause reason, the second opinion and the overseer's decision. Preserve missing counts as unread. |

A `lane-long` event with neither a `design-review` nor a `long-reason` ruling for its item is a finding for the owner's audit. The missing row identifies it. No gate reads it.
