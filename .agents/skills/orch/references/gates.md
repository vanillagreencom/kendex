# Review gate and waiter reference

Load where a workflow reads the review gate, requests Copilot or waits on one pull request. The review gate is the orch runtime's `verify-review` operation, CI on one pull request its `verify-pr` operation, and the merge queue its `queue-watch` verb. The workflows route each verdict; this file holds the review call, what its reply means and the words the three share.

## Gate-mode routing

Bind `[REVIEW_BASE_CHECKOUT]` to a checkout of the target pull request's consumer base, never the catalog checkout or the pull request's updated tree. If that checkout is unavailable, stop.

The gate mode is the `mode` of [the review call](#the-review-call)'s reply. The runtime resolves it on the item's first call and records it as `pr_review.mode`; every later call reads that record, so a retarget to another base keeps the mode the first call read. It reads the consumer's `REVIEW_GATE_MODE` from the base checkout's `kendex.settings.toml`, `.kendex/settings.toml` and private env file, never from the caller's environment, and runs nothing from that checkout. `off` is the mode. `enforce`, or no value, reads GitHub's approval requirement on the base: the base's ruleset pull-request rules, then classic branch protection's required reviews. A ruleset rule that requires an approval, code-owner review, last-push approval or a team minimum, or enabled classic protection with a required-reviews object at any count, is `approval`; anything else is `off`. A failed read is an `unreadable` reply with no mode, never `off`: repeat the call, and report a second failure rather than pick a mode.

| `mode` | Meaning | Route |
|--------|---------|-------|
| `approval` | consumer policy is `enforce`, and the base's rulesets require approval or classic protection requires reviews | the review wait |
| `off` | consumer base-checkout policy is `off`, or the base's rulesets require no approval and classic protection requires no reviews | no review wait: the call requests nothing and answers `complete` with verdict `off` and records it, `pending copilot-pending` while Copilot's work in flight on the head holds it ([§ Copilot requests](#copilot-requests)), or `blocked` while a regression blocker stands ([§ Which waiter answers which state](#which-waiter-answers-which-state)); record the gate not-applicable only on `off` |

Under the `off` gate mode, open review threads still stop the merge: submit-pr's gate 3 applies, and so do the readers [thread-read.md § What reads an open thread](thread-read.md#what-reads-an-open-thread) lists. Required CI checks, commit guards, exact-head checks and conflict refusal are untouched in both modes, and the merge path still refuses a `CHANGES_REQUESTED` review at its readiness check. In `approval` mode an unresolved thread holds the wait at `comments` even beside an approval, because orch's own merge gates refuse an open thread: submit-pr's gate 3 and merge-pr's thread read ([thread-read.md](thread-read.md)). A base rule refuses one too where it requires thread resolution.

The call reads its settings at its start, the caller's environment over the private env file and the settings files' `[env]`, and refuses a value outside its form as `setting-invalid key=[KEY] value=[VALUE]`. `PR_REVIEW_ON_TIMEOUT` and `ORCH_COPILOT_HOLD_SECS` are in [settings.md](settings.md); these two are this gate's alone:

| Setting | Meaning | Default |
|---------|---------|---------|
| `PR_REVIEW_WAIT_SECS` | Seconds of one review period, counted from the head's record, or from the head's last `timeout` | `900` |
| `PR_COPILOT_REQUESTS` | `on` lets the review call request Copilot on a head under the `approval` gate mode; `off` sends no request. What the call records and notices under each value is [§ Copilot requests](#copilot-requests) | `on` |

## The review call

Run it from the caller's checkout, `[ROOT]`: the lane's worktree, or the main checkout merge-pr runs from. `[OWNER/REPO]` is what `gh repo view --json nameWithOwner --jq .nameWithOwner` answers there, and `[STATE_KEY]` the caller's workflow state key, `[ISSUE_ID]` in a lane. `[MARK_READY]` is `true` where the step says so, which marks an open draft ready before its request under either mode, and `false` everywhere else:

```bash
jq -cn --arg repo "[OWNER/REPO]" --argjson pr [PR_NUMBER] --arg base "[REVIEW_BASE_CHECKOUT]" --argjson ready [MARK_READY] \
  '{op: "verify-review", repo: $repo, pr: $pr, base_checkout: $base, mark_ready: $ready}' \
  > "[ROOT]/tmp/verify-review-request-[STATE_KEY].json"
.agents/skills/orch/scripts/orch-runtime op --item [STATE_KEY] --request "[ROOT]/tmp/verify-review-request-[STATE_KEY].json"
```

One call reads the pull request once and reads or records the gate mode. Under the `off` gate mode it requests nothing and answers `off`, `blocked` while a regression blocker stands, or `pending copilot-pending` while Copilot's work runs on the head (§ Copilot requests). Under `approval` it counts the head's open threads and reads its reviews, then settles the head's Copilot request (§ Copilot requests) before its verdict, and a head with no verdict after those reads takes its review period. The call records each act it makes, the ready mark, the Copilot request and the error retry, under the head before making it, so a repeated call repeats no act it saw confirmed: a ready mark still unconfirmed while the pull request reads draft is sent again, and the request's and the error retry's one resend are § Copilot requests'. A step that needs only the mode or the request runs the call once and reads that field; on `approval`, a reply that carries `request` has also settled the head's Copilot request.

The reply's fields, under `.result`:

| Field | Meaning |
|-------|---------|
| `status` | `complete`: `verdict` is recorded on the item. `pending`: the head is not judged yet, and `reason` says why. `unreadable`: a read failed, and `reason` is its cause key |
| `mode` | `approval` or `off`, present once the mode is read |
| `head` | The head this call read |
| `request` | What the head's record holds: `outcome` `requested`, `existing` or `fallback`, with `reason` or `cause`, and `recorded_now`, true on the call that wrote it |
| `notices` | The head's `copilot-fallback` notices the gate owes the lane's overseer ([§ Copilot requests](#copilot-requests)), each `{notice, owner, sent_now}`: its first line, `owed`, `sent`, `unsent:<cause>` or `unanswered:<cause>`, and whether this call sent it, with `unmarked`, the store's refusal key, where this call's mark failed; absent where the head owes none |
| `copilot` | Copilot's work on the head against the hold: `state` `none`, `pending` or `expired`, with `run` and `started_at` |
| `unresolved_count` | The open threads counted on the head |
| `verdict` | With `complete`: `approved`, `changes_requested`, `comments`, `timeout`, `proceeded`, `copilot-error`, `off` or `blocked` |

A `pending` reply's `reason` is `review-pending copilot=[STATE] remaining=[SECS]` while the period runs with no Copilot work held, `request-refused exit=[N]` in its place on the call where GitHub refused the head's request, `copilot-pending run=[ID] remaining=[SECS]` while Copilot's work in flight on the head, a Copilot check with no Copilot review of the head submitted since it started or a pending Copilot request, holds a verdict that permits a merge, `approved`, `proceeded` or `off`, or the review period's own answer, `request-fallback cause=draft` for a draft the call was not asked to mark ready, which starts no period, `ready-head-moved head=[SHA]` where a push landed with the ready mark, or `head-moved head=[SHA]` where the pull request's head moved between the call's reads; the next call reads either moved head as the new head. A refusal exits nonzero with its keyed line: `pr-not-open` for a closed or merged pull request, `verify-request-invalid field=[FIELD]` for a request outside its form, `setting-invalid` as above, `record-missing` for an item with no state.

**The review wait.** A step that waits on the verdict runs the call through [Waiter launch](waiter-launch.md), repeated no more often than every 30 seconds while `result.status` is `pending`; an `unreadable` reply takes the step's `unreadable` row, which repeats it within that row's bound. The period is the runtime's: `complete` with `timeout` or `proceeded` arrives once `PR_REVIEW_WAIT_SECS` has passed and Copilot's work on the head has ended or its hold has passed, so the workflow keeps no budget of its own, and a `timeout` starts the head's next period. A step that names a shorter wait runs the call as `env PR_REVIEW_WAIT_SECS=[SECS] .agents/skills/orch/scripts/orch-runtime op ...`, and a step that must never proceed on a silent reviewer as `env PR_REVIEW_ON_TIMEOUT=block ...`: the call reads its caller's environment over the settings files.

**A new head.** The record is the head's: a push starts a new record, request and period. A reply whose `head` differs from the head the step bound takes that step's moved-head route.

## Copilot requests

Under the `approval` gate mode the review call settles the head's Copilot request before it answers the head's verdict, whatever the verdict: it requests Copilot itself where the head needs a request and may take one (`requested`), and otherwise records why none went out (`existing`, `fallback`). Every `approval` reply that passed the request carries `request`, `approved` included; a refusal, an `unreadable` reply, and a `pending ready-head-moved` or `head-moved` reply can lack it. Under the `off` gate mode the call requests nothing. Route the `request` before the verdict word. The reply's `request` reports what the head's record holds:

- `requested`: the call sent the request. A later call on a head that may take a request sends it once more where it finds neither Copilot work in flight on the head nor a Copilot review of the head, whether GitHub never recorded it or its work ended with no review, its check completed or cancelled or the request removed. An `existing-run` whose run ends the same way is claimed and sent on the next call on a head that may take a request: `request` reads `requested` with `recorded_now` true, and that request takes the same one resend. A miss after the resend falls back `cause=unconfirmed` and owes its notice. A head's request is so sent at most twice, by either route; Copilot's error answer takes its own retry (**Copilot's error answer** below). With `PR_COPILOT_REQUESTS` `on`, a call on a refresh head or a draft the call keeps sends neither the claim nor the resend: a request recorded, or an `existing-run` standing for one, and not yet resent stays as it stands, spending neither, and a resent one still falls back `unconfirmed` on a miss. Under `PR_COPILOT_REQUESTS=off` a record that has not fallen back, resent or not, falls back `off` instead (`fallback` below), a refresh head's excepted, which stays as with the setting `on`.
- `existing`: no request was needed. `reason` is `existing-run` for Copilot's work in flight on the head, which `requested` above follows once that work ends with no review of the head, `existing-review` for a Copilot review standing on it, or `existing-error-retry` for a retry of Copilot's error answer standing on it.
- `fallback`: no request went out, and `cause` says why. A head whose request fell back keeps that fallback on every later call, whatever `PR_COPILOT_REQUESTS` reads, and owes no second notice for it, a `draft` fallback excepted, which lapses as `draft` says. `off`: the call recorded the fallback while `PR_COPILOT_REQUESTS` was `off`, over no record or an unspent one (`requested`, sent or resent, or an `existing` answer), on any head but a refresh head; the cause names the record, not the setting the repository holds now. `draft`: the head is a draft the call was not asked to mark ready; keep the draft. The fallback lapses once the gate's ready mark lands, or once the view and `pulls/N` both read the head ready: that call answers the head's request as on a head with no request recorded, under `PR_COPILOT_REQUESTS=off` an `off` fallback with its notice, and starts the head's hold and review period. `refresh`: the consumer's base-checkout `REVIEW_GATE_REFRESH_REVIEW=overseer` declares this pull request its refresh head, which takes [copilot-head-notices.md § Fallback approval](copilot-head-notices.md#fallback-approval); the call judges it before `PR_COPILOT_REQUESTS` and the draft, so a refresh head falls back `refresh` under `PR_COPILOT_REQUESTS=off` too. `no-files`: Copilot's current-head answer says it could review no files, which takes the same Fallback approval without another request. `error`: the item already recorded an error fallback at this head. `refused` with `exit`: GitHub answered the request with a 4xx refusal; a transport failure, a 5xx or a timeout is an `unreadable` reply instead, and the request's claim stands for the next call's confirmation. `unconfirmed`: the request and its resend drew neither Copilot work still in flight nor a Copilot review of the head. The fallback grants no approval. Without a standing approval the approval gate stays unmet, and the step's review wait keeps running until the overseer's approval ends it. With an approval standing, the call that records the fallback answers that approval's verdict in the same reply, so the head can merge with no Copilot review while the gate sends the `copilot-fallback` notice in a lane (**The fallback notice** below). Outside a lane, report the unavailable Copilot review and route the verdict by the same rule.

**The fallback notice.** The review call sends the `copilot-fallback` notice itself where the item runs in a lane, its launch marker standing. The call that records a fallback owes the notice in the same write, sends it into the lane's mailbox and marks it, from the lane's worktree or the main checkout alike. A `draft` or `refresh` fallback owes none, nor does an item with no launch marker: a `claude-cloud` session lane has none, so the gate owes it no notice. Its first line is `copilot-fallback PR #[PR_NUMBER] head [HEAD_SHA] cause=[CAUSE]`, with ` exit=[N]` after `refused`, and its second line the lane status path, for the overseer to read. The reply's `notices` names each notice and how it stands, and no step sends it.

A call that finds a notice owed sends it and marks it `sent` on the mailbox's receipt or its repeat answer. A send the mailbox program refuses by its key, or that never starts, is marked `unsent:<cause>`, and no call sends it again. A send with no answer is marked `unanswered:<cause>`: the next call sends it once more, and a second send with no answer marks it `unsent`. A repeat past the mailbox's minute window is a second notice. A notice owed on a head the pull request has since moved past is never sent: the call reads the head it views, and the new head takes its own request and its own fallback.

The call records a fallback before it answers the head's verdict, so no notice is held while Copilot's work runs, while a review thread stays open or while a change request stands, a `cause=off` notice included. The overseer's approval can therefore post on a head whose threads are answered but open, or that carries a change request: `overseer-approve --hold-copilot` holds on Copilot's work, and the `check-review-replies` it runs judges what each thread's replies say, not whether a thread is open ([copilot-head-notices.md § Fallback approval](copilot-head-notices.md#fallback-approval)). The merge stays guarded: merge-pr's thread read holds every merge call on an open thread ([thread-read.md](thread-read.md)), a `comments` answer from the review call takes that read ([merge-pr.md § 3.3](../workflows/merge-pr.md#33-thread-read)), `pr-merge --check` refuses `changes_requested` ([merge-pr.md § 3.2](../workflows/merge-pr.md#32-act-on-the-result)), and GitHub's own rules hold the merge where the base requires thread resolution or a review. A head fallen back `off` takes no new request when `PR_COPILOT_REQUESTS` is turned back on, but Copilot's error answer on it still earns its one retry, claimed and resent as **Copilot's error answer** below says; a new head requests as usual.

**Copilot's error answer.** With `PR_COPILOT_REQUESTS` `on`, a Copilot review on the head that is its error sentence takes one retry; under `PR_COPILOT_REQUESTS=off` the call takes no retry and goes on to the review period. Copilot's work already in flight on the head stands for the retry: the call records it so and sends nothing, and no later call requests for that error review, whether or not the work ends. Otherwise the call claims a `requested` retry on the head's record and sends it; a later call that finds neither Copilot's work nor a request event since the error sends that requested retry once more, so the retry goes out at most twice. On a draft the call keeps, or a head the refresh policy newly names, the call neither claims nor resends the retry and keeps its record unspent; the call where the head may take a request again claims or resends it. A retry the call sends drops the call's work read, so the call reads the retry as Copilot's work, which **Copilot's work in flight** below holds only within the head record's remaining bound. The verdict is `copilot-error`, its `reason` `copilot-error cause=[CAUSE]`, where the retry cannot stand: `refused exit=[N]` when GitHub refused the retry's request, `error` when Copilot answered the retry with another error, `unconfirmed` when the retry went out twice with no sign of Copilot's work, `refresh` when the refresh policy held the request back. The call sends the `copilot-fallback` notice for a `copilot-error` of cause `refused exit=[N]`, `error` or `unconfirmed` as for a fallback (**The fallback notice** above), its first line ending with that cause, on a head the refresh policy names after its retry went out too; a `copilot-error` of cause `refresh` owes none, its route the overseer's [Fallback approval](copilot-head-notices.md#fallback-approval) through pr-watch's `refresh-ready`. Then keep the review wait running for the overseer's approval: the head's retry record keeps later calls from retrying again. Every wait restart still uses its caller's head-budget route. Outside a lane, report the unavailable Copilot review and keep the approval gate unmet.

**Copilot's work in flight.** Under either gate mode, while a Copilot check runs on the head with no Copilot review of the head submitted since the check started, or a Copilot request stands pending on the pull request, within `ORCH_COPILOT_HOLD_SECS` of the head's record, the call holds a verdict that permits a merge, `approved`, `proceeded` or `off`, or the review period's own answer, as `pending copilot-pending`, a refused request's `request-refused` standing before it. Past the bound, `copilot.state` reads `expired` and the verdict stands as read; the expiry grants no approval. A Copilot review of the head submitted while its check still runs ends the hold: the call answers its verdict with `copilot.state` `none`. The call's own request, or its error retry, is that work from the call that sends it, so an `approved` beside a request the call made answers `pending copilot-pending` until Copilot's review of the head is submitted, its check completes, or the bound passes. A step that merges runs the call before every merge call and repeats it while it answers so ([merge-pr.md § 5](../workflows/merge-pr.md#5-execute-the-merge) step 1). The triage waits on the same work before it reads threads through `orch-runtime copilot-wait` ([review-pr-comments.md § 1](../workflows/review-pr-comments.md#1-fetch-and-parse)), a read that requests and records nothing and holds no merge call, never through this call. Under the `off` gate mode the call requests nothing, so the hold reads only the work already running or requested on the head.

## Which waiter answers which state

| Waiting on | Tool |
|------------|------|
| Reviewer verdict on one PR | `verify-review` (`orch-runtime op`), [§ The review call](#the-review-call): `status` `complete` with verdict `approved`/`changes_requested`/`comments`/`timeout`/`proceeded`/`copilot-error`/`off`/`blocked`; `pending` repeated, `unreadable` routed by each step |
| CI on one PR | `verify-pr` (`orch-runtime op`) — `status` `complete` with verdict `pass`/`fail`/`none`; `pending` or `unreadable` repeated through [Waiter launch](waiter-launch.md); a `fail` verdict is rerun once per head through `github.sh ci-rerun --required-only` before ci-fix, the item's `ci_rerun` record written first ([submit-pr.md § 5.1](../workflows/submit-pr.md#51-ci-failure-recovery)); the merge state is read through `pr-merge --check` before the first call, and `CONFLICTING` takes the workflow's `conflict` route and never the wait |
| Copilot's work on one PR's head, before a triage read | `orch-runtime copilot-wait --repo [OWNER/REPO] --pr [PR_NUMBER]`: bounded by `ORCH_COPILOT_HOLD_SECS` from its own start, its reply's `status` and `state` routed by [review-pr-comments.md § 1](../workflows/review-pr-comments.md#1-fetch-and-parse)'s table |
| Merge-queue / auto-merge outcome | `orch-runtime queue-watch --item [STATE_KEY] --repo [OWNER/REPO] --pr [PR_NUMBER] --poll [SECS] --max-wait [SECS]`: one wait bounded by `--max-wait`, its reply's `status`, `verdict` and `cause` routed by [merge-pr.md § 5](../workflows/merge-pr.md#5-execute-the-merge) step 1's table |
| Many PRs, long horizon | `pr-watch.sh` — § Multi-PR watching |

Per-verdict routing lives in the workflows (`submit-pr.md` § 4 and § 5, `merge-pr.md` § 5, [merge-attempt.md](merge-attempt.md)). `verify-review`'s reply fields are § The review call's, `verify-pr`'s are in `submit-pr.md` § 5's result table, and `queue-watch`'s verdict and cause words are in `merge-pr.md` § 5 step 1's table.

`blocked` is an approval, a `proceeded` or an `off` the runtime refuses to publish, under either mode: an `escalated_items[]` entry of `kind` `regression-against-main`, a break the branch made, stands with an outcome other than `skipped`, and `reason` reads `regression-open location=[LOCATION]`. It is never a met gate. [review-pr.md § At The Cap](../workflows/review-pr.md#at-the-cap) and its [§ 7 Converged](../workflows/review-pr.md#converged) exit write the entry, and it stands until its outcome reads `skipped` or it leaves `escalated_items`.

`queue-watch` names three states on an armed head. `queued` has a merge-queue entry, and progress is read from the entry's merge-group head; `cause: progress_unobservable` means that head could not be read. `queued` has one other shape, which is no armed head at all: `cause: exit_unconfirmed` is a PR the last poll saw out of the queue and unarmed, its ejection or disarm short of its confirmation count, so nothing is armed to fire on its own. `armed_awaiting_checks` is armed, not enqueued, with no failed check at the wait's last check read: `merge-pr.md` § 5 step 1 waits again on the same head, spending no recovery cycle, until `QUEUE_WAIT_ARMED_MINUTES` (default 90) of wall clock hands it back. `armed_blocked` is armed and not enqueued when the wait ended: a failed check takes the recovery cycle, which `CI_FIX_MAX_CYCLES` bounds, and `cause: not_mergeable` is a last check read that settled as `pass` or `none` with no entry, which `merge-pr.md` § 5 step 1 reads again before it routes. The wait reads the checks through one `verify-pr` read per `QUEUE_WAIT_PROBE_INTERVAL` (default 120 seconds), and only while a poll still fits after it before `--max-wait`; an answer that arrives past that budget is no reading. A deadline cause, `checks_pending`, `checks_unread` or `not_mergeable`, is therefore the last reading before the deadline, never a check verdict.

A wait is a running waiter, never a session sitting at its prompt.

## Stacked pull requests

Under the `approval` gate mode the review call settles every head's Copilot request itself ([§ Copilot requests](#copilot-requests)), so a stacked pull request whose base the repository's automatic-review rulesets do not target takes its request like any other head; which bases those rulesets target is the github skill's [automatic-review.md](../../github/references/automatic-review.md). Merging the bottom of a stack retargets the next pull request onto the new base without moving its head: its head record and request stand, and its gate mode stays the one the item recorded. Where the new base's diff needs Copilot's review, push a new head, which takes its own request.

## GitHub authentication

`verify-review`, `verify-pr`, `queue-watch` and `copilot-wait` run `gh` as the calling process is authenticated, and select no token of their own beyond the github router's own order on `queue-watch`'s guard calls. A failed read is an `unreadable` reply, or `queue-watch`'s `status: error`, at once for a refused read and once its budget is spent for a transient one, never a verdict. The runtime's watch selects its token once at its start: [DEVELOPMENT.md § GitHub auth ladder](https://github.com/vanillagreencom/kendex/blob/main/skills/orch/DEVELOPMENT.md#github-auth-ladder).

## Multi-PR watching

The waits above are single-PR waits. For many PRs across a long horizon, the github skill ships `scripts/pr-watch.sh`, a needs-attention reducer; its contract is `pr-watch.sh --help`. The fleet watch, `orch-runtime watch run`, runs it once per repository per long pass; with the script missing, that duty fails each pass as `reducer-failed`. Each pass reads GitHub's review state for every open PR, its unresolved threads, `reviewDecision`, auto-merge arm and merge-queue entry, and writes nothing. The fallback without it is per-PR `verify-review` and `queue-watch`. `queue-watch` watches only the one PR it is given and only while it runs, so the fallback gives no standing view across PRs and no `awaiting-stale` report. A PR that no wait watches warrants a manual read of `gh pr view [N] --json reviewDecision,autoMergeRequest` and its queue entry.
