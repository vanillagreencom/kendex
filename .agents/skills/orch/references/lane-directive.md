# Lane directive

Load from [oversee.md § Lane directive](../workflows/oversee.md#lane-directive) when a launch finds no lane or refuses, and from [oversee.md § Recovery relaunch](../workflows/oversee.md#recovery-relaunch) to resume a dead or walled lane.

## No lane has room

On `lanes pick` exit 3, read `lanes list`, wait only when its lanes are over the threshold, and report every `expired`, `unreachable`, `refused`, `no_credentials`, `no_usage_data` or `error` lane, and every `rate_limited` lane with a null `headroom_pct`, to the operator. Which of these statuses a failed Codex renewal takes, and its remedy, is stated once, in the `lanes` script header under "Why a Codex token is renewed by the Codex CLI". An `expired` lane is one whose login is proven dead, or a Codex lane whose failed renewal that section lists as `expired`; its `detail` names why, and it is the only one of these an operator answers by logging in again, or by the command its `detail` names. A `rate_limited` lane met an endpoint answering HTTP 429. A usage refresh refused while the host holds an eligible figure is reported on that figure, with its age in `usage_age_s`, and judged on it like an `ok` lane. The figure must be younger than the 5-hour session window. A consumed bucket reset ends eligibility before that age limit. A live recorded refusal still blocks a new request after the reset and reports no usable figure, with null `headroom_pct`. A token renewal refused with 429, or a usage 429 with no eligible figure, carries no window. An `unreachable` one met an endpoint answering 5xx, an endpoint it could not reach, or a credentials lock another tool held. Both leave the login untested, so the answer is another lane and never a re-login. A `refused` one met a usage endpoint answering another code outside 2xx, 401 and 403 included; `detail` carries the code, and it is not a re-login either, since the code names no cause `lanes` judges. Where an endpoint answered, `detail` carries the code and the lane is left alone until the recorded window passes. An `error` lane failed a step on this machine, a renewal's included. Every Claude account `error` for a missing OAuth client id needs `ORCH_LANES_CLAUDE_CLIENT_ID`, set once per host.

Two more causes of exit 3 are not a reset to wait for. An account `lanes list` shows with room can be counted `walled` on its projection: its `claims`, each charged its burn on the binding bucket and on the 5-hour session window up to that window's reset, carry `projected_headroom_pct` to the threshold. It returns as those live lanes end, so wait for a lane on it to close. A refusal carrying `seats=` above 0 names each window-account overseer seat it left out on a `lanes: pick-seat-omitted` line. No wait returns one to the candidates: launch on another account, or add one. A Copilot pool pick, through Copilot or Pi, never omits an overseer seat; its pool reading and monthly claim burn bound the pick.

A Codex account past its plan windows is not walled while its credit balance is above `ORCH_LANE_CODEX_CREDIT_FLOOR`, its reading has credits, and it has reached neither its overage limit nor its spend control: `lanes list` shows the balance as its HEADROOM, and `lanes list --json` and the `account` event carry `verdict=room` and `binding_bucket=credits`. A Codex exit 3 that counts such an account walled means one of those failed; `lanes pick --lane [DIR] --harness codex` names its `credits=` balance and the `credit-floor=` it was held to. Its windows still reopen at `binding_resets_at`, so wait for that reset as for any wall.

A pi pick on a `github-copilot/` model is judged on the Copilot pool, which `lanes list` never shows: read the table the refused `lanes pick --harness pi` printed, or `lanes pick --lane [DIR] --harness pi --model [MODEL] --json`. The pool is read live from the lane host's `accounts` row for the Pi root ([lane-host.md](../schemas/lane-host.md), `harness=pi`). `ORCH_LANE_COPILOT_POOL` is the override, judged only for a Pi root no row reads. `copilot-pool-unstated` (exit 5) means no read measured any pool; its `fix=` line names the read that failed and the repair: store the seat on the provider, repair the provider's read its row's `status=` and `detail=` name, check `lanes host-accounts --harness pi --no-cache`, or state the override. Never wait it out. `copilot-pool-unread` (exit 1) is a failed or busy `accounts` read: ask again. A pool the host read that is walled reopens at its `binding_resets_at`, like a Claude window. A walled stated reading moves only when the owner restates it: report it to the operator. A pi pick on a `pi-claude/` model is a claude pick on the Claude seats and is read as one. `pick-provider-unmeasured` (exit 5, no record under `--json`) is a pi model naming no provider or another provider, which nothing measures: answer it as `lane-provider-unmeasured` below.

## Lane preference

`ORCH_LANE_PREFERENCE` uses the grammar in [kendex.settings.toml.example](../kendex.settings.toml.example) § Fleet. Unset or empty leaves the caller's route unchanged. An explicit model in `--cmd` or `--launch-flags` also keeps that route. Otherwise, a harness launch walks the entries through `lanes pick` on each eligible entry's harness and model. Permission eligibility follows the existing walk rule in [oversee.md § 4](../workflows/oversee.md#4-watch-and-advance), through `ol_entry_permitted`. Exit 3 tries the next entry; any other failed pick stops the launch. A walk with no room refuses `lane-unavailable` with `walk=` naming the list. The fleet record carries the chosen `preference_entry` beside `model`. Each later tmux batch item and each `--wait-slot` rejudgment repeats the walk from the original caller input and rebuilds the command and its harness checks before creating the worktree.

A Codex entry can return an account on its credits, `binding_bucket=credits`, only when no Codex account has plan room: plan allowance resets and credits do not, so `lanes pick` ranks every account with plan room first. The walk takes that account as the entry's pick. The credits are already bought, so spending them is no overage.

A model-free `--cmd` is an argument template starting with the plain harness name. The launcher replaces that name, model and effort with the chosen entry and quotes the remaining arguments, leaving a bare `{brief}` for brief-file delivery. The shared overseer flag builder preserves or transfers the caller's permissions and supplies the chosen harness's question-tool and compaction settings. Other arguments must suit the chosen harness. Use an explicit model for arbitrary shell commands. Invalid entries refuse `invalid-preference` before any pick; a template starting with another command refuses `preference-command-invalid` before any window opens.

## Launch gate

`open-terminal` refuses foreign GitHub repositories and, with `LINEAR_TEAM` configured, foreign Linear team keys as `item-foreign repo=[REPO] route=peer-mail`; route their prioritized tracker issues with `lane-mail peer send --repo [REPO]`, or ask a live registered master, else the owner, with a launch recommendation when no repository overseer runs. A `--state-dir` launch from another repository's checkout goes ahead only where the overseer's checkout lists that repository in `ORCH_CONNECTED_REPOS` ([README § Setup](../README.md#setup)), and otherwise refuses as `overseer-foreign`, or as `overseer-unjudged` where the binding cannot be judged, its refusal text naming each cause; one whose fleet names no overseer repository binds to its own checkout's repository and goes ahead.

After applying [§ Lane preference](#lane-preference), `open-terminal` refuses a lane launch on a harness its flag table names that names no model, and one that names no effort where that harness has an effort flag, one keyed refusal per missing half, because a harness default changes without notice.

`open-terminal` reads the model and the effort out of the one text the launch runs: the `--cmd` command where there is one, `--launch-flags` where there is not. It refuses a launch that names either nowhere, and refuses `--launch-flags` beside `--cmd`, which are appended to no command and reach nothing. For a preference walk on a named lane, it resolves and checks that lane once and asks each pick with `--projected`. It uses the successful pick at launch. An explicit-model launch judges the named lane on that model again, so a lane picked without `--model` can be refused here. A hosted launch, `--relaunch` included, is judged on the provider's reading of that window where its `accounts` row for the account carries one, and on this machine's reading otherwise; only an account nothing measured then turns on whether the provider holds it, per `open-terminal --help` § `--host`. It still names a model and an effort. The gate emits eleven refusals, each with its own answer:

- `launch-model-missing` and `launch-effort-missing` (naming `harness`, `lane` and the `spellings` that harness takes): the launch made only part of the choice of lane, model and effort. Add the missing word to the text the launch runs; never let the harness pick.
- `launch-question-tool-missing` (naming `harness` and one `word` per word): the `--cmd` command leaves that harness's question tool on. Add the words, in order, to the command; [skill-rules.md § Coordination](skill-rules.md#coordination) lists them.
- `launch-unattended-missing` (naming `harness`, with the text printed on the refusal's last line): neither the brief file nor the `--cmd` command of a lane naming a harness carries the unattended words. Add the text, whole, to the brief file; [skill-rules.md § Coordination](skill-rules.md#coordination) names them.
- `launch-flags-unreachable` (naming the `flags`): the launch passed `--launch-flags` beside `--cmd`, which appends no launch flags to either an explicit-model or model-free template, so those words would have gated and been recorded while the harness ran its own default. Move them inside the `--cmd` command, or drop `--cmd`.
- `lane-model-walled` (naming `lane`, `model`, `pct`, `bucket` and `projected-headroom`): that account's deciding window, with the expected burn of the lanes already live on it, is at or above the threshold. `bucket` is the window whose projected room is the smaller: the 5-hour `session` window where those lanes spend it before it resets, otherwise the shared or model window that binds. `pct` is that window's reading and `projected-headroom` the room left after that burn. Where `pct` is under the threshold, the live lanes decided it, as [§ No lane has room](#no-lane-has-room) says. For a Codex account with a credit reading, the `lanes: pick-lane-walled` line above it names the `credits=` balance and the `credit-floor=`: the balance was at or under the floor, or the reading has no credits or reached its overage limit or spend control. Re-run [oversee.md § Lane directive](../workflows/oversee.md#lane-directive) step 3 with `--model`, never retry the same lane. A hosted relaunch meets it too: the window belongs to the account, so resuming would spend the sandbox start to open on a usage banner.
- `lane-model-unreadable` (appending `status` and `detail` after `step=windows`): no window of that account measures the model, or its usage could not be read. For a Copilot CLI account, the `fix=` line names `ORCH_LANE_COPILOT_POOL=<dir>=<used>/<granted>` where the stored login does not read, or a provider `accounts` row with `harness=copilot` and `monthly-pct`. For a pi launch on a `github-copilot/` model, neither the lane host's `harness=pi` row nor `ORCH_LANE_COPILOT_POOL` reads a pool for that Pi root, and the `fix=` line names the repair. An unread window is never an empty one, so the answer is the same re-pick.
- `lane-provider-unmeasured` (naming `harness` and `model`): a pi model names no provider, or a provider other than `pi-claude/` and `github-copilot/`, so nothing measures the account it spends, named lane or `auto`. Spell the model `pi-claude/<model>` or `github-copilot/<model>`, or pass `--provider` beside a bare `--model`; a re-pick on the same model is refused again.
- `host-pi-claude-seat` (naming `host` and `model`): a hosted pi launch on a `pi-claude/` model, refused before any pick or host work because the host protocol hands a Pi lane its account as its Pi root and carries no Claude seat. Launch it with `--host local`, or on a `github-copilot/` model.
- `host-credential-dead`: the account read expired, and the provider reports holding that same account. The expired copy is this machine's, which could not be renewed, or the provider's where its `accounts` row reports `expired`; `lanes list` names which in its THROUGH column. For this machine's copy, renew the login here for that config dir; a provider that re-seeds the host from that directory at every `create` sends the dead copy again. On this machine's reading it is reported for claude and codex lanes, the ones whose local credential `lanes` reads an unrenewable expiry from; a codex lane's `detail` names the codex command that renews it. For the provider's copy, renew the credential the provider holds. A relaunch onto that same account proceeds instead, on the copy the provider installed.
- `lane-claims-unreadable` (naming the `lane`): the in-flight claim store could not be read, so the lanes already on the account could not be charged; `--lane auto` refuses on it too. Fix the claims directory the keyed `lanes:` line above names, or set `OVERSEE_WATCH_STATE_DIR`.
- `lane-judge-failed`: the judge refused before it answered, a malformed `--lane-max-pct` among the causes. The keyed `lanes:` line above it names which.

A fleet launch, one naming `--state-dir`, meets one more gate, which admits a harness only where the lane runs with its own compaction off and a harness adapter can name its window:

- `launch-compaction-missing` (naming `harness` and one `word` per word): the `--cmd` command leaves that harness's own compaction on. Add the words, in order; [skill-rules.md § Coordination](skill-rules.md#coordination) lists them.
- `launch-window-unknown` (naming the claude `model`): the claude adapter names no window for that model. Launch on a model its window table names.
- `unsupported-for-oversee` (naming `harness`, `none` for a launch naming none): no adapter reads that harness, or, with `reason=no-window-read`, the Pi carrier installed sends no `context_window`. Launch on claude, codex, or a Pi with the current pi-hooks. A copilot fleet item is refused with `reason=no-context-hooks` (naming the `item`) where neither its worktree's project hook scope nor the lane's `COPILOT_HOME` global one holds all three of `lane-mail-check`, `lane-mail-compact` and `lane-mail-start`: commit them on the base the worktree is made from, or install them in that global scope through kendex, then launch again with `--relaunch`, since the worktree stands. With the hooks in place, it is refused with `reason=hooks-disabled` (naming the `item` and the `file`) where `disableAllHooks` is true in a Copilot settings file of that home or worktree that no later file sets false, or in the `.json` document of one of those three hooks in the scope that holds them, as `kendex hooks-off` reads them: set it false there, then launch again with `--relaunch`. It is refused with `reason=hooks-unjudged` (naming `exit`) where that query could not answer, a missing kendex, one too old to take `--hook-document`, or a file it cannot read or parse as commented JSON included: install or repair kendex, then launch again with `--relaunch`. It is refused with `reason=no-context-reader` where that home cannot be made to run the `kendex-lane-context` Copilot extension, its context reader; `file` and `detail` name where and why, and `detail=disabled` is an `enabledFeatureFlags.EXTENSIONS` the operator set false, which the launch never overrides: there the lane is admitted only on the fallback reader, the session record its account's status line writes, and `cause=` names what failed in that status line ([copilot-runtime.md](copilot-runtime.md#account-setup)). `detail=pending-unwritable` names in `file` the directory under the launch's HOME where the extension marks a reading on its way, which could not be made or written. It is refused with `reason=relative-home` (naming `home`) where the lane's `COPILOT_HOME` is no absolute path, before any worktree is made: set it to an absolute path, then launch again. One refused with `reason=hosted` launches locally ([skill-rules.md](skill-rules.md#coordination), Compaction).
- `compaction-on` and `pi-settings-unreadable` (naming the `file`): Pi would compact the lane, or its settings file could not be read. Set Pi's `compaction.enabled` to `false`, or repair the file.
- `pi-carrier-unreadable` (naming the `file`): the host's pi-hooks carrier file could not be read.
- `pi-mail-wake-missing` (naming `root`, `scope`, `location`, `update` and `retry`): the selected pi-hooks lists no lane mail wake. Repair that install on the lane machine using [pi-runtime.md § Lane mailbox wake](pi-runtime.md#lane-mailbox-wake-pi), including its project repair route for linked worktrees. A hosted retry needs `--relaunch` because `create` already owns the item.

A hosted Pi lane's settings and carrier are its host's, read after `create`, so the host keeps the item a Pi refusal leaves: launch it again with `--relaunch` after the fix.

`host-accounts-unanswered` is a notice, not a refusal: nothing said which accounts the host holds, so the launch is judged on this machine's reading as an unhosted one is. A keyed `lanes:` line above the notice names a provider failure, with the provider's own message above that line; no line above it means the read of the answer failed on this machine. Fix what that line names, or read the launch's outcome as a local measurement.

## Brief file

A `--cmd` launch's brief travels as a file. Write it under `tmp/` with the harness's file tool, pass it as `--brief-file [BRIEF_PATH]`, and put `{brief}` in the `--cmd` command where the brief goes, bare and outside every quote. `open-terminal` supplies the shell quoting. Local GUI and tmux launches save a copy of the brief in the worktree's git directory. The shell reads that copy when the command runs, so brief newlines never enter terminal input. Worktree removal deletes the saved copy. Only a hosted terminal launch quotes the brief text inline for the remote shell behind the provider's prefix. Each route preserves the brief's text, less trailing newlines. An apostrophe, a double quote, `$` or a backtick in the brief reaches the harness as written. A brief typed inline in `--cmd` is the caller's own shell text: two apostrophes in a single-quoted brief balance each other, and the harness receives the words between them split and altered, or the shell runs them. Each refusal below comes before any worktree or window:

- `cmd-unbalanced-quote` (naming `item`): the `--cmd` command leaves a quote open. Move the brief to a file, as above.
- `brief-quoted` (naming `item`): the command puts `{brief}` inside a quote or behind a backslash. The launcher supplies shell quoting, so additional quoting can split or expand the brief. Write `{brief}` bare.
- `brief-unreferenced` (naming `option=--brief-file`): no `--cmd` command carries `{brief}`, so the file would reach no harness. Pass a `--cmd` command with `{brief}` where the brief goes; a launch without `--cmd` renders its own brief and takes no file.
- `brief-file-missing` (naming `option=--cmd`): the command carries `{brief}` with no `--brief-file`. Pass the file.
- `brief-file-unreadable` (naming `path`): the path is not a readable file. Write the brief and pass that path.
- `brief-file-empty` (naming `path`): the file holds only whitespace, so the harness would start with nothing to do. Write the brief into it.

## Caps

The fleet cap refuses a launch before its worktree; a `--relaunch` meets it only where it adds a lane. It counts the `running`, `preparing` and `parked` lane records, so it bounds items in flight: a parked lane keeps its slot, and its resume adds no lane. No cap bounds the lanes on one account: `lanes pick` chooses the account by its headroom.

- `cap-reached`: launch once a lane closes.
- `cap-unreadable`, `cap-lock-unopenable`, `cap-lock-failed`, `cap-reserve-failed`, `claim-unrecorded`: fix what the line names; never launch around it.

A launch queued behind the cap, such as a chain script, passes `--wait-slot`, which waits for room; the overseer writes no counting loop. `--over-cap` admits one deliberate exception, recorded as the lane record's `over_cap`.

## Tmux session

Every lane window opens in one tmux session, named in the record's `window` as `SESSION:WINDOW`: `ORCH_TMUX_SESSION` when set, else the session the state records as `tmux.session`, else the launching pane's session. The first tmux launch records the session it opened in, `ORCH_TMUX_SESSION` or the pane's, once tmux confirms it exists. A launch with no live pane and neither refuses as `tmux-session-unresolved`, and a named session tmux does not hold refuses as `tmux-session-missing` with its source. A detached launch chain with `ORCH_TMUX_SESSION` set needs no `$TMUX`: it reaches that session on the person's own tmux server, the socket tmux derives from their uid. One with neither refuses as `tmux-missing`, so set `ORCH_TMUX_SESSION` for such a chain.

## Recovery relaunch

A dead or walled terminal lane uses native resume. A tmux relaunch replaces the item's existing window in the resolved session, for local and hosted lanes alike. A Linear key identifies the item, so replacement needs only the same name. A GitHub window requires the repository and worktree identity the launcher records on it. An untagged GitHub window remains open and emits window-preserved. With no replaceable match, the launcher opens a new window. Start with the [handoff.md](../workflows/handoff.md) § 2 terminal command. Add `--relaunch`, the selected `--lane`, the chosen `--launch-flags` and `--state-dir [OVERSEE_STATE_DIR]`. Keep the tracker, repository, harness, and item arguments, and `--lane-refresh` for a refresh lane, since a relaunch without it removes the lane's refresh record. Local relaunches and hosted Claude, Codex and Pi relaunches need no `--cmd`. Hosted Codex and Pi select a matching session on the host, or run the `start` brief in the same call when none exists. A `--cmd` relaunch follows [§ Lane preference](#lane-preference), with no session lookup, harness-switch check or `start` template. A relaunch that matches a session resumes that session's own workflow at its recorded tier: a `small` lane keeps running small.md under its bounds, and a `micro` lane micro.md. A relaunch that matches no session, or takes the `start` template by a route below, renders it and runs the standard cycle on the branch the tier's run left, its [start-worktree.md](../workflows/start-worktree.md) § 1 recording the tier as `standard`. A local relaunch of an item whose handoff record stands looks for no session: its lane ended that session when it wrote the record, so the launcher reports `session-retired` and renders the `start` template, whose [start.md](../workflows/start.md) § 0 continues from the record; a record the launcher cannot read refuses as `handoff-unreadable`. The launcher asks from the lane's worktree, where the lane wrote the record. A hosted relaunch selects from the host's sessions, since its handoff record is not read locally. A record carrying `host` adds `--host [HOST]`: the provider keeps its tree. A hosted Claude relaunch runs the `start` brief when `claude --continue` exits 1 for no session. Hosted no-command Claude, Codex and Pi relaunches require a harness screen or Claude's brief check, including a fresh start after a harness switch. A pane that fails the screen wait is `harness-screen-missing`, not launched. Under a fleet, its window closes and its record reads `stopped`: a foreground launch writes that status only after a successful close; the background job writes it whatever the close answered. When changing harnesses, supply the new brief required by [handoff.md § 2](../workflows/handoff.md#2-launch) through `--brief-file` and `--cmd`. Without a custom command, a relaunch whose lane record names another harness as the last one to run the lane renders the `start` template directly, reported as `harness-switched`. Relaunch identity during preparation follows the `lanes` contract in [workflow-state.md § Oversee state](../schemas/workflow-state.md#oversee-state). A record whose status is `parked` ([oversee-lanes.md § Parking a merge wait](oversee-lanes.md#parking-a-merge-wait)) takes the same command: the launcher starts the stopped sandbox through `lane-host start` before its `create --relaunch`, requires the provider's `sandbox-started` line, and refuses as `host-start-failed` with the record still parked when the provider does not answer it, so a resume is never reported on a sandbox nothing confirmed up; a confirmed start rewrites the record `stopped` before the create, so a create that fails after it leaves a stopped record a plain relaunch recovers. The resumed harness continues the transcript on the disk the park kept; a parked record keeps its fleet slot, so its relaunch replaces the lane it holds and never meets `cap-reached` ([§ Caps](#caps)). A hosted relaunch is judged on the account's usage window like any other launch, read from the provider's `accounts` row where that row carries one, and is refused as `lane-model-walled` when that window is at or above the threshold; `open-terminal --help` § `--host` holds what the provider's answer decides: that window where its row carries a reading, and, for an account nothing measured, whether the provider holds it. A relaunch the provider reports holding the account for proceeds there, reported as `host-relaunch-credential`, and the resumed session reports its own usage banner, which [oversee.md § 4](../workflows/oversee.md#4-watch-and-advance) reads as `usage-limit`. A local relaunch of an unmerged item whose rebase onto the base conflicts aborts that rebase and starts the session on the tree as it stands, reported as `relaunch-unrebased`: the restack stays the lane's. The launcher delivers the continuation line in the resumed command itself and keeps a merged item's tree as it stands, so nothing is pasted into the pane after the resume. An actual hosted Codex resume is the exception: it stays promptless and reports `resume-lineless`. Only that notice requires a continuation paste. A fresh start carries its brief and needs no paste. Paste the resumed lane's continuation through [oversee-lanes.md § Talking to a lane](oversee-lanes.md#talking-to-a-lane), Pane paste, the way a walled lane gets its nudge.
