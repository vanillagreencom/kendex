# Lane reach

Load from [oversee-lanes.md § Talking to a lane](oversee-lanes.md#talking-to-a-lane) when a wake is refused or a lane shows a harness dialog, and from [oversee.md § 4](../workflows/oversee.md#4-watch-and-advance) when a lane closes. Reaching a lane at the pane is the Pane paste paragraph in oversee-lanes.md.

## Wake refusals

For a lane judged by its pane, `unjudged` from `lanes state` means the pane settled nothing, not that a wake would be refused: the wake reads the harness process as well, so it can still answer where `lanes state` cannot. `idle` is likewise the pane's word alone there: the wake also reads the harness process, and it refuses a lane whose process reads busy. A live Codex or Copilot lane is refused every time, because neither publishes an idle signal: as `working` where its process has a shell under it, and as `unjudged` otherwise. A harness process another user owns, root among them, answers `unjudged` for the whole lane while it runs, and on a host with no `/proc` the wake's process read answers `unjudged` for any lane whose harness has a process on the box. None of that reaches `lanes state`, which makes no process read: its own `unjudged` is the pane's silence, or a Pi lane's missing rows, and the table below keeps the two apart under one row each.

The watch and `lanes state` judge a Pi lane from what Pi emits and never from its pane: the Stop row the `lane-mail-check` hook writes in the lane's mailbox at each turn end, and the PreToolUse row it writes at the first tool call of each turn (`scripts/lib/session-rows.sh`), both read through the same verdict. The last row answers `idle`, `working`, or `walled` for a turn that ended on an error the limit banner rule reads. A Pi lane never reads `asking`, since Pi's carrier sends no dialog event, and one with no row reads `unjudged`. The pane judge is the last-resort fallback, taken only for a window no running fleet record names as a Pi lane's, whatever harness runs there. One pane read of a Pi lane remains until its follow-up lands: `lane-close`'s close guard hands the judge no rows, so it reads a Pi lane's pane.

The rows are the wake's refusal reasons, plus the different silence `lanes state` reports under the same word. A local Pi wake goes to the live session through pi-bridge and is never put to the judge, so no row refuses one; a hosted Pi lane takes the `wake-invalid` row like any hosted lane.

| Reason | What the judge read | How the lane is reached |
|--------|---------------------|-------------------------|
| `working` | A turn in flight, or a pane that cannot be read as anything else: a frame scrolled up its own history reads `working` while it stays there, and so does a lane streaming its last message. | Send, and a lane still taking tool calls reads it at the next one, and a turn in flight reads it at its end. For a lane already idle, scroll the pane back to the bottom and read the state again; a refusal that stays is [§ Mail the wake cannot deliver](#mail-the-wake-cannot-deliver). |
| `asking` | A dialog is waiting on an answer. | Answer it by the harness column of [§ Per harness](#per-harness), not by mail. |
| `walled` | The account is spent and the turn is over. | Reads no mail. Reach it by Pane paste, or relaunch after the reset its banner names. |
| `exited` | Nothing is running under the pane. | Reads no mail. Relaunch it. |
| `wake-invalid` for a hosted lane | Nothing: the wake reaches no lane host, so it refuses every hosted lane before any judge runs. | [§ Mail the wake cannot deliver](#mail-the-wake-cannot-deliver). |
| `unjudged` from a wake | The process read gave no positive idle: a live Codex or Copilot process, a harness process another user owns, a host with no `/proc` carrying a process named for that harness, or a limit-banner scan that failed. | The turn may already have ended, so the lane reads nothing until its next turn starts: [§ Mail the wake cannot deliver](#mail-the-wake-cannot-deliver). |
| `unjudged` from `lanes state` | No process is read at all. A Pi lane has written no row, or its rows could not be read. Otherwise the pane settled nothing: no pane on this server carries the name, because the window closed or two windows share it, or the pane's screen carries no marker. | A closed window is relaunched under [lane-directive.md § Recovery relaunch](lane-directive.md#recovery-relaunch). For a shared name, find the lane's own window before touching either: `tmux list-panes -a -F '#{window_name} #{pane_id} #{pane_current_path}'` prints both with their working directories, and the lane's is the one sitting in its worktree. Rename the other, with `tmux rename-window`. Renaming the lane's own leaves the name on no pane, which the next watch pass reads as `window-gone` and relaunches the item beside its live session, so make the check first. A markerless screen is read at the pane. |

## Mail the wake cannot deliver

Every lane the wake refuses while its session still runs takes this route, whatever its harness: `working`, `unjudged` from a wake, and a hosted lane's `wake-invalid`. The mail waits by default, and the lane reads it at the next point the Lane mail rule in [skill-rules.md § Coordination](skill-rules.md#coordination) names, a waiter's return included; a lane idle at its prompt reads nothing until its next turn starts. Mail that cannot wait ends the session by signal, then closes and relaunches the lane, never as a second session beside a running one:

1. Stop the harness. A hosted lane takes `lane-host stop --item [ITEM] --harness [HARNESS]` and needs its `stopped item=[ITEM] processes=[COUNT]` line. A local lane takes the stop `lane-close` runs for an idle lane, `lane_stop_local` from `scripts/lib/lane-state.sh`, which ends the harness and then the turn an earlier wake started, which runs detached outside the pane and may be the turn the wake refused on as `working`. The command below sources and calls it, run from the lane's repository checkout. `[PID]` and `[START]` are the lane record's `launch.pid` and `launch.start`, and `[WAKE_PID]` and `[WAKE_START]` its `wake.pid` and `wake.start`, which `.agents/skills/orch/scripts/workflow-state --state-dir [OVERSEE_STATE_DIR] get oversee '.lanes[] | select(.item == "[ITEM]") | {launch, wake}'` prints, each passed as `""` where it prints null. `[PANE_PID]` is the process of the lane's pane, which `tmux display-message -p -t [PANE] '#{pane_pid}'` prints for the record's `launch.pane`, the exact pane id; only where `launch` is null does `[PANE]` take the record's `window`, a name tmux may match by prefix on another session:

   ```bash
   bash -c '. .agents/skills/orch/scripts/lib/lane-state.sh && lane_stop_local "$1" "$2" "$3" "$4" "$5" "$6" && echo "stopped processes=$LANE_STOP_COUNT identity=$LANE_STOP_IDENTITY" || { echo "stop-failed target=$LANE_STOP_TARGET cause=$LANE_STOP_CAUSE pid=$LANE_STOP_PID" >&2; exit 1; }' _ [PANE_PID] [PID] "[START]" [WAKE_PID] "[WAKE_START]" [HARNESS]
   ```

   Status 0 prints `stopped processes=[COUNT] identity=[IDENTITY]`: every `[HARNESS]` process at or below the pid the stop signalled by has exited, and so has the woken turn where the record names a live one. `identity=recorded` is the record's own; `identity=pane` is the harness under `[PANE_PID]`, read because the record named none or named a harness that has exited or whose pid a later process holds. Status 1 prints `stop-failed target=[TARGET] cause=[CAUSE]`: `target=harness` or `target=wake` is the stop that failed and the cause comes from that library's list above `lane_stop_local`, both empty where the library did not load, and the lane or its woken turn may still run.

2. Wait for the lane's `lane-exited` event.

3. Run `lane-close --keep-sandbox --state-dir [OVERSEE_STATE_DIR] [ITEM]`. It ends a local lane's validation runs, closes the window and records the lane `stopped`, keeping a hosted lane's sandbox.

4. Relaunch under [lane-directive.md § Recovery relaunch](lane-directive.md#recovery-relaunch).

Follow that recovery section's continuation rule: only `resume-lineless` requires a paste after the relaunch. The stop interrupts any turn in flight, so it is never the default.

## Lane close

`lane-close` ends an idle Claude, Codex, Pi or Copilot CLI harness by SIGTERM, through `lane-host stop` for a record carrying `host`, and for a local lane by its launch identity, the record's `launch`, or the harness under the pane where the record names none or names one that has exited or whose pid a later process holds; it then waits for the pane to read exited. A local close of any lane also stops the turn a wake started, by the record's `wake`. A hosted stop that finds the harness by the item's worktree, a provider that records no identity or a lane with none to stop by, answers an item whose worktree is gone with `stop-worktree-removed`, and a full close then skips the stop and the exit wait as `stop-skipped`. Nothing is typed into the pane. An exited lane needs no stop. It removes a finished item's files through `workflow-state remove`, calls the recorded lane host, kills the window by pane id, and records `done`. `--keep-sandbox` records `stopped` instead. `--park --pr [PR_NUMBER]` records `parked`: it ends a hosted lane's clean merge wait, whatever the lane is doing, once the record's provider answers `stop-sandbox --check` and the pull request reads open, queued or else armed and `CLEAN`, and silent to the review-gate reducer, then stops the sandbox through `lane-host stop-sandbox` and requires its `sandbox-stopped` line; `park-refused` names the condition that stopped it and changes nothing, and `park-failed` is a sandbox the provider could not stop after the harness ended, recorded `stopped` ([oversee-lanes.md § Parking a merge wait](oversee-lanes.md#parking-a-merge-wait), `lane-close --help`). A merged hosted item keeps its record `running` until the watch calls that verb and reports `lane-closed` or `lane-close-refused`; a parked item is not closed on the `merged` of the pull request its record names: the watch prints `parked-merged`, the overseer relaunches the lane, and the resumed lane is closed as a merged hosted item is. Every other `lane-close` exit is neither event: the watch writes `lane-close-failed item=[ITEM] exit=[N]` on stderr with the verb's own refusal lines under it, leaves the record `running` and retries the close on the next pass, so an `ask-unanswered` or a `mail-read-failed` refusal repeats until the cause the refusal names is fixed, the ask answered or the mailbox repaired. A nonterminal or working lane refuses as `lane-live`. A limit banner below the lane's last turn is passed over only where `lanes pick --lane`, run under the record's `host`, reads the record's `account` as room, for the record's `model` or over the whole account where it names none, and the banner dates no reset still ahead and names none the host cannot resolve; every other reading keeps the lane walled, and its `lane-live state=walled` refusal names the reading as `account=`. Two panes with the recorded name refuse as `pane-ambiguous`, and a window no pane on this server carries as `pane-missing`, bar a full close of a hosted record whose item is terminal, which goes on with no exit wait; the recorded window resolves in either form tmux accepts, a bare name or `SESSION:WINDOW` whose session name must match exactly. A stop that fails refuses as `stop-failed`, and a pane that outlives the stop as `exit-timeout` ([oversee-events.md](oversee-events.md#event-kinds)). A lane holding an ask nobody answered refuses as `ask-unanswered`; answer it with `lane-mail send --item [ITEM] --re [ASK_ID] --file [PATH]`, which a lane whose record carries `host` takes with `--root [MAIL_ROOT] --host` under the [oversee.md § Lane record](../workflows/oversee.md#lane-record) mailbox rule, and close again, and a mailbox the close cannot read refuses as `mail-read-failed`. An exited lane takes neither refusal, and the `stopped` record `--keep-sandbox` leaves behind takes the ask one, its kept sandbox being relaunchable into a session that reads the reply. A record written before the launcher recorded the lane's tracker, repository and harness carries none of the three; an exited lane closes without them, and an idle one reads its tracker from a tracker-identifier item key and its harness from the pane where that pane runs the harness. An `issue-N` key answers no tracker, being the key a GitHub lane and a Linear lane are both given, so such a record refuses as `tracker-read-failed cause=key-ambiguous`. The identity a caller still supplies is `--tracker linear|github` for an `issue-N` record carrying none, `--repo [OWNER/REPO]` for a GitHub lane and `--harness claude|codex|pi|copilot` for a lane whose pane runs a wrapper; where the item key does answer the tracker, `--tracker` only pins what it says. Each fills only a field the record leaves null or absent and refuses as `record-invalid` where it contradicts one the record carries. On the surfaces of [oversee.md § 1](../workflows/oversee.md#1-resolve-the-launch-surface), surface 2 uses its native close and then sets its lane record `done`, because it has no tmux pane for `lane-close` to resolve. Surface 3 continues in the overseer session and has no separate session or lane record to close.

A local lane's close ends every validation run its worktree still holds, through `dev-validate-run --stop`, and refuses as `validate-stop-failed` where one of them could not be ended. The `dev-validate-run: stop-failed` line above names the run directory, then either the unit ([job-units.md](job-units.md)) and systemctl's own words or the process id and the step that failed. The window and record are unchanged: end that run, then close the lane again.

## Per harness

What stays per harness is launching, resuming and the harness's own dialogs; the Pi commands are the pi-session-bridge CLI, documented in its [README](https://github.com/vanillagreencom/kendex/blob/main/pi-extensions/pi-session-bridge/README.md) and `pi-bridge --help`, and every Pi call selects the lane by `--name` or `--cwd`.

| Claude Code | `open-terminal` into a tmux pane ([oversee.md § 3](../workflows/oversee.md#3-launch)). In a tmux pane, a first launch in a folder the wrapper has not trusted shows a trust prompt with "No, exit" selected: press `Down`, then `Enter`, with `pane-write --key`, then relaunch. | Follow [oversee.md § Bounded lane reads](../workflows/oversee.md#bounded-lane-reads). | Press `Up` or `Down`, then `Enter`, with `pane-write --key [KEY]` on the lane's window, `--expect` as Pane paste gives it; the recorded choice line confirms it. The prompt of Claude Code's critical-path check ("This shell -c script runs rm and could not be checked") fires even under bypass. Where the `critical-path-deny` hook is installed, it denies that prompt at once in a launched lane, and the lane does not wait. The denial carries the [permission-modes page](https://code.claude.com/docs/en/permission-modes.md#rewrite-a-flagged-command)'s rewrite for each flagged form, and the lane rule for a long inline script: write it to a file under the lane's `tmp/`, every `rm` target in it still guarded with `:?` or literal.
