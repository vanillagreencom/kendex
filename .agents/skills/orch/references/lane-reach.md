# Lane reach

Load from [oversee-lanes.md § Talking to a lane](oversee-lanes.md#talking-to-a-lane) when a wake is refused or a lane shows a harness dialog, and from [oversee.md § 4](../workflows/oversee.md#4-watch-and-advance) when a lane closes. Reaching a lane at the pane is the Pane paste paragraph in oversee-lanes.md.

## Wake refusals

The wake serves a Claude lane and a Pi lane on this machine. A Claude wake asks `orch-runtime lane status --item [ITEM]` and wakes only on `idle`: its `wake-refused reason=WORD` carries that read's `result.state`, and a refused or unreadable reply gives `unjudged`. The status read selects one in-flight fleet record. It reads the provider's status where the host kind declares `status=verb`: `exited` is `exited`, a failed status read is `unjudged` with its cause, and `running` takes the harness as up. For `pane=verb`, it judges the provider's capture with no local pane or foreground read. On the local-pane path it reads the recorded pane and its screen through the watch's classifier, and the pane's foreground process only where no provider answered `running`: on a bare local host a screen reads `idle` only with the harness in the foreground.

The watch and `orch-runtime lane status --item [ITEM]` judge a Pi lane's last session row after the applicable host, pane, process and screen checks: the Stop row the `lane-mail-check` hook writes in the lane's mailbox at each turn end, and the PreToolUse row it writes at the first tool call of each turn (`scripts/lib/session-rows.sh`). That row answers `idle`, `working`, or `walled` for a turn that ended on an error the limit banner rule reads. A Pi lane with no row or unreadable rows reads `unjudged`; its screen supplies no idle fallback. One pane read of a Pi lane remains: `lane-close`'s close guard hands the judge no rows, so it reads a Pi lane's pane.

A Codex or Copilot lane, a hosted or cloud lane, and a record not in flight (`status=stopped`, `parked`, `done` or none) take `wake-invalid` before the status read: a Codex or Copilot session is never resumed beside itself, so its mail waits for the lane's next turn or its relaunch, and a lane that ended is relaunched under [lane-directive.md § Recovery relaunch](lane-directive.md#recovery-relaunch). A record whose `wake` names a turn an earlier wake started that still runs under its recorded start refuses `wake-refused reason=wake-running`, and one whose `wake` cannot be read refuses `wake-refused reason=unjudged` with `cause=`, both before the status read. A local Pi wake then goes to the live session through pi-bridge without a status read.

| Reason | What the judge read | How the lane is reached |
|--------|---------------------|-------------------------|

## Mail the wake cannot deliver

Every lane the wake refuses while its session still runs takes this route, whatever its harness: `working`, `wake-running`, `unjudged` from a wake, and the `wake-invalid` of a Codex, Copilot or hosted lane. The mail waits by default, and the lane reads it at the next point the Lane mail rule in [skill-rules.md § Coordination](skill-rules.md#coordination) names, a waiter's return included; a lane idle at its prompt reads nothing until its next turn starts. Before stopping a lane for mail that cannot wait, read [lane-directive.md § Recovery relaunch](lane-directive.md#recovery-relaunch): stop only a lane it can relaunch, and otherwise keep the session, window, record and pending mail. For a lane it can relaunch, end the session by signal, then close and relaunch it, never as a second session beside a running one:

1. Stop the harness. A hosted lane takes `lane-host stop --item [ITEM] --harness [HARNESS]` and needs its `stopped item=[ITEM] processes=[COUNT]` line. A local lane takes the stop `lane-close` runs for an idle lane, `lane_stop_local` from `scripts/lib/lane-state.sh`, which ends the harness and then the turn an earlier wake started, which runs detached outside the pane and may be the turn the wake refused on as `working`. The command below sources and calls it, run from the lane's repository checkout. `[PID]` and `[START]` are the lane record's `launch.pid` and `launch.start`, and `[WAKE_PID]` and `[WAKE_START]` its `wake.pid` and `wake.start`, which `STATE_READ="$(.agents/skills/orch/scripts/orch-runtime --state-dir [OVERSEE_STATE_DIR] state get --fleet /lanes)" && jq -c '.result.value[] | select(.item == "[ITEM]") | {launch, wake}' <<<"$STATE_READ"` prints, each passed as `""` where it prints null. `[PANE_PID]` is the process of the lane's pane, which `tmux display-message -p -t [PANE] '#{pane_pid}'` prints for the record's `launch.pane`, the exact pane id; only where `launch` is null does `[PANE]` take the record's `window`, a name tmux may match by prefix on another session:

   ```bash
   bash -c '. .agents/skills/orch/scripts/lib/lane-state.sh && lane_stop_local "$1" "$2" "$3" "$4" "$5" "$6" && echo "stopped processes=$LANE_STOP_COUNT identity=$LANE_STOP_IDENTITY" || { echo "stop-failed target=$LANE_STOP_TARGET cause=$LANE_STOP_CAUSE pid=$LANE_STOP_PID" >&2; exit 1; }' _ [PANE_PID] [PID] "[START]" [WAKE_PID] "[WAKE_START]" [HARNESS]
   ```

   Status 0 prints `stopped processes=[COUNT] identity=[IDENTITY]`: every `[HARNESS]` process at or below the pid the stop signalled by has exited, and so has the woken turn where the record names a live one. `identity=recorded` is the record's own; `identity=pane` is the harness under `[PANE_PID]`, read because the record named none, or named a harness that has exited or whose pid a later process holds. The stop compares the start in the form the record spells it: the runtime's `ticks:` or `lstart:` start ([workflow-state.md § Oversee state](../schemas/workflow-state.md#oversee-state) `launch`), or the bare `ps -o lstart=` text a wake and a released launch record; a `ticks:` start on a host with no `/proc` is unread, `target=harness` with `start-read-failed`. A lane no pane carries takes `""` as `[PANE_PID]`: its harness is stopped only by the record's `launch`, and `identity=none` is a record naming no live one, no harness this stop can reach; the woken turn is stopped as above. Status 1 prints `stop-failed target=[TARGET] cause=[CAUSE]`: `target=harness` or `target=wake` is the stop that failed and the cause comes from that library's list above `lane_stop_local`, both empty where the library did not load, and the lane or its woken turn may still run. A failed harness stop still stops the woken turn and reports the harness's failure, so the command run again after a `target=wake` failure reaches the turn even though its harness is gone, and reads `target=harness` with `identity-stale` or `identity-unread`.

2. Wait for the lane's `lane-exited` event.

3. Run `lane-close --keep-sandbox --state-dir [OVERSEE_STATE_DIR] [ITEM]`. It ends a local lane's validation runs, closes the window and records the lane `stopped`, keeping a hosted lane's sandbox.

4. Relaunch under [lane-directive.md § Recovery relaunch](lane-directive.md#recovery-relaunch).

The relaunch's brief carries the continuation, so nothing is pasted after it. The stop interrupts any turn in flight, so it is never the default.

## Lane close

`lane-close` ends an idle Claude, Codex, Pi or Copilot CLI harness by SIGTERM, through `lane-host stop` for a record carrying `host`, and for a local lane by its launch identity, the record's `launch`, or the harness under the pane where the record names none or names one that has exited or whose pid a later process holds; it then waits for the pane to read exited. A local close of any lane also stops the turn a wake started, by the record's `wake`. A hosted stop that finds the harness by the item's worktree, a provider that records no identity or a lane with none to stop by, answers an item whose worktree is gone with `stop-worktree-removed`, and a full close then skips the stop and the exit wait as `stop-skipped`. Nothing is typed into the pane. An exited lane needs no stop. It removes a finished item's files through `workflow-state remove`, calls the recorded lane host, kills the window by pane id, and records `done`. `--keep-sandbox` records `stopped` instead.

`--park --pr [PR_NUMBER]` records `parked`: it ends a hosted lane's clean merge wait, whatever the lane is doing, once the record's provider answers `stop-sandbox --check` and the pull request reads open, queued or else armed and `CLEAN`, and silent to the github skill's reducer, then stops the sandbox through `lane-host stop-sandbox` and requires its `sandbox-stopped` line; `park-refused` names the condition that stopped it and changes nothing, and `park-failed` is a sandbox the provider could not stop after the harness ended, recorded `stopped` ([oversee-lanes.md § Parking a merge wait](oversee-lanes.md#parking-a-merge-wait), `lane-close --help`).

A merged hosted item keeps its record `running` until the watch calls that verb after an exit, or two idle passes with its worktree gone (one for a Codex lane whose screen has moved past the turn), or two consecutive long passes with a hosted Pi lane's rows missing, its merged row recorded and its worktree gone, and reports `lane-closed` or `lane-close-refused`; the watch closes a parked or stopped record whose tracker item is terminal through the runtime close, after it records the merge's cycle ([oversee-events.md § Event kinds](oversee-events.md#event-kinds) `merged`). A provider refusal is reported once per lane record and terminal state. A parked item with unfinished work, including a Done item with an unchecked box, is not closed on the `merged` of the pull request its record names: the watch prints `parked-merged`, the overseer relaunches the lane, and the resumed lane is closed as a merged hosted item is. Its retained PR identity follows [workflow-state.md](../schemas/workflow-state.md#oversee-state), so an OPEN PR prevents terminal close after a failed recovery create. Every other `lane-close` exit is neither event: the watch's `watch-step-failed` line carries `lane-close-failed item=[ITEM] exit=[N]` on stderr with the first line of the verb's output beside it, leaves the record `running` and retries the close on the next pass, so an `ask-unanswered` or a `mail-read-failed` refusal repeats until the cause the refusal names is fixed, the ask answered or the mailbox repaired. A close that started and gave no answer is `lane-close-unanswered`; its marker stands, and while the record still reads `running` a later pass reports `lane-close-unconfirmed` and leaves the lane to the operator: read the lane record, then close the lane by hand.

A working lane, or an idle one whose item is not terminal, refuses as `lane-live`, bar an idle lane whose record carries the `cycle` `oversee-cycle record` writes and whose worktree, the record's `mail_root`, is gone, which closes with its item left open, for an item held open past its merge by a box the overseer checks itself. A Pi lane read `unjudged` also takes the recorded merge cycle and removed worktree rule; every other `unjudged` lane refuses as `lane-live`. A record keeps its `cycle` across a relaunch, so a worktree still standing, a relaunch for more work or a lane inside its merge close-out, keeps the refusal; a hosted worktree is read through `lane-host cat`, and a read that fails refuses as `worktree-read-failed`. A limit banner below the lane's last turn is passed over only where `lanes pick --lane`, run by the close under the record's `host`, reads the record's `account` as room, for the record's `model` or over the whole account where it names none, and the banner dates no reset still ahead and names none the host cannot resolve; every other reading keeps the lane walled, and its `lane-live state=walled` refusal names the reading as `account=`.

Two panes with the recorded name refuse as `pane-ambiguous`, and a window no pane on this server carries as `pane-missing`, bar a full close of a record whose item is terminal, which goes on with no exit wait, a local one stopping only a harness its record's `launch` still names, and refusing as `pane-missing cause=renamed` where the tmux server its `launch` recorded still lists its launch pane, its window or session renamed or the window moved, and as `pane-read-failed` with `server=` where that server runs a tmux this close does not reach or its pane list cannot be read. A server started since and handed the recorded pid lists panes of its own under the same ids, so confirm the listed pane sits in the lane's worktree or runs its harness before restoring the recorded window; where it does not, clear the record's `launch` through `workflow-state update oversee` and close again. The recorded window resolves in either form tmux accepts, a bare name or `SESSION:WINDOW` whose session name must match exactly. A stop that fails refuses as `stop-failed`, and a pane that outlives the stop as `exit-timeout` ([oversee-events.md](oversee-events.md#event-kinds)).

A lane holding an ask nobody answered refuses as `ask-unanswered`; answer it with `lane-mail send --item [ITEM] --re [ASK_ID] --file [PATH]`, which a lane whose record carries `host` takes with `--root [MAIL_ROOT] --host` under the [oversee.md § Lane record](../workflows/oversee.md#lane-record) mailbox rule, and close again, and a mailbox the close cannot read refuses as `mail-read-failed`, bar a full close of a hosted record on a terminal item whose provider's `lane-host list` names no sandbox for it, as its `close --force` leaves it: no session holds an ask there, so the close prints `host-absent` and records `done` with no provider stop or close, and a list `lane-host` refuses at its cap exits `69` as `lane-host-busy step=list`. An exited lane takes neither refusal, and the `stopped` record `--keep-sandbox` leaves behind takes the ask one while its item is open, its kept sandbox being relaunchable into a session that reads the reply. A full close of a stopped record on a terminal item reads no mailbox.

A record written before the launcher recorded the lane's tracker, repository and harness carries none of the three; an exited lane closes without them, and an idle one reads its tracker from a tracker-identifier item key and its harness from the pane where that pane runs the harness. An `issue-N` key answers no tracker, being the key a GitHub lane and a Linear lane are both given, so such a record refuses as `tracker-read-failed cause=key-ambiguous`. The identity a caller still supplies is `--tracker linear|github` for an `issue-N` record carrying none, `--repo [OWNER/REPO]` for a GitHub lane and `--harness claude|codex|pi|copilot` for a lane whose pane runs a wrapper; where the item key does answer the tracker, `--tracker` only pins what it says. Each fills only a field the record leaves null or absent and refuses as `record-invalid` where it contradicts one the record carries.

On the surfaces of [oversee.md § 1](../workflows/oversee.md#1-resolve-the-launch-surface), surface 2 uses its native close and then sets its lane record `done`, because it has no tmux pane for `lane-close` to resolve. Surface 3 continues in the overseer session and has no separate session or lane record to close.

A local lane's close ends every validation run its worktree still holds, through `dev-validate-run --stop`, and refuses as `validate-stop-failed` where one of them could not be ended. The `dev-validate-run: stop-failed` line above names the run directory, then either the unit ([job-units.md](job-units.md)) and systemctl's own words or the process id and the step that failed. The window and record are unchanged: end that run, then close the lane again.
