# Oversee events

[oversee.md](../workflows/oversee.md) § 4 applies these rules at every watch event.

## Judgement rules

The overseer owns fleet judgement, not just liveness; every `oversee.md` § 4 event is handled under these rules. The fleet log is the oversee state's `fleet_log[]` ([schemas/workflow-state.md § Oversee state](../schemas/workflow-state.md#oversee-state)), which exists before the first append per `oversee.md` § 3 Lane record; every record a rule below asks for is one append, `[KIND]` being `proposal`, `ruling`, `close`, `peer` or `use1` and `[ITEM]` the issue or repository it is about. `[ONE_LINE]` carries text the overseer did not author, so the record crosses a file and never argv ([SKILL.md](../SKILL.md) § Harness-Safe Shell): write it with the harness file-write tool, then bind the path. Append each record before replacing the file for the next one. The record carries no time: `append-file` stamps `at` from its own clock and refuses as `fleet-log-at-future` a record already dated later than it. `[ONE_LINE]` holds at most `ORCH_FLEET_LOG_ROW_BYTES` bytes, default 600, and a longer one is refused as `fleet-log-row-bytes`. The `append-file` entry in `workflow-state --help` names the rest of what it refuses on that field.

```json
{"kind":"[KIND]","item":"[ITEM]","text":"[ONE_LINE]"}
```

```bash
.agents/skills/orch/scripts/workflow-state append-file oversee fleet_log tmp/fleet-log-record.json
```

- **Lane proposals.** Record each lane's `Proposal comment:` notice in the fleet log as an authorized tracker, repository, issue, and returned comment ID or URL binding. Partition pending authorized comments by tracker and source PR repository. For each batch, launch one fresh one-shot canonical `tpm` subagent, the catalog's planning agent that owns the creation bar, priority, placement, duplicate and cancellation analysis, on the lowest-cost model the surface exposes, with the launch call, surface rule, single-return capture and retirement of the `triage` verifier under § Event kinds, naming `tpm` where that call names `maintainer`. A proposal sweep creates no carrier item and starts no `open-terminal` or hosted lane, and its TPM analysis never runs in the overseer. Send it the [proposal-sweep](../../project-management/workflows/proposal-sweep.md) workflow with a brief that supplies a checkout of the source repository on this host as its worktree, the batch tracker, tracker repository, source repository, fleet issue IDs, and authorized and resolved comment bindings. Accept the return only when it contains no other text and parses as one issue-mode audit object whose `tracker` type, and for GitHub its `repository`, equal the batch's. Its proposal rows are its `create` and `skip` rows: each carries exactly one `proposal_sources[]` entry by `index`, each entry names a distinct authorized binding of this batch, and no entry points at another row. A proposal whose source PR has not merged has no row and stays pending for the next sweep. Stop without a reply or fleet-log outcome on a launch, capture, parse, or validation failure. Write the accepted object with the harness file-write tool to `tmp/proposal-audit-[UTC_EPOCH].json` in the overseer's checkout, `[UTC_EPOCH]` fresh per batch. Check its rows against live fleet work, then invoke [audit-issues](../../project-management/workflows/audit-issues.md) from `oversee.md` § 1 as `audit-issues --analyzed tmp/proposal-audit-[UTC_EPOCH].json` under `PM_CREATE_AUTONOMY`. Its normal route parses the tracker, runs its tracker preflight and label inventory, skips TPM analysis, and continues through §§ 5-7. For Linear, reply with `.agents/skills/linear/scripts/linear.sh comments create [ISSUE_ID] --parent [COMMENT_ID] --body-file [PATH]`. For GitHub, use `gh issue comment [NUMBER] --repo [OWNER/REPO] --body-file [PATH]`; its first line is `Proposal outcome for [COMMENT_URL]:`. Each outcome carries the created issue ID or one-line decline. Record the source and outcome in the fleet log.
- **Heartbeat backstop for lane proposals.** At each `heartbeat` and before fleet close, run the Lane proposals sweep with every fleet issue in its tracker and repository batch. This catches a comment posted without another event.
- **Heartbeat backlog audit.** At each `heartbeat`, apply [Heartbeat audit](heartbeat-audit.md), independently of the lane-proposal sweep and the fleet-lane `triage` verifier.
- **Cut scope blowups.** A PR whose diff outgrows its issue's Done-when goes back to the contract: keep the oversized work on a branch, land the contract. Machinery no issue ordered — a new subsystem, scanner, or lexer — is cut, never reviewed into shape.
- **End spirals.** A round whose finding shares a root cause with one a prior round patched is dispositioned by [references/finding-disposition.md § Recurrence](finding-disposition.md#recurrence), which states the branches and their limits. Bots drip-feeding one class get the class exhausted in one audit pass, then dispositions without pushes. After five bot rounds on one PR, the lane answers the standing threads once and starts no further fix round. The review gate and the user's merge authorization still apply. The overseer never orders a blanket `Declined` across a PR's open findings: each one is dispositioned on its own mechanism, and a label-only decline violates [finding-disposition.md § Decision flow](finding-disposition.md#decision-flow).
- **Fix the source.** The same finding class on a third PR is a mechanism gap: file it and route the smallest deterministic check (a guard lane, a preflight rule, a refusing script) or one sentence in the owning skill through a lane as its own item — the overseer still implements nothing. Deterministic beats prose where it stays simple; complex or brittle machinery is worse than either. A package or workflow gap is never a harness memory or a local note: a lane's is a proposal ([skill-rules.md § Coordination, Tracked issue creation](skill-rules.md#coordination)), and the overseer's own is filed as File one item alone below states.
- **File one item alone.** Before filing, read [Design review](design-review.md). One item the overseer files itself, a class under Fix the source above or an issue an `owner-note` asks for, goes through [audit-issues](../../project-management/workflows/audit-issues.md) as `audit-issues --single [FILE_PATH]`, the file holding that one item per [audit-issues-input.md](../../project-management/schemas/audit-issues-input.md) with `source: "oversee"`, `parent_issue: null` and the fleet's `tracker`. After filing, append one fleet-log `ruling` whose text starts `filed ` and names the filed item, its Location file(s) and its defect-class rule, stated as the rule every site breaks. `--issues` is for a batch: its TPM run sweeps the whole backlog for cancellations.
- **Rule once for the fleet.** A ruling that answers one lane's question is sent to every lane in the same situation and recorded in the fleet log.
- **Held merges.** Under `ORCH_MERGE_AUTONOMY=ask` (`oversee.md` § 3) the lane's merge question arrives as `lane-question`. Read the gate results without reproducing them, then relay the question to the user, worded as [communication-modes.md](communication-modes.md) requires. Send `MERGE` to the lane only after the user authorizes it, or send exactly one directive the user gave. A directive may carry the authorization ("with that landed, MERGE stands"), and the lane then merges once the change is in without a second answer. Under `ask` a `disarmed` pr-watch line on a `land=lane` record is not a wake; on a running `land=handoff` record it launches the landing lane (`pr-watch` below).
- **Lanes merge their own pull requests.** A lane whose gates read met merges its own head by [merge-pr.md](../workflows/merge-pr.md) § 5 step 1, where `pr-merge` picks the route. The overseer runs no normal merge for a lane. Its own GitHub App acts for the head approvals [copilot-head-notices.md](copilot-head-notices.md) sets, and for nothing else except an emergency merge in a consumer whose ruleset lists that app as a bypass actor, which that step's "Who acts" names. A merge group that cannot pass because a CI input read from the default branch broke takes the recovery route in [review-gate SKILL.md § 4. Operations](../../review-gate/SKILL.md#4-operations).
- **Hand off a lane before it runs out.** The `lane-mail-check` turn-end hook reads the lane's context through its harness adapter, from the transcript, or on Copilot CLI from the reading its kendex Copilot extension recorded from Copilot's `session.usage_info`, against the limit Copilot compacts at, and where none stands from Copilot's statusLine session record ([copilot-runtime.md](copilot-runtime.md#measurement)), and its account headroom on its own credential, and refuses the turn end at either mark until the record below stands, so a lane hands itself off with no directive. Copilot honours a turn-end block 8 times in a row and then ends the turn unheld; the refusal returns at the session's next turn end. What follows is the BACKSTOP for a lane whose hook refused nothing, such as one past its account mark with no turn end since. On the `oversee.md` § 1 tmux surface, at every `oversee.md` § 4 event, read each live lane's context use:

  ```bash
  .agents/skills/orch/scripts/lanes context
  ```

  The three-argument context rule in `../scripts/lib/lane-context.sh::lane_context_handoff_due`, without an agent reserve, requires handoff at 400000 tokens used, or strictly past the effective percentage of the printed window. `ORCH_HANDOFF_CONTEXT_PCT` accepts 1 to 100 and defaults to `90`; values above `90` use `90`. A lower setting requests an earlier handoff only after usage strictly exceeds that percentage. Equality at any percentage does not trigger handoff, unless the independent token limit is reached. The token limit applies even when capacity is unknown. Below that token limit, unknown capacity remains unmeasured. Capacity means the limit before automatic compaction, or the actual window when automatic compaction is disabled; [skill-rules.md](skill-rules.md#coordination), Compaction, defines the harness controls.

  `ORCH_HANDOFF_AGENT_RESERVE_TOKENS` reserves nonnegative whole tokens for attached agent returns before the earlier context mark. Its default is `150000`. The reserve applies only to the attached-launch refusal, and only while an attached agent this session launched may still be out. On Claude Code the hook reads that roster from the session's task registry where the payload carries one, else from the transcript's Agent-call results, task notifications, teammate idle notifications and sends; an unreadable roster, or an entry neither read classifies, is unknown. Every other harness reads no roster, so its roster is unknown. While the reserve applies, the existing tool hook refuses attached launches at or above that mark minus the reserve, including equality. A launch refused by the reserve alone, below the plain mark, with an agent out names waiting for the attached agents to return, the job runner or a separate session, and no handoff. With the roster unknown no return can be observed, so that refusal names the job runner or a separate session, and for a lane its handoff record, never a wait. The reserve protects only a new launch. The turn-end judge and every `oversee-succeed` run use the three-argument rule above, even with an agent out, because a succession waits for every attached child ([oversee.md](../workflows/oversee.md) § Succession step 1) or names each unfinished one in the handoff. Missing required context also refuses the launch. Claude Code, Pi and Copilot CLI enforce this launch rule. Codex enforces it for `spawn_agent` and for `followup_task`, which starts a new turn on an attached agent, under any tool namespace. `send_message` only queues a message and is admitted. OpenCode installs advisory instructions only. Longer work uses the orch job runner ([waiter-launch.md, Launch](waiter-launch.md#launch)) or a separate session, with its run directory on the handoff. The general wait and emergency recovery rule is the Jarvis `long-session.md`, Handoff, contract.

  `lanes context` reports the context reading each lane's hook recorded at its last turn end, hosted lanes included, and account headroom. It sets `handoff_required` when the shared context rule requires handoff, or when the binding account bucket has headroom at or below `ORCH_HANDOFF_HEADROOM_PCT`. A lane on an overseer seat also requires handoff at or below `ORCH_OVERSEER_SEAT_RESERVE_PCT`. The caller's own row keeps the ordinary account mark. Headroom never marks a Codex account room on its credits, per `lanes --help` under `context`. A Copilot lane's launch takes no `--lane`, so no claim names it: its row is read from its running lane record. Every other lane is read through its claim alone. A row reading `unrecorded` has no reading yet, which is not room. A row reading `window-unread` has unknown capacity and remains below the independent token limit: direct it to write its handoff at its next safe point. The default is `3`, so a lane whose account reaches 97 percent used is marked for the overseer's next sweep, and the hook refuses the turn end on that same setting. Both resolve it through the kendex settings ladder, the hook through `orch-env` and this poll through its own project-env load, so a settings file sets one mark for both. At each event, tell every lane the poll marks and the hook has not already stopped to write its handoff at the next safe point, as for the context mark; a lane whose record already stands is handing itself off and needs no directive. Use `oversee-lanes.md` § Talking to a lane until lane mail is installed; then send the directive through lane mail. At either mark, wait for a safe point such as a landed merge or held PR. Never interrupt a round or an unpushed tree. The lane records the fixed shape below and exits. The record carries no time: `workflow-state set` stamps `written_at` from its own clock and refuses as `handoff-written-at-future` a record already dated later than it. The `set` entry in `workflow-state --help` names the rest of what it refuses on that field. The watch reports `handoff [ISSUE_ID]` once. Relaunch the item through [lane-directive.md § Recovery relaunch](lane-directive.md#recovery-relaunch), which uses the handoff record as durable recovery state; a copilot lane's relaunch starts a fresh session on that record rather than resuming the one that handed off.

  ```bash
  .agents/skills/orch/scripts/workflow-state set [ISSUE_ID] handoff '{"merged":["[PR]"],"remaining":["[STEP]"],"branch":"[BRANCH]","worktree":"[WORKTREE_PATH]","open_pr":[PR_NUMBER_OR_NULL],"traps":["[TRAP]"]}'
  ```

  The record, the event and the relaunch are surface-independent. Surfaces 2 and 3 register no lane claim, so `lanes context` reports no worker lane there: on surface 2 read a lane's context through the harness's own session tooling and hand off at the same mark; surface 3 has no lane to hand off.

  On a hosted fleet, also run `lane-host list`: a row not `available` whose item, the last segment of repository/item, has no `running` lane record is a sandbox with no live claim; surface it to the user.

  The overseer's own triggers are the shared context mark, its account mark, projected wall time at `ORCH_OVERSEER_WALL_MINUTES`, and the qualifying-accounts trigger. `oversee-succeed --help` defines the account, wall and qualifying-accounts judgement. Only the `lane-mail-check` hook's current reading judges the context mark. An unread or unmeasured trigger is never room. The watch reports reached account triggers as `overseer-mark` in [overseer-session-events.md](overseer-session-events.md), at the crossing and every `ORCH_OVERSEER_MARK_REPEAT` passes while they stand. A silent interval does not mean the mark lifted. `ORCH_OVERSEER_SUCCESSION=off` disables account-trigger refusals and automatic succession; the event still carries `succession=off`. The context refusal remains until this session records its handoff. The caller's row in `lanes context`, marked `*`, is the account backstop. Its context reads `unrecorded`. Its `HANDOFF` cell uses the shared context mark and lane headroom threshold, not the overseer's account, wall or qualifying-accounts triggers. At a trigger, follow [oversee.md § Succession](../workflows/oversee.md#succession) for preparation, launch and every refusal branch.

  Every refusal of a live self-succession, from the mode decision onward, records one fleet-log row and sends one owner notice through `lane-mail notice --to owner`. The keyed line names the mark, or `unknown` before the run judges one. Only `mark=headroom` names the account and reset time. A notice the owner already received within the last 24 hours can be refused as `owner-notice-repeated`; the fleet-log row still lands and the succession's refusal status stands. Check and print modes write neither channel.

  An overseer that DIES reaches none of this: it runs no turn, so it judges no mark and calls nothing. The successor reads available output from the predecessor's children before repeating their tasks, under the general recovery rule above. `oversee-watch` carries that case, from the session rows the overseer's own harness writes, its pane process and its recorded launch line, and reports it as `overseer-dead` in [overseer-session-events.md](overseer-session-events.md). An overseer that WALLS reaches none of it either, for the same reason and with the harness still running: the watch reads the same rows and reports it as `overseer-walled` there, recovering it on an account the pick judged rather than on the recorded line's spent one. One that WEDGES on a full context reads as `overseer-dead` `source=context`.

- **Keep the report's inputs current.** After each `oversee.md` § 2 selection, `workflow-state set oversee launch_queue '["[ITEM]",...]'` with the items not yet launched, in launch order. The queue is the order and the tracker the membership: the `heartbeat` handling below adds what the tracker says the fleet owes. A question sent to the owner is an owner ask ([communication-modes.md § Owner asks](communication-modes.md#owner-asks)), and the report's Waiting on you row reads the unresolved ones from the mailbox itself; nothing is recorded in the state for it.
- **Decide without the user.** The ask set is [communication-modes.md](communication-modes.md) § Ask set, which nothing here narrows or widens. Any other call takes the option that costs nothing and is recorded in the fleet log as that file's § Recording requires.

## Direct-push cycle records

When a lane reports a successful direct push to the base branch, record its cycle before closing it or removing its workflow state. Run from a checkout of that repository. A direct push raises no PR `merged` event. Refuse to record a push with several commits and report it in the fleet log; `oversee-cycle --help` defines the single-commit contract.

```bash
.agents/skills/orch/scripts/oversee-cycle --state-dir [OVERSEE_STATE_DIR] record --commit [PUSHED_SHA] [ITEM_KEY]
```

Use `--tier [TIER]` only for an old lane record without a launch tier. Add `--repo [OWNER/REPO]` when the lane record names no repository. `merged` is the time the push reached the base branch, as GitHub's repository activity log records it, never the commit's committer date; where that read fails, `actual` prints `-`, `missing` names `merged`, and a `merged-unread` line names the cause. Unknown fields print `-`. Report a refusal without blocking lane close.

## Event kinds

`watch-step-failed step=triage count=N` means the fleet state's `triaged` read failed. The watch prints it on the first failure and every `ORCH_OVERSEER_MARK_REPEAT` failed reads. The count persists in the watch baseline across restarts and resets after a successful read. The pass still exits 2. Read the `triage-state-failed` diagnostic and retained cause on stderr. Correct a malformed record against the [triaged schema](../schemas/workflow-state.md#oversee-state) before retrying. For another read failure, correct the cause stderr names.

`tracker-quota` means this pass could not finish its tracker reads. Keep owner answers unread. An absent owed or Verifying line during this hold is unavailable evidence, not proof that no work remains. Follow the linear skill's quota contract and its `patterns/workflow-actions.md` for held writes. Mail, available GitHub and lane checks, and report-due checks continue. The heartbeat repeats the scheduling receipt while it stands.

A lane's successful direct-push completion takes [§ Direct-push cycle records](#direct-push-cycle-records) before lane close.

To wake a lane below is to send it the directive and wake it per `oversee-lanes.md` § Talking to a lane, which wakes only a Claude Code or Codex lane whose send receipt reads `monitor=none`.

- `merged` → the PR is in; the owning lane finishes `merge-pr.md` § 5 on its own and a GitHub merge alone is not lane completion. A parked or stopped item that the close command judges terminal gets its cycle record from the watch before terminal close. A parked record whose pull request is open or queued stays parked, whatever the tracker state. A resumed record whose retained PR is OPEN also stays in the fleet, including after failed create leaves it stopped; [workflow-state.md](../schemas/workflow-state.md#oversee-state) owns the retained identity. A parked Done item with an unchecked Done-when box takes the parked-merged rule after its recorded pull request merges. A stopped Done item with an unchecked box also stays open for Recovery relaunch, including after a parked resume starts the sandbox but fails to create the harness. The watch reports a recorder refusal through `lane-close-failed item=[ITEM] step=cycle exit=[N]` and continues close. It uses the recorded launch tier and does not invent a missing tier. Read its cycle output under the verdict rules below. The class target forgives one clean final-head CI run and the merge group. `oversee-cycle --help` owns the class bases. The cycle row keeps lane-controlled time as `lane=` and end-to-end open-to-merge time as `open=`. The rollup and progress report show both medians and the miss share on lane-controlled time. The cycle row is the report for a Done item with no open box; no lane completion check or relaunch is required. A parked item with work left takes the `parked-merged` rule, which records the cycle once relaunch brings its sandbox up. For a running item, first, before any step below and while the lane's own workflow state still stands, record the lane's cycle from the overseer's base checkout, or from a checkout of the lane's repository where its `mail_root` is another repository's worktree, as `oversee.md` § 3 runs `lane-mail` for it: `.agents/skills/orch/scripts/oversee-cycle --state-dir [OVERSEE_STATE_DIR] record --pr [PR_NUMBER] --tier [TIER] [ITEM_KEY]`, `[TIER]` being what `oversee.md` § Item Tier gives the item, and `--repo [OWNER/REPO]` added for a lane whose record names none in another repository. It logs its own row. A `verdict=miss` line needs nothing more; a `repeat-miss` line is three lanes missing on one phase, and files one CI or process issue in that repository naming the phase, the lanes and the `causes` the line gives each, per [skill-rules.md § Coordination](skill-rules.md#coordination). A refusal is reported and never blocks the rest of this rule. A hosted item stays in the watch until its `lane-closed` or `lane-close-refused` event, per § Event kinds. Wake it only if it is not still inside that run, and read a reported failure there rather than advancing the item. For a parked or stopped item this rule ends here. Items the close command judges terminal close in the watch. A parked item with work left gets `parked-merged` and its resumed lane runs `merge-pr.md` § 5 steps 2-6. For an item that is not parked, follow the repository's declared refresh owner in its consumer instructions. On a hosted fleet, run `.agents/skills/orch/scripts/sync-base` in the control checkout. The first sync can receive the item merge before the owner's refresh commit exists; it is not refresh completion. Keep refresh and verification with the declared owner outside the control host, and run `sync-base` again after its reviewed outputs merge. Report a failed owner workflow. Consumer refresh stays in each consumer's own Actions through the [refresh workflow](../../review-gate/references/adoption.md). On a local fleet, run `.agents/skills/orch/scripts/post-merge --command-only` in the overseer's base checkout when a declared workflow owns refresh. When the local fleet is the refresh owner, run `.agents/skills/orch/scripts/post-merge` without a mode flag. After either local mode succeeds, run the repo's lifecycle check. All post-merge modes retain checkout changes; report those diffs to their declared owner. A later sync can refuse pending changes; report that refusal and preserve the changes. Stop on a failed step and report its status. When the fleet's LAST item completes, run the `heartbeat` triage pass before closing out, whatever the tracker; items living in Linear also get `.agents/skills/orch/scripts/reconcile-work-items` (a GitHub-item fleet skips that with a note). Report both with the close-out.
- `parked-merged [ITEM] pr=[N] repo=[OWNER/REPO]` → the wait PR merged and the item has work left. A dependency park selects `parked.until_pr`, even with no own `parked.pr`. Its own PR merge cannot clear that wait. A queue park selects `parked.pr`. Relaunch through [lane-directive.md § Recovery relaunch](lane-directive.md#recovery-relaunch). The launcher starts the sandbox before resume. It reports `host-start-failed` and keeps the record parked if the provider does not confirm the start. A lane that resumes without a transcript is a blocker to report. For a dependency park, the lane rebases and continues the held step. Record no cycle for the dependency's merge. For a queue park, record the item's cycle under `merged` once the sandbox is up. The lane finishes `merge-pr.md` § 5 steps 2-6 and § 6. The watch repeats this hand before each heartbeat while the record still reads parked. Recovery relaunch rewrites the record before harness creation, so replay cannot start a second harness. Report a capacity refusal and handle the next repeat.
- `parked-closed [ITEM] pr=[N] repo=[OWNER/REPO]` → the dependency PR closed without merging. The watch reports it once. Resolve the hold or resume the lane through the same Recovery relaunch route.
- `lane-exited` → the window is alive but the harness under it is gone (the lane's closing lines follow the event and say why; `payload-noise-only lines=N` in their place means the lane deleted its own worktree and the shell has drawn nothing since). A lane stopped by a harness session limit ("You've hit your session limit · resets 9:50am") is not dead: resume it under another auth lane (`lanes pick --harness [HARNESS] --model [MODEL]` for the model the replacement will run, then [lane-directive.md § Recovery relaunch](lane-directive.md#recovery-relaunch)), or wait for the shown reset and use Recovery relaunch on the original account. The relaunch carries its own continuation line, except on a hosted codex lane, which resumes without one and takes it by Pane paste ([lane-directive.md § Recovery relaunch](lane-directive.md#recovery-relaunch)). A lane that reported `handoff` on an earlier run is relaunched per that event, not resumed or nudged. Any other exit is the `window-gone` rule below.
- `overseer-dead`, `overseer-walled`, `overseer-reserve`, `overseer-context-unmeasured`, `overseer-context-stale`, `overseer-mark` → the overseer's own session: [overseer-session-events.md](overseer-session-events.md).
- `handoff` → the item's lane recorded its handoff and exited: relaunch it per § Judgement rules, Hand off a lane; the record follows the event line.
- `lane-closed` → the watch ran `lane-close` under the [Lane close contract](lane-reach.md#lane-close). Record the line below in the fleet log, the provider's `kept=PATH`, `kept=none` for no archive, or `closed=absent item=ITEM` for a host that no longer held the item and ran no archive pass ([lane-host.md](../schemas/lane-host.md) `close`).
- `lane-close-refused` → `lane-close` relayed exit 3 from the provider and the sandbox stays. Surface the `path=` line that follows to the user; its value is the checkout the close stopped on, never the path that stopped it. Render-only drift is saved as a binary patch under the hosted clone's `tmp`, restored, and refreshed before close, and the provider refuses on any of several conditions. An untraced change in the checkout is the common one; a saved patch that does not carry a path the close was about to restore or remove is another. Several of them leave every changed path inside the generated inventory, so a hunt for an untraced path can find none. Inspect the directory and never force the close.
- `lane-close` refusing `stop-failed` or `exit-timeout` → the idle lane's harness did not end by signal, and the window and record stay. `stop-failed` names the failed step as `cause=`: `cause=timeout` is a harness that ignored its signal, which on a hosted lane arrives as `cause=provider` with the provider's own lines above the refusal, `cause=identity-unread` is a local record naming no launch identity over a pane with no harness process under it, `cause=identity-stale` one naming a harness that has exited, or whose `pid=` a later process holds, over a pane with none under it either, and `cause=process-read-failed` a process read under the pane, or the process table read at the identity the stop signals by, that failed. `target=wake` is the turn a wake started, stopped by the record's `wake` before the record reads done or stopped. A hosted stop by `lane-host-ssh` refusing `stop-identity-invalid` is a clone whose `.git/lane-host-pid` holds no pid and start: remove that file and close again, which stops the lane by its worktree. `cause=provider status=4` under `--keep-sandbox` is a hosted item whose worktree its own close-out removed, under a stop that finds the harness by that directory: the stop has no directory to find the harness by, and only a full close, which prints `stop-skipped cause=worktree-removed`, closes it: its host close ends the harness where the provider's `close` ends the sandbox, and otherwise the window kill hangs up the lane's ssh session. That reading needs the provider's `stop-worktree-removed item=[ITEM]` line above the refusal; `cause=provider status=4` without it is the provider's own `4`, such as a sandbox it stopped, whose line above names it: start the sandbox, then close again. `exit-timeout` on a local lane names `identity=`, the identity the stop signalled by: `recorded`, the record's `launch`, or `pane`, read off the pane because the record named none or a stale one. `processes=0` there is a harness that identity named which exited before its signal, or under `recorded` no process named for the harness at or below the recorded pid. `processes=` above 0 means that many harness processes were signalled and confirmed exited, yet the pane still does not read exited: inspect what the pane now runs. Report the refusal lines to the user. Never type into the pane to end the harness instead.
