# Oversee events

[oversee.md](../workflows/oversee.md) § 4 applies these rules at every watch event.

## Judgement rules

The overseer owns fleet judgement, not just liveness; every `oversee.md` § 4 event is handled under these rules. The fleet log is the oversee state's `fleet_log[]` ([schemas/workflow-state.md § Oversee state](../schemas/workflow-state.md#oversee-state)), which exists before the first append per `oversee.md` § 3 Lane record; every record a rule below asks for is one append, `[KIND]` being `proposal`, `ruling`, `close` or `peer` and `[ITEM]` the issue, carrier or repository it is about. `[ONE_LINE]` carries text the overseer did not author, so the record crosses a file and never argv ([SKILL.md](../SKILL.md) § Harness-Safe Shell): write it with the harness file-write tool, then bind the path. Append each record before replacing the file for the next one.

```json
{"at":"[NOW]","kind":"[KIND]","item":"[ITEM]","text":"[ONE_LINE]"}
```

```bash
.agents/skills/orch/scripts/workflow-state append-file oversee fleet_log tmp/fleet-log-record.json
```

- **Lane proposals.** Record each lane's `Proposal comment:` notice in the fleet log as an authorized tracker, repository, issue, and returned comment ID or URL binding. Partition pending authorized comments by tracker and source PR repository. For each batch, mint a fresh tracker-valid launch item from the UTC epoch, such as `KEN-[UTC_EPOCH]` for Linear or `[UTC_EPOCH]` for GitHub; record the launcher's carrier ID, and never use a fleet issue identity. On the `oversee.md` § 1 terminal surface, run the low-cost TPM [proposal-sweep](../../project-management/workflows/proposal-sweep.md) lane from the source repository with `open-terminal --cmd '[COMMAND]' --state-dir [OVERSEE_STATE_DIR] [CARRIER_ID]`, `[OVERSEE_STATE_DIR]` being the fleet state `oversee.md` § 3 Lane record resolves: without that flag the sweep lane is recorded nowhere and no watch carries it. On the managed-session surface, use its native launcher with the same fresh identity, source-repository checkout, low-cost model, and brief. On the no-parallel surface, defer the batch until a parallel surface exists; never run its TPM analysis in the overseer. The brief supplies the batch tracker, tracker repository, source repository, issue IDs, authorized and resolved comment bindings, status file, and mailbox. The launcher records the sweep lane in the fleet state that flag names, so the watch carries it (`oversee.md` § 4). Wait for its `lane-notice` whose text, with the watch's two-space indent removed, is exactly `Proposal sweep complete: [STATUS_FILE]`; read no output file before that durable event. Read the status through `oversee.md` § Bounded lane reads. For a hosted terminal sweep, use `lane-host cat` after the successful probe to transfer the audit. On the managed-session surface, use its native file transfer. Stop on any failure. Put the audit bytes at `tmp/proposal-audit-[CARRIER_ID].json` in the overseer's checkout; for a local terminal sweep, copy the named audit there. Read no verification text. Check the local rows against live fleet work, then invoke [audit-issues](../../project-management/workflows/audit-issues.md) from `oversee.md` § 1 as `audit-issues --analyzed tmp/proposal-audit-[CARRIER_ID].json` under `PM_CREATE_AUTONOMY`. Its normal route parses the tracker, runs its tracker preflight and label inventory, skips TPM analysis, and continues through §§ 5-7. For Linear, reply with `.agents/skills/linear/scripts/linear.sh comments create [ISSUE_ID] --parent [COMMENT_ID] --body-file [PATH]`. For GitHub, use `gh issue comment [NUMBER] --repo [OWNER/REPO] --body-file [PATH]`; its first line is `Proposal outcome for [COMMENT_URL]:`. Each outcome carries the created issue ID or one-line decline. Record the source and outcome in the fleet log. After transfer, close the hosted terminal with `.agents/skills/orch/scripts/lane-host close --item [CARRIER_ID]`, the local terminal with `tmux kill-window -t [SWEEP_WINDOW]`, or the managed session with its native close. Remove a terminal checkout with `.agents/skills/worktree/scripts/worktree remove [CARRIER_ID]`; use native checkout disposal on the managed surface. A failed close or removal blocks the next batch; set the carrier's record to `done` per `oversee.md` § 4 and record successful disposal.
- **Heartbeat backstop for lane proposals.** Include every fleet issue in its tracker and repository batch at each `heartbeat` and before fleet close. This catches a comment posted without another event. Never reuse a sweep identity. Record its disposal before the next batch.
- **Cut scope blowups.** A PR whose diff outgrows its issue's Done-when goes back to the contract: keep the oversized work on a branch, land the contract. Machinery no issue ordered — a new subsystem, scanner, or lexer — is cut, never reviewed into shape.
- **End spirals.** A round whose finding shares a root cause with one a prior round patched is dispositioned by [references/finding-disposition.md § Recurrence](finding-disposition.md#recurrence), which states the branches and their limits. Bots drip-feeding one class get the class exhausted in one audit pass, then dispositions without pushes. After five bot rounds on one PR, the lane answers the standing threads once and starts no further fix round. The review gate and the user's merge authorization still apply. The overseer never orders a blanket `Declined` across a PR's open findings: each one is dispositioned on its own mechanism, and a decline that is nothing but a label turns the gate red.
- **Fix the source.** The same finding class on a third PR is a mechanism gap: file it and route the smallest deterministic check (a guard lane, a preflight rule, a refusing script) or one sentence in the owning skill through a lane as its own item — the overseer still implements nothing. Deterministic beats prose where it stays simple; complex or brittle machinery is worse than either.
- **Rule once for the fleet.** A ruling that answers one lane's question is sent to every lane in the same situation and recorded in the fleet log.
- **Held merges.** Under `ORCH_MERGE_AUTONOMY=ask` (`oversee.md` § 3) the lane's merge question arrives as `lane-question`. Read the gate results without reproducing them, then relay the question to the user. Send `MERGE` to the lane only after the user authorizes it, or send exactly one directive the user gave. A directive may carry the authorization ("with that landed, MERGE stands"), and the lane then merges once the change is in without a second answer. Under `ask` a `disarmed` pr-watch line is not a wake.
- **Hand off a lane before it runs out.** The lane triggers this, not the overseer. The `lane-mail-check` turn-end hook reads the lane's own context out of the transcript the harness writes and the lane's own account headroom through the credential it runs on, and refuses the turn end at either mark until the record below stands, so a lane hands itself off with no directive from here. What follows is the BACKSTOP for a lane that hook does not reach, a surface with no hook installed or a harness whose Stop payload names no transcript. On the `oversee.md` § 1 tmux surface, at every `oversee.md` § 4 event, read each live lane's context use:

  ```bash
  .agents/skills/orch/scripts/lanes context
  ```

  `lanes context` reports context use and account headroom. It sets `handoff_required` when the binding account bucket has headroom at or below `ORCH_HANDOFF_HEADROOM_PCT`. The default is `3`, so a lane whose account reaches 97 percent used is marked for the overseer's next sweep, and the hook refuses the turn end on that same setting. Both resolve it through the kendex settings ladder, the hook through `orch-env` and this poll through its own project-env load, so a settings file sets one mark for both. At each event, tell every lane the poll marks and the hook has not already stopped to write its handoff at the next safe point, as for the context mark; a lane whose record already stands is handing itself off and needs no directive. Use `oversee.md` § Talking to a lane until lane mail is installed; then send the directive through lane mail. The context mark is `CONTEXT_TOKENS` past `ORCH_HANDOFF_CONTEXT_TOKENS`, default `500000`, the same setting the hook judges. At either mark, wait for a safe point such as a landed merge or held PR. Never interrupt a round or an unpushed tree. The lane records the fixed shape below and exits. The watch reports `handoff [ISSUE_ID]` once. Relaunch the item through `oversee.md` § 3 Recovery relaunch, which uses the handoff record as durable recovery state.

  ```bash
  .agents/skills/orch/scripts/workflow-state set [ISSUE_ID] handoff '{"written_at":"[NOW]","merged":["[PR]"],"remaining":["[STEP]"],"branch":"[BRANCH]","worktree":"[WORKTREE_PATH]","open_pr":[PR_NUMBER_OR_NULL],"traps":["[TRAP]"]}'
  ```

  The record, the event and the relaunch are surface-independent. Surfaces 2 and 3 register no lane claim, so `lanes context` reports no worker lane there: on surface 2 read a lane's context through the harness's own session tooling and hand off at the same mark; surface 3 has no lane to hand off.

  On a hosted fleet, also run `lane-host list`: a row not `available` whose item, the last segment of repository/item, has no `running` lane record is a sandbox with no live claim; surface it to the user.

  The overseer's own case: its own pane is in the `lanes context` report, claim or no claim, marked with a leading `*` on its lane name, and that row carries its account headroom beside its context use. That row's `HANDOFF` cell reports the lane threshold alone and never this trigger. The overseer succeeds itself at either mark: a 1M window past the context mark, or account headroom at or below `ORCH_OVERSEER_HEADROOM_PCT`, default `20`. At either mark, wait for a safe point with no `merged` event mid-handling and no lane waiting on a root answer. Rewrite the overseer handoff file per `oversee.md` § 5, then run `.agents/skills/orch/scripts/oversee-succeed -- [FLAGS]` under a shell-tool timeout longer than its `--wait-secs`. `[FLAGS]` are the permission flags this overseer runs under, plus its own model and effort flags when `ORCH_OVERSEER_PREFERENCE` is empty. Add `--handoff [PATH]` when the fleet brief names another handoff path. It chooses the successor's lane by its own rule, which `oversee-succeed --help` owns and this file does not restate, opens the successor overseer there and closes this window. On `context-below-mark` or `window-below-mark`, neither mark is reached: keep running and run it again at a later event; the `headroom` field on those lines reads a number where the account was measured, and `none` or `unreadable` where nothing measured it, which is not the same as having room. `no-lane-qualifies` means no lane of any preference entry walked has room for a successor. Its `mark` field says which mark fired: at `mark=account` the line also carries `account` and `resets`, this overseer's own account and the time its binding bucket frees up, and both go to the user; at `mark=context` this overseer's own account either has room or was never measured, so report the refusal without naming an account. On `succession-off` or any other refusal, keep running and hand off by hand: tell the user the handoff file is written and a fresh overseer session must start.

- **Decide without the user.** SKILL.md's ask gates stand unchanged — scope expansion, recorded decisions, and merge autonomy still ask. Any other reversible call takes the option that costs nothing, recorded in the fleet log; destructive actions and product direction wait for a human.

## Event kinds

- `merged` → the PR is in; the owning lane finishes `merge-pr.md` § 5 on its own and a GitHub merge alone is not lane completion. A hosted item stays in the watch until its `lane-closed` or `lane-close-refused` event, per § Event kinds. Wake it only if it is not still inside that run, and read a reported failure there rather than advancing the item. On a hosted fleet the base checkout is the control host: run `.agents/skills/orch/scripts/sync-base` and `kendex refresh --scope project --yes --leave` there; CI and the lane ran build and verify. Otherwise, in the overseer base checkout, run `.agents/skills/orch/scripts/post-merge`, then the repo's lifecycle check. Stop on a failed step and report its status. Either way, classify the paths from `git diff --name-only [MERGE_COMMIT]^..[MERGE_COMMIT]` against the source-catalog layout from the repository's `kendex.toml`: the manifest itself, the configured or default skill and agent directories, and the format's fixed directories for other package kinds are shipped paths. A match runs [consumer-train.md](../workflows/consumer-train.md) after those steps, with `MERGED_RANGE` bound to `[MERGE_COMMIT]^..[MERGE_COMMIT]`. When the fleet's LAST item completes, run the `heartbeat` triage pass before closing out, whatever the tracker; items living in Linear also get `.agents/skills/orch/scripts/reconcile-work-items` (a GitHub-item fleet skips that with a note). Report both with the close-out.
- `lane-exited` → the window is alive but the harness under it is gone (its pane tail says why). A lane stopped by a harness session limit ("You've hit your session limit · resets 9:50am") is not dead: resume it under another auth lane (`lanes pick --harness [HARNESS] --model [MODEL]` for the model the replacement will run, then `oversee.md` § 3 Recovery relaunch), or wait for the shown reset and use Recovery relaunch on the original account. The relaunch carries its own continuation line, except on a hosted codex lane, which resumes without one and takes it by Pane paste (`oversee.md` § 3). A lane that reported `handoff` on an earlier run is relaunched per that event, not resumed or nudged. Any other exit is the `window-gone` rule below.
- `handoff` → the item's lane recorded its handoff and exited: relaunch it per § Judgement rules, Hand off a lane; the record follows the event line.
- `lane-closed` → the watch closed the merged hosted lane's sandbox through `lane-host close`: record the `kept=` line that follows in the fleet log, the provider's `kept=PATH` or the watch's `kept=none` for a close that archived no tmp records.
- `lane-close-refused` → `lane-host close` exited 3: a checkout of the merged hosted lane, its clone or its worktree, has uncommitted files and the sandbox stays: surface the `path=` line that follows to the user. Never run `lane-host close --force`.
- `usage-limit` → read the pane tail first and confirm the banner is the harness's own, not text the lane printed while working; a lane still working is left alone. Confirmed: keep the window and its watch registration while selecting a replacement. Run `lanes pick --harness [HARNESS] --model [MODEL]` for the same harness first, naming the model the replacement will run: this is the recovery taken precisely because a window is full, and a pick that does not name the model can hand back an account with no allowance left for it. When a lane qualifies, kill the old window and use `oversee.md` § 3 Recovery relaunch on the selected lane. When no lane of that harness qualifies, pick another terminal harness. When that lane qualifies, kill the old window and launch with the one-sentence continuation brief from `handoff.md` § 2, including the matching path from the prior harness's transcript store. When no replacement qualifies and the event has `resets=`, keep the old window and wait for that reset. The window then announces `usage-limit-passed`, and the overseer sends its one-line continuation nudge. A `resets=` pinned from a clock or weekday is an upper bound, so read the tail. Never launch onto the spent account again until its reset, and never park a lane against an estimate of your own when `resets=` states the time. A parked lane stays in the watch: its window is what announces the reset, as `usage-limit-passed`. A wall reported without `resets=` is announced once and nothing announces it again, so select another account on that event. If none qualifies, report the blocked recovery and keep the old window until a replacement qualifies.
- `usage-limit-passed` → read the pane tail first, as for `usage-limit` above: a lane still working is left alone. Confirmed, the wall named by `resets=` has already lifted and the lane is still sitting under the old banner. Send it a one-line continuation nudge; do not move the item and do not wait. The nudge is the whole remedy: this event never licenses a fresh launch onto that account, and a nudge that does not take means the wall still stands.
- `model-capacity` → resend one continuation line through Pane paste; the next pass watches the lane again. Never relaunch the lane: the selected model stopped one turn, not the session.
- `idle-after-return` → read its pane tail. A lane that has returned is available for another fleet launch; a lane still inside `merge-pr.md` § 5 step 1 is blocked on its queue wait, which reads as work in flight rather than idle. A directive for an idle lane is sent and then woken per `oversee.md` § Talking to a lane.
- A lane whose session ended AFTER its PR merged but before `merge-pr.md` § 5 steps 2-6 finished → send it `merge-pr [PR_NUMBER]` as a directive per `oversee.md` § Talking to a lane, then relaunch it per `oversee.md` § 3 Recovery relaunch. The order is fixed: the relaunch's continuation line tells the lane to read its inbox first, so a directive already waiting there is what binds the pull request number. That run's already-merged route skips the merge and runs the tracker sync, project verification and worktree removal the dead lane never reached. The launcher keeps a merged item's tree as it stands and reports it as `worktree-reuse-merged` with the merge commit. The rule below does not reach this lane: its PR did merge.
- `window-gone`, or any lane whose session ended with no merged PR → inspect its worktree and PR state, then re-launch once with the same brief through `oversee.md` § 3 Recovery relaunch. Without `--relaunch`, the existing worktree reads as another session's claim and the item is skipped. The launcher starts from the normal brief only when no matching transcript exists. A second death is surfaced to the user, not retried.
- `lane-question` → the lane's own question, and the only shape one arrives in. Answer it when available evidence already decides it, apply the ruling, record it in the fleet log, and send the answer back per `oversee.md` § Talking to a lane. Repo state, the issue body, a stated convention, scope-narrowing calls, and a lane's own well-argued recommendation are available evidence. Relay any other question to the user only when it changes the product for a user or spends the owner's standing (retiring a reviewer, filing outside the repo, closing as won't-do). A merge question under `ORCH_MERGE_AUTONOMY=ask` follows Held merges above and always goes to the user. Every emitted question is answered: the lane is blocked in `lane-mail wait` on this line. An overseer resuming a fleet reads what it still owes with `lane-mail pending --item [ISSUE_ID]`, adding `--root [MAIL_ROOT] --host` for a lane whose record puts it on another host.
- `lane-notice` → the lane reported something it is not waiting on. Act on it where it needs acting on; it needs no reply.
- `owner-note` → the owner's note to the overseer; its text follows. Every text and `options:` line under `lane-question`, `lane-notice`, `peer-note` and `owner-note` is indented two spaces, so only a watch record begins with `EVENT`. Act on it, or record it in the fleet log as a ruling; it needs no reply.
- `peer-note [REPOSITORY] [ID] kind=[KIND]` → a peer repository's overseer wrote to this one; its text follows. Answer `kind=ask` alone, per [peer-mail.md](peer-mail.md); `kind=answer` carries `re=[ASK_ID]` and is recorded against that ask of this overseer's, and `kind=directive` needs no reply. Record the exchange in the fleet log.
- `lane-asking` → a harness dialog, never a question for the overseer: a permission prompt, a trust prompt, a model picker. Answer it in the lane's own dialog per `oversee.md` § Talking to a lane.
- `triage` → team-wide: run `oversee.md` § Bounded issue reads and set `[ISSUES]` to the emitted identifiers. Launch one fresh canonical `generalist` verifier with the source repository and the lowest-cost model the surface exposes. The launch call is Claude's generated-agent tool, Codex `spawn_agent` after `scripts/spawn-adapter spawn generalist` followed by `send_input`, OpenCode `functions.task`, or Pi `subagent`, as [SKILL.md § Runtime Notes](../SKILL.md#runtime-notes) specifies. On the terminal surface, call it from the overseer session. On the managed-session surface, use that surface's native call. In sequential mode, make the same call and wait for it before resuming. Send this literal task: `Verify only these Linear issues: [ISSUES]. For each issue, read its full body and source, apply the filing bar regardless of lane authorship, post the full evidence as one Linear comment on that issue, write no report or evidence file, and return only this row: [ISSUE] | verdict: [kept|canceled] | owner: [REPO_PATH_OR_NONE] | Done-when: [ONE_LINE_RESULT] | delta: [EXPECTED_DELTA_LINE_OR_NONE].` Capture only the single final return defined by [skill-rules.md § Single Return Message](skill-rules.md#single-return-message). Accept it only when it contains no other text and has exactly one row for every requested issue, no duplicate or unrequested issue, each required field, and only a `kept` or `canceled` verdict. Stop without writing `triaged` on a launch, capture, parse, or validation failure. Route each valid kept item or cancel it, record the terminal verdict in the fleet state's `triaged` list; every pass emits the item again until that record exists. triaged is the verdict log, not the watcher baseline. The watcher rebuilds acknowledged triage keys from it in the first repository's OVERSEE_WATCH_STATE_DIR baseline; the default directory is `<project-root>/tmp/oversee-watch`. Deleting that baseline resets watcher dedup: the next pass rebuilds terminal keys, while pending items emit again.
- `pr-watch` → handle every attention line. What each kind MEANS is `pr-watch.sh --help`; what follows is only what the overseer does about it. A detail ending in `(QUEUED: dequeue before pushing)` rides several kinds and outranks all of them: the lane dequeues before it can push anything.
  - `gate-stale` → healed only where a `heal-dispatched` line rides the same reduction. The reducer re-dispatches on every pass the line stands, so a standing line is dispatch-to-converge lag, not a queue of work: judge it on whether the dispatched writer run COMPLETED, never on a pass count, and read a cancelled pending duplicate in the writer's concurrency group as ordinary lag too. A standing line comes back only as reducer output appended to the next wake or heartbeat, never as a fresh event. Beside an `error` naming a failed writer dispatch, nothing was healed and the once-per-invocation budget is spent, so no other stale PR got a dispatch either: fix the dispatch path for the repo the line names before waiting on another pass, the workflow name against `PR_WATCH_WRITER_WORKFLOW`, `actions:write` on the credential, Actions enabled on that repo.
  - `heal-dispatched` → the reducer's note that this invocation's one dispatch fired. Nothing to do, and never an event on its own.
  - `threads-open` → verify the count against the API, then wake the owning lane with it.
  - `changes-requested` → wake the owning lane: a standing objection is the lane's to answer, never the overseer's to dismiss.
  - `untracked-claim`, `unreasoned-decline` → wake the lane to rewrite the reply per [references/finding-disposition.md](finding-disposition.md); the gate stays red until it does.
  - `suppressed-findings` → wake the lane with the file:line list on the line: the reviewer wrote those findings into its review body, so no thread carries them. The lane dispositions each entry and answers it in one PR comment as the PR author, opening with the line `Dispositions at <sha>` naming this head, the only thing that binds the comment, and opening a line per entry with the `file:line` the line above prints, followed by `Fixed in <sha>`, `Declined: <reason>` or `Tracked: <ID>` ([merge-pr.md](../workflows/merge-pr.md) § 3.2). The lane answers every entry in the review body's `Suppressed comments (N)` or `Previously missed (N)` block, which is the complete list; the status detail and this line are bounded and say how many they dropped. An entry the comment answers is subtracted; a label, an unanchored tracking claim, or a comment with no `Dispositions at <sha>` line for this head still blocks.
  - `disarmed` → under `ORCH_MERGE_AUTONOMY=auto`, wake the lane to arm auto-merge; under `ask` it is not a wake, the lane holds the PR for § Judgement rules, Held merges. Arming stays the lane's reply-pass discipline; the overseer never adopts it as its own step. A detail marked `UNCONFIRMED` came from a cheap-mode reducer, and that one is evaluated before anyone arms.
  - `awaiting-stale` → trigger a re-review, or apply the fleet's on-timeout policy.
  - `head-moved` → the reduction describes the old head. Do nothing; the next pass reads the new head.
  - `error` → many producers, and each line's own detail carries its remedy: follow that. One exception, whose remedy the detail does not carry: `writer dispatch failed for …` means fixing the dispatch path, never re-running, since a re-run re-attempts the same failing dispatch. An unevaluated PR is never healthy.
- `heartbeat` → the triage pass: run `oversee.md` § Bounded issue reads. Drop IDs already recorded in the fleet state's `triaged`, and send the remaining candidate IDs through the `triage` verifier. Judge only issues a fleet lane filed — the candidate set is each lane item's created-issue records in workflow state (`audit_issues_created`, `pr_comment_review.issues_created`) plus each lane PR body's Created Issues section; the created-since listing backstops trackers without that state. Anything outside the set is left alone. Record each verdict by writing `{"issue": "[ID]", "verdict": "[kept|canceled]", "reason": "[ONE_LINE]"}` to `tmp/triage-verdict-[ID].json` with the harness file-write tool and running `workflow-state append-file oversee triaged tmp/triage-verdict-[ID].json`, in the state `oversee.md` § 3 Lane record creates before the first append; the next pass runs on its own.
