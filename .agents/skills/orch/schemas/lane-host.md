# Lane host

The `scripts/lane-host` command selects a host from `ORCH_LANE_HOST`. `resolve` prints `local` when the setting is empty or unset, and `claude-cloud` as it is set. Any other value is an executable script path. Credentials do not select a provider. `open-terminal --host SPEC`, or this setting, launches a lane through `create`; `oversee-watch --hosted` reads a hosted lane's mailbox and workflow state through `cat` and closes the lane through `close`; `lane-mail --host` adds a line to a hosted mailbox through `append`; `lane-close` ends an idle hosted lane's harness through `stop`, and reads whether its worktree stands through `cat` before it closes a merged lane on an open item.

## Host kinds

Every place a lane runs is a host kind. `lane-host capabilities` prints the kind's one tab-separated `key=value` line, and every caller acts on a declared value, never on a host or provider name. The dispatcher answers the line for `local` and `claude-cloud`, the kinds kendex owns; for a provider path it asks the provider, taking no slot since the verb reads no host state. A provider that gives the absent-verb answer gets the static `ssh` line `lane-host-ssh capabilities` prints; the arm reads two answers as absent, exit `2`, and exit `64` with a `verb-unsupported verb=capabilities` line on stderr, which is fleet's Daytona provider's answer. A key outside the set below, a missing key or a value outside its key's set refuses as `capability-invalid key=KEY value=VALUE` with exit `1`. Provider verbs under `claude-cloud` refuse as `host-kind-verb kind=claude-cloud verb=VERB` with exit `2`.

## Provider protocol

| Verb | Arguments | Result |
|---|---|---|
| `create` | `--item ID --repo OWNER/REPO --harness claude\|codex\|pi\|copilot --account CONFIG_DIR [--relaunch] [--reuse]` | One stdout line: `ssh-target=TARGET`, `path=WORKTREE`, `remote-prefix=PREFIX`, separated by literal tabs, plus `state=preparing` from a create that returns before its preparation ends, and for a Pi lane `pi-root=DIR` where its Pi root is not Pi's default. |
| `wait` | `--item ID` | Block until the preparation a `state=preparing` create accepted ends. Exit `0` when the item is ready; any other status is a failed preparation, its cause on stderr. |
| `cat` | `--item ID PATH` | Exact file bytes on stdout. A relative `PATH` resolves under the host user's home directory. A missing file exits `2`. Any other failure exits nonzero and not `2`, so a caller can tell an unwritten file from a read it could not make. |
| `put` | `--item ID PATH` | Write stdin to the file with private permissions, through a temporary file beside it that is renamed over the target once the whole transfer has arrived. A provider that crosses a network compares the bytes it staged against the count the sender declared before renaming, because a sender that dies mid-feed closes the stream and the receiver reads that as an ordinary end of input. A transfer that fails never replaces the file, and no reader meets a half-written one. No credential bytes in argv or diagnostics. |
| `append` | `--item ID PATH` | Append stdin to the file under a lock taken on the host that holds it, creating the file with private permissions when it is not there. The lock must be the one mechanism every writer of that file on that host takes, since two mechanisms do not exclude each other and a writer under each tears the other's bytes; a provider reaching a kendex checkout takes it through that checkout's `scripts/lib/file-lock.sh`. A last line with no newline is closed before the bytes are added, so a fragment an interrupted writer left never swallows the line that follows. Compare the bytes staged against the count the sender declared before any of them reach the file, because a sender that dies mid-feed closes the stream and the receiver reads that as an ordinary end of input. For a mail envelope on a host with the repeat guard, the same lock holds the whole-envelope minute check in `scripts/lib/mailbox-append.sh`; a repeat exits `4` with `duplicate id=FIRST` on stderr and appends nothing. A host with an older append library skips that check and can append repeats. The static SSH provider reports `append-library-outdated path=LIBRARY repeat-check=skipped` on stderr in that case. An append that fails adds nothing. No credential bytes in argv or diagnostics. |
| `touch` | `--item ID` | Keep the host alive, or probe a static host with no idle expiry. |
| `status` | `--item ID --harness claude\|codex\|pi\|copilot` | Read the named harness processes in the item's owned worktree. Print `running` for a live match, otherwise `exited`, with exit `0`; an item the provider holds no sandbox for, as `close` states it, is no match and answers `exited`. Signal nothing. A caller asks it only of a kind that declares `status=verb` (§ Host kinds), so exit `2` there is a provider fault and the lane stays unjudged; no pane stands in. Ownership or process read failures use another nonzero status with no verdict. `oversee-watch` calls `lane_state` once per listed hosted lane per pass with the harness its running record names, selected by [LANE_RUNNING_JQ](../scripts/lib/lane-claims.sh). Without that identity, explicit watches keep pane judgment. Failed valid reads leave the lane `unjudged`, never `exited`. |
| `close` | `--item ID [--merged]` | When kendex classifies every dirty path as a changed whole-file render, save their binary patch under the clone's `tmp`, restore them to `HEAD`, sync the base, and continue. This includes a deleted render recorded by the committed inventory. Build the untracked renders' half of that patch from an index the provider writes, never from a working-tree comparison: a comparison follows a render symlink into the directory it names and exits there with the same status it uses for a real difference, so the caller cannot tell the two apart and nothing is saved for a link a `kendex apply` inside the lane added. Read the patch back and restore or remove nothing unless it carries every path. Refuse a shared settings file, any other dirty path, a path the patch does not carry, and a render the provider's index cannot read, each with exit `3` and a stderr line holding `close-refused path=PATH` naming that checkout. Archive remaining `tmp` records before deletion and print `kept=PATH` on stdout. An archive or sync failure stops close. `--merged` is the caller's word that the item's pull request merged: `lane-close` passes it on a hosted full close of an item its tracker holds completed, a Linear `state_type` of `completed` or a GitHub issue closed with the reason `COMPLETED`, where the record carries the `cycle` `oversee-cycle` writes at a merge or `worktree merged ITEM` exits `0`. Under it a provider may cut each of the item's archives to one evidence file of the lane's `tmp` records, or keep none under its `LANE_HOST_MERGED_ARCHIVE=none` and then print no `kept=` line, which `lane-close` reports as `kept=none`. A close without the flag keeps the whole archive, as does the close of a canceled item: a record keeps its `cycle` across a relaunch, so a merge it names does not prove the item's last work merged. Every provider accepts the flag, since a close that refuses it closes nothing; a provider that cuts nothing reads it as a no-op. An item the provider holds no sandbox for, one an earlier close, a hand close or the provider itself already removed, is closed: exit `0` with the stdout line `closed=absent item=ID` and no `kept=` line, which `lane-close` relays in place of `kept=none` and records `done`. A caller reads a close by its status alone, never by the provider's stderr, so any other nonzero status fails the close. |
| `stop` | `--item ID --harness claude\|codex\|pi\|copilot` | Stop the named harness processes and print `stopped item=ID processes=COUNT`; an empty match is a successful stop with `processes=0`, and an item the provider holds no sandbox for, as `close` states it, is an empty match. Two rules find them. By launch identity, where the provider recorded one when the lane launched, the pid and start time of the shell its `remote-prefix` execs into the harness: the processes named for the harness at or below that pid, where it still runs and started at that time. No directory is read, since a lane's own close-out removes its worktree before its harness exits and a later create may make a tree at the same path. By worktree, for a provider that records no identity and for a lane with none to stop by, launched before its provider recorded one or whose recorded pid has exited or now started at another time: the processes named for the harness whose current directory is the item's owned worktree. Under that rule an item whose owned worktree is no longer a directory, removed by the item's own close-out, signals nothing and exits `4` with a stderr line holding `stop-worktree-removed item=ID`. A provider may also exit `4` on any verb for a state of its own, such as a sandbox it stopped, so `lane-close` reads a `4` as a stop to skip only beside that line naming the item, on the terminal item it alone stops: it prints `stop-skipped cause=worktree-removed` and closes the host and the window. A `4` without the line refuses as `stop-failed cause=provider status=4` under the provider's own words. The host close ends the harness where the provider's `close` ends the sandbox; otherwise the window kill hangs up the lane's ssh session, which ends it. Under `--keep-sandbox`, where no host close follows, it refuses as `stop-failed`. A process that exits or becomes a zombie counts as stopped. A recorded identity the provider cannot read, a process-table, start-time, directory or ownership read failure, a process that leaves the worktree before its signal under the worktree rule, or a process that does not exit inside the provider bound fails the operation. Never paste a shell command into the lane pane. |
| `stop-sandbox` | `--item ID` or `--check --item ID` | Stop the sandbox's compute and keep its disk whole: the worktree, the harness's session store, the mailbox and `tmp`. Print `sandbox-stopped item=ID` on stdout; a caller reads the sandbox as stopped only on that line, never on the status alone. The lane's harness is already ended through `stop` before this verb runs, so nothing here signals a process. A `close` that follows this verb completes without a caller `start`: the provider brings the disk back as far as its own archive and restore need, and starts no harness. Any failure exits nonzero with its cause on stderr and leaves the sandbox as it was. `--check` changes nothing: it prints `sandbox-stoppable item=ID` on stdout when the provider implements this verb and `start` for the item, and is the one reading `lane-close --park` makes of the provider before it signals anything; a provider without the pair exits `2` on it, the absent-verb status above, which that caller refuses as `park-refused reason=provider-unsupported`. |
| `start` | `--item ID` | Bring a sandbox `stop-sandbox` stopped back up on the same disk. Print `sandbox-started item=ID` on stdout; a caller reads the sandbox as up only on that line. A sandbox already up answers the same line with exit `0`: the caller that meets one is a relaunch of a record `open-terminal` could not rewrite after a confirmed start, its `parked-record-failed`, which still reads parked and so starts the sandbox again. The harness is not started: `create --relaunch` follows and resumes it natively on the disk `stop-sandbox` kept, which is where the transcript the resume continues lives. Any failure exits nonzero with its cause on stderr, and a caller leaves the lane recorded as parked. |
| `list` | none | Tab-separated repository/item, state, age, name for each configured host of this repository. State `available` marks a host holding no item. A provider can append fields. |
| `accounts` | none | Optional verb. One tab-separated `key=value` line per account the provider holds a credential for, carrying the usage windows read through that credential. `account=CONFIG_DIR`, the value `create --account` receives, and `harness=claude`, `harness=codex`, `harness=copilot` or `harness=pi` are required. `status=`, `detail=`, `session-5h-pct=`, `weekly-pct=`, `model-pct=`, `monthly-pct=`, `model-label=`, `session-resets=`, `weekly-resets=`, `model-resets=` and `monthly-resets=` are optional; each percentage is a whole number from 0 to 100 and each reset is a timestamp. `status=` takes the STATUS words `lanes list` prints, and defaults to `ok`: `unreachable` is a read the provider never made through its copy (nothing answered, or an endpoint answered 5xx), `refused` is a usage endpoint answering another code outside 2xx and 429 through that copy, and `rate_limited` a 429. `detail=` is the provider's own text for that status, such as `http-429-rate_limit_error` or `http-403-permission_error`, and `lanes` carries it as written into the record's `detail` field; it changes no judgement. A `harness=pi` row is a Pi root's Copilot pool: `account=` is the absolute Pi root a Pi lane on that pool receives as `create --account`, `monthly-pct=` the share of the seat's monthly credit grant used, rounded up and `100` at or past the grant, and `monthly-resets=` the grant's reset; it is the line `account=/home/me/.1pi<TAB>harness=pi<TAB>monthly-pct=5<TAB>monthly-resets=2026-10-01T00:00:00Z`. A provider can append fields. |

- `create` uses a durable repository/item identity. A retry or reuse reaches the same host. An existing owner returns `75`; `--relaunch` requests reuse. Other create failures produce `host-create-failed` through the dispatcher. No failure starts a local lane. The caller runs `create` for one host one at a time, so a provider reads, merges and writes shared host files during `create` without a lock.
- `create` may return once it has accepted the work, before its preparation ends. By then it holds the item's durable identity, so a second `create` exits `75` and a retry reaches the same host, and its line names the host and path the lane will use and adds `state=preparing`. The caller learns the outcome from `wait`. What a synchronous `create` owes by its return, the worktree, the launch record and the pre-approval below, an accepted one owes by `wait`'s success. A provider whose `create` returns only once its preparation ends prints no `state` and needs no `wait`. `open-terminal` under a fleet state then opens the item's window, records the lane `preparing` and moves on to the next item, handing `wait` and the rest of the launch to a background job whose outcome `oversee-watch` reports; with no fleet state, and for a hosted codex relaunch that resumes, it waits itself.
- The dispatcher passes all provider bytes and exit codes unchanged, except for `capabilities`, whose absent-verb answers become the static `ssh` line and whose invalid line refuses as `capability-invalid` with exit `1` (§ Host kinds). Slot admission failures exit `1`, except the busy refusal `69`; internal setting, directory, lock and write statuses never become provider replies. `tests/lane-host.sh` exercises this boundary and its must-fail control. A missing provider path, a non-executable file or a directory refuses with `host-unavailable` and exit `1`, not the provider's absent-verb `2`. Provider verbs under `local` refuse with `host-local` and exit `2`; the launcher owns local work. That is the same `2` a provider uses for a missing file, so a caller reading `cat`'s `2` as an unwritten file confirms the host with `touch` first: every dispatcher refusal fails that verb too.
- The dispatcher admits at most `ORCH_LANE_HOST_MAX_CALLS` provider processes at once per home, for every verb but `capabilities`, default `4`: one slot directory under `$HOME`, shared by every overseer and checkout that user runs on the machine, with a slot per admitted call that it releases on exit and a slot whose process is gone reclaimed at the next take. A call at the cap waits up to `ORCH_LANE_HOST_BUSY_WAIT_SECS` for a slot, default `30`, then runs nothing and exits `69` with the stderr line `lane-host: lane-host-busy count=N cap=M verb=VERB item=ID`, `item=-` for a verb without one. No provider verb exits `69`, so a caller tells a busy dispatcher from a failed host by the status alone, and every orch caller branches on it before its host-failure key and reports `lane-host-busy`, never a failed host. `lane-mail` refuses with the same status and probes nothing; `oversee-watch` records the lane's event and reads the next lane; `lane-close` exits `69` with the window and record unchanged; `lanes` and `oversee-report` name it in place of `host-unreachable`, `host-accounts-unreadable`, `item-state` and `mail-read`. `open-terminal` fails a foreground create, wait or marker call, and its background launch job asks again, so the record stays `preparing` and the window open. A provider process started outside the dispatcher is outside the bound.
- A file several machines write is appended, never put. `put` replaces the whole file, so a writer that wants to add a line reads it, adds the line and puts it back under a lock on its own disk; two machines doing that hold different locks, both read the same file, and the second put drops the first one's line with no error. `append` takes its lock where the file is, one mechanism that every writer of that file reaches. A provider that does not implement `append` fails the verb, and the caller refuses rather than falling back to a read and a put.
- `cat`, `put` and `append` on a path under `tmp/lane-mail/` refuse, with a status other than `2` and before reading or writing, when its `tmp/lane-mail` or item directory is a symlink or not a directory, or the file is a symlink or not a regular file; every other path is unaffected.
- The credential a hosted lane runs on is the copy the provider put on the host. `create` receives the account's config directory as `--account` on every call, `--relaunch` included. A provider that installs its own secret for that account leaves the two copies independent, and either can expire while the other works. A provider that re-seeds the host from that directory at every `create`, as the reference implementation does, puts the control machine's copy on the host again, on a relaunch as much as a fresh launch. The caller's `CLAUDE_CONFIG_DIR` environment prefix reaches the host in neither case. `accounts` is the only place a provider reports which accounts it holds, and no provider has to implement it. A provider without the verb exits `2` on it. The verb takes no path, so `2` there means only that the verb is absent, not a failure. A provider answers `accounts` through the credential copy it holds itself. The reference implementation, which re-seeds from the control machine, implements no `accounts` verb. A row with no `status=` and no percentage names an account the provider holds without a reading. Any other non-zero status is the verb failing, which `lanes list` and `lanes pick` alike report as `host-accounts-unreadable` below the provider's own message, or as `lane-host-busy` on `69`. For reading precedence and model eligibility, see the `pick` section of [lanes --help](../scripts/lanes).
- One reader inside `lanes` parses this verb, for `lanes list`, `lanes pick` and `lanes host-accounts` alike, and `lanes host-accounts` is the form another program asks it through. That command prints one validated row per account as `config-dir` and `harness`, tab-separated and `@tsv`-escaped, or the whole records under `--json`, which is the exact form a caller comparing a config directory reads. Its exit status is `0` for an answer, `2` for an absent verb, and `1` for any failure to produce one: a failed verb, an unbounded read it declined to make, `ORCH_LANE_HOST=local`, or a render it could not finish. The keyed `lanes:` line names which. A caller decides what the host holds from that command, never from the provider's bytes.
- A Pi launch on a `github-copilot/` model spends a Copilot seat's monthly credit pool, and `lanes pick --harness pi` reads that pool from the provider's `harness=pi` rows. A row carrying `monthly-pct=` replaces the `ORCH_LANE_COPILOT_POOL` override for its Pi root, and its `monthly-resets=` reaches the record as `binding_resets_at`. A row with no reading leaves the override standing where the setting states one. Where no read measures any pool, `lanes pick` refuses `copilot-pool-unstated` and `open-terminal` refuses a named lane as `lane-model-unreadable`, `lanes` printing a `fix=` line that names the read that failed and its repair: an absent `accounts` verb, no row for the root, or the row's own `status=` and `detail=`. A failed or busy `accounts` read, with no override entry for a Pi root, refuses as `copilot-pool-unread` (exit 1), which asking again can answer. An entry for a Copilot CLI home names no Pi root. The `fix=` line for a provider with no row counts only rows `ORCH_LANE_EXCLUDE` and `ORCH_LANE_RETIRE` leave in. `lanes list` shows no Pi row; `lanes host-accounts --harness pi` prints them.
- `TARGET` opens an SSH shell session. The caller then types `PREFIX 'cd WORKTREE && exec START_COMMAND'` with shell quoting. `PREFIX` belongs to the provider. The caller does not add the local `CLAUDE_CONFIG_DIR` environment prefix. The local account path remains the claim identity.
- The provider fetches or clones the repository and writes the remote clone's `.env.local`. It calls the installed worktree command to create the item with `--hosted`, adding `--reuse` for relaunch or reuse only when the item worktree exists. Before the first turn, the provider places the caller's per-harness pre-approval, such as folder trust and hook approval, where that harness reads it. A failed preparation remains a failed create, or a failed `wait` after an accepted one, and leaves what it made for `close`. A local lane has no provider to do this, so `scripts/lib/lane-launch.sh` makes the same folder-trust record itself before the window opens. For Codex: the account's own config where it already trusts the launch directory, otherwise a `CODEX_HOME` of that launch's own under the account, holding the account's files by link and a `config.toml` carrying the account's tables plus the directory's trust entry. For Claude: `projects.<dir>.hasTrustDialogAccepted` beside `hasCompletedOnboarding` in the config dir's own `.claude.json`, the pair the harness itself records when the dialog is answered at the pane, which `tools/harness-smoke` seeds a harness home with and the provider's pre-approval merges key by key from the operator-staged `ACCOUNT/lane-host/.claude.json`, with every other key kept. The launchers name the route they took and refuse `launch-trust-missing` where the entry could not be made, rather than opening a pane on the folder-trust question. An account config already answering for that directory with anything other than trust is such a refusal: a recorded answer is honored, never overwritten.
- A hosted lane's worktree sits at one path per clone: `<parent of clone>/.worktrees/<clone name>/<WORKTREE_HOSTED_NAME>`, by default ending in `lane`, which the clone's `worktree path --hosted` prints. `WORKTREE_BASE_DIR` does not move it, so two clones of a repository on one host never share it, and clones placed at one path on every host, as the fleet places them, get one path in every lane. sccache keys a Rust compile by its absolute source path, so only a path every lane shares lets one lane's build, or a warm snapshot's, answer another's. A provider that snapshots a warm build runs it at that path, as kendex's `tools/lane-setup` does under `FLEET_WARM=1`. The item-keyed path stays for local lanes, where several worktrees of one repository coexist. A reader finds the tree through `worktree path ITEM`, which follows the item's registered branch, or the item the tree records while a paused restack leaves it detached, or through the `path=` field `create` printed, never by composing the item-keyed spelling.
- `create` writes the lane's launch record: the lane's root in `lane-mail/<item in lower case>` under the clone's common git directory, and the lane's own `tmp/lane-mail/<item>`. `lane-mail-check` hands a lane its mail and judges its handoff marks only where that record stands. The included provider writes it by calling the clone's own `scripts/lane-marker`, which owns both halves and their containment. `open-terminal --host` verifies that record rather than trusting the provider: after `create`, or after `wait` for an accepted create, it reads the worktree's `.git` through `cat` for the clone's common git directory, writes the lane's root through `put` at the path `lane-marker --marker-path` names, and reads it back through `cat`. Each step that fails names itself and fails the item, which is then never reported as launched: a `.git` the host does not produce is `host-gitfile-unread`, a `.git` that does not name a linked worktree git directory is `host-gitfile-invalid` and carries the line it read, and a marker that could not be written or that does not read back holding that root is `marker-failed`. A relaunch runs the same steps. `put` creates the marker's parent directory. The marker is outside `tmp/lane-mail/`, so the mailbox guard does not cover it. The launcher writes that half only; the mailbox half is created on the host by the first `append` that reaches it. It then puts the refresh record at the path `lane-marker --refresh-path` names for the worktree git directory that `.git` names: the lane's root for an `open-terminal --lane-refresh` launch, an empty file otherwise, because no verb deletes. A failed put is `marker-failed` naming that path.
- A lane's tree is a worktree of the repository's base branch at its current tip: a fresh clone, or an existing one the provider fast-forwards first. The render in that tree is the one the base branch commits, so `create` runs no `kendex refresh`. A clone whose checkout carries no committed render fails `create`. The Pi packages a Pi lane loads from outside its tree are one global-scope install at the Pi root the lane runs under, which the lane image carries or the host's preparation makes once with `PI_CODING_AGENT_DIR=<that root> kendex update-pi --scope global`; `create` runs no `update-pi`. A project-scope Pi package the tree declares has no install record in the lane until `update-pi` runs in that tree, and kendex reports it as drift until then; a repository that declares none starts its lanes with no render drift.
- A Pi lane runs under one Pi root on its host. A provider that sets the lane's `PI_CODING_AGENT_DIR` names that absolute directory as `pi-root=` on the `create` line; with no such field the lane runs at Pi's default root, `.pi/agent` under the host home. Under a fleet state, `open-terminal` judges a hosted Pi launch on the host's own files once `create`, or the `wait` after it, stands and before the harness starts: it reads `settings.json` under that root and `.pi/settings.json` in the lane's tree through `cat`, a `2` confirmed by `touch` counting as a file Pi does not read, and applies the local Pi rule to them. Compaction left on refuses `compaction-on`, and a read that fails, or a file jq cannot parse, refuses `pi-settings-unreadable`, both naming the host path. It then reads the pi-hooks carrier the same way: the first of `.pi/packages` in the tree and `packages` under the root whose `@vanillagreen/pi-hooks/package.json` the host holds, and that carrier's `extensions/vocab.ts`. A carrier that sends no `context_window`, or none installed, refuses `unsupported-for-oversee reason=no-window-read`, and a read that fails refuses `pi-carrier-unreadable`. The host keeps the item after any of these refusals, so the next launch takes `--relaunch`. A carrier whose `package.json` lists no lane mail wake among its `pi.extensions` refuses `pi-mail-wake-missing` naming the carrier's version and the required pi-hooks update ([pi-runtime.md § Lane mailbox wake (Pi)](../references/pi-runtime.md#lane-mailbox-wake-pi)).
- A Copilot lane's identity is the login stored in its account directory's `config.json`, which the host's copy of that directory holds; no token is copied or handed in. The provider's prefix sets `COPILOT_HOME` to the account and nothing else: the rest of the Copilot launch policy, the cleared `COPILOT_GITHUB_TOKEN`, the shared skills and the folder trust, rides in the start command `open-terminal` types, which runs after the login shell's profile. A Copilot lane places no approval file.
- `.kendex-lock.json` is committed and arrives with the clone. A provider neither copies nor commits it by hand. This machine's half of the record, `.cache/kendex/lock-local.json`, is per host: a provider does not copy it.

## Codex hook approval

A provider that places Codex hook approval writes one `hooks.state` entry in the account's `config.toml` per `command` handler and per `mcp_tool` handler outside `session_end`; `prompt` and `agent` handlers, and `mcp_tool` handlers on `session_end`, get no entry. An entry whose `trusted_hash` differs from the value Codex computes leaves the hook unapproved.

| Item | Value |
|---|---|
| Key | `<hooks.json path>:<event label>:<group index>:<handler index>`; the event label is snake_case, such as `pre_tool_use`, not the hooks.json name `PreToolUse`; both indices are zero-based positions in hooks.json |
| Hash input | `{"event_name": <event label>, "matcher": <matcher>, "hooks": [<normalized handler>]}`, with every field still unset after normalization omitted; the normalized `timeout` is always present |
| Digest | `sha256:` followed by the SHA-256 hex of the hash input as compact JSON, keys sorted at every level |
| `command` handler | `{"type": "command", "command", "timeout", "async"}`, `async` as written |
| `mcp_tool` handler | `{"type": "mcp_tool", "server", "tool", "input", "timeout"}`, plus `statusMessage` when set |

- Timeout: `session_end` and `interrupt` hash the timeout clamped to 1..3, 1 when absent. Every other event hashes the timeout floored at 1, 600 when absent, so a timeout of 0 hashes as 1.
- Matcher: `user_prompt_submit`, `stop` and `interrupt` never hash a matcher, even when the group sets one. Every other event hashes the group's matcher as written, an empty string included.
- Extra fields: a `command` handler adds `statusMessage` when set, and `additionalContextLimit` only when it is set to a value other than 2500 on `pre_tool_use`, `post_tool_use`, `session_start`, `user_prompt_submit` or `subagent_start`. `commandWindows` never enters the hash.
- Key path: the path Codex builds, `<dir>/.codex/hooks.json`, made absolute without resolving symlinks. A linked Git worktree keys under the main checkout's `.codex/hooks.json`.

These rules mirror Codex 0.154.0: `codex-rs/hooks/src/engine/discovery.rs` `hook_hash`, `codex-rs/config/src/fingerprint.rs` `version_for_toml`, and `codex-rs/config/src/loader/mod.rs` for the worktree key. Check a later Codex release against those files, never against this section.

## Static SSH implementation

`scripts/lane-host-ssh --help` owns the inventory shape, source selection, account files and static-host lifecycle. The inventory binds each item to a target and clone before dispatch; it performs no automatic allocation. The host already has SSH access, Git, gh, Bash, kendex and the selected harness, and for a Pi lane the Pi packages installed at global scope under the inventory row's `account` directory, which `create` sets as the lane's `PI_CODING_AGENT_DIR`: `PI_CODING_AGENT_DIR=<row account> kendex update-pi --scope global` on the host. A clone whose checkout carries no committed render refuses `create`: `render-missing` where a render script is absent, `render-untracked` where it is present but not committed at `HEAD`. The reference requires Python 3.8 or later on the control machine.

It implements neither `accounts` nor the `stop-sandbox` and `start` pair: a static machine has no sandbox to stop, and its parser exits `2` on all three, the absent-verb status above, so `lane-close --park` on a static host refuses as `park-refused reason=provider-unsupported` on its `stop-sandbox --check` read, before it signals the harness or reads the pull request. It copies the account's files from the control machine at every `create`, `--relaunch` included: `ACCOUNT/setup-token` for claude, `ACCOUNT/auth.json` for codex and pi, and nothing for copilot, whose host account holds its own login. Those are not the files `lanes list` measures. A claude lane runs on `ACCOUNT/setup-token` while `lanes` measures `ACCOUNT/.credentials.json`; a codex lane runs on a copy of `ACCOUNT/auth.json` that diverges from the local file once either side renews. Its argument parser exits `2` on the unknown `accounts` verb, which is the absent-verb status above, so a launcher asking what this host holds gets no answer and judges the lane on the control machine's reading.

`status` reads the canonical root from the launch marker after confirming the clone's item owner. It uses the installed lane process owner even after cleanup removes that root. A live process with that deleted current directory still counts as running. An unreadable marker or process yields no verdict. Every `create` refuses as `identity-recorder-missing` where the clone's `lib/lane-state.sh` holds no `lane_identity_record`, a library older than the recorder. Its `remote-prefix` sources that library and records, through `lane_identity_record`, the pid and start time of the shell that then execs the harness in `.git/lane-host-pid` beside the item marker; a record that fails ends the prefix with an `identity-record-failed` line on the pane before the harness starts. `stop` confirms the clone's item owner, reads that identity and runs the installed `lane_stop_identity` on it, reading no directory, and waits for every signaled process to exit. A clone holding no identity file, a lane launched before its prefix recorded one, and an identity whose pid has exited or now started at another time, which prints `stop-identity-stale` first, take the worktree rule: `stop` resolves the item through the installed worktree command, answers the removed-worktree `4` where that path is no directory, and otherwise runs the installed `lane_stop_owned`, which signals the named harness processes whose current directory is that worktree, checking the directory again before each signal. An identity file holding no pid and start refuses as `stop-identity-invalid`: remove `.git/lane-host-pid` from the clone, which the next stop reads as a lane with no identity, and stop again. `close` removes the identity with the item marker. A clone holding neither a marker naming the item nor the item's worktree, as a finished close leaves it whether or not a create for another item followed, holds nothing of the item: `stop` answers `processes=0`, `status` answers `exited` and `close` answers `closed=absent`, touching nothing of the other item. A marker missing or naming another item beside the item's standing worktree, which a failed create leaves, refuses as `stop-unowned`, `status-unowned` or `close-unowned` with exit `75`. `close` accepts `--merged` and keeps the whole archive under it. It checks the clone and any remaining worktree for uncommitted files. It asks kendex for the changed whole-file renders, so a shared settings file or unrelated path refuses cleanup. It archives their remaining `tmp` records on the control machine and prints the saved path before delegating worktree removal to the installed worktree command. No remaining `tmp` means no archive and no `kept` line. A worktree already removed by lane cleanup does not prevent close, but its deleted records cannot be recovered. Close keeps the static machine, source clone and account files. `list` reports configured hosts, including available ones; static hosts have no age or expiry timer.

[`tests/fixtures/lane-host`](https://github.com/vanillagreencom/kendex/blob/main/skills/orch/tests/fixtures/lane-host) implements the same protocol with fixed output and a call log. Launcher and watcher suites can install it without SSH or a provider account.
