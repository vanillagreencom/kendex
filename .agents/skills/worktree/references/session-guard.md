# Session guard limits

The claim/release/status contract and exit codes live in `worktree-session-guard --help`; each worktree command's lease behaviour is in its own `--help`.

The `worktree-prompt-claim` companion uses the session hook's claim decision before each Claude prompt. A required claim failure blocks the prompt. A successful prompt claim refreshes the lease. When `--adopt` takes the environment owner's lease under an issue ID, the guard records that original owner in the lease. SessionStart and prompt claims both use that verified association with their unchanged process environment and keep the issue owner, so a resumed, cleared or compacted session refreshes its adopted lease. A claim whose environment owner the lease does not record as its session owner refuses that issue lease, unless the lease can be taken over as [Session processes](#session-processes) states.

Claiming is the caller's job: `create` never claims, the orchestrating workflow claims once the worktree is the session's, and `remove` releases at teardown. The catalog's `worktree-session-claim` hook claims at session start under the env ladder below, so a session opened by hand holds a lease too. It claims only a worktree whose private git dir holds the `kendex-issue` record, which every tree `create` returns carries, one adopted through `--reuse` or `--restack` included, and runs no worktree command to learn that. By default, a start meeting a lock another owner name or tool holds, an issue lease with no association to this session included, leaves that lock as it stands and says nothing. The exception is a guard lease past the TTL that records session processes all verified dead: the start takes it over. The hook's catalog declaration defines which harnesses refuse or only advise in its optional required-claim mode. The workflow's `claim --owner <ISSUE_ID> --adopt` takes over a lease the caller's env identity holds, so its claim follows the hook's. Without `--adopt` a claim under any other owner refuses that lease, with the same takeover exception. That refusal keeps cleanup's own `--owner` claim off a tree a session claimed after cleanup probed it, since a lease taken after that probe is fresh. `refresh` takes over nothing. Probe with `status`, which is read-only, never with `claim`: `claim` takes or rewrites the lease.

The lease is scoped to the OWNER string, which the calling workflow sets to the issue ID: two sessions on the same issue share one lease and either may release it at close-out. The lease's `pid` belongs to the short-lived guard writer, which exits after claim or refresh. For a lease that records no session process, automatic release by `remove` requires that writer PID to be absent on this host. A live writer PID protects only the guard write window; it does not establish whether the harness is still working. A remote host or an unknown process state also keeps the lease. Bare `create <ID>` exits 75 on existing ownership; `create --reuse|--restack` skips that refusal, so **nothing prevents a second implementer there**. The per-issue claim lock is a repository-local flock held only inside one `create` invocation and is not that gate either.

For a lease that records no session process, staleness is heartbeat age with **no liveness check**. The heartbeat moves only when a caller re-enters or re-claims the tree, and nothing does so on a timer, so such a lease past its TTL is unlocked by `release --stale` or `sweep` while its session may still work. `worktree-session-guard refresh <path> --owner <ISSUE_ID>` holds it open. Nothing runs `sweep` automatically; confirm the owner is really gone before releasing such a lease.

A Git worktree lock does not block writes, commits, or rebases inside the worktree, and `git worktree remove -f -f` or a plain `rm -rf` still destroy a claimed tree; use `status` and `list` to attribute such a removal afterwards.

`remove <ID>` and `create <ID> --reuse` use the issue ID they were addressed with first. A path-addressed `remove` reads the issue from the private Git directory's `kendex-issue` record. Issue identity uses the same case normalization as worktree creation. The env ladder (`$KENDEX_SESSION_OWNER`, else `$HT_SESSION_OWNER`, else `$USER`) supplies a fallback identity. Two sessions on one machine share the `$USER` fallback identity, and either can adopt a lease held under it under an issue ID. `cleanup` never releases on an owner match: it skips every lease regardless of owner. The one lease that admits anything is the owner's own under `cleanup --targets-only --worktree PATH --owner ID`, which prunes that worktree's Cargo build output and leaves the lease held.

## Session processes

A claim with `--session` or `--adopt` records in the lease the harness session process it runs under. The guard reads that process from its own ancestry: the nearest ancestor that is not a shell or command launcher, by PID and start, with the PID namespace and boot id where the system exposes them. Where `/proc` exists the start is the process's start in clock ticks since boot, which a wall-clock step such as an NTP correction or a VM resync after host sleep does not move; elsewhere, as on macOS, it is `ps -o lstart=`, fixed at fork. `scripts/lib/process-identity.sh` owns these reads. No harness has its own code; the hook and a workflow's shell command each sit under their harness process. A write adds the caller's process and drops only processes that read dead, so sessions sharing one lease keep each other's records. A plain `--owner` claim records nothing, and a session-bound claim that cannot read its process records nothing and says `guard-session-unidentified`.

The guard reads each recorded process as live, dead or unknown, as `worktree-session-guard --help` defines. A process recorded on this host under another boot id is dead, so a sandbox stopped and relaunched in the same worktree, which boots anew, does not keep its old session's lease. A zombie is dead. A process in another PID namespace on the same boot, such as a restarted container's, is unknown, because the guard cannot read it from here. A lease holds while any recorded process is live or unknown, without another prompt, start or timer:

- `claim` takes over a foreign lease only when it is past the 720-minute TTL, records at least one process and every recorded process is verified dead, under the same lock hold as its write.
- `release --stale`, `sweep` and `cleanup --stale` release a lease past the TTL only when every recorded process is verified dead.
- `release --inactive`, and so `remove`, refuses while any recorded process other than the caller's own is live or unknown. The caller's own process does not hold the lease, so a lane can remove its own worktree. `remove` names that refusal `lease-session-held`: let that session end, or confirm it has ended, before `release --force`.
- A lease that records no process, an older lease or a plain `--owner` claim, is released by `release --stale`, `sweep` and `cleanup --stale` on the age-only rule above, and `claim` never takes it over. `release --force` stays the operator override.

A claim with `--session` on a lease its owner holds that already records the caller's process is established. It takes the guard's lock in one attempt and refreshes the heartbeat; a guard lock that is busy or cannot be taken, or a failed write, exits 6 and leaves the lease standing, which the hook reports as an advisory notice, so compaction, `/clear` and Claude prompts do not stop the session. A claim that is not established keeps the admission path and every refusal. These established-session failures still take the admission path and refuse in required mode: an unreadable worktree lock, an unresolvable worktree registration, the hook's failed reads of Git's repository variables, the common Git directory or the worktree root, and a missing guard.
