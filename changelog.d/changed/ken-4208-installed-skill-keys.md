- An installed copy of a skill now carries one frontmatter key set for every tool: `name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools`, `argument-hint`, `user-invocable`, `disable-model-invocation` and `repo-effects`. `dependencies`, `summary`, `tags` and other keys stay in the catalog, where install, `kendex check`, the Library, fork and import read them. `metadata` keeps its string values, quoted. Where a skill writes no `compatibility`, the copy states its required commands as one. `kendex check` reads a skill's command declarations from its source at the installed revision, and reports a source it cannot read, or one it has no time left to read, as could-not-check. An in-place skill keeps its authored file. The first plan after this release reports every copied skill whose catalog frontmatter carries a key the copy cuts, or `metadata` the copy re-quotes, as having newer content, and refresh rewrites it. A safety finding in a copied skill's `SKILL.md` body, in a plan or the available-package preview, is cited at its line in the catalog file, the line `kendex check --catalog` cites, where the project's own instructions leave the body as published. A finding inside the cut frontmatter is cited with no line number. Fork and import of an edited copy put the cut keys back from the catalog file at the revision the copy was installed from: a fork refuses, and import lists the edited copy as not importable, where that file cannot be read or either frontmatter does not parse. Comparing an install with a catalog version reads the version as a copy holds it, so an unedited copy shows no difference.
