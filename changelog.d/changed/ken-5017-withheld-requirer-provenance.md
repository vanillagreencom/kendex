- Removal now uses recorded dependency ancestry to keep the same items removed when a catalog is unavailable, including dependencies of hooks withheld from a tool. Lock version 11 gains optional `requirerProvenance` facts. Older writers discard them, and older verification can reject the new serialization. Removal refuses when a legacy or rewritten record lacks the ancestry needed to decide whether a requirer stays, when a local edit holds an item or its record is marked as one a hold kept as it was, by a local edit, even one since undone, or by a catalog that would not read, and no record roots it while the read cannot account for every declaration (a catalog, item or set it could not read, or a dependency it could not satisfy), and when a set carries an item declared from another catalog and the record holds no reading of that set, as is always so for a local folder catalog's set. Otherwise, where no reading roots an item and the read cannot account for every declaration, removal keeps the item removed when its record names a requirer or set that stays, as before.

  You do: if removal reports missing provenance, follow the step it names: `step=apply`, apply with the catalog readable using a build that records requirer provenance, removing what it reports left over, and retry; `step=resolve-edit`, resolve the local edit to the item it names or apply with `--discard-edits`, with the catalog readable, and retry; `step=retry-readable`, retry the removal once the catalogs as they sit now, which can differ from the revisions the record holds, account for every declaration, starting with the causes the refusal names; and if it reports a set's reading missing, retry while that set's catalog is readable and still carries the item, or remove the set with it.
