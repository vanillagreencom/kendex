# Pi

The only harness with an extension kind kendex installs end to end, and the only one whose tool surface is deny-only over an open vocabulary, so an allowlist is refused. Owner: `crates/core/src/harness/pi.rs`.

## Roots

| Scope | Path | Relocated by |
|---|---|---|
| Global | `~/.pi/agent` | `PI_CODING_AGENT_DIR` |
| Project | `<project>/.pi`, plus the shared `<project>/.agents` | nothing |

`PI_CODING_AGENT_DIR` is trimmed, `~` expands against the configured home, and the override is used only when it is anchored to a named root: a drive or UNC share on Windows, a leading `/` on POSIX. Empty, whitespace-only, relative and driveless-rooted values fall back to `~/.pi/agent`. `pi_root_is_absolute_for` in `crates/core/src/harness/pi.rs` is the rule, and every standalone Pi package's runtime readers carry their own copy, held to the Rust source case by case by the pi-hooks suite. The `scripts/append-system.mjs` install helpers are outside it: they resolve the variable as given, at install time, into a directory that already exists.

Project markers: a `.pi/` or `.agents/` directory.

## Surfaces

| Kind | Global | Project | Caps |
|---|---|---|---|
| agent | `~/.pi/agent/agents/*.md` | `.pi/agents/*.md` | managed, both |
| skill | `~/.agents/skills/<name>/SKILL.md`, shared with Codex, OpenCode, Gemini and Copilot; `~/.pi/agent/skills/<name>/SKILL.md` for a copy delivery | `.agents/skills/<name>/SKILL.md`, shared with Codex and Antigravity | managed, both |
| command | `~/.pi/agent/prompts/*.md` | `.pi/prompts/*.md` | managed, both |
| hook | `~/.pi/agent/kendex/hooks/<name>.sh` plus `kendex/hooks.json` | `.pi/kendex/hooks/<name>.sh` plus `.pi/kendex/hooks.json` | managed, both; enforced while the `pi-hooks` carrier is registered and enabled |
| mcp-server | — | — | unsupported |
| plugin | — | — | unsupported |
| pi-extension | `~/.pi/agent/settings.json` `packages[]`, and `~/.pi/agent/extensions/*.{ts,js,mts,mjs,cts,cjs}` | `.pi/settings.json` `packages[]`, and `.pi/extensions/*.{ts,js,mts,mjs,cts,cjs}` | managed, both |

## Format

- Name rule `Any`; namespace separator `__`.
- MCP transports: none; Pi reads no MCP servers.
- Command file: markdown installed as `prompts/<name>.md`. The filename gives the `/name` typed. The source bytes stay unchanged when no command instructions apply. See [consumer instructions](../authoring/README.md#a-consumers-own-instructions) for configured output. Pi reads the same frontmatter keys a Claude command carries (`description`, `argument-hint`) and ignores the rest, and every `$` placeholder Claude expands (`$ARGUMENTS`, `$1`, `$2`) expands on Pi too, beside Pi's own `$@`, `${1:-default}` and `${@:N}`; a Claude ``!`…` `` shell inline reaches the model as text, said as a warning (`crates/core/src/render/validate/command.rs`). Discovery is non-recursive and only `.md` loads, so a namespaced name flattens to `__` and the `.disabled` rename toggle is safe. Project prompts load only once Pi trusts the project: a saved decision, `--approve`, or `defaultProjectTrust = "always"` for a headless run; and `.pi/prompts` is one of the directories whose presence makes Pi ask for that trust, so the first command kendex installs into a project that had none turns the question on. Pi's own `pi config` switch writes a `-prompts/<name>.md` row into that scope's `settings.json` `prompts` array; kendex's switch is the rename, and it does not read that row.
- Agent file: YAML frontmatter and a markdown body, `<name>.md`. Fields written: `name`, `description`, `deny-tools`, `allowed-subagents`, `model`, `effort`, `color`, `pane` (`crates/core/src/render/agent/pi.rs`). No frontmatter schema is enforced beyond the name rule.
- Model dialect: the renderer retains canonical class intent for the child dispatcher under [D021](../decisions/D021-runtime-model-classes.md). Exact ids use `provider/model`; `inherit` omits the field. Effort remains a separate key and a model suffix. Accepted effort values live in `models::effort_levels`; absent effort uses Pi's default thinking level.
- Permissions: deny-only. `allowed-subagents` and `deny-tools` are resolved together: engineers delegate to `scout` by default and every other role is a leaf; `subagent`, `get_subagent_result`, `steer_subagent` and `stop_subagent` are always denied; `delegate_subagent` is denied unless delegation was declared; every agent but a `role: planner` denies `question`, and a `role: reviewer` agent also denies `tasks_write`. An `AllowOnly` intent is a hard refusal naming both fixes: an explicit `deny-tools` override for Pi, or dropping Pi from the agent's harnesses.

## Hooks

Pi executes nothing per hook itself. The `pi-hooks` carrier extension hosts native listeners, and hook content rides in the registry kendex renders one level under the root: `<root>/kendex/hooks/<name>.sh` plus `<root>/kendex/hooks.json`, keyed by Pi's listener names (`pi_listener`, `crates/core/src/harness/caps.rs`: `PreToolUse` to `tool_call`, `PostToolUse` to `tool_result`, `Stop` and `TaskCompleted` to `turn_end`, `StopFailure` to `agent_before_settle`, `SessionStart` to `session_start`, `SessionEnd` to `session_shutdown`). An event outside that map installs nothing on Pi. The [hook-delivery rule](../architecture/harnesses.md#rules) applies to a hook that declares Pi: `managed` never implies enforcement, and an advisory install says so. The tests are `crates/core/tests/pi_carrier.rs` and the pi-hooks suite under `pi-extensions/pi-hooks/`.

The carrier's rules:

- Every key `pi_listener` can return is one the carrier dispatches, so a registration kendex labels enforced is one something runs. The `agent_before_settle` and `session_shutdown` keys need pi-hooks 0.18.0 or later, and kendex does not check the carrier's version: beside an older carrier it labels them enforced and nothing runs them. On each listener the carrier runs every registration whose `matcher` covers the event, in the order the registry names them, so a catalog guard and a `[[custom-hooks]]` command of the person's own both fire; the carrier knows no hook's name in advance, and a custom hook has no file at all, so the registry is the only place it exists. Absent, empty and `*` matchers cover everything; anything else is a whole-string regex over the word Claude Code writes matchers against: the tool on `tool_call` and `tool_result`, said in Claude Code's words (`vocab.ts`, held by a test to `render::vocab::claude_tool_name`), the session source on `session_start`, where Pi's `reload` is said as `resume` and its `new` and `fork` as `clear`, and the reason on `session_shutdown`, said in Claude Code's `SessionEnd` words: `new` and `fork` as `clear`, `resume` and `reload` as `resume`, and `quit` as `prompt_input_exit`. `Stop` and `TaskCompleted` take no matcher, so every `turn_end` registration covers the turn, and Pi names no error kind, so every `agent_before_settle` registration covers the error.
- Only `tool_call` gates. Exit 2 is the refusal and its stderr is what the agent reads. Every other nonzero status blocks too, under a reason the carrier writes: a hook exiting 1, a failed spawn, a run past its budget, a registry that exists and cannot be read, and a rendered hook the registry names whose script no scope holds are all a guard that reached no verdict, and a guard that did not run does not stand aside. Only an absent registry allows, because that is kendex having installed nothing. Only exit 0 reaches the next registration; stderr beside it is an advisory for the person. Successful stdout, with additionalContext envelopes unwrapped by `dispatch.ts::agentLine`, reaches the model through Pi's `sendMessage` without starting another turn. The report still delivers that context when a later registration refuses. `pi-extensions/pi-hooks/tests/pre-tool-context.test.ts` checks both scopes through real Pi sessions in UI and headless modes.
- Pi refuses nothing on `tool_result`, `turn_end` and `session_start`, so a hook's word is delivered rather than obeyed, through the one channel each has: `tool_result` appends it to the tool result the model reads, `turn_end` appends it to the session at Pi's settle boundary and asks for one more model request, so a headless session answers for it before the run ends, and `session_start` adds it to the session's opening context without holding the session open. Every registration runs, since nothing is left to refuse. Exit 2's stderr is the word, exit 0's stdout is, and any other status, a budget overrun and a missing render included, is reported rather than read as an all-clear. What one event's hooks say to the agent, a `tool_call` refusal's reason included, is kept to Pi's bound for a tool's output, with the whole text saved to a file a `hook-output-truncated=<file>` line names, or, where that file cannot be written, a `hook-output-unsaved=<cause>` line (`pi-extensions/pi-hooks/extensions/dispatch.ts::boundForAgent`).
- `turn_end` is the registry key and `agent_before_settle` is the listener the carrier reads it on: Pi's own `turn_end` fires once per LLM turn inside the tool loop, while `Stop` and `TaskCompleted` mean the agent has finished responding, which is the run's final boundary Pi fires `agent_before_settle` at, so a request taking ten tool-calling rounds consults these registrations once. The carrier returns their word as one session entry with `continue: true`, Pi's one continuation inside the same run. The dispatch at the end of that continuation says `stop_hook_active: true`, the field a `Stop` hook reads on Claude Code, and records what it is told without asking again. A response reaches at most two dispatches whatever a hook says, so a registry that will not parse or a render that is gone cannot drive an unattended session. This, and `StopFailure` below, needs Pi 0.87.0 or later, the floor the carrier's Pi peer range names. Neither kendex nor Pi checks that range at install, so on an older Pi the carrier puts a `hook-host-unsupported=pi <version>` line in each fresh session, and in a notification where the session has a UI.
- `agent_before_settle` is also the registry key for `StopFailure`, read at the same boundary only where Pi's `outcome` is `error` (present from Pi 0.87.0); a `completed` or `aborted` run dispatches none. `Stop` and `TaskCompleted` still run on an errored run, unlike Claude Code, which fires `StopFailure` in their place: the Pi lane's walled verdict reads that `Stop` row, and a `Stop` row written after a `StopFailure` row lifts it, so the `StopFailure` registrations run after the `turn_end` ones on every errored settle, whatever those return. `session_shutdown` dispatches `SessionEnd` with Pi's `reason` (present from Pi 0.68.0), and Pi awaits it before it replaces or disposes the session. Claude Code reads nothing either hook says, and the agent has no turn left to read it in, so what they say, a hook that reached no verdict included, goes to the person and never into the session: as a notification where the session has a UI, and on stderr where it has none and at a `quit` the person asks for, whose TUI Pi stops before it emits `session_shutdown`.
- Every payload carries the fields Claude Code names the caller with: `session_id` from `getSessionId()`, `transcript_path` from `getSessionFile()` where the session has a file, and `agent_type` from `PI_SUBAGENT_CHILD_AGENT` where that is set. A `Stop` payload and a `PostToolUse` payload also carry `context_window`, the window `getContextUsage()` names, where it names a whole one: Pi's session file names none. The lane mail wake's run of the `PostToolUse` hook carries no tool fields and no `context_window`, since no tool ran. A Pi subagent is its own process with its own session file, so that file is already the calling agent's transcript and no `agent_id` is sent. A Pi `StopFailure` payload carries no `error`, since Pi names no error kind; from pi-hooks 0.19.0 it carries `last_assistant_message`, the `errorMessage` of the last assistant message in the settle's `context.contextMessages`, where that message has one.
- A process started with `PI_SUBAGENT_CHILD_AGENT` set dispatches no `turn_end` and no `agent_before_settle` registrations: Claude Code ends a subagent with `SubagentStop`, never `Stop`, and `pi_listener` maps no `SubagentStop`, so a `Stop` or `TaskCompleted` hook judges the lead session alone; a `StopFailure` hook tells a subagent's failure by the `agent_id` a Pi payload never carries, so it judges the lead alone too. The carrier's own clippy check still runs there.
- The carrier's own end-of-turn clippy check and session-start drift report are independent of the registry: they port catalog hooks whose `harnesses:` line leaves Pi out, so nothing registers them for Pi and nothing doubles. A person who installs their own copy gets both, and one setting (`taskCompletedCheck`, `sessionDriftCheck`) turns off both.
- A hook kendex rendered is spawned at `<root>/kendex/hooks/<name>.sh` under the root whose registry named it, never through the command that names it, so the rendered guards run the same bytes under Claude, Codex and Pi; any other command is the person's own and runs through a shell as written.
- The carrier resolves the project with `discover.rs::project_root_from`, not the adapter's two markers: a walk up that stops at home. The lock file wins, home's own included, else the nearest ancestor carrying one of the seven `MARKER_DIRS`; home itself is never a project otherwise, and nothing above home answers for a start below it. A start outside home walks to the filesystem root. That is what kendex asks before it renders, so the carrier reads where the renderer wrote.
- The project's registry is read only where Pi reports the workspace trusted; Pi saves that decision for the folder or any parent. Untrusted or outside any project, the project scope contributes nothing and the global root still answers.

Enforcement is read live (`enforcement`, `crates/core/src/pi_ext/carrier.rs`): with the carrier registered and its extension filter enabled in either scope's settings the hook is enforced; with no enabled carrier anywhere Pi loads, the install downgrades to advisory, said per item.

Reserved names: Pi warns on two directory names directly beside a root it loads and halts an interactive start until a keypress, `hooks/` on the name alone and `tools/` when it holds entries beyond Pi's own `fd` and `rg` binaries and dotfiles. kendex keeps scripts and registry under `kendex/` (`HOOK_HOME`, `crates/core/src/harness/pi.rs`) and writes nothing to `tools/`; an extension's `bin` entries link into the scope's `bin/`.

Beside the root, kendex does nothing at all: `engine::targets::pi_hook` names only `<root>/kendex/hooks.json`, `engine::owned::hook_owned` derives only `<root>/kendex/hooks/<name>.sh`, `harness::pi::hook_surfaces` lists only the first, and the carrier reads `<root>/kendex/hooks.json` alone. A `hooks.json` or `hooks/` directly beside the root is read, written, scanned, listed and removed by nothing, `kendex remove` included, and enforces nothing.

Agent scoping: none; only `agents = "all"` custom hooks are enforced, carrier permitting, and scoped ones render as advisory prose in the agent files.

## Pi extensions

An extension is an npm-shaped package a source ships under `pi-extensions/<name>/`. kendex copies it into the scope's `packages/` directory, resolves its production dependencies with npm (`--omit=dev --package-lock=false --legacy-peer-deps --no-audit --no-fund`), links its `bin` entries into the scope's `bin/`, registers it in the scope's `settings.json`, and mirrors its `pi.appendSystem` file into the scope's `APPEND_SYSTEM.md` as a marker block (`crates/core/src/pi_ext/`). A package that is off gets no block, and install strips the one it had: its declaration is disabled, or its own `enabled` setting under `kendex.extensionManager.config` is `false`. kendex reads that setting the way each package's `readPackageConfig` does: Pi's user `settings.json` first, then a project scope's `.pi/settings.json`, a value in the later file winning and a file with no value keeping the earlier one. Pi loads one `APPEND_SYSTEM.md`: a trusted project's own `.pi/APPEND_SYSTEM.md` when it has one, else the global one; the two are not combined. A project block therefore loads only where Pi trusts the project, which is also where each package reads the project file, so kendex reads that file for every project-scope install. The global file serves every project without a trusted file of its own, so a global install reads the user file alone. In a trusted project with no `.pi/APPEND_SYSTEM.md` of its own, a project value that overrides the user setting is not reflected in the global block: with the user setting `false` and the project's `true`, that project loads the package's tools with no block, and with the reverse it keeps the block for tools it does not load. A change to that setting or to the declaration takes effect at the next plan: `verify` reports the block, and the next `apply` or `refresh` adds or strips it without failing on it. A plan fails on an `APPEND_SYSTEM.md` it cannot read, so a toggle over one refuses before it saves the manifest. The tests are `a_package_that_is_off_writes_no_append_system_block` in `crates/core/src/pi_ext/tests.rs`, `refresh_moves_the_block_when_the_package_setting_flips` in `crates/cli/tests/pi_staleness.rs`, and `a_declaration_switch_pi_already_made_moves_only_its_block` and `a_toggle_over_an_unreadable_append_system_refuses_and_writes_nothing` in `crates/core/tests/pi_carrier.rs`.

[Pi reads the trusted project's append file instead of the global file](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/configuration.md#project-pi-directory). Project apply and project package install write global package instructions and global output styles into an `inherited-global` marker block when the project has an append file or contributes its own instructions. Global packages must have an enabled native extension filter. A project's package `enabled` value overrides the global value; only `false` suppresses instructions. Project apply updates or removes inherited content after global packages, styles or settings change. A combined apply writes the global scope before it refreshes the project plan. Project instructions and local output styles stay in their own blocks. `project_append_keeps_global_instructions_under_merged_settings` in `crates/core/tests/output_styles.rs` proves the inheritance rule.

An append file holds inherited text only beside text of its own. A write that leaves it nothing else removes the file, so Pi reads the global file again: a package install or disable, a package or style removal, a style disable. Apply moves the file to the trash; the package writer deletes it. A blank file counts as nothing of its own, since Pi would read it in place of the global file. Apply composes every edit to the file into one mutation, a package removal's block and the inherited update included, so a combined apply that changes a global style and removes the project's last package writes or retires the project file once. `crates/core/src/pi_ext/mod.rs::append_system_retires` is the rule. `crates/cli/tests/pi_append_fallback.rs` proves it through the CLI.

In a trusted project without its own `.pi/APPEND_SYSTEM.md`, a project `enabled` value that overrides the user value does not change the global block. Pi still reads the global file, whose blocks follow user settings alone. A project override can therefore enable a package's tools without loading its instructions.

The native switch is the package object's `extensions` filter, documented in [Pi packages](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/packages.md#select-package-resources). Disable writes `"extensions": []`; enable removes that empty filter. Pi's settings cannot store the prior selection beside an empty filter, so the settings owner refuses disable or disabled-declaration install/update when the existing `extensions` array is nonempty. No-op enable and enabled-declaration update keep that selection. Other package filters and settings stay unchanged. This switches extension code and the package's `APPEND_SYSTEM.md` block, not skills, prompts, themes or bin links. Package files and registration order stay unchanged. Install and update preserve a disabled filter, and a disabled declaration starts with that filter. A toggle refuses an incomplete or unmatched carrier rather than saving only the manifest. Lock and list read the native switch; verify reports a filter that differs from the declaration. The tests are `crates/core/tests/pi_carrier.rs` and `crates/cli/tests/toggle.rs`.

The same package under two names or at two scopes registers twice and crashes Pi at startup, so kendex checks for the duplicate before writing (`duplicate_elsewhere`, `crates/core/src/pi_ext/renames.rs`). Catalog packages live under the `@vanillagreen/` npm scope, and `RENAMES` in the same file maps every current name to each name an install or lock may carry for it, so an install under another of its names is recognized rather than reinstalled beside itself. `same_package` in that file decides whether two spellings are one package by folding each to the current name its rename family carries, so any two members of one family are one registration, two earlier names among them. `duplicate_elsewhere` builds its candidate set from that same current name, so a copy installed under one member is found from a declaration written under another.

Declare a Pi extension at global scope. A global install reaches every project on the machine, so a project's `kendex.toml` declares one only where that file states why the project needs its own. A project declaration the global manifest also holds is the arrangement Pi will not start under, and `kendex check` reports it from the two manifests alone, with nothing installed: the row sits under `declared at both scopes`, opens on `pi-declared-twice=<name>`, names the global manifest's spelling, says Pi will not start with one package registered twice, and names the edit that settles it: remove the `[pi-extensions."<name>"]` table from the project's manifest file, `kendex-local.toml` in a source catalog and `kendex.toml` everywhere else, the global declaration being the copy that stays. The row carries no remedy from the report's command set, because the removal verb does not make that edit: against a declaration with nothing installed and nothing recorded its plan holds no trash, package removal or lock write, so it reports that it removed nothing and the row returns next session. A global manifest that will not parse leaves the pair unjudged and is one could-not-check line, never a project reported free of a conflict nothing looked for: `pi declared at both scopes: global manifest: <reason>`, once per report however many project scopes it covers, and suppressed where the run also checks the global scope, whose own manifest read names that same file. The line reaches only a scope the check would have run for. A project declaring no Pi extension, and a directory that is no kendex project, stay clean under an unreadable global manifest. `crates/cli/tests/pi_declared_both_scopes.rs` holds the rule.

Pi also loads what sits under each root's `extensions/`, the global root's and the current project's together: a loose module file with one of the extensions the table above lists, a directory holding an `index.ts`, `index.js`, `index.mts` or `index.mjs`, or a directory whose `package.json` declares `pi.extensions`. The last rule comes from a machine kendex observed, not from Pi's extension manager, whose inventory reads a directory by its index file: a package directory an earlier installer had left under `extensions/` ran beside the managed copy. kendex installs under `packages/` alone, so `update-pi` and `kendex check` both read those two `extensions/` directories, once each and only for a scope declaring a Pi package, for a second copy of a declared package (`crates/core/src/pi_ext/shadow.rs`): an entry named for the package under its current, earlier or unscoped name (`matches_name`, `crates/core/src/ownership.rs`), or a directory whose `package.json` names it so or declares the managed copy's entry files; a loose file is matched by its name alone, since a catalog entry module is named for its function and a person's own file carries that name as well. The read is manifests and directory listings, never a module file. Each verb reports the copy with both paths and versions and the directory to move it out of, and a root that will not read as one could-not-check line beside the copies found, each once per report however many scopes declare the package; nothing is moved or deleted.

## Output styles

| Scope | Route | Drift and lock |
|---|---|---|
| Global | `<Pi root>/APPEND_SYSTEM.md`, `kendex:append-system output-style-<name>` block | Block position, marker and content hash; never ownership of the whole file |
| Project | `.pi/APPEND_SYSTEM.md`, the same marker block | Block position, marker and content hash; no repository `AGENTS.md` block |

The block contains the style body without its Claude frontmatter. Reapply preserves the surrounding instructions. An edited block is a conflict unless explicit discard names the recorded style; missing content is drift. Discard does not authorize an unrecorded block. Linked files are refused; linked directories still follow the scope containment rule. `crates/core/tests/output_styles.rs` holds both scopes, reapply and hand edits.
