# In place

Covers: crates/core/src/discover.rs, crates/core/src/engine/tree_plan.rs, crates/core/src/engine/desired_skill.rs, crates/core/src/engine/holds.rs, crates/core/src/engine/generated_paths.rs, crates/core/src/hash.rs, hooks/block-worktree-refresh.sh

Two places where the thing kendex writes is also the thing it reads: a linked git worktree that carries its own manifest, and a package whose source is its files in place.

## Boundaries

- The project a bare project-scope verb writes is the one `crates/core/src/discover.rs::project_root_from` resolves from the working directory. Inside a linked git worktree that project is its own where its manifest file (`manifest::project_manifest_path`: `kendex.toml`, or `kendex-local.toml` for a source catalog) exists there, readable or not; where it carries none, the declarations are the main checkout's and a project write typed there lands in that checkout. One predicate, asked in two places: the catalog's `block-worktree-refresh` hook spells discover's markers in Bash, and `drift::report::remedy_target` resolves the same answer for the check report. Enforced by `hooks/tests/block-worktree-refresh.test.sh` and `crates/core/tests/drift_worktree_remedy.rs`.
- An in-place package's source is its files in place (`manifest::INPLACE_SOURCE_NAME`). kendex holds the harness links, the project-instructions block in `SKILL.md` and the record, and nothing else of the tree: apply writes the block into `SKILL.md` where it is missing or stale and no other byte, the record's `sourceHash` covers the manifest sections that shape the block and never the tree's bytes, and the record carries no `renderedHash` because kendex wrote no render. An edit to the tree is therefore never a stale row, a local-edit hold, an unmanaged copy or a record mismatch, so `refresh`, `check` and `verify` read one comparison: the links, the block and the entry point. A missing `SKILL.md` or source tree is still a failed row, and a missing link is still missing. Whether a tree is the source is decided once, where the artifact is built (`Artifact::Tree::in_place` in `crates/core/src/engine/desired_skill.rs`): only the tree standing where the source stands is the source, so a copy delivered from an in-place declaration is a render with a rendered hash and a hash over its bytes, held on edit and taken on removal like any other; and every pass reads that field rather than asking again. An in-place skill's name is its directory's, which carries no `/`; a namespaced declaration is not found in the in-place source, so no other spelling is ever written into the person's name line. The first plan after a build that records in-place entries this way re-records each existing entry once, as a stale row; from then on an edit moves nothing. Enforced by `crates/core/tests/in_place_edits.rs`, `crates/cli/tests/in_place_verbs.rs` and `crates/core/tests/in_place_preservation.rs`.

## Decisions

- A bare `kendex refresh`, `apply`, `updates --apply` or `check` typed in a worktree that owns its manifest targets that worktree: the target is unambiguous, so the CLI resolves it with no flag and the hook refuses nothing. The hook refuses only a write whose target is another checkout: an unflagged whole-scope verb in a worktree with no manifest of its own, a verb that writes where it is typed in such a worktree, and `update-pi` at project scope in any worktree, whose Pi package roots it leaves unjudged. `--project-path PATH` stays the explicit form for writing another project from anywhere. Enforced by `hooks/tests/block-worktree-refresh.test.sh`.
- A check report's remedy for a worktree that owns its manifest is the bare verb, `Fix::Here`; only the main checkout's project is named with `--project-path`. Enforced by `crates/core/src/drift/report/tests_render.rs` and `crates/core/tests/drift_worktree_remedy.rs`.
- A rendered guard never requires a CLI flag the installed CLI lacks. The one judge of which flags a verb takes is the installed CLI's own parser, so before a refusal names `--project-path` the hook asks `kendex refresh --help` once and reads whether the flag is listed. Where it is not, the refusal names the installed `kendex --version` and the route that works on that CLI: the same command from the main checkout. A version comparison is not the judge, because a main build and the release both print the same version, and a table of flags per version in the hook would be a second copy of the parser. The probe runs on the refusal path only. Enforced by `hooks/tests/block-worktree-refresh.test.sh`.
- The packaged `1.0.0` CLI predates `--project-path`; KEN-1830 ships the flag in the packages as `1.0.1`, and KEN-787 removes the `5.0.1` release, so version placement needs nothing here.
