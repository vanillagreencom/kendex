# CI and merge rail

Covers: .github/workflows/, .github/actions/, skills/harness-ci/, skills/review-gate/, skills/orch/workflows/merge-pr.md, skills/github/scripts/commands/pr-merge.sh

Each repository owns its pull requests and refresh workflow. The classifier determines the change class. CI selects its jobs from that class, and the review gate posts a separate commit status. A green pull request that is not queue-only merges past the merge queue by the lanes app's bypass, and the queue merges the rest, per [D013](../decisions/D013-admin-merge-green-prs.md). Consumers pull kendex updates in their own GitHub Actions runners, per [D003](../decisions/D003-one-merge-path.md).

The classifier answers one five-class verdict, `change_class`, beside the two narrow questions `harness_only` and `docs_only`, and prints `queue_only` off the `queue` lines of `skills/orch/references/narrow-change.conf` and the repository's own `HARNESS_CI_QUEUE_PATHS`. `.github/actions/change-class` is the composite action that publishes the class, the changed-path families, `lanes` and per-lane verdicts; it wraps the shipped scripts and classifies nothing itself. Its `proof` reads whether a passing run of the same workflow already tested the same tree, a merge group against its pull request's run and the queue's push against the merge group's, stands down what that run's record covers of the lanes invariant 8 names, and uploads this run's record for the next; the rules are [../../skills/harness-ci/references/wiring.md](../../skills/harness-ci/references/wiring.md#proof-reuse) § Proof reuse. In this repository `tools/ci-job-set` turns the class, the changed paths, read through `tools/rust-reads`, and the event into one selection per lane of `skill-tests.yml` and the runner list of its shard matrix, less what the run a proof names ran, and `tools/ci-aggregate` holds each required context to those selections; the `CI` job holds every lane the older aggregators hold, plus `gate-selftest`, Preflight and Markdown, and those aggregators keep the names kendex's required-checks ruleset requires. A lane reads the same class before it opens a pull request: orch's `dev-validate-run` classifies the worktree through `skills/orch/scripts/lib/change-class.sh`, and the `changes` job's action reads the shipped scripts itself from its trusted checkout. `dev-validate-run` exports the class, the docs verdict and the changed paths to `DEV_VALIDATE_CMD`. `tools/guard --full` hands those three to `tools/ci-job-set`, as the `changes` job does. The classifier proves `render` in a private checkout of the range's head, which for `dev-validate-run` is a snapshot commit of the worktree, so its uncommitted render edits are weighed. A wrong local class costs a red CI check, since CI classifies the branch again.

## Boundaries

- `harness-ci` writes nothing under `.github/`, so the repository wires the classifying step itself, from one of the four shapes or the CI template in [../../skills/harness-ci/references/wiring.md](../../skills/harness-ci/references/wiring.md). That the package writes no workflow is stated in [../../skills/harness-ci/SKILL.md](../../skills/harness-ci/SKILL.md) § This package never edits a workflow, and is not mechanically enforced. `skills/harness-ci/tests/wiring-shapes.test.sh` proves only that each shipped shape keeps its expression, ordering and script path, and `skills/harness-ci/tests/ci-template.test.sh` that the template's `CI` job needs every other job and that both events read each lane's verdict the same way.
- The review gate answers review and nothing else: it reads no job result and re-runs nothing. Enforced by `skills/review-gate/tests/review-predicate-selftest.sh`, which pins the predicate's answers and which the `gate-selftest` job runs ungated on every pull request. That no CI lane is conditioned on the verdict is a wiring rule the repository holds, stated in [adoption.md](../../skills/review-gate/references/adoption.md#recommended-ci-shape--the-fastfull-split) and not mechanically enforced.
- `kendex refresh` renders skill copies and settings. Workflow adoption owns files under `.github/workflows/`. Adoption records each verbatim workflow copy in `.kendex-generated.json` with its template hash. `kendex verify` checks equality against that template. A changed workflow copy cannot qualify as a render. `skills/review-gate/tests/adopt-refresh.test.sh` checks adoption. [Review-gate adoption](../../skills/review-gate/references/adoption.md) defines setup and updates.
- Consumer refresh calls the release-installed orch's `ol_preference_entries` after refresh when orch is present in the consumer root. The parser runs read-only under `env -i` with only `PATH` and `HOME`. The preserved default-branch runner validates its stdout as data before publication. Settings files are parsed, never sourced. `refresh-report.py --settings` formats the refused and deprecated arrays; it does not parse entries. An absent orch or a clean parse adds no section. Extraction failure stops publication and auto-merge. Held by `skills/review-gate/tests/refresh-consumer.test.sh` and `refresh-report.test.sh`.
- `skills/review-gate/scripts/validate-standard.sh` checks, read-only, a repository's GitHub settings. Its rule rows check part of [review-gate-platform.md § Target](../plans/review-gate-platform.md#target), not each context's app binding, and its `standard-bypass-actors` row checks [D016](../decisions/D016-merge-route-reads-bypass.md) item 3. Its environment rows check [D003](../decisions/D003-one-merge-path.md) item 2. Its `--help` lists each row and where its values come from. The owner-run `provision-environment.sh` creates the environment and secrets.
- The merge route is chosen in one place, `skills/github/scripts/commands/pr-merge.sh` (`merge_route`), per [D016](../decisions/D016-merge-route-reads-bypass.md) item 1. The lane's immediate `pr-merge` on its exact head, [merge-pr.md](../../skills/orch/workflows/merge-pr.md) § 5 step 1, passes `--admin` only where the queue is all it would skip, by the reads `pr-merge --help` § Merge route names. The early arm of [submit-pr.md](../../skills/orch/workflows/submit-pr.md) § 2 step 5, `--auto --unless-admin`, arms only under the approval rules that step names and only where the same route takes the queue; `--auto` never passes `--admin`. Enforced by the route, merge-queue, approval-gate and retired-flag rows of `skills/github/tests/pr-merge.test.sh` and the `queue` rows of `skills/harness-ci/tests/narrow-change.test.sh`. The bypass actors are GitHub configuration the owner holds.

## Invariants

1. Every case the classifier cannot prove answers `false`, which authorizes no classifier-based skip. Enforced by `skills/harness-ci/tests/fail-closed.test.sh`. A `false` verdict does not mean every lane runs: in the two-gate shape a lane's own path-family predicate still applies. The verdict is not read from the diff alone either. Docs mode reads the changed paths; harness mode also reads `.kendex-generated.json` at both endpoints.
2. Every required context reports on every event the ruleset requires it on. The classifying job sits inside the workflow, never in an `on.<event>.paths` filter, and the job carrying the required name runs unconditionally. Both are repository wiring rules, stated in [wiring.md](../../skills/harness-ci/references/wiring.md#shape-3--merge-queues-where-the-required-context-must-report) and not mechanically enforced. The snippets `skills/harness-ci/tests/wiring-shapes.test.sh` reads carry no trigger block, so that test checks expression closure, script paths, options, endpoint ordering, lane conditions and indentation only. `skills/harness-ci/tests/ci-template.test.sh` holds the CI template to both triggers and to a `CI` job that runs whatever its needs did.
3. `aggregate-needs` accepts a skipped job only where the classifier succeeded and either its waiver is `true` with the job in the caller's skippable set, or the job's own lane verdict is `false`, so a lane that skipped for any other reason reds the required context. Enforced by `skills/harness-ci/tests/aggregate-needs.test.sh`, with a must-fail control per rule.
4. The gate answers one question, whether this exact head was reviewed, and two green checks never stand in for a review. Enforced by `skills/review-gate/tests/review-predicate-selftest.sh`, which pins the decision table. That the answer reaches the head as a commit status is the writer's half, enforced by `skills/review-gate/tests/review-writer.test.sh`.
5. The active class policy follows the [review-gate class table](../../skills/review-gate/README.md#class-policy), which states the scope: a `none` row puts the pull request outside the review gate, objections and suppressed findings included; its open threads still stop the merge, per [thread-read.md](../../skills/orch/references/thread-read.md#what-reads-an-open-thread). The legacy docs-only and render-only waivers still waive evidence alone, so objections, unresolved threads and suppressed findings block. Required CI contexts, commit guards and merge conflicts remain under their existing owners. Enforced by the class-policy gate suite and `skills/review-gate/tests/docs-only-lane.test.sh`. `skills/orch/tests/queue_wait.sh` holds the open-thread clause for the guard alone; the lane's read is workflow text.
6. One component owns the class-to-policy MAPPING for the whole rail: `skills/review-gate/scripts/review-policy`. The CI predicate consumes its answer and does not re-derive it; the CI writer reads the policy from the default branch it checks out, item 7's boundary, not this one's. Orch reads no policy: its gate mode is what GitHub requires on the pull request's base, which `approval-wait --resolve-mode` reads from the base's rulesets and the pull request's `reviewDecision`, and its micro admission in [micro.md](../../skills/orch/workflows/micro.md) § 4 reads the class through `item-tier` and admits only a base whose gate mode is `approval`, since a micro run has no internal review. Enforced for the predicate by `skills/review-gate/tests/class-policy-gate.test.sh`; that orch reads no policy is not mechanically enforced.
7. The classifier a merge trusts, and the settings file its policy is read from, are the default branch's copies, never the pull request's. Held for the classifier scripts: the `changes` job of `skill-tests.yml` reads `skills/harness-ci/scripts` and orch's measurement contract from a separate default-branch checkout, through the action's `classifier` input. The action wrapper, `tools/ci-job-set`, `tools/ci-aggregate` and `tools/rust-reads` still run from the pull request's tree; review holds them, and `tools/ci-job-set` runs every lane for a change to one of them. Held for the classifier's own measurement settings: `change-class` reads `ORCH_SIZE_*` and `HARNESS_CI_TRIVIAL_*` from its environment, else from the `[env]` tables the commit `--base` names holds, and `HARNESS_CI_QUEUE_PATHS` from those tables alone, the pull request's base tip or a merge group's base and never the merge base, parsed and never sourced, and a pull request that changes a settings file classifies `standard`. Held for the policy's settings file: its one merge reader, the CI writer, runs `review-policy` in its default-branch checkout. Not mechanically enforced. The package's own source repository is the standing exception, because its checker and its candidate are the same commit, per [../../skills/bot-instructions/SKILL.md](../../skills/bot-instructions/SKILL.md) § A pull request changing its own review.
8. A proof stands down only what a completed, successful run of the same workflow on the same tree recorded, and of that only the lanes the workflow says do the same work on every event: all of them under `covers-all-lanes` with no declaration, or each lane its declaration marks `:event-uniform`. The run reading the record judges the mark, and the run writing it records what passed: in `tools/tests/change-class-action.test.sh` the row `lanes-decl-gated` holds a covered unmarked lane running, and `pr-decl-gated` holds an unmarked lane a run ran recorded as covered. Every refusal answers `reuse=false` with a reason and runs the lanes. Enforced by `tools/tests/change-class-proof.test.sh`, a must-fail control per rule, and `tools/tests/change-class-action.test.sh`, which holds what a record stands down and what a run records.

## Decisions

- A workflow path filter prevents the required context from reporting. A merge queue then waits for a check nothing reports.
- Adoption adds the ungated validate job. A repository that wants the docs waiver also takes the fast/full split.
- Consumer refresh follows [D003](../decisions/D003-one-merge-path.md). `skills/review-gate/tests/refresh-consumer.test.sh` checks each consumer's refresh branch and pull request. Consumer secrets stay in that repository's `kendex` environment. The catalog is excluded under [D007](../decisions/D007-lock-record-on-main.md). `adopt-refresh.test.sh` and `dispatch-refresh.test.sh` exercise that exclusion. The overseer takes no part in refresh.
- In kendex itself `REVIEW_GATE_CARRY_FORWARD` is `docs`: evidence carries across markdown-only deltas, never across a change to an excluded policy path. The class policy is active, so the docs-only and render-only lanes, which run only under an inactive policy, are unassigned; a documentation or render diff needs the review evidence its change class sets.
- Two merge routes, per [D013](../decisions/D013-admin-merge-green-prs.md) and [D016](../decisions/D016-merge-route-reads-bypass.md). The owner-credential merge, `--force` and `ORCH_MERGE_BYPASS` of [D003](../decisions/D003-one-merge-path.md) stay retired.
- The install record is recorded on `main` after each merge by `.github/workflows/lock-record.yml` and landed through one rolling pull request, never on a branch, per [D007](../decisions/D007-lock-record-on-main.md); no pull request check judges it.
- A pull request that repairs a broken gate engine, which cannot turn its own `Review gate` context green, is merged by the overseer's GitHub App, per [../../skills/review-gate/SKILL.md](../../skills/review-gate/SKILL.md) § 4. Operations.
