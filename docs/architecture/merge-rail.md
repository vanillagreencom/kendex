# Each repository owns its merges and its refresh

Read before changing CI, the review gate, the merge route or consumer refresh.

## The approach

A change class is derived from the paths a change touches, by the classifier in `skills/harness-ci/scripts/change-class`, and CI selects its jobs from that class. GitHub enforces approval, stale-approval dismissal, thread resolution and the required contexts through rulesets; kendex publishes no review status of its own, per [D018](../decisions/D018-platform-review-requirements.md). The merge route is chosen in one place, `pr-merge` in the github skill, which reads the queue ruleset's bypass and merges past the queue only where the queue is all it would skip, per [D016](../decisions/D016-merge-route-reads-bypass.md). Consumers pull kendex updates in their own GitHub Actions runners through the shared workflow `.github/workflows/refresh-consumer.yml` at a major tag. The workflow installs the release tagged on its own commit and runs that checkout's refresh scripts and classifier, per [D003](../decisions/D003-one-merge-path.md). The kendex app and CLI open no pull request in a consumer.

## Why

A path filter that stops a workflow from starting leaves a required context that never reports and a queue that waits forever, so the class is computed inside a job. A direct merge rebuilds every running queue group, so the route proves the queue empty before it skips it. A consumer's own runner does the refresh, so propagation costs kendex nothing and no kendex credential can reach a consumer.

## Rules

- Do classify inside a job, never in an `on.<event>.paths` filter, and run the job carrying a required name unconditionally. `skills/harness-ci/references/wiring.md` is the wiring, and `skills/harness-ci/tests/ci-template.test.sh` holds the template to it.
- Do treat the merge-group run as the only proof of a head, per [D028](../decisions/D028-queue-only-consumer-default.md). A repository whose base settings name no `HARNESS_CI_PER_PUSH_REASON` reads every change queue-only. A workflow that passes the change-class action's `queue-only-default: true` and gates its lanes on the action's `lanes` output, as the harness-ci template does, then stands every lane down on a pull-request or push run and reports `CI` alone; its nightly `schedule` run on the default branch runs every lane, `:nightly` platform lanes included. A workflow that passes no input keeps its lanes on every run. The stand-down waits for the render that reads the setting in both the default branch and the judged head. `skills/harness-ci/tests/lanes-output.test.sh` and `tools/tests/change-class-action.test.sh` hold it. This repository's `skill-tests.yml` reaches the same result by its own event terms, under the rule below on its pull requests. A red merge-group run returns the change to its lane, and an unchanged head never re-enters the queue, per the orch skill's `workflows/merge-pr.md` § 5.
- Do defer a slow lane from a pull request to the merge group, in a repository that names `HARNESS_CI_PER_PUSH_REASON`, by marking it `:queue` in its default-branch `.github/ci-lanes.conf`. There the classifier derives `queue_only` from the `queue` rows of `skills/orch/references/narrow-change.conf`, `HARNESS_CI_QUEUE_PATHS`, each `:queue` lane's globs and the jobs the `HARNESS_CI_QUEUE_SELECTOR` command names, read off the base commit; with no reason it reads the first alone and answers every change queue-only. `.github/actions/change-class` publishes it beside the class.
- Do fail closed: every case the classifier cannot prove answers `false`, which authorizes no skip; `skills/harness-ci/tests/fail-closed.test.sh` holds it.
- For CI, do trust the default branch's classifier, never the pull request's, for the classifier scripts and their measurement settings; the package's own repository is the one exception, because checker and candidate are the same commit. The action wrapper and the `tools/` files `LANE_SOURCES` in `tools/ci-job-set` names still run from the pull request's tree, so review holds them and a change to one runs every lane.
- Do read the merge route from GitHub: `--admin` only where every ruleset answers that the queue is all it would skip, the base queue is empty and the change is not queue-only; `--auto` never passes `--admin`. Under the harness-ci queue-only default every change keeps the queue; only a repository that names `HARNESS_CI_PER_PUSH_REASON` runs its lanes on the pull request and reads `HARNESS_CI_QUEUE_PATHS` there. This repository names no reason, so every change keeps the queue and merges only after its merge-group run passes, per [D027](../decisions/D027-merge-queue-proves-every-change.md).
- Never stand a lane down on another run's proof: no run records a proof for a later event to reuse, and every surviving lane a merge group selects runs against the integrated tree. [D027](../decisions/D027-merge-queue-proves-every-change.md) declares KEN-4718's temporary coverage exception; main-only results cannot supply the excluded premerge proof.
- Do run no lane on a pull request in this repository: its run reports the required `CI` context alone. The merge group runs the lanes its class and paths select, the selected macOS shell shards and cargo legs included, except for the explicit temporary roster in `skill-tests.yml`; `CI` holds each selected surviving leg. A push to `main` compiles the cargo lanes and runs the complete eligible Linux and macOS shell roster. Ordinary shards exclude the temporary entries and the dedicated family runs them exactly once, with real failures outside `CI`'s inputs. This adds ordinary main shell execution to the earlier cargo-only route; added time and cost remain unmeasured. Scheduled/manual native coverage remains intact. A nightly scheduled run on `main` runs the macOS cargo tests, Windows tests and complete native shell profile outside required contexts. The overseer's watch reports a red nightly run.
- Do keep every Linux shell contract and control. On macOS retain native, mixed and unresolved contracts under [D026](../decisions/D026-macos-native-contracts.md), including its temporary event exception and restoration criteria. `tools/macos-test-contracts` owns eligibility and native replacements for the existing runner and selector. A suite's Bash runtime declaration supplies its eligibility when no reviewed JSON entry exists. A suite must not use both sources. Suites with neither source remain selected as unresolved until reviewed. The ownership proof covers every eligible discovered suite exactly once: the required group plus its explicit exceptions equals the original roster, and ordinary plus dedicated main equals that roster. Narrow dependency selection only when all source, helper and fixture inputs are proved; otherwise keep the existing conservative selection.
- Do keep workflow files out of `kendex refresh`: adoption preserves the selected environment, secret-name inputs and matching secret mappings. It checks every other caller byte against shipped template history. An adopted caller gets a generated-file inventory record only when an in-consumer template has exactly the same bytes. The classifier follows the [shared refresh caller ownership contract](../../skills/harness-ci/SKILL.md#shared-refresh-caller-ownership).
- Do render a consumer's default catalog from `main` with the released CLI. A `v1` consumer receives compatible package changes at its next hourly refresh after their merge. Renderer, apply, refresh, install, verify, manifest and lock changes wait for a release and the `v1` move. A catalog change that raises the minimum also waits. Only the existing catalog reader's `catalog-needs-engine` refusal selects the release catalog for a retry. The run prints `catalog-held min=X engine=Y` and explains the hold in its pull request or run summary. [Source selection](sources.md#rules) keeps a declared `rev` ahead of the run selector and keeps the existing recorded-commit floor. The refresh must stop if the retry refuses. `refresh/tests/shared-refresh-workflow.test.sh` and `refresh/tests/refresh-consumer.test.sh` hold this route.
- Do read only the two fixed credential pairs from the protected environment in the shared refresh workflow: a complete `KENDEX_APP_ID` / `KENDEX_APP_PRIVATE_KEY` pair first, then `FLEET_GH_APP_ID` / `FLEET_GH_APP_PRIVATE_KEY`. The caller forwards the fixed names. Adoption refuses copies of any fixed name in repository or organization Actions secrets, including the optional issue-token pair. The shared secret-placement judgment owns that refusal. Same-name environment precedence cannot prevent outside values from filling names absent there. Deprecated name inputs and neutral mapping aliases stay accepted for shipped callers and select no credential. The [caller adoption contract](../../skills/review-gate/references/adoption.md#caller-adoption-contract) owns the configuration details, and `refresh/tests/adopt-refresh.test.sh` and `shared-refresh-workflow.test.sh` hold it.
- Do carry the selected configuration owner's render in the refresh pull request: the refresh run renders through kendex where the package is installed and configured, per [repo-effects.md](repo-effects.md), because the consumer's own check judges the pull request with the refreshed package.
- Do report a consumer's stale settings in the refresh pull request body and remove none of them, from the one list `skills/review-gate/retired-settings.json`; a failed report stops publication and auto-merge like a failed extraction. `refresh/tests/refresh-consumer.test.sh` and `refresh-report.test.sh` hold it.
- Never replay a consumer refresh in a kendex pull-request check: kendex is public, a check without secrets reads only what kendex commits, and a committed copy of a consumer's inputs would publish private repositories' files.
- Never record the install record on a branch; `main` re-records it after each merge through one rolling pull request, per [D007](../decisions/D007-lock-record-on-main.md).

## The canonical example

The `changes` job of `.github/workflows/skill-tests.yml`: it checks the default branch's classifier out separately, runs it through `.github/actions/change-class`, publishes the class and per-lane verdicts, and every gated job reads them. A new lane reads a verdict from that job and adds its row to `tools/ci-job-set`.

## Revisit when

Merge-group runs, red ones included, cost more than a run on each pull-request push would, or a served repository cannot use GitHub rulesets, Actions or a merge queue.

## Not governed

What each lane tests: `skills/AGENTS.md` and `tools/AGENTS.md`. How a lane shepherds one pull request through the gate: the orch skill's `workflows/merge-pr.md`.
