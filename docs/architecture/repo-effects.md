# A package that changes a repository runs under a licence

Read before changing repository effects, the arming record, a package's declared checks, or the hold on the commit offer.

## The approach

A package may declare, in its `SKILL.md` frontmatter, an effect on files in the checkout beyond its own render: the review instruction files the selected configuration package writes, the git hooks commit-guards arms. kendex locates the package, runs its declared installer, checker and uninstaller, and surfaces their results; it judges no part of the package's grammar. Package code runs only under a licence: the arming record kendex writes in the git directory, which git clones for nobody; a person pressing the control that asks; or an invocation that asks for the one run itself and records nothing, `kendex bot-instructions-render`, which a consumer refresh run makes in the checkout it creates for that run. Commits walk through the commit-guards package's committed scripts whatever tool makes them; kendex implements no check of its own, and `kendex check` relays the package's verdict.

## Why

A package is catalog content, and kendex runs no catalog code until a person on this machine said so. One licence per checkout, in a place a clone does not carry, keeps "set up here" a local decision for kendex and local clones. A repository's committed cloud-session hook follows [D022](../decisions/D022-cloud-session-hook-arming.md). The refresh run's render needs no person because it licenses no person's machine: the runner's checkout is created and discarded per run, only the default branch reaches the kendex environment under [D003](../decisions/D003-one-merge-path.md), the package renders only where that checkout's manifest declares `[bot-instructions]`, and the render runs with no credential. Leaving the grammar to the package keeps kendex from carrying a second copy of each package's rules that drifts from the first.

## Rules

- Do run a declared installer, checker or staged checker as declared, with no argument added, and only where the arming record licenses it or the invocation asks for that run itself; an apply, refresh or check in a checkout with no record runs no package code and names the setup step, save the setup the hold on the commit offer lets a run that commits take.
- Do select one configuration effect through `crates/core/src/bot_instructions.rs`: `github-repository-settings` when it declares repository effects, otherwise `bot-instructions`. Installation is not selection: a successor the lock records only as another package's dependency, and armed neither here nor in the main checkout of a linked work tree, leaves an installed predecessor selected, and a render through that predecessor names the successor's pending setup. Selection reads only the successor's own record, so a checkout with no records, a consumer refresh run's included, renders the predecessor. The successor's setup through core's existing consent moves ownership; `add` and `apply` with `--allow-repo-effects` set up the successor-most configuration package they bring before their render and commit offer; a predecessor arriving beside it is not set up, and their later walkthrough leaves both out. Without the flag, an `add` or `apply` that installed a successor selection passes over for an installed predecessor holds its commit offer, which names the setup and sets nothing up: the action's only consent for that setup comes after the offer, at a terminal, or is not given. The offer reads that successor from the selection, not from the render, so a predecessor set up after the render, beside the main checkout's or at the offer, still holds it, and a successor whose configuring table the commit's manifest lacks holds nothing, as a package not set up here does. Otherwise select before checking the owner's record: an unarmed selected owner names its setup step and runs neither package. The commit-guards pre-commit chain reads no lock and keeps its own staged-check rule, `skills/commit-guards/references/hooks-and-settings.md` item 3. Other packages gain no automatic installer run.
- Do transfer configuration ownership through core's setup operation under its existing disclosure and consent. Keep the predecessor's declaration readable for retirement and recovery; a declaration is not an arming licence. The selected package's declared installer also serves ordinary rendering and one-run refresh, so every call preserves its unmanaged-file gate. Core licenses the declared uninstaller for removal and failed-install cleanup, including marked writes made before successful arming. While the predecessor remains armed, preserve its shared-marker outputs for core's recovery render; that render regenerates current inputs rather than restoring prior edited bytes. Ordinary direct package writes read the existing worktree arming inventory; they never create or revoke records. An installer refusal retains core's actual recovery outcomes.
- Do run the selected renderer after a project apply, an empty plan included, and carry the whole files and regions it reports into the same action's commit offer, never a later one. The commit offer and automatic lapse checks ask only the selected configuration owner's checker. The commit offer includes changes to the superseded renderer dependency among that owner's inputs.
- Do skip the not-set-up commit hold when a package's declared `configured-by` table is absent from the offered commit's effective manifest: `kendex.toml`, or `kendex-local.toml` when that commit declares a source catalog. Read only manifest data from the candidate index for this decision. A present table keeps the hold. Leftover bot files after table removal remain the pre-commit chain's to refuse through the package's orphan findings.
- Do ask each armed package whether the commit the offer would make carries its files stale, through its staged checker over a candidate index that never touches the repository's own index; a failing answer, or a package the commit changes that is not set up here, holds the commit and offers the setup, per [engine.md § The commit offer](engine.md#the-commit-offer), except where the pending successor above holds it, when the offer sets nothing up. `add`, `apply` and `remove` run with `--allow-repo-effects` and a commit choice take that setup without asking, the say-so a scripted run gives for its own checkout; the flag with no commit choice sets nothing up.
- Do render the selected configuration owner in a consumer refresh run, `refresh/refresh-consumer.sh`, through `kendex bot-instructions-render` after staging the refresh, under `env -i` with no credential; the verb locates the installed copy wherever the install put it, writes no record, and relays the package's answer, so an unconfigured or absent package is a skip line the run prints. `refresh/tests/refresh-consumer.test.sh` and `crates/cli/tests/bot_instructions_render.rs` hold it.
- Do splice an owned `AGENTS.md` region with the byte bounds the package's parser supplies, so every other byte of the file stays as the person left it.
- Do verify whole bot files through a trusted package supplied for that invocation, outside the checked Git worktree, or outside the project when it has no worktree. `guard::Repo` resolves this boundary from filesystem markers before any tool runs. The launch owner uses that boundary for the checker, its working directory and its tool directories. The checker reads the installed doctrine as data through `--spec` and reports its own render paths after comparison. This licence runs no code from the checked branch and records no setup. It grants no ownership of shared regions.
- Do keep the arming record per work tree: a linked work tree whose main checkout armed the package names that checkout in its skip line and is offered the setup in one step.
- Never run installed package code from a session hook or a check that could reach a repository the person has not armed, except a SessionStart hook may run the commit-guards installer when `CLAUDE_CODE_REMOTE=true` and its project registration is committed in `HEAD:.claude/settings.json`, per [D022](../decisions/D022-cloud-session-hook-arming.md). A global install grants no repository consent. This exception licenses no kendex package run or local clone. Never read the record from a clone.

## The canonical example

`crates/core/src/repo_effects/`: `declaration.rs` names in `FIELDS` every key a package may declare, `armed.rs` writes and reads the arming record, and `crates/core/tests/bot_instructions_refresh.rs` plants an unarmed doctrine change and watches the commit held. A new effect adds a key to the reader before any catalog declaration uses it.

## Revisit when

A harness or git itself gains a per-clone consent record kendex could read instead of writing its own, or another package needs to run at a moment no arming record and no one-run invocation can license. The fresh cloud clone condition is met for the committed SessionStart hook under [D022](../decisions/D022-cloud-session-hook-arming.md).

## Not governed

What each package's checker judges: that package's own `CHECKS.md` or `--help`. What the offer commits: [engine.md § The commit offer](engine.md#the-commit-offer).
