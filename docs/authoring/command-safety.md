# Command safety hook

The `command-safety` bundle refuses recognized whole-environment reads in submitted shell command text unless a proven direct pipe filters named variables. It also refuses supported relative destructive targets reachable after a failed directory change in a flat literal command list, a download a shell or interpreter runs as its program, an upload to a host the project does not list and a push to a remote the repository does not have. It applies a project command pattern and offers an opt-in Git history policy. The bundle includes the hook and the commit-guards settings loader. It classifies submitted commands without reading a desktop session or process list.

Install the `command-safety` bundle; its environment-dump check needs no setting and cannot be disabled by the project pattern. The pattern defaults to the host-safety rule below. To replace that pattern, set `COMMAND_SAFETY_DENY_PATTERN` in `kendex.settings.toml` under `[env]`, or in the install with `kendex add --bundle command-safety --setting COMMAND_SAFETY_DENY_PATTERN=<pattern>`; the bundle's commit-guards skill declares the key. The value is a nonempty POSIX extended regular expression. The shared settings grammar and precedence are documented in [the commit-guards skill](../../skills/commit-guards/SKILL.md#configuration).

Claude Code, Codex, Gemini CLI, and GitHub Copilot execute the hook. Pi executes it while the `pi-hooks` carrier is registered. Cursor and OpenCode install advisory instructions instead of an executable check. Antigravity executes hooks but does not receive this one: it sends the command as `toolCall.args.CommandLine`, not the `tool_input` this hook reads, and a hook reaches Antigravity only by naming it in its `harnesses` line.

The fixed check recognizes unnamed `env` and `printenv` reads, `export -p`, bare `set`, `declare` and `typeset` with no name (bare, after `--`, with only `-g` or `-I`, or with only those flags and expanding words that name no variable, such as `"$@"` or `"$opt"`, which can expand to an option or to no word; only a word that starts with a literal name, alone or before `=` or `+=`, such as `FOO="$x"`, names one), unnamed `declare -p`, `declare -x` and `typeset -x`, `systemctl show-environment` with or without `--user`, and unnamed `tmux show-environment` or `showenv` reads with `-g`, `-s` or `-t TARGET`. A tmux read naming one literal variable passes. Unknown tmux options before the verb refuse; `-s` output cannot gain filter permission because it emits shell statements. A `/proc/*/environ` input redirect to any program other than `cat`, `strings`, `tr` or `xargs` also refuses, because a shell or a reader of its descriptors can print it. Read a named variable with `printenv NAME`, or use a direct pipe such as `systemctl --user show-environment | grep '^NAME='`. Direct `grep NAME` and `grep -E '^(A|B)='` filters pass only for proven newline records. A raw NUL read must use the literal NUL-to-newline tr stage before named grep. Default xargs output joins the entries onto one line and cannot gain that permission. Grep modes that change record framing, unknown producer options and unproved transformations cannot approve a dump. `env NAME=value command` is a launcher; its target is checked separately. `--` ends env options while following assignments remain assignments. A `-u`, `--unset`, `-C` or `--chdir` operand that is not literal, such as `"$@"`, can expand to no word and refuses.

The hook requires a literal property selection before the `systemctl show` verb, as in `systemctl --user --property=ActiveState show -- UNIT`. Systemctl versions differ on whether they apply options after the verb. The hook refuses environment properties and execution command properties that can carry assignments. It also refuses `systemctl status`, whose process and journal output can contain environment values, and raw unit configuration from `systemctl cat`. The same property check covers recognized systemd D-Bus queries. The hook refuses manager dumps and value-bearing introspection. For process reads, it checks procfs environment file operands, recognized file input options, and input redirects. This includes relative paths under a literal working directory supplied by the payload, an earlier flat shell directory change, or the reader's env chdir option. A `cd`, `pushd` or `popd` the check does not follow leaves the directory unknown for every relative `environ` read in the command, before or after it, except a read under an absolute env chdir, so `builtin cd /proc/self; env -C /tmp cat environ` passes. The check follows only a literal `cd` destination at the head of a stage, not a `cd` after a reserved word such as `do` or `then`, so `builtin cd /proc/self && cat environ`, `pushd /proc/self && cat environ`, `cd -P /proc/self && cat environ`, `cd "$DIR" && cat environ` and `for i in 1; do cd /proc/self; done; cat environ` refuse. A loop can run a later `cd` before an earlier read, and a `{ }` function body runs where it is called. So the check does not follow a `cd` after a relative `environ` read that a command inside reserved-word syntax makes directly, as its operand, file option or input redirect, in a stage that neither opens nor closes that syntax, and `while :; do cat environ; cd /proc/self; done` refuses. A `cd` in text that `eval`, `source` or `.` runs moves the shell that runs that text, so `eval 'cd /proc/self'; cat environ` refuses. A shell's command string runs in a child, so `bash -c 'cd /proc/self'; cat environ` passes. In a command with a word that names `CDPATH`, a `cd` whose operand is relative with a first component other than `.` or `..` is not followed either: `cd` searches CDPATH for such an operand first, so `CDPATH=/proc; cd self && cat environ` refuses. Deferred shell input inherits the reaching command's directory. Shell redirects still use the shell's own directory. The hook checks xargs file options before the child executable and uses the child's argument rules after it. Search patterns stay data. The hook also refuses `ps` environment flags. An `e` option can expose values under BSD or legacy personalities, including when written with a dash. Use a process metadata query such as `ps -A -o pid,comm`.

The fixed check judges a word only where the shell runs it. Elsewhere a word is data: an argument, a quoted example, a redirect target, a loop list, a function name or a case pattern. The executable positions are the command head of each stage, the forwarded operands of a shell or `source` script, of `orch-runtime launch-job`, of a shell or `env -S` command string, of `exec` and of `builtin`, the command string a shell, `eval` or `env -S` runs, and literal input. The same producer grammar decides every position. A reserved word selects the next command head. Reserved-word syntax, a subshell, a substitution or a heredoc anywhere in the command removes filter permission from every dump in it, so `if true; then :; fi; env | grep '^NAME='` refuses.

The check reads ordinary literal quoting, supported env, command and sudo prefixes, and direct pipe and list boundaries; `|&` is a pipe. Command heads can also use literal dollar quotes and mixed or adjacent quote fragments in the C locale. A command head with a backslash in an ANSI-C dollar quote refuses; the check does not decode those escapes. A known producer argument with such an escape, such as `systemctl $'show-\x65nvironment'`, also refuses. These refusals add `command-safety: reason=undecoded-ansi-escape` under the keyed line: decode the escape, or pass the value as a literal argument. A dollar-quoted grep pattern or `printenv` name keeps its conservative handling, so `env | grep $'^NAME='` refuses. An ANSI-C escaped word outside these positions, the shell source and the stage input below, is data.

Waiter launchers run forwarded argv as a command. Each operand after the script operand of a shell or `source`, each word after `orch-runtime launch-job`, each word after a shell's command string, which the string can run as `$0` or `"$@"`, and each word after `exec` or `builtin`, is judged as a possible command head beside its own operands. `exec` and `builtin` take no option grammar. So `bash wrapper.sh env -i NAME=value command-name` launches `command-name` and passes, while `bash wrapper.sh env`, `bash wrapper.sh cat ~/.fleet/env`, `source wrapper.sh env` and `sh -c '"$@"' _ env` refuse. A quoted operand past the forwarded program is also parsed as a command string, and after a shell command string so is every quoted operand, `$0` included, so `sh -c '$0' 'export -p'` refuses; neither holds when the launcher stage redirects its output. That includes a double-quoted operand that expands a variable, so `--test "cd $DIR && env"` refuses, and so does `--test "env -u $NAME bash test.sh"`, whose unset operand can expand to no word. Inside that forwarded text, a stage the producer cannot classify, and a body that holds heredocs, refuse on any known producer name. One quoted operand of a three-word `bash` script invocation stays data.

A shell `-c` string, an `eval` join and an `env -S` string use the existing shell-source decoder. For a supported literal `env -S` prefix, the decoder appends the invocation's later arguments with their original word kinds and boundaries before selecting the executable. Those tail arguments are not joined into shell text. The selected program owns any forwarding: a shell `-c` still receives positional arguments, while Git receives its global operands and subcommand together. `eval` takes one leading `--`. A non-literal `eval` word can expand to nothing, to options or to several words, so such a join also refuses when any word in it names a producer, as `eval "$PREFIX" "printenv NAME"` does, and `eval "$PREFIX" "printf done"` passes. Shell options that group two `o` or `O` letters cannot be counted, so every later word is parsed as source. A shell option word that is not literal, such as `"$MODE"`, can expand to `-c`, so the word after it is parsed as source too. Parsed source never grants filter permission, so `bash -c 'env | grep NAME'` refuses.

A shell, `eval` or `source` runs every registered heredoc body and here-string it gets, including non-stdin descriptors. Each body is parsed alone, so quotes in one body cannot hide another. A Python, Node, Ruby or Perl interpreter at a stage's own head judges its heredoc bodies and quoted inline programs using its own whole-environment pattern, rather than shell builtin names. Whole os.environ, whole process.env, Ruby ENV.to_h or ENV.each and Perl %ENV refuse; named Python and Node reads remain permitted. A literal cat receiver of one quoted heredoc body is data, and so is a literal cat that writes one quoted body to a file. Every other heredoc body a cat or unknown receiver gets, an unquoted one included, is parsed alone as shell source. Input to `exec`, `builtin` or a stage of reserved words alone, such as `done <<'EOF'`, is parsed alone as shell source and also judged by the four interpreter patterns; so is piped input to such a stage, as in `cat <<'EOF' | exec python3`. Unquoted heredoc substitutions are checked independently. Missing body identifiers, unread registered bodies and undecoded escaped delimiters refuse. An ANSI-C escaped word judged as shell source, an `eval` join holding one included, refuses with `reason=undecoded-ansi-escape`, with no producer in it. So does one redirected as input, by a here-string or a descriptor, to a shell, `source`, `eval`, `exec`, `builtin`, script-operand or compound shell stage, even where that stage reads it as data: `while read -r a b; do :; done <<< $'x 1\ny 2'` and `{ cat; } <<< $'a\tb'` refuse, while `cat <<< $'a\tb'` is data. Piped, it refuses only for a shell, `source` or `eval` receiver; an `exec`, `builtin` or compound receiver reads it as data, so `cat <<< $'a\tb' | { cat; }` passes.

A grep in another list command does not permit a dump. A stdout redirect or an intermediate program such as tee cannot prove direct filtering. Nested dumps refuse even with an inner or outer grep. An unanchored `grep NAME` can also match NAME in a value; permitted filtering is not output redaction.

The check does not reach unseen programs, aliases, functions, PATH replacements or runtime-built names, or a command written to a file and run later. An unknown launcher such as `timeout 5 env` is not a recognized producer at a command head. The same holds inside reserved-word syntax, such as `if true; then timeout 5 env; fi`, as a quoted forwarded argument when the launcher stage redirects its output, and inside a body an unknown receiver gets. Here-string input is judged only where a shell, `eval` or `source` runs it or an `exec`, `builtin` or syntax-only stage gets it. Every other receiver's here-string is not judged, an unknown program's and a Python, Node, Ruby or Perl head's alike, so `ssh host <<< env` and `python3 <<< 'import os; print(os.environ)'` pass. In `declare` and `typeset`, an expanding option word after an attribute flag, such as `declare -r "$x"`, and a double-quoted command substitution or brace word, such as `declare "$(printf -- -p)"` or `declare {-p,}`, are not judged. A `trap` action word, such as `trap 'env' EXIT`, is shell source the check does not parse. An interpreter body that is forwarded or nested in shell source, such as `bash wrapper.sh python3 <<'EOF'` or `bash -c "python3 <<'EOF' ... EOF"`, is parsed as shell source but not judged by the interpreter patterns. Process substitutions, shell programs, transformed pipes and env split strings have no general interpretation guarantee.

The fixed check runs before cwd, Git and project settings. It also runs outside a Git worktree. An argument array keeps each argument; a pipe character in one argument does not establish a shell pipe. A missing payload reader or unreadable payload produces an advisory warning and allows the call.

The fixed targeting check reads flat literal shell lists separated by `;`, newlines, `&&` and `||`. It refuses a supported relative target when an earlier `cd DIR` or `cd -- DIR` can fail and execution can still reach that target. For example, `cd DIR; rm -rf X` and `cd DIR || true; git init` refuse with `command-safety: refused=relative-target`. `cd DIR && rm -rf X` and `cd DIR || exit 1; rm -rf X` gain no targeting refusal. Output redirects run before their command, so `cd DIR; exit 1 > .git/config` refuses, and a redirected exit cannot prove that failure stops the list. A prior failed directory change remains possible after a later `cd`, so `cd FIRST; cd SECOND && rm -rf X` also refuses. Use a success-dependent command, stop on failure, or name a verified literal absolute target. This check does not establish ownership of an absolute target.

Supported targets are flags-first recursive `rm` operands using `-r`, `-R`, `--recursive`, optional `-f` or `--force`, combined short flags and `--`; direct `git init` with its implicit `.` target or one literal path, optionally after `--`; and relative file targets of `>`, `>>`, `<>`, `&>` or `&>>` whose spelling has a `.git` component. The check includes stderr and redirection-only writes. A leading `/` makes a target absolute by spelling. An argument naming `.git/config`, an input read and a quoted command example are not write targets. No filesystem read proves path equivalence, symlinks or the intended directory. Bare unprefixed `true`, `false` and `:` supply their builtin status; a supported unredirected `exit` with zero or one numeric operand terminates its path. Other ordinary commands have unknown status.

Whole-source eligibility limits this new relation. A nested construct, substitution, assignment prefix, unknown or escaped word, forwarded source, unsupported invocation or operator leaves the submission without targeting proof. Any word with glob, brace or tilde punctuation is excluded even when quoted, because whole-word quote evidence cannot prove each fragment's protection. Shell bodies, `set -e`, conditionals, loops, `pushd`, prefixed `cd`, implicit `cd`, Git global options, other rm/init options and option permutation have no targeting guarantee. Literal argv operators stay data. Exclusion leaves every independent environment-dump check active; it does not certify that a submission is safe. Unreadable payloads retain the advisory behavior above. The targeting check, like the environment check, runs before cwd, Git and settings, including outside a worktree.

Native permission declarations match subcommands, argv prefixes or text patterns. They do not expose the preceding directory-change outcome together with a later target's execution condition. The existing pre-tool hook owns this bounded relation. The documented interfaces are [Claude Code permissions](https://code.claude.com/docs/en/permissions), [Codex rules](https://learn.chatgpt.com/docs/agent-configuration/rules), [Copilot tool permissions](https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli/allowing-tools) and [Gemini policies](https://geminicli.com/docs/reference/policy-engine/); Pi's existing hook carrier uses its blocking extension event.

An absent setting applies the shipped host-safety pattern, so a fresh install refuses a `systemd-run` memory cap measured in kilobytes or megabytes, quoted or not:

```text
(^|[^[:alnum:]_-])systemd-run[[:space:]][^&;|]*Memory(Max|High)=[[:punct:]]?[0-9]+[KkMm]([^[:alnum:]]|$)
```

A cap that small starved a build's cgroup into a kernel allocation failure inside a filesystem transaction, and the host's root volume went read-only. A cap in gigabytes, or a run with no cap, passes. A project that sets the key replaces this pattern, so its own pattern keeps this rule where it still wants it; `^$` turns only project-pattern matching off. The project-pattern part stays inactive outside a Git worktree. An explicitly empty value, invalid pattern, missing policy tool or unreadable setting produces one keyed warning and allows that pattern check. These conditions do not disable the earlier fixed check.

A malformed value on any `[env]` key produces one keyed warning and leaves both project checks unavailable, not only a malformed pattern. The settings loader reads the file whole, like every kendex settings reader, so a policy read past the bad line would come from a file the rest of the toolchain rejects. The warning replays the loader's line naming the file, the line and the key to rewrite.

The project pattern matches tool command text both as received and with backslash-newline pairs removed. For that pattern alone, an argument array is joined with spaces. Quotes and comments remain text, so a matching literal example is also refused. Put isolated validation behind a script whose invocation does not match the pattern.

For a Quickshell project, this example blocks direct `qs -c vshell`, `qs -p quickshell/vshell`, and `pkill quickshell` calls. It allows `scripts/validate qml`.

```toml
[env]
COMMAND_SAFETY_DENY_PATTERN = "(^|[[:space:];|&])qs[[:space:]]+(-c[[:space:]]+vshell|-p[[:space:]]+quickshell/vshell)([[:space:];|&]|$)|(^|[[:space:];|&])pkill([[:space:]]+-[^[:space:];|&]+)*[[:space:]]+quickshell([[:space:];|&]|$)"
```

Missing settings support produces one keyed warning and leaves both project checks unavailable because the hook cannot determine whether a policy exists. Repair the installed commit-guards support. Keep the pattern specific to the commands the project must prohibit. The hook does not classify commands hidden inside scripts.

## Downloads, uploads and pushes

These three refusals stop the ways an injected instruction turns into remote code, sent data or pushed code. They read the text a shell runs, as the environment check does: the command itself, a command string a shell or `eval` runs, the forwarded operands of a shell or `source` script, `exec` and `builtin`, and a body a shell reads as its input. A body that an unknown receiver gets, such as `git commit -F - <<'EOF'`, is data to these checks, so a commit message or a pull request body that quotes one of these commands passes.

The download refusal, `command-safety: refused=download-into-shell`, applies to `curl` or `wget` output that a shell or interpreter runs as its program. The line under it names the form. `form=pipe` is a download piped to a later stage of the same pipeline whose program runs its input: a shell with no command string and no script, or with `-s`, `source /dev/stdin`, or Python, Node, Ruby or Perl with no inline program and no script, or with `-`. A script operand of `/dev/stdin`, `/dev/fd/0` or `/proc/self/fd/0` runs the input too. An interpreter option can take the next word as its argument, so a script operand counts only when no option comes before it. Python's `-c` and `-m`, Node's `-e`, `--eval`, `-p` and `--print`, and Ruby's and Perl's `-e` name the program the interpreter runs instead. A subshell that reads the pipe counts when any stage in it runs its input, a brace group only when its first command does, and a command that carries the download in a substitution counts as the download. `curl URL | sh`, `curl URL | tee log | sudo bash -s`, `curl URL | exec bash`, `curl URL | python3 -W ignore -`, `curl URL | (sh)` and `echo "$(curl URL)" | sh` refuse. `form=substitution` is a download in `$(...)`, backticks or `<(...)` that a shell, `eval`, `source` or interpreter takes as its program: its command string, its script or its input. `bash <(curl URL)`, `sh -c "$(curl URL)"`, `eval "$(curl URL)"` and `sh <<< "$(curl URL)"` refuse. A download that becomes data passes, as in `curl URL | jq .`, `curl URL | python3 -m json.tool`, `curl URL | bash script.sh` and `bash script.sh "$(curl URL)"`. Save the download to a file, read it, then run the file in a separate command: `curl -fsSLo install.sh URL && sh install.sh` passes.

The upload refusal, `command-safety: refused=upload-host`, applies to a command that sends local data: `curl -T` or `--upload-file`, a `curl` data option (`-d`, `--data`, `--data-ascii`, `--data-binary`, `--json`) or `-H`/`--header` whose value starts with `@`, `--data-urlencode`, `--url-query` or `--variable` with `name@file` or `@file`, `-F` or `--form` with `=@` or `=<`, `wget --post-file` or `--body-file`, and `scp` or `rsync` whose last operand is a remote. A long option also counts in its `--name=value` form. Each destination host must be in `COMMAND_SAFETY_UPLOAD_HOSTS`, a whitespace-separated list of host names under `[env]` in `kendex.settings.toml`, compared without case. The default is empty, so every upload refuses until the project lists its hosts. The host is the one the URL's authority names: a scheme counts only at the start, and text in its path or query does not name the host. For `scp` and `rsync` it is the part before the first colon, or a bracketed IPv6 address at the start or right after the user's `@`, as OpenSSH 9.6 scp reads it; a bracket in the remote file name does not name the host. The line under the refusal is `host=<host>`. It is `reason=unresolved-host` where the command can choose the host: an expansion, substitution or glob in the host part, a quote, backslash or space left in it after shell decoding (so `https://evil."example"/a` names `evil.example`), an unquoted expanding operand, no URL, a curl proxy, `--resolve`, `--connect-to`, `--doh-url`, socket or `-K` config option, a curl `--expand-` option, wget `-e`, `--config`, or `-i` or `--input-file`, which read more URLs from a file, scp `-F`, `-J`, `-S` or an ssh option that names a host name or proxy, or an rsync `-e` command that does. So is an assignment before the program word, `NAME=value` or `NAME+=value`, as a prefix or an `env` or `sudo` operand, such as `http_proxy=`, `ALL_PROXY=`, `CURL_HOME=`, `HOME=` or `RSYNC_RSH=`, or before the `exec`, `builtin`, `eval`, shell or script that runs the program: each program reads proxy variables, a config file or its remote shell from its environment, so `http_proxy=http://proxy.example:3128 curl -T notes.txt https://uploads.example.com/a`, `http_proxy=$(cat proxy.txt) curl -T notes.txt https://uploads.example.com/a` and `http_proxy=http://proxy.example:3128 exec curl -T notes.txt https://uploads.example.com/a` refuse with a listed host. That refusal adds the line `cause=assignment`. curl and wget take a unique prefix of a long option, so an option that is not spelled in full and begins a sending or routing option, such as `--upload-fi` or `--resol`, refuses with this reason too. A `curl` request with inline data, such as `-d '{"query":"..."}'`, is not an upload. Outside a Git worktree no project file answers, so only an exported `COMMAND_SAFETY_UPLOAD_HOSTS` lists hosts. Unreadable settings or commit-guards support leave this check unavailable, under the warning the project pattern gets.

The push refusal, `command-safety: refused=push-remote`, applies to a `git push` that names its repository, as an operand or with `--repo`, and to any push whose command sets a repository option or Git configuration. Any assignment the hook sees reaching a push refuses, whatever its name. This covers command prefixes, launcher operands and assignments in recognized `export`, `declare -x` or `typeset -x` statements earlier in the same shell. The push and its pre-push hook inherit these assignments, which can change their credentials or configuration. The refusal names the assigned variables. For GitHub authentication, use the github skill's `git-https-auth push origin HEAD` to keep push authority in the credential-helper child. The repository must have the destination as a remote: a remote name, or a URL that `git remote -v` lists, given as written or as `url.<base>.insteadOf` rewrites it. A path is not a remote, so `git push . HEAD:main` refuses. Git keeps no other record of where a repository pushed: a push to a URL writes no ref and no log. A push with none of these and no repository operand goes to a configured remote and passes. The line under the refusal is `remote=<operand>`. It is `reason=unresolved-remote` where the command can choose where the push goes: an expanding or substituted operand, a substitution before the operand, a long option that is not one `git push -h` lists in full, such as the abbreviation `--exe`, a `-c` or `--config-env` setting, `--exec-path`, an assignment reaching the push, an inline alias or include, or a `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_`, `GIT_CONFIG_VALUE_` or `GIT_CONFIG_PARAMETERS` assignment, which Git reads as inline configuration, each of which can make any word a push, or a `git remote` or `git config` anywhere in the same command that can change where the push goes. That refusal adds the line `cause=remote-change`, and it applies to every push of the command, one with no repository operand included. A `git config` that can define an alias, one whose key or rename-section target names an `alias` or `include` key or section, one that opens an editor, or one with a word the check cannot read where an option or the key can stand, makes every other `git` word of the command a push, so `git config alias.p "push URL HEAD" && git p` refuses with that cause; a value after a literal key cannot, so `git config user.email "$EMAIL" && git commit -m x` passes. That `git remote` is any but the listing, `show`, `get-url`, `add` and the fetch-side `prune`, `update`, `set-head` and `set-branches`. That `git config` is any but a read: the `get` or `list` subcommand, a read action such as `--get` or `-l` among the options before the first operand, or one operand and no action, as in `git config user.name`. Git stops reading options at the first operand and gives an option such as `--comment` the next word, so `git config remote.origin.pushurl URL --get` and `git config --comment --get remote.origin.pushurl URL` write. A loop can run such a change before the push, so its place in the command does not matter: `git remote set-url --push origin URL && git push origin HEAD`, `git config remote.origin.pushurl URL && git push origin HEAD` and `git config remote.origin.pushurl URL && git push` refuse. It is `reason=unresolved-repository` where the check cannot settle the repository: a `-C` it cannot read, such as `git -C "$WORKTREE" push`, a word it cannot read where a Git global option can stand, when the first literal word after it that is no option or option argument is `push`, such as `git $OPTS push` or `git $OPTS -C . push`, any `--git-dir` or `--work-tree`, a `GIT_DIR`, `GIT_WORK_TREE` or `GIT_COMMON_DIR` assignment, a `cd` whose operand is not one literal word, a `cd` a launcher runs, such as `builtin cd DIR`, any `cd` in text that `eval`, `source` or `.` runs in the same shell, such as `eval cd DIR` or `source /dev/stdin <<< 'cd DIR'`, but not one in a shell's command string or input, such as `bash -c 'cd DIR'`, which runs in a child, `pushd` or `popd`, a `cd` after a reserved word, such as `then cd DIR`, a `cd` after a relative `environ` read that the process-read check does not follow, a relative `cd` operand whose first component is not `.` or `..`, such as `src` or `.hidden`, in a command with a word that names `CDPATH`, since cd searches CDPATH for it first, such as `CDPATH=/srv; cd src && git push origin HEAD`, a `cd`, `env -C` or `git -C` operand that starts with an unquoted `~`, which the shell expands against a `HOME` the command can set first, such as `cd ~/repo && git push origin HEAD`, or a directory that is not in a Git work tree when the hook runs, which a clone or init earlier in the command can create. It is `reason=unreadable-repository` where the directory is in a Git work tree but `git remote -v` fails there, as on a configuration file Git cannot parse; Git's own words follow the refusal. The check judges the push in each directory it can run in: the payload directory moved by literal `cd` destinations and env's `-C`, then by the push's own `-C` chain. So `cd /other/repo && git push origin` refuses unless both repositories have `origin`. An absolute `git -C` operand settles the repository despite an unfollowed `cd`, so `builtin cd DIR; git -C /srv/repo push origin HEAD` is judged in `/srv/repo`. A word named `git` after a launcher the hook does not resolve, such as `timeout 60 git push URL`, is judged as a push, and so is the same word as data, as in `echo git push fork`. A remote added in the same command, as in `git remote add backup URL && git push backup`, refuses; a remote an earlier command added is one the repository has.

A stage, one command of a pipeline, holds a transfer when a literal word in it names `curl`, `wget`, `scp` or `rsync`, or names `git` with a later literal `push`; each such word is judged as that program's command, after a launcher such as `timeout 60` too. A stage is plain when it has only literal words, with no expansion, substitution, glob, brace or line continuation, stands in no group, subshell, substitution or compound command, and sits in a pipeline whose every stage is plain. A newline after a pipe leaves an empty stage, which is not plain. The refusals above read the forms they name, substitutions, groups and expansions included, and refuse them. So what refuses is a form one of those checks reads, in any stage; the plain-stage rule refuses nothing. A command they pass that holds a transfer in a stage that is not plain only gets a report, from that rule: the hook writes `command-safety: report=plain-stage`, then one `command-safety: would=<check> program=<program> cause=<cause>` line for the check that would refuse the stage if the rule enforced: `upload-host` when its curl or wget sends local data and for any scp or rsync, `push-remote` when it holds a push, and `download-into-shell` for any other curl or wget. The cause is `expansion`, `glob`, `continuation`, `nesting` for a substitution or subshell, `compound` for a brace group, a compound command or a reserved word, `empty-stage` or `undecoded-split`, with a `pipeline-` prefix when another stage of the pipeline carries it. So `{ curl URL; } | sh`, `if true; then curl URL; fi | sh`, `curl URL | { read -r x; sh; }`, whose brace group runs its shell after its first command, `F=-C; git $F . push URL`, where the unread word takes `.` as its argument and the check reads `.` as the subcommand, a download piped across a line break, an upload to a listed host or a push to a known remote inside a compound command or split by a line continuation, `curl -s "$URL" | jq .`, `x=$(curl -s URL)` and `git push origin "$(git branch --show-current)"` pass with a report. A refused command gets no report.

To run one of these three refused commands on purpose, the owner starts the session with `COMMAND_SAFETY_OWNER_COMMAND` set to the exact command text. The hook reads the variable only from its own process environment, which the harness passes from the environment the session started with. A settings file does not set it, because the session can write that file. A command with a word that names the variable refuses with `command-safety: refused=owner-command`, except where that word is an argument of `grep`, `rg` or `cat`, which search or print it. A `sed` script can run a command or write a file, so a `sed` word that names the variable refuses. So a search such as `grep -rn COMMAND_SAFETY_OWNER_COMMAND docs` passes, and a commit message that names the variable goes in a file or a quoted heredoc body. The exception covers these three refusals only.

These checks read submitted text, like the environment check. They do not refuse a receiver behind a launcher the hook does not resolve, such as `curl URL | timeout 60 bash` or `timeout 60 bash <<'EOF'`, a download passed on through a variable, such as `x=$(curl URL); sh -c "$x"`, an output substitution, such as `curl URL > >(sh)`, or a substitution a forwarded shell takes, such as `exec bash -c "$(curl URL)"`; the plain-stage rule reports the last three, whose download stands in a substitution. They do not reach a host alias in an ssh config file, Git configuration an earlier command or a file write sets, such as `>> .git/config`, `GIT_` variables or aliases an earlier command or file sets, a proxy variable or config file an earlier command exports or writes, an `export`, `declare -x` or `typeset -x` of such a variable before an upload in the same command, as in `export http_proxy=URL; curl -T notes.txt URL`, the commands inside a sourced script or a script file, a CDPATH the session's shell already holds, an alias that a configuration file a variable assigned before `git` names, such as `GIT_CONFIG_GLOBAL` or `HOME`, defines, other upload programs, a program name built at runtime, or the owner's variable set by a script or a name built at runtime. A program that makes its own network calls, such as a Python or Node script, an SDK or an interpreter given a file, sends data these checks never see: the upload refusal covers curl, wget, scp and rsync where the command names them, and is no boundary for such a program.

## Git history policy

Set `COMMAND_SAFETY_HISTORY_POLICY = "no-lazy-fetch"` under `[env]` in `kendex.settings.toml` to select the native Git fence. An absent value or `off` preserves ordinary history reads. Selection uses the same settings loader as the project pattern. The hook does not detect partial clones or change clone, promisor, fetch or update configuration. The selected policy applies within the Git-project settings boundary, including full clones.

Each reached `log`, `show`, `whatchanged`, `rev-list`, `diff`, `diff-tree`, `diff-index`, `diff-files`, `range-diff`, `format-patch` or `cherry` invocation requires the exact literal global `--no-lazy-fetch` before its subcommand. Metadata-only log and worktree-only diff need the same fence. Counts, refs, paths, formats and `GIT_NO_LAZY_FETCH=1` alone grant no exception. For bounded commit inspection, use `git --no-lazy-fetch log -1 --oneline HEAD` or `git --no-lazy-fetch show HEAD`. With Git 2.45.1 or later, Git reads local objects or fails without fetching missing objects on demand.

Use Git 2.45.1 or later before selecting this policy. [Git 2.45.0](https://github.com/git/git/blob/v2.45.0/git.c) adds the option, and upstream Git 2.44.0 rejects it. In 2.45.0 the option does not stop a diff's blob prefetch. For patch, stat and pickaxe output, [`diffcore_std`](https://github.com/git/git/blob/v2.45.0/diff.c) runs `diff_queued_diff_prefetch`, which calls `promisor_remote_get_direct`, and that release's [`fetch_objects`](https://github.com/git/git/blob/v2.45.0/promisor-remote.c) starts the fetch without reading the fence. In [Git 2.45.1](https://github.com/git/git/blob/v2.45.1/promisor-remote.c), `fetch_objects` returns before fetching while `GIT_NO_LAZY_FETCH` is set, and the option sets it. So 2.45.1 is the earliest upstream release where the fence holds for that diff output. Vendor backports are unknown. This opt-in cost adds no kendex engine minimum version. Source evidence alone does not prove an installed build or a consumer's missing-blob behavior.

The existing executable-argument matcher selects the Git invocation. Supported prefixes, nested shell source and forwarded arguments keep their existing reach and limits described above. A quoted example, an option operand, a path, an option after the subcommand or an unrelated later command supplies no native fence. An unknown or expanding Git global option position refuses under selection because it cannot establish the subcommand boundary. A launcher the matcher does not resolve, such as `timeout 5` or `nice -n 5`, can run any later word as its command, and a word named `git` can also be the launcher's own operand, as in `doas -u git git log -p`. Under selection, every literal word named `git` after such a head, by name or path, is judged as a Git invocation. So `timeout 5 git log -p --all`, `doas -u git git log -p` and `runuser -u git -- git log -p` refuse, and `timeout 5 git --no-lazy-fetch log -1 HEAD` and `runuser -u git -- git --no-lazy-fetch log -p` pass. Git refuses every global option the hook does not list, `--` included, so such a word followed by one of those options runs no Git read and its judgment ends there, as in `grep -rn git -- .` or `log --grep git --oneline`. The same word as data refuses when a history subcommand name or an expanding word follows it, as in `echo git log`, `man git log` or `grep git "$file"`. Quoting the single word `git` does not help. For a command that is not a Git read, reorder the operands, as in `grep -rn -- git .`, write the text as one word, as in `echo 'git log'`, name the page as `git-log`, or match with a pattern such as `'gi[t]'`. Shell, `eval` and `source` operands keep their own source and forwarding rules. A command string a launcher hands to a shell, such as `timeout 5 bash -c 'git log -p'`, is not judged: the hook recognizes only the launcher options it lists, so it cannot tell that string from the launcher's own operands. Launch Git directly instead, as in `timeout 5 git --no-lazy-fetch log -p`. Unseen programs, aliases and runtime-built executable names remain outside the guarantee.

Inside a worktree, that project's selection judges every reached invocation, including one whose `-C` names another repository. Outside any worktree, a refused invocation's `-C` chain names its project. Git resolves the chain from the hook's payload working directory, once the hook has expanded a leading `~`, alone or before `/`, against `HOME` where the shell does: when no byte before that `/` is quoted or escaped, as in `~/project` or `~/"My Repo"`. The policy of the resulting worktree judges the invocation. An exported `COMMAND_SAFETY_HISTORY_POLICY` overrides that project's file, as it does for every setting. So `git -C /path/to/clone log -p --all` refuses there when the clone's project selects the policy. The project pattern stays inactive outside a worktree. Wherever the payload stands, the hook loads its settings support from its own installation, never from the payload directory or a `-C` target: the harness root's `skills/`, then a project install's `.agents/skills`, then `~/.agents/skills`, where a global install keeps it, including one whose harness home `CODEX_HOME`, `COPILOT_HOME` or `PI_CODING_AGENT_DIR` moves. Where none holds it, the hook warns with `settings=no-loader`. Outside a worktree, these name no project whose settings the hook can read, so they are not judged:

- an invocation with no `-C`, or with a `-C` target in no worktree
- one that names its repository only by `--git-dir`, `--work-tree` or `GIT_DIR`
- a chain holding an expanding word, such as `"$REPO"`, a glob, `~user` or a quoted tilde prefix such as `"~"/repo`, or cut off before the subcommand by an expanding word or an option Git refuses
- a relative chain in a command that changes directory with `cd`, `pushd` or `popd`, wherever it stands, since a loop can run that change first
- a target whose settings cannot be read, which warns with `settings=unreadable` once every other target is judged

A launcher's own directory option, such as `sudo -D` or env's `-C` and `--chdir`, is resolved as if it were absent: the hook resolves a chain from the payload directory and follows no launcher's directory change. Name the repository in Git's own `-C` instead, as in `sudo -u builder git -C /path/to/clone log -p`.

History refusal uses `command-safety: refused=history-policy`, followed by `reason=missing-no-lazy-fetch` or `reason=unresolved-git-argv`. The fixed environment check still runs first. History admission runs before the independent project pattern, so `^$` or an invalid pattern cannot clear a history refusal. A fenced read can still match the project pattern.

An empty or unknown history value reports `settings=invalid-history-policy` and leaves this check unavailable while the project pattern still runs. Unreadable payloads, support or settings retain the advisory warning-and-allow contract; none proves protection. Consumer enablement and private-guard removal require the consumer owner's installation and actual supporting-Git evidence.
