# Command safety hook

The `command-safety` bundle refuses recognized whole-environment reads in submitted shell command text unless a proven direct pipe filters named variables. It also refuses supported relative destructive targets reachable after a failed directory change in a flat literal command list, applies a project command pattern, and offers an opt-in Git history policy. The bundle includes the hook and the commit-guards settings loader. It does not inspect a desktop session or process list.

Install the `command-safety` bundle; its environment-dump check needs no setting and cannot be disabled by the project pattern. The pattern defaults to the host-safety rule below. To replace that pattern, set `COMMAND_SAFETY_DENY_PATTERN` in `kendex.settings.toml` under `[env]`, or in the install with `kendex add --bundle command-safety --setting COMMAND_SAFETY_DENY_PATTERN=<pattern>`; the bundle's commit-guards skill declares the key. The value is a nonempty POSIX extended regular expression. The shared settings grammar and precedence are documented in [the commit-guards skill](../../skills/commit-guards/SKILL.md#configuration).

Claude Code, Codex, Gemini CLI, and GitHub Copilot execute the hook. Pi executes it while the `pi-hooks` carrier is registered. Cursor and OpenCode install advisory instructions instead of an executable check. Antigravity executes hooks but does not receive this one: it sends the command as `toolCall.args.CommandLine`, not the `tool_input` this hook reads, and a hook reaches Antigravity only by naming it in its `harnesses` line.

The fixed check recognizes unnamed `env` and `printenv` reads, `export -p`, bare `set`, `declare` and `typeset` with no name (bare, after `--`, with only `-g` or `-I`, or with only those flags and expanding words that name no variable, such as `"$@"` or `"$opt"`, which can expand to an option or to no word; only a word that starts with a literal name, alone or before `=` or `+=`, such as `FOO="$x"`, names one), unnamed `declare -p`, `declare -x` and `typeset -x`, `systemctl show-environment` with or without `--user`, and the supported reads of `/proc/*/environ`. A `/proc/*/environ` input redirect to any program other than `cat`, `strings`, `tr` or `xargs` also refuses, because a shell or a reader of its descriptors can print it. Read a named variable with `printenv NAME`, or use a direct pipe such as `systemctl --user show-environment | grep '^NAME='`. Direct `grep NAME` and `grep -E '^(A|B)='` filters pass only for proven newline records. A raw NUL read must use the literal NUL-to-newline tr stage before named grep. Default xargs output joins the entries onto one line and cannot gain that permission. Grep modes that change record framing, unknown producer options and unproved transformations cannot approve a dump. `env NAME=value command` is a launcher; its target is checked separately. `--` ends env options while following assignments remain assignments. A `-u`, `--unset`, `-C` or `--chdir` operand that is not literal, such as `"$@"`, can expand to no word and refuses.

The fixed check judges a word only where the shell runs it. Elsewhere a word is data: an argument, a quoted example, a redirect target, a loop list, a function name or a case pattern. The executable positions are the command head of each stage, the forwarded operands of a shell or `source` script, of a shell or `env -S` command string, of `exec` and of `builtin`, the command string a shell, `eval` or `env -S` runs, and literal input. The same producer grammar decides every position. A reserved word selects the next command head. Reserved-word syntax, a subshell, a substitution or a heredoc anywhere in the command removes filter permission from every dump in it, so `if true; then :; fi; env | grep '^NAME='` refuses.

The check reads ordinary literal quoting, supported env, command and sudo prefixes, and direct pipe and list boundaries; `|&` is a pipe. Command heads can also use literal dollar quotes and mixed or adjacent quote fragments in the C locale. A command head with a backslash in an ANSI-C dollar quote refuses; the check does not decode those escapes. A known producer argument with such an escape, such as `systemctl $'show-\x65nvironment'`, also refuses. These refusals add `command-safety: reason=undecoded-ansi-escape` under the keyed line: decode the escape, or pass the value as a literal argument. A dollar-quoted grep pattern or `printenv` name keeps its conservative handling, so `env | grep $'^NAME='` refuses. An ANSI-C escaped word outside these positions, the shell source and the stage input below, is data.

Waiter launchers run forwarded argv as a command. Each operand after the script operand of a shell or `source`, each word after a shell's command string, which the string can run as `$0` or `"$@"`, and each word after `exec` or `builtin`, is judged as a possible command head beside its own operands. `exec` and `builtin` take no option grammar. So `bash wrapper.sh env -i NAME=value command-name` launches `command-name` and passes, while `bash wrapper.sh env`, `bash wrapper.sh cat ~/.fleet/env`, `source wrapper.sh env` and `sh -c '"$@"' _ env` refuse. A quoted operand past the forwarded program is also parsed as a command string, and after a shell command string so is every quoted operand, `$0` included, so `sh -c '$0' 'export -p'` refuses; neither holds when the launcher stage redirects its output. That includes a double-quoted operand that expands a variable, so `--test "cd $DIR && env"` refuses, and so does `--test "env -u $NAME bash test.sh"`, whose unset operand can expand to no word. Inside that forwarded text, a stage the producer cannot classify, and a body that holds heredocs, refuse on any known producer name. One quoted operand of a three-word `bash` script invocation stays data.

A shell `-c` string, an `eval` join and an `env -S` string use the existing shell-source decoder. For a supported literal `env -S` prefix, the decoder appends the invocation's later arguments with their original word kinds and boundaries before selecting the executable. Those tail arguments are not joined into shell text. The selected program owns any forwarding: a shell `-c` still receives positional arguments, while Git receives its global operands and subcommand together. `eval` takes one leading `--`. A non-literal `eval` word can expand to nothing, to options or to several words, so such a join also refuses when any word in it names a producer, as `eval "$PREFIX" "printenv NAME"` does, and `eval "$PREFIX" "printf done"` passes. Shell options that group two `o` or `O` letters cannot be counted, so every later word is parsed as source. A shell option word that is not literal, such as `"$MODE"`, can expand to `-c`, so the word after it is parsed as source too. Parsed source never grants filter permission, so `bash -c 'env | grep NAME'` refuses.

A shell, `eval` or `source` runs every registered heredoc body and here-string it gets, including non-stdin descriptors. Each body is parsed alone, so quotes in one body cannot hide another. A Python, Node, Ruby or Perl interpreter at a stage's own head judges its heredoc bodies and quoted inline programs using its own whole-environment pattern, rather than shell builtin names. Whole os.environ, whole process.env, Ruby ENV.to_h or ENV.each and Perl %ENV refuse; named Python and Node reads remain permitted. A literal cat receiver of one quoted heredoc body is data, and so is a literal cat that writes one quoted body to a file. Every other heredoc body a cat or unknown receiver gets, an unquoted one included, is parsed alone as shell source. Input to `exec`, `builtin` or a stage of reserved words alone, such as `done <<'EOF'`, is parsed alone as shell source and also judged by the four interpreter patterns; so is piped input to such a stage, as in `cat <<'EOF' | exec python3`. Unquoted heredoc substitutions are checked independently. Missing body identifiers, unread registered bodies and undecoded escaped delimiters refuse. An ANSI-C escaped word judged as shell source, an `eval` join holding one included, refuses with `reason=undecoded-ansi-escape`, with no producer in it. So does one redirected as input, by a here-string or a descriptor, to a shell, `source`, `eval`, `exec`, `builtin`, script-operand or compound shell stage, even where that stage reads it as data: `while read -r a b; do :; done <<< $'x 1\ny 2'` and `{ cat; } <<< $'a\tb'` refuse, while `cat <<< $'a\tb'` is data. Piped, it refuses only for a shell, `source` or `eval` receiver; an `exec`, `builtin` or compound receiver reads it as data, so `cat <<< $'a\tb' | { cat; }` passes.

A grep in another list command does not permit a dump. A stdout redirect or an intermediate program such as tee cannot prove direct filtering. Nested dumps refuse even with an inner or outer grep. An unanchored `grep NAME` can also match NAME in a value; permitted filtering is not output redaction.

The check does not reach unseen programs, aliases, functions, PATH replacements or runtime-built names, or a command written to a file and run later. An unknown launcher such as `timeout 5 env` is not a recognized producer at a command head. The same holds inside reserved-word syntax, such as `if true; then timeout 5 env; fi`, as a quoted forwarded argument when the launcher stage redirects its output, and inside a body an unknown receiver gets. Here-string input is judged only where a shell, `eval` or `source` runs it or an `exec`, `builtin` or syntax-only stage gets it. Every other receiver's here-string is not judged, an unknown program's and a Python, Node, Ruby or Perl head's alike, so `ssh host <<< env` and `python3 <<< 'import os; print(os.environ)'` pass. In `declare` and `typeset`, an expanding option word after an attribute flag, such as `declare -r "$x"`, and a double-quoted command substitution or brace word, such as `declare "$(printf -- -p)"` or `declare {-p,}`, are not judged. A `trap` action word, such as `trap 'env' EXIT`, is shell source the check does not parse. An interpreter body that is forwarded or nested in shell source, such as `bash wrapper.sh python3 <<'EOF'` or `bash -c "python3 <<'EOF' ... EOF"`, is parsed as shell source but not judged by the interpreter patterns. Process substitutions, shell programs, transformed pipes and env split strings have no general interpretation guarantee.

The fixed check runs before cwd, Git and project settings. It also runs outside a Git worktree. An argument array keeps each argument; a pipe character in one argument does not establish a shell pipe. A missing payload reader or unreadable payload produces an advisory warning and allows the call.

The fixed targeting check reads flat literal shell lists separated by `;`, newlines, `&&` and `||`. It refuses a supported relative target when an earlier `cd DIR` or `cd -- DIR` can fail and execution can still reach that target. For example, `cd DIR; rm -rf X` and `cd DIR || true; git init` refuse with `command-safety: refused=relative-target`. `cd DIR && rm -rf X` and `cd DIR || exit 1; rm -rf X` gain no targeting refusal. Output redirects run before their command, so `cd DIR; exit 1 > .git/config` refuses, and a redirected exit cannot prove that failure stops the list. A prior failed directory change remains possible after a later `cd`, so `cd FIRST; cd SECOND && rm -rf X` also refuses. Use a success-dependent command, stop on failure, or name a verified literal absolute target. This check does not establish ownership of an absolute target.

Supported targets are flags-first recursive `rm` operands using `-r`, `-R`, `--recursive`, optional `-f` or `--force`, combined short flags and `--`; direct `git init` with its implicit `.` target or one literal path, optionally after `--`; and relative file targets of `>`, `>>`, `<>`, `&>` or `&>>` whose spelling has a `.git` component. The check includes stderr and redirection-only writes. A leading `/` makes a target absolute by spelling. An argument naming `.git/config`, an input read and a quoted command example are not write targets. No filesystem read proves path equivalence, symlinks or the intended directory. Bare unprefixed `true`, `false` and `:` supply their builtin status; a supported unredirected `exit` with zero or one numeric operand terminates its path. Other ordinary commands have unknown status.

Whole-source eligibility limits this new relation. A nested construct, substitution, assignment prefix, unknown or escaped word, forwarded source, unsupported invocation or operator leaves the submission without targeting proof. Any word with glob, brace or tilde punctuation is excluded even when quoted, because whole-word quote evidence cannot prove each fragment's protection. Shell bodies, `set -e`, conditionals, loops, `pushd`, prefixed `cd`, implicit `cd`, Git global options, other rm/init options and option permutation have no targeting guarantee. Literal argv operators stay data. Exclusion leaves every independent environment-dump check active; it does not certify that a submission is safe. Unreadable payloads retain the advisory behavior above. The targeting check, like the environment check, runs before cwd, Git and settings, including outside a worktree.

Native permission declarations match subcommands, argv prefixes or text patterns. They do not expose the preceding directory-change outcome together with a later target's execution condition. The existing pre-tool hook owns this bounded relation. The documented interfaces are [Claude Code permissions](https://code.claude.com/docs/en/permissions), [Codex rules](https://learn.chatgpt.com/docs/agent-configuration/rules), [Copilot tool permissions](https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli/allowing-tools) and [Gemini policies](https://geminicli.com/docs/reference/policy-engine/); Pi's existing hook carrier uses its blocking extension event.

An absent setting applies the shipped host-safety pattern, so a fresh install refuses a `systemd-run` memory cap measured in kilobytes or megabytes, quoted or not:

```text
(^|[^[:alnum:]_-])systemd-run[[:space:]][^&;|]*Memory(Max|High)=[[:punct:]]?[0-9]+[KkMm]([^[:alnum:]]|$)
```

A cap that small starved a build's cgroup into a kernel allocation failure inside a filesystem transaction, and the host's root volume went read-only. A cap in gigabytes, or a run with no cap, passes. A project that sets the key replaces this pattern, so its own pattern keeps this rule where it still wants it; `^$` turns only project-pattern matching off. The project-pattern part stays inactive outside a Git worktree. An explicitly empty value, invalid pattern, missing policy tool or unreadable setting produces one keyed warning and allows that pattern check. These conditions do not disable the earlier fixed check.

A malformed value on any `[env]` key produces one keyed warning and leaves both project checks unavailable, not only a malformed pattern. The settings loader reads the file whole, like every kendex settings reader, so a policy read past the bad line would come from a file the rest of the toolchain rejects. The warning replays the loader's line naming the file, the line and the key to rewrite.

The project pattern matches tool command text both as received and with backslash-newline pairs removed. For that pattern alone, an argument array is joined with spaces. Quotes and comments remain text, so a matching literal example is also refused. Put isolated validation behind a script whose invocation does not match the pattern.

For a Quickshell project, this example blocks direct `qs -c vshell`, `qs -p quickshell/vshell`, and `pkill quickshell` calls. It allows `scripts/validate qml`.

```toml
[env]
COMMAND_SAFETY_DENY_PATTERN = "(^|[[:space:];|&])qs[[:space:]]+(-c[[:space:]]+vshell|-p[[:space:]]+quickshell/vshell)([[:space:];|&]|$)|(^|[[:space:];|&])pkill([[:space:]]+-[^[:space:];|&]+)*[[:space:]]+quickshell([[:space:];|&]|$)"
```

Missing settings support produces one keyed warning and leaves both project checks unavailable because the hook cannot determine whether a policy exists. Repair the installed commit-guards support. Keep the pattern specific to the commands the project must prohibit. The hook does not classify commands hidden inside scripts.

## Git history policy

Set `COMMAND_SAFETY_HISTORY_POLICY = "no-lazy-fetch"` under `[env]` in `kendex.settings.toml` to select the native Git fence. An absent value or `off` preserves ordinary history reads. Selection uses the same settings loader as the project pattern. The hook does not detect partial clones or change clone, promisor, fetch or update configuration. The selected policy applies within the Git-project settings boundary, including full clones.

Each reached `log`, `show`, `whatchanged`, `rev-list`, `diff`, `diff-tree`, `diff-index`, `diff-files`, `range-diff`, `format-patch` or `cherry` invocation requires the exact literal global `--no-lazy-fetch` before its subcommand. Metadata-only log and worktree-only diff need the same fence. Counts, refs, paths, formats and `GIT_NO_LAZY_FETCH=1` alone grant no exception. For bounded commit inspection, use `git --no-lazy-fetch log -1 --oneline HEAD` or `git --no-lazy-fetch show HEAD`. On a supporting Git build, Git reads local objects or fails without fetching missing objects on demand.

Use Git 2.45.1 or later before selecting this policy. [Git 2.45.0](https://github.com/git/git/blob/v2.45.0/git.c) adds the option, and upstream Git 2.44.0 rejects it. In 2.45.0 the option does not stop a diff's blob prefetch. For patch, stat and pickaxe output, [`diffcore_std`](https://github.com/git/git/blob/v2.45.0/diff.c) runs `diff_queued_diff_prefetch`, which calls `promisor_remote_get_direct`, and that release's [`fetch_objects`](https://github.com/git/git/blob/v2.45.0/promisor-remote.c) starts the fetch without reading the fence. In [Git 2.45.1](https://github.com/git/git/blob/v2.45.1/promisor-remote.c), `fetch_objects` returns before fetching while `GIT_NO_LAZY_FETCH` is set, and the option sets it. So 2.45.1 is the earliest upstream release where the fence holds for that diff output. Vendor backports are unknown. This opt-in cost adds no kendex engine minimum version. Source evidence alone does not prove an installed build or a consumer's missing-blob behavior.

The existing executable-argument matcher selects the Git invocation. Supported prefixes, nested shell source and forwarded arguments keep their existing reach and limits described above. A quoted example, an option operand, a path, an option after the subcommand or an unrelated later command supplies no native fence. An unknown or expanding Git global option position refuses under selection because it cannot establish the subcommand boundary. A launcher the matcher does not resolve, such as `timeout 5` or `nice -n 5`, can run any later word as its command. Under selection, the first literal word named `git` after such a head, by name or path, is judged as a Git invocation. So `timeout 5 git log -p --all` refuses and `timeout 5 git --no-lazy-fetch log -1 HEAD` passes. The same word as data to a program, as in `echo git log`, also refuses; quote the text as one word, as in `echo 'git log'`. Shell, `eval` and `source` operands keep their own source and forwarding rules. A command string a launcher hands to a shell, such as `timeout 5 bash -c 'git log -p'`, is not judged: the launcher's own option grammar is unknown, so the hook cannot find its shell operand. Unseen programs, aliases and runtime-built executable names remain outside the guarantee.

Inside a worktree, that project's selection judges every reached invocation, including one whose `-C` names another repository. Outside any worktree, a refused invocation's `-C` operands name its project. Git resolves them in order from the working directory, as the read would, and the policy of the resulting worktree judges the invocation. An exported `COMMAND_SAFETY_HISTORY_POLICY` overrides that project's file, as it does for every setting. So `git -C /path/to/clone log -p --all` refuses there when the clone's project selects the policy. The project pattern stays inactive outside a worktree. An invocation outside a worktree with no `-C`, with a `-C` target in no worktree, or naming its repository only by `--git-dir`, `--work-tree` or `GIT_DIR` is not judged: it names no project whose settings the hook can read.

History refusal uses `command-safety: refused=history-policy`, followed by `reason=missing-no-lazy-fetch` or `reason=unresolved-git-argv`. The fixed environment check still runs first. History admission runs before the independent project pattern, so `^$` or an invalid pattern cannot clear a history refusal. A fenced read can still match the project pattern.

An empty or unknown history value reports `settings=invalid-history-policy` and leaves this check unavailable while the project pattern still runs. Unreadable payloads, support or settings retain the advisory warning-and-allow contract; none proves protection. Consumer enablement and private-guard removal require the consumer owner's installation and actual supporting-Git evidence.
