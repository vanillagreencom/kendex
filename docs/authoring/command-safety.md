# Command safety hook

The `command-safety` bundle refuses recognized whole-environment reads in submitted shell command text unless a proven direct pipe filters named variables. It also applies a project command pattern. The bundle includes the hook and the commit-guards settings loader. It does not inspect a desktop session or process list.

Install the `command-safety` bundle; its environment-dump check needs no setting and cannot be disabled by the project pattern. The pattern defaults to the host-safety rule below. To replace that pattern, set `COMMAND_SAFETY_DENY_PATTERN` in `kendex.settings.toml` under `[env]`, or in the install with `kendex add --bundle command-safety --setting COMMAND_SAFETY_DENY_PATTERN=<pattern>`; the bundle's commit-guards skill declares the key. The value is a nonempty POSIX extended regular expression. The shared settings grammar and precedence are documented in [the commit-guards skill](../../skills/commit-guards/SKILL.md#configuration).

Claude Code, Codex, Gemini CLI, and GitHub Copilot execute the hook. Pi executes it while the `pi-hooks` carrier is registered. Cursor and OpenCode install advisory instructions instead of an executable check. Antigravity executes hooks but does not receive this one: it sends the command as `toolCall.args.CommandLine`, not the `tool_input` this hook reads, and a hook reaches Antigravity only by naming it in its `harnesses` line.

The fixed check recognizes unnamed `env` and `printenv` reads, `export -p`, bare `set`, `declare` and `typeset` with no name (bare, after `--`, with only `-g` or `-I`, or with a non-literal word such as `"$@"` that can expand to no word), unnamed `declare -p`, `declare -x` and `typeset -x`, `systemctl show-environment` with or without `--user`, and the supported reads of `/proc/*/environ`. A `/proc/*/environ` input redirect to any program other than `cat`, `strings`, `tr` or `xargs` also refuses, because a shell or a reader of its descriptors can print it. Read a named variable with `printenv NAME`, or use a direct pipe such as `systemctl --user show-environment | grep '^NAME='`. Direct `grep NAME` and `grep -E '^(A|B)='` filters pass only for proven newline records. A raw NUL read must use the literal NUL-to-newline tr stage before named grep. Default xargs output joins the entries onto one line and cannot gain that permission. Grep modes that change record framing, unknown producer options and unproved transformations cannot approve a dump. `env NAME=value command` is a launcher; its target is checked separately. `--` ends env options while following assignments remain assignments. A `-u`, `--unset`, `-C` or `--chdir` operand that is not literal, such as `"$@"`, can expand to no word and refuses.

The fixed check judges a word only where the shell runs it. Elsewhere a word is data: an argument, a quoted example, a redirect target, a loop list, a function name or a case pattern. The executable positions are the command head of each stage, the forwarded operands of a shell or `source` script, of a shell or `env -S` command string, of `exec` and of `builtin`, the command string a shell, `eval` or `env -S` runs, and literal input. The same producer grammar decides every position. A reserved word selects the next command head. Reserved-word syntax, a subshell, a substitution or a heredoc anywhere in the command removes filter permission from every dump in it, so `if true; then :; fi; env | grep '^NAME='` refuses.

The check reads ordinary literal quoting, supported env, command and sudo prefixes, and direct pipe and list boundaries; `|&` is a pipe. Command heads can also use literal dollar quotes and mixed or adjacent quote fragments in the C locale. A command head with a backslash in an ANSI-C dollar quote refuses; the check does not decode those escapes. A known producer argument with such an escape, such as `systemctl $'show-\x65nvironment'`, also refuses. These refusals add `command-safety: reason=undecoded-ansi-escape` under the keyed line: decode the escape, or pass the value as a literal argument. A dollar-quoted grep pattern or `printenv` name keeps its conservative handling, so `env | grep $'^NAME='` refuses. An ANSI-C escaped word outside these positions is data.

Waiter launchers run forwarded argv as a command. Each operand after the script operand of a shell or `source`, each word after a shell's or `env -S` command string, which the string can run as `$0` or `"$@"`, and each word after `exec` or `builtin`, is judged as a possible command head beside its own operands. `exec` and `builtin` take no option grammar. So `bash wrapper.sh env -i NAME=value command-name` launches `command-name` and passes, while `bash wrapper.sh env`, `bash wrapper.sh cat ~/.fleet/env`, `source wrapper.sh env` and `sh -c '"$@"' _ env` refuse. A quoted operand past the forwarded program is also parsed as a command string, unless the launcher stage redirects its output. That includes a double-quoted operand that expands a variable, so `--test "cd $DIR && env"` refuses, and so does `--test "env -u $NAME bash test.sh"`, whose unset operand can expand to no word. Inside that forwarded text, a stage the producer cannot classify, and a body that holds heredocs, refuse on any known producer name. One quoted operand of a three-word `bash` script invocation stays data.

A shell `-c` string, an `eval` join and an `env -S` string are parsed again as shell source. `eval` takes one leading `--`. A non-literal `eval` word can expand to nothing, so the literal words after it are parsed as their own source too. Shell options that group two `o` or `O` letters cannot be counted, so every later word is parsed as source. A shell option word that is not literal, such as `"$MODE"`, can expand to `-c`, so the word after it is parsed as source too. An ANSI-C escaped source refuses. Parsed source never grants filter permission, so `bash -c 'env | grep NAME'` refuses.

A shell, `eval` or `source` runs every registered heredoc body and here-string it gets, including non-stdin descriptors. Each body is parsed alone, so quotes in one body cannot hide another. A Python, Node, Ruby or Perl interpreter at a stage's own head judges its registered bodies and quoted inline programs using its own whole-environment pattern, rather than shell builtin names. Whole os.environ, whole process.env, Ruby ENV.to_h or ENV.each and Perl %ENV refuse; named Python and Node reads remain permitted. A literal cat receiver of one quoted heredoc body is data, and so is a literal cat that writes one quoted body to a file. Every other heredoc body a cat or unknown receiver gets, an unquoted one included, is parsed alone as shell source. Input to `exec`, `builtin` or a stage of reserved words alone, such as `done <<'EOF'`, is parsed alone as shell source and also judged by the four interpreter patterns; so is piped input to such a stage, as in `cat <<'EOF' | exec python3`. Unquoted heredoc substitutions are checked independently. Missing body identifiers, unread registered bodies and undecoded escaped delimiters refuse.

A grep in another list command does not permit a dump. A stdout redirect or an intermediate program such as tee cannot prove direct filtering. Nested dumps refuse even with an inner or outer grep. An unanchored `grep NAME` can also match NAME in a value; permitted filtering is not output redaction.

The check does not reach unseen programs, aliases, functions, PATH replacements or runtime-built names, or a command written to a file and run later. An unknown launcher such as `timeout 5 env` is not a recognized producer at a command head. The same holds inside reserved-word syntax, such as `if true; then timeout 5 env; fi`, as a quoted forwarded argument when the launcher stage redirects its output, and inside a body an unknown receiver gets. Here-string input to an unknown receiver, such as `ssh host <<< env`, is not judged. An interpreter body that is forwarded or nested in shell source, such as `bash wrapper.sh python3 <<'EOF'` or `bash -c "python3 <<'EOF' ... EOF"`, is parsed as shell source but not judged by the interpreter patterns. Process substitutions, shell programs, transformed pipes and env split strings have no general interpretation guarantee.

The fixed check runs before cwd, Git and project settings. It also runs outside a Git worktree. An argument array keeps each argument; a pipe character in one argument does not establish a shell pipe. A missing payload reader or unreadable payload produces an advisory warning and allows the call.

An absent setting applies the shipped host-safety pattern, so a fresh install refuses a `systemd-run` memory cap measured in kilobytes or megabytes, quoted or not:

```text
(^|[^[:alnum:]_-])systemd-run[[:space:]][^&;|]*Memory(Max|High)=[[:punct:]]?[0-9]+[KkMm]([^[:alnum:]]|$)
```

A cap that small starved a build's cgroup into a kernel allocation failure inside a filesystem transaction, and the host's root volume went read-only. A cap in gigabytes, or a run with no cap, passes. A project that sets the key replaces this pattern, so its own pattern keeps this rule where it still wants it; `^$` turns only project-pattern matching off. The project-pattern part stays inactive outside a Git worktree. An explicitly empty value, invalid pattern, missing policy tool or unreadable setting produces one keyed warning and allows that pattern check. These conditions do not disable the earlier fixed check.

A malformed value on any `[env]` key produces one keyed warning and allows the pattern check, not only a malformed pattern. The settings loader reads the file whole, like every kendex settings reader, so a policy read past the bad line would come from a file the rest of the toolchain rejects. The warning replays the loader's line naming the file, the line and the key to rewrite.

The project pattern matches tool command text both as received and with backslash-newline pairs removed. For that pattern alone, an argument array is joined with spaces. Quotes and comments remain text, so a matching literal example is also refused. Put isolated validation behind a script whose invocation does not match the pattern.

For a Quickshell project, this example blocks direct `qs -c vshell`, `qs -p quickshell/vshell`, and `pkill quickshell` calls. It allows `scripts/validate qml`.

```toml
[env]
COMMAND_SAFETY_DENY_PATTERN = "(^|[[:space:];|&])qs[[:space:]]+(-c[[:space:]]+vshell|-p[[:space:]]+quickshell/vshell)([[:space:];|&]|$)|(^|[[:space:];|&])pkill([[:space:]]+-[^[:space:];|&]+)*[[:space:]]+quickshell([[:space:];|&]|$)"
```

Missing settings support produces one keyed warning and allows the pattern check because the hook cannot determine whether a policy exists. Repair the installed commit-guards support. Keep the pattern specific to the commands the project must prohibit. The hook does not classify commands hidden inside scripts.
