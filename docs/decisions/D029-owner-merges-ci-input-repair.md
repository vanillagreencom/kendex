# D029: One landing app pushes a proved commit past the rulesets, and the repository owner merges a CI-input repair under a one-head bypass

[← Decision Index](INDEX.md)

**Date**: 2026-10-17

**Status**: Active

**Research**: [KEN-4249](https://linear.app/vanillagreen/issue/KEN-4249); [KEN-5098](https://linear.app/vanillagreen/issue/KEN-5098), the landing app; fleet's D095 ([FLT-1355](https://linear.app/vanillagreen/issue/FLT-1355)), the organization rule that removed every app bypass from the organization's rulesets

**Supersedes**: [D003](D003-one-merge-path.md) in part, the landing of a proved render; [D007](D007-lock-record-on-main.md) in part, the landing of the install record; [D016](D016-merge-route-reads-bypass.md) in part, the gate repair; [D018](D018-platform-review-requirements.md) in part, the overseer app's emergency merge; [D027](D027-merge-queue-proves-every-change.md) in part, the bypass actors

**Decision**: The rulesets admit one app bypass, the landing app, and one temporary bypass for a person. The landing app is `vanillagreen-kendex-land`, app id 5726115. The organization owns it, it holds Contents read and write and Metadata read alone, and it is installed on each repository that lands with it. It pushes one commit that its own Actions run proved to the default branch, with no pull request. In a consumer, that commit is the one the refresh run made, measured as class `render`. In kendex, it is the install record that `tools/lock-record` wrote on the head it judged. A run pushes only while the merge queue holds no entry. The app's pair, `KENDEX_LAND_APP_ID` and `KENDEX_LAND_APP_PRIVATE_KEY`, lives only in each repository's protected `kendex` environment. The runs use its token for that one push, and no script opens, arms or merges a pull request with it. The lanes app is never the landing app. The organization owner sets the accepted ruleset shape: one organization ruleset holds `pull_request` and `workflows` with the landing app as its only bypass actor, in mode `always`; organization ruleset 24148602 keeps `deletion` and `non_fast_forward` with no bypass actor; each repository's merge-queue and required-checks rulesets list the landing app. Where a repository names the app in `REVIEW_GATE_STANDARD_LAND_BYPASS`, the review-gate standard admits it on those rulesets and refuses it on any ruleset that holds another rule. A ruleset that refuses the push leaves the update on the rolling pull request. No other app bypasses a ruleset, so the overseer app has no emergency merge. When a merge group cannot pass because a CI input read from the default branch broke (the classifier checkout, the lane declaration, the aggregate's needs or the change-class action), the overseer asks the repository owner, or the person the owner delegates, by mailbox, naming the broken input and the repair's pull request. That person adds a bypass for their own credential to the required-checks and merge-queue rulesets through the API and reads it back, merges that one repair head with `gh pr merge <N> --admin --match-head-commit <SHA>`, removes both bypasses and reads that back, and records both steps on the repair's work item. No lane runs a raw `--admin` merge and the repair gives no app token a merge path, so D016's rule against a lane's raw admin merge holds with no exception.

**Why**: A proved commit needs no second proof. kendex's merge queue proves the content of the kendex catalog, and the refresh run proves that its commit holds that content as kendex renders it. The install record is a function of the merged tree, which that tree's merge group proved. A rolling pull request for such a commit spends an approval and a merge group and proves nothing more. A push to a branch whose queue holds an entry makes GitHub rebuild every running group, so a run pushes only into an empty queue, and an update waits no longer than the queue. GitHub's required workflows rule blocks every direct push, so the landing app needs a bypass on the `pull_request` and `workflows` rules; those two rules sit in a ruleset apart from `deletion` and `non_fast_forward`, which nobody bypasses. The accepted cost is that no consumer pull-request check, merge group or review judges a landed commit. A bad package is undone by a revert on kendex `main`, which each consumer's next refresh renders and lands by the same route. Contents write is also the permission GitHub's merge endpoint requires, so the protected environment and the single use of the token hold the limit, not the app's permissions. Fleet's D095 removed every app bypass; this record admits one again, and D095 is fleet's to change. For the repair, `pr-merge` never takes `--admin` for a queue-only change, whatever bypass a ruleset lists, and every kendex change is queue-only under D027, so a restored lanes-app queue bypass is never used. A repair whose broken input also fails its own required check is refused by the required-checks ruleset too. A person's own bypass on both rulesets, held for one head and read back when added and removed, is the smallest grant that merges the repair.

**Rejected**: The lanes app as the landing app: it opens, arms and merges pull requests, so its bypass would cover every pull request it handles. A second proof of a landed commit in the consumer: it repeats the proof of kendex's merge queue. Restoring the lanes app's merge-queue bypass for the repair: `pr-merge` sends the queue-only repair to the queue, and the required-checks ruleset still refuses a repair that fails its own check. A standing overseer-app bypass: the organization rule removed it.

**Revisit when**: `pr-merge` gains a route that merges a queue-only change past a broken merge group, the landing token needs a second use or a second permission, a landed commit breaks a consumer before a revert reaches it, or the organization's rulesets admit a second app bypass.
