# D033: One landing app pushes a proved commit to the default branch with no pull request

[← Decision Index](INDEX.md)

**Date**: 2026-11-12

**Status**: Active

**Research**: [KEN-5098](https://linear.app/vanillagreen/issue/KEN-5098); the owner's approval, Slack messages 1794469528.369859 and 1794471291.314249 and BRAD-130 comment 12f98815; fleet's D095 ([FLT-1355](https://linear.app/vanillagreen/issue/FLT-1355)), the organization rule that removed every app bypass from the organization's rulesets

**Supersedes**: [D003](D003-one-merge-path.md) in part, the landing of a proved render; [D007](D007-lock-record-on-main.md) in part, the landing of the install record; [D027](D027-merge-queue-proves-every-change.md) in part, the bypass actors; [D029](D029-owner-merges-ci-input-repair.md) in part, its rule that no app bypasses a ruleset

**Decision**: One GitHub App, the landing app, bypasses the rulesets for one use: it pushes one commit that its own Actions run proved to the default branch, with no pull request. The app is `vanillagreen-kendex-land`, app id 5726115: the organization owns it, it holds Contents read and write and Metadata read alone, and it is installed on each repository that lands with it. Its pair, `KENDEX_LAND_APP_ID` and `KENDEX_LAND_APP_PRIVATE_KEY`, lives only in each repository's protected `kendex` environment. A run uses the token for that one push, and no script opens, arms or merges a pull request with it. The lanes app is never the landing app. In a consumer, the proved commit is the one the refresh run made, where the classifier measures class `render` and every enabled source of every selected project is the kendex catalog with no `path` and no `rev`; an update from any other source keeps the rolling pull request. In kendex, it is the install record that `tools/lock-record` wrote on the head it judged. A run pushes only while the merge queue holds no entry. The ruleset shape is a target that the organization owner sets after the release that ships this route: `pull_request` and `workflows` move to an organization ruleset of their own, with the landing app as its one bypass actor in mode `always`; organization ruleset 24148602 keeps `deletion` and `non_fast_forward` with no bypass actor; each repository's merge-queue and required-checks rulesets list the landing app. On 2026-11-12, ruleset 24148602 holds `deletion`, `non_fast_forward`, `pull_request` and `workflows` together, so GitHub refuses the landing push in every repository it covers, and each update keeps the rolling pull request until the owner sets the target. Where a repository names the app in `REVIEW_GATE_STANDARD_LAND_BYPASS`, the review-gate standard admits it on those rulesets and refuses it on any ruleset that holds another rule. [D029](D029-owner-merges-ci-input-repair.md) keeps the rest: no other app and no other commit skips the repository rules, the overseer app has no emergency merge, and the repository owner repairs a broken CI input under a one-head bypass.

**Why**: kendex's merge queue proves the content of the kendex catalog once, and the refresh run proves that its commit holds that content as kendex renders it. A source outside that catalog has no such proof, so its update keeps the pull request. The install record is a function of the merged tree, which that tree's merge group proved. A rolling pull request for such a commit spends an approval and a merge group and proves nothing more about that content. A push to a branch whose queue holds an entry makes GitHub rebuild every running group, so a run pushes only into an empty queue, and an update waits no longer than the queue. GitHub's required workflows rule blocks every direct push, so the landing app needs a bypass on `pull_request` and `workflows`; the target puts those two rules in a ruleset apart from `deletion` and `non_fast_forward`, which nobody bypasses. Accepted costs: no approval, review thread, pull-request check or merge group judges a landed commit in the consumer. The landing stays on class `render`, so a landed render runs no consumer lane that claims a path it changes. Render proof does not show that the consumer's tests pass against the rendered files, and under the queue-only default the nightly full run is the first lane run against them. A bad package is undone by a revert on kendex `main`, which each consumer's next refresh renders and lands by the same route. Contents write is also the permission GitHub's merge endpoint requires, so the protected environment and the single use of the token hold the limit, not the app's permissions. Fleet's D095 removed every app bypass; this record admits one again, and D095 is fleet's to change.

**Rejected**: The lanes app as the landing app: it opens, arms and merges pull requests, so its bypass would cover every pull request it handles. A landing gate that lands only a render no consumer lane claims, or any second proof of a landed commit in the consumer: KEN-5098 keeps one proof of package content, in kendex's merge queue, adds no gate, and accepts the cost above.

**Revisit when**: The landing token needs a second use or a second permission, a landed render breaks a consumer lane that claims a path it changed, a landed commit breaks a consumer before a revert reaches it, or the organization's rulesets admit a second app bypass.
