# D033: One landing app pushes a proved commit to the default branch with no pull request

[← Decision Index](INDEX.md)

**Date**: 2026-11-12

**Status**: Active

**Research**: [KEN-5098](https://linear.app/vanillagreen/issue/KEN-5098); the owner's approval, Slack messages 1794469528.369859 and 1794471291.314249 and BRAD-130 comment 12f98815; fleet's D095 ([FLT-1355](https://linear.app/vanillagreen/issue/FLT-1355)), the organization rule that removed every app bypass from the organization's rulesets; [KEN-5378](https://linear.app/vanillagreen/issue/KEN-5378) and [KEN-5608](https://linear.app/vanillagreen/issue/KEN-5608), the revisits that held the landing of a render that removes a path, then narrowed that hold to a render that drops an emitted position; [KEN-5710](https://linear.app/vanillagreen/issue/KEN-5710), the revisits that defer a render on a busy queue instead of opening a pull request and grant the app Workflows write, the second under Jarvis note 1795645619 of 2026-11-25 on the owner's word

**Supersedes**: [D003](D003-one-merge-path.md) in part, the landing of a proved render; [D007](D007-lock-record-on-main.md) in part, the landing of the install record; [D027](D027-merge-queue-proves-every-change.md) in part, the bypass actors; [D029](D029-owner-merges-ci-input-repair.md) in part, its rule that no app bypasses a ruleset

**Decision**: One GitHub App, the landing app, bypasses the rulesets for one use: it pushes one commit that its own Actions run proved to the default branch, with no pull request. The app is `vanillagreen-kendex-land`, app id 5726115: the organization owns it, it holds Contents read and write, Workflows read and write and Metadata read alone, and it is installed on each repository that lands with it. Its pair, `KENDEX_LAND_APP_ID` and `KENDEX_LAND_APP_PRIVATE_KEY`, lives only in each repository's protected `kendex` environment. A run uses the token for that one push, and no script opens, arms or merges a pull request with it. The lanes app is never the landing app. In a consumer, the proved commit is the one the refresh run made, where the classifier measures class `render`, every path the commit removes or renames against the base the run judged lies at or below a path the commit's root `.kendex-lock.json` still emits, and every enabled source of every selected project is the kendex catalog with no `path` and no `rev`; an update from any other source, or one that drops an emitted position, keeps the rolling pull request. In kendex, it is the install record that `tools/lock-record` wrote on the head it judged. A run pushes only while the merge queue holds no entry. The ruleset shape is a target that the organization owner sets after the release that ships this route: `pull_request` and `workflows` move to an organization ruleset of their own, with the landing app as its one bypass actor in mode `always`; organization ruleset 24148602 keeps `deletion` and `non_fast_forward` with no bypass actor; each repository's merge-queue and required-checks rulesets list the landing app. On 2026-11-24, GitHub took a landing push under the organization's rulesets: vgshell run 45449034468 printed `refresh-state=landed pr=none class=render`, and its landed commits have no pull request. The lanes app cannot read the organization's rulesets, so this record states the push GitHub took, not the rulesets' shape. Where a ruleset still refuses the push, the update keeps the rolling pull request, and a deferral on a busy queue only delays it. Where a repository names the app in `GITHUB_STANDARD_LAND_BYPASS`, or until 2.0 in the deprecated `REVIEW_GATE_STANDARD_LAND_BYPASS`, the github-repository-settings standard report admits it on those rulesets and refuses it on any ruleset that holds another rule. [D029](D029-owner-merges-ci-input-repair.md) keeps the rest: no other app and no other commit skips the repository rules, the overseer app has no emergency merge, and the repository owner repairs a broken CI input under a one-head bypass.

**Why**: kendex's merge queue proves the content of the kendex catalog once, and the refresh run proves that its commit holds that content as kendex renders it. A source outside that catalog has no such proof, so its update keeps the pull request. A landed render that removed a cited file once broke a consumer's reference check on every later commit, which met the revisit trigger below. The cause was a check that judged a citation into a rendered file, which the consumer cannot keep current with kendex. KEN-5608 fixed it in that check for every path the lock still emits, so a render that removes or renames a file inside a still-emitted position lands like any other. The check reads only the head lock, so a citation into a position the render drops from the lock, such as a pruned package or a removed or renamed per-file agent, is judged and dead; such a render keeps the rolling pull request, which merges under the consumer's own rules. A consumer program that calls a package script by path is covered where the package changes: removing or renaming one needs the caller search of the release standard in `changelog.d/README.md`. The install record is a function of the merged tree, which that tree's merge group proved. A rolling pull request for such a commit spends an approval and a merge group and proves nothing more about that content. A push to a branch whose queue holds an entry makes GitHub rebuild every running group, so a run pushes only into an empty queue. A consumer render that meets a busy queue opens no pull request and waits for a later refresh run that meets an empty queue, the next daily or release-dispatched run, since a pull request would spend the CI run and approval the owner's word of 2026-11-12 rules out for a kendex package update; Jarvis decision 1795641405 of 2026-11-25 set this under delegated authority. Nothing re-dispatches the deferred run, so a queue busy at every run holds the render until one meets it empty. GitHub's required workflows rule blocks every direct push, so the landing app needs a bypass on `pull_request` and `workflows`; the target puts those two rules in a ruleset apart from `deletion` and `non_fast_forward`, which nobody bypasses. Accepted costs: no approval, review thread, pull-request check or merge group judges a landed commit in the consumer. The landing stays on class `render`, so no consumer lane that claims a path a landed render changes judges that render before it lands. Render proof does not show that the consumer's tests pass against the rendered files, and under the queue-only default the nightly full run is the first lane run against them. A bad package is undone by a revert on kendex `main`, which each consumer's next refresh renders. A revert that drops no emitted position lands by the same route, and one that drops a package or a per-file item the bad change added keeps the rolling pull request. GitHub refuses an app's push that changes a file under `.github/workflows` without Workflows write, and a release that changes the caller template rewrites each consumer's `.github/workflows/kendex-refresh.yml` in its next render, so without that permission each such release opened one pull request in every consumer. With it, the app can change what CI runs as well as the other files it already lands, which matters only if its key leaks. Contents write is also the permission GitHub's merge endpoint requires, so the protected environment and the single use of the token hold the limit, not the app's permissions. Fleet's D095 removed every app bypass; this record admits one again, and D095 is fleet's to change.

**Rejected**: The lanes app as the landing app: it opens, arms and merges pull requests, so its bypass would cover every pull request it handles. A landing gate that lands only a render no consumer lane claims, or any second proof of a landed commit in the consumer: package content keeps one proof, in kendex's merge queue, and the cost above stands. The dropped-position condition is neither. It reads which paths the render deletes and which positions the head lock still emits, not which consumer lanes claim a changed path, and it proves nothing about a commit that lands: a render that drops a position does not land.

**Revisit when**: The landing token needs a second use or a permission beyond Contents and Workflows, a landed render breaks a consumer lane that claims a path it changed, a landed commit breaks a consumer before a revert reaches it, or the organization's rulesets admit a second app bypass.
