# Package settings: one documented contract, editable in the app

Owner request, 2026-08-27. Revised after Codex challenge rounds 1 and 2 (findings folded throughout; dispositions at the end). Owner decisions at approval (2026-08-27): roadmap approved; the `.env` layer is dropped from the canonical precedence everywhere (generalizing KEN-560's second-opinion decision; a lingering `.env` is silently ignored and the changelog says so — the loud-error detail of KEN-560 is superseded by the newer no-migration rule; KEN-560 cancels as absorbed into work item 1).

## Problem

A package that wants user-tunable env vars has no documented way to ship them, and a consumer has no obvious place to tune them. Today the mechanism exists but is invisible: skills ship `kendex.settings.toml.example`, the engine seeds those keys into the consumer's root `kendex.settings.toml`, and per-skill shell resolvers read the values. Nothing tells a marketplace author this exists, the kendex repo root carries a hand-maintained aggregate example kept in sync only by tests, and the app has no settings UI at all.

## Current state (verified)

- **Seeding** (`crates/core/src/settings_seed.rs`): a skill ships `kendex.settings.toml.example` with one `[env]` table. At project plan time (`engine/mod.rs:156` → `engine/scope_writes.rs:184-241`, project scope only), each installed skill's template is read off sealed source bytes (`engine/desired_skill.rs:197-210`) and any key absent from the project's `kendex.settings.toml` is inserted with its comment block. Write-if-absent per key; value lines never touched; byte-faithful splicing (the one exception: inserting at EOF after an unterminated final line adds the missing terminator once, by design). The lock's `settings-seeds` map records per key an owner skill + FNV-1a hash of the seeded comment block; a comment refreshes to a newer template revision only while its on-disk text still hashes to that record (`settings_seed/refresh.rs`). When several installed skills ship the same key, insertion order is package-name (`BTreeMap`) order, and the ledger's recorded owner sticks across refreshes — at runtime the key is global, so every shipping package reads the same value.
- **Reading**: no Rust. Skills vendor one of two resolver families:
  - `settings.sh` family (review-gate, growth-guards, size-ratchet): grep/sed, matches keys file-wide regardless of TOML table, accepts only quote-free single-line double-quoted values, errors on duplicate assignment. Precedence varies by skill: review-gate reads env > committed `kendex.settings.toml` > default; size-ratchet adds `.env.local` and `.kendex/settings.toml` layers.
  - `kendex-env.sh` family (second-opinion, orch, worktree): parses only the `[env]` table, layers `.env` > `kendex.settings.toml` / `.kendex/settings.toml` > `.env.local` (later wins) under process env, sources dotenv files as shell code, and decodes `\"` / `\\` escapes. The families disagree on precedence, table awareness, and value decoding. The common denominator both read identically: a single-line double-quoted value containing no `"` and no `\`. Three deliberate, tested per-key exceptions to any uniform precedence exist: Linear makes project-file `LINEAR_API_KEY` beat an inherited environment key (wrong- workspace protection); `SECOND_OPINION_CURRENT_MODEL` refuses every project-file source (same-model-review protection); `REVIEW_GATE_MODE` ignores dotenv files (local waiter and CI gate must resolve the switch identically).
- **Docs**: `docs/authoring/README.md` never mentions settings; no template in `docs/authoring/templates/`. `docs/architecture/overview.md` describes the seeding invariant.
- **Root example**: repo-root `kendex.settings.toml.example` (316 lines) is hand-maintained and policed by `settings-example-sync.test.sh` copies in several skills. It is NOT a pure union of per-skill templates: it is the only consolidated declaration for `WORKTREE_*`, bot identity, `DEV_VALIDATE_CMD`, `DECISIONS_DIR`, several GitHub settings, and keys (e.g. `LINEAR_FORMAT`) missing from the owning skill's own template. Some entries are commented opt-ins that seeding ignores by design.
- **App**: zero settings UI. The Customize feature edits `kendex.toml` manifest overlays only, via `updateManifest(scope, draft, base)` with base-hash stale refusal (`crates/app/src/whole_file.rs`, `crates/app/src/editor/save.rs`, `ui/src/stores/editor.ts`). A manifest save runs a full scope plan, which may itself seed or refresh `kendex.settings.toml` (`editor/save.rs:121`).
- **Validator**: `kendex marketplace check` ignores `kendex.settings.toml.example`. Check runs strict (`crates/cli/src/commands/marketplace_cmd.rs:316`); structural advisories fail it (`crates/core/src/check_catalog.rs:178`).

## Decisions

1. **The contract is the existing mechanism, named and documented.** A package ships `kendex.settings.toml.example` at its root: one `[env]` table; every seeded key preceded by an immediately adjacent comment block (no blank line between comment and key) that is the user-facing explainer; every value single-line, double-quoted, containing no `"` and no `\`. Keys are prefixed with the package name upper-snake as a documented convention, not a check finding — packages deliberately shipping a companion package's key (orch ships review-gate keys) are legitimate. Keys a package documents but does not seed (opt-ins) live in the package's own docs, which the marketplace page already renders. No rename, no new file format, no metadata schema. The consumer edits exactly one file: the repo-root `kendex.settings.toml`.
2. **Every setting lives in its owning package; the root example dies.** Root-example-only settings move into their owning skill's template (or its docs, for opt-ins) first; the aggregate file and its sync tests go only after a completeness check shows nothing orphaned.
3. **One canonical resolver contract — default precedence plus named per-key exceptions — made true in kendex's own skills.** The default: process env > `.env.local` > `.kendex/settings.toml` > `kendex.settings.toml` > default. The `.env` file is not read by anything (owner decision, generalizing KEN-560): three homes, one job each — `kendex.settings.toml` for shared project settings, `.env.local` for personal and secret overrides, process env for one-off session control. A lingering `.env` is silently ignored; the changelog says so. A key may document a stricter source policy where safety requires it; the three existing exceptions (Linear key, second-opinion session model, review-gate mode) keep their semantics and tests, documented beside their keys. All readers become `[env]`-table-aware so runtime, seeding, and the app agree on what an assignment means; duplicate assignment of a key inside `[env]` stays an error.
4. **Settings become the third customization axis in the app** — per project, per package, written to the repo-root `kendex.settings.toml` through one save transaction composed inside core planning.
5. **Out of scope**: per-key shadow/effective-value claims in the UI (static parsing of `.env.local` lies and executing it runs project code; help copy states the precedence instead); UI editing of `.kendex/settings.toml`, `.env.local`, `.env`; settings templates for non-skill kinds; migration machinery (changelog + reinstall covers contract tightening, per the no-migration rule); apply-layer changes to rollback-vs-concurrent-external-writer semantics and symlink-swap-race hardening (pre-existing, feature-independent properties of every whole-file write — see dispositions).

- Each touched skill's tests cover the precedence order and the exceptions.

Done-when: every kendex skill that reads settings resolves the default order with only the three named exceptions (each skill's precedence test proves it), and all readers ignore assignments outside `[env]`.

## Work item 3 — engine: diagnostic template parser + check coverage + conflict surfacing

Depends on item 2 (templates must conform before the check enforces).

- **Diagnostic parser** (core, beside `settings_seed`): parses a settings template strictly against the contract and returns located findings — file does not parse; assignment outside `[env]`; more than one `[env]` header; key with no adjacent comment block; value not single-line double-quoted or containing `"` / `\`; duplicate key in file. Also returns, for valid files, the decoded rows (key, comment text, default value, line spans). `extract_env_entries` stays as the lenient seeding reader; the diagnostic parser is the strict one the validator and the app read model (work item 4) share.
- `kendex marketplace check` runs the diagnostic parser on a package's `kendex.settings.toml.example` when present and reports its findings. No prefix finding (decision 1).
- **Conflict surfacing at plan time**: when installed packages ship the same key with more than one distinct default value, the plan/audit output emits one note per key, grouped, naming every owner and each distinct default (same key + same default everywhere is the legitimate companion pattern and stays silent — today's orch/review-gate shared keys, e.g. `REVIEW_GATE_MODE = "enforce"`, produce no note). Behavior stays write-if-absent in package-name order. Follow the existing user-facing plan-note pattern (`engine/item_plan.rs:128-133`).
- Tests: fixture per finding; fixtures for the differing-default note (including three owners with defaults A/A/B → one grouped note), same-default silence.

Done-when: check on a malformed template names each defect above with its location; installing packages sharing a key with differing defaults surfaces one grouped note per key naming all owners, same-default pairs stay silent; kendex's own skills pass the new check clean.

## Work item 4 — app: package settings in the Customize UI

Depends on work item 3's diagnostic parser.

### Core planning + commands (Rust first, TS generated)

- **Scope-level read model**, one command (e.g. `scope_settings(scope)`): for a project scope, returns per installed settings-shipping skill one of four states — *ships no template*, *template unreadable* (pending/disabled/moved source), *template invalid* (strict parser findings; the lenient seeder may still have seeded it), or *rows* — plus the settings file's base hash. Each row: key, explainer text, default, and `current` as a three-state value — *absent*, *value* (single well-formed `[env]` assignment), or *invalid/ambiguous* (duplicate assignment, assignment outside `[env]` only, undecodable value). Only *value* rows compare against the default; invalid rows render a designed state and are never reported as stock. Reads the `[env]` table only, matching decision 3. Scope-level so Library rows and the Customize index can mark packages without opening each package page. Global scope returns an explicit known-empty answer so facts resolve to false, never permanently unknown.
- **Save transaction composed in core planning.** Settings value edits (each bound to `(skill, key, value)`) become an input to the scope plan: `plan_settings_seed` (or a sibling planning step) merges seeds, value replacements, and ledger changes into exactly one settings `WriteFile` op with one coherent lock snapshot, before `plan_lock_write`. The editor save command passes the settings edits alongside the (optional) manifest draft; base preconditions per file are checked up front; the whole plan applies under `apply::execute` with journaled rollback. This composition exists because a manifest save re-plans the scope and may itself rewrite `kendex.settings.toml` (an appended second write would always be stale), because N sequential single-key writes invalidate each other's base, and because a seed and an edit of the same key in one save must land as one write. Settings-only saves pass no manifest draft. The transaction guarantee is between the two drafts (both land or neither); concurrent external writers remain subject to the apply layer's existing semantics.
- Write semantics: core verifies each edited key is declared by the named installed skill's template; edits replace exactly the key's quoted value span in the repo-root `kendex.settings.toml`; values are validated against the contract grammar (single line, no `"`, no `\`) and refused otherwise; an edit targeting an *invalid/ambiguous* key refuses with a message naming the offending lines; "reset to default" writes the viewed skill's template default. A key absent from the file is inserted through the existing seed splicing *and recorded in the seed ledger* (comment + value + `settings-seeds` entry), so later comment refreshes still work. The writer repeats seeding's non-regular-file refusal (`scope_writes.rs:202`): symlink, directory, or other non-regular settings file refuses.
- Stale refusal reuses `WriteRefused::Stale` / `whole_file.rs`.

### UI

- `ItemCustomize` (package page → Customize tab) gains a **Settings** section for skills whose scope row has rows, project scope only: one row per key — key name, explainer text, text input with the default as placeholder, current value when set, reset-to-default. A value differing from the template default is labeled as differing from the package default (factual — seeded values do not track later package-default changes, so the label never claims the *user* changed it). Invalid/ambiguous rows and invalid/unreadable templates render designed states, not empty sections. Section help copy states the write target and that environment variables and `.env.local` override values from this file.
- Drafts buffer in the editor store as a second file-draft with the existing `dirty`/`stale`/refusal UX; one Save bar saves manifest and settings edits through the one transaction above.
- Customized index: a package with any *value* row differing from its default counts, via a new fact in `ui/src/lib/customized-places.ts` fed by the scope-level read (null until reported, per the existing never-claim-stock-early rule; global scope's known-empty answer resolves the fact to false) — Library row, package header, and Customize index pick it up.
- Copy per repo voice rules: state what a thing does, no selling.

Done-when: on a project install of growth-guards, the Customize tab lists its keys with explainers; saving an edited value rewrites only that value span (comments and CRLF intact); a save while the file changed externally refuses stale with reload; manifest + settings edited together save in one action with neither lost; a save that both seeds a missing key and edits it lands as one write; reset restores the template default; the package marks as customized in Library and the Customize index; a duplicate or out-of-`[env]` assignment shows the designed invalid state and refuses edits naming the lines; skills without templates and global scope show no Settings section; a symlinked settings file refuses.

## Review dispositions

**Round 1 folded**: resolver-contract falsehood (→ decisions 3/5; shadow detection dropped), diagnostic parser (→ item 3, item 4 dependency), root example not a union (→ item 2 ownership moves + completeness derivation), templates fail the proposed validator (→ prefix demoted to convention; adjacency fixed; strict-mode noted), save atomicity (→ transactional save), value grammar (→ no-`"`-no-`\` everywhere), collision semantics (→ corrected description; differing-default-only note; per-skill-bound edits and reset), path safety (→ non-regular-file refusal), index data path (→ scope-level read model), shadow-detection safety (→ dropped), default pinning (→ "differs from package default" labeling; opt-ins stay docs), unbound write command (→ edits bound to skill+key, core-verified), plus edge cases: duplicate-key refusal naming lines, two-`[env]` finding, ledger-recorded UI inserts, unreadable-vs-absent template states, EOF-terminator wording, `.agents/` re-render step.

**Round 1 declined**: metadata-schema alternative (new format the mechanism doesn't need); reject-collisions-unless-declared (differing-default note covers the real conflict without a new declaration surface).

**Round 2 folded**: per-key precedence exceptions (→ decision 3, item 1), transaction composition point inside core planning before `plan_lock_write` (→ item 4), `[env]`-awareness everywhere (→ decision 3, item 1; UI reads `[env]` only), invalid/ambiguous consumer-value state (→ four template states, three value states; invalid never reports stock), doc-before-behavior sequencing (→ items reordered 1→2→3→4), grouped conflict notes (→ item 3), global known-empty resolving facts to false (→ item 4), seed-then-edit-in-one-save (→ composed single write).

**Round 2 declined**: rollback-vs-concurrent-external-writer semantics — a pre-existing property of `apply::execute` affecting every multi-file plan the app already runs, not introduced or worsened here; the plan's guarantee is scoped to the two drafts. Symlink swap-race hardening — the new writer matches seeding's existing refusal; the check-then-use window is shared by every current whole-file write and sits outside this feature's threat model (local attacker racing the user's own app); tightening it is an apply-layer decision for the owner to order separately if wanted.
