# hooks/

Catalog hooks, one bash script per hook, each with its suite under `tests/<name>.test.sh`.

- A hook opens with a commented frontmatter block between `# ---` lines: `name`, `event` (a name from `crates/core/src/hook.rs::EVENTS`), `matcher`, `description`, `summary`, `safety`, `timeout` (seconds), an optional `harnesses: [..]` restricting delivery (Antigravity is reached only when named there, because its payload is `toolCall.args`, not `tool_input`) and an optional `requires: [..]` naming companion hooks, `requires-on: [..]` restricting those hook requirements to named harnesses, and `requires-skills: [..]` naming skills this hook needs in the same scope; `crates/core/src/hook.rs::parse_hook` reads it.
- A hook that runs a companion beside itself names it under `requires`. A hook that needs a skill names it under `requires-skills`. `crates/core/src/engine/deps.rs` installs both through the existing dependency walk. Required skills come from the hook's catalog in the same scope. The requiring hook's `requires-on` line defines where it requires companion hooks. Without it, the requirement covers every harness the requiring hook runs on. A companion's own `harnesses` line further limits where it is required. A required dependency kept removed or switched off withholds the hook on the tools that need it, with a finding naming both. An applicable companion that cannot be delivered also withholds the hook. Cross-catalog ownership, kept records and orphan removal follow [engine.md](../docs/architecture/engine.md).
- A name added to a `requires:` line needs this repository's own `harnesses` pin on that companion in `kendex-local.toml` to list every harness both hooks run on: a narrower pin withholds the requiring hook on the rest, and `cargo test -p kendex-core --lib own_inventory` fails on its renders gone stale.
- A `harnesses:` line spells each harness by its `HarnessId::name` id. For each hook-running harness the line leaves out, `description` carries one sentence `Not run on <id>: <reason>.` naming the payload field or event that harness lacks.
- `description` is the constraint, for the agent. `summary` is one or two plain sentences for the person browsing: what the hook stops and what it costs them. It is what a catalog row, a Library row and the package page show, and a hook that writes none is shown its `description` instead. Both are one line — the header is read line by line, not as YAML.
- Exit 0 allows; exit 2 refuses with the reason on stderr; a payload that cannot be read is a refusal, never a pass. On Copilot a turn-end refusal is `decision: block` on stdout at exit 0 (`lane-mail-check.sh::refuse`); its `agentStop` also fires at a custom subagent's end, under the subagent's own session and the lead's transcript (Copilot CLI 1.0.91; its hooks reference names the main agent alone), which a turn-end hook tells from the lead's through `lane-mail-check.sh caller` or leaves `copilot` off `harnesses:`.
- A refusal the caller cannot clear is a trap, not a guard. Where the remedy would name a command the install does not carry, or a fact outside the caller's reach, report the gap under its own key and exit 0; a gap the session must act on reaches it as context (`lane-mail-check.sh::hand_over`), never on stderr alone, which Claude Code keeps from the model. Exit 2 is for a condition the refusal's own text tells the caller how to end. A hook that holds every turn end on something nothing the caller does will lift stops the session from ever ending.
- A hook here is guard code for finding disposition, its turn-end refusals and the marks it reports included: a mark passed with no keyed line is a fail-open defect, never an excluded class.
- A refusal states what it refused, why, and the preferred remedy first, before any exemption path.
- The first line of a refusal or a notice is `<hook-name>: <key>=<value>`; the rule it follows is [`../skills/code-quality/SKILL.md`](../skills/code-quality/SKILL.md). Nothing precedes it: where a command the hook runs writes its own words, capture them at the site and hand them to the message function, which prints the keyed line, then the English, then that cause. A suite asserts the keyed line at position 1 and the cause below it.
- A suite runs the hook `HOOK_UNDER_TEST` names, else the one beside it, so a must-fail control reruns its assertions on a planted copy.
- There is no exception for text a person or a model reads. A format is exempt only where a named program parses that exact whole output; none does here, so what a suite would have read out of prose (which base `doc-drift-check` compared against, which arm `session-drift-check`'s exit code chose) is emitted as a value and pinned as one. Relay producer reports unchanged, except for the lane count in `session-drift-check.sh::report`.
- The one thing a hook cannot put under its keyed line is a diagnostic from shell startup, before the script runs; everything the hook itself runs is captured at the site and replayed.
- Two hooks have their keys fixed by what reads them, and they do not move. `block-bare-cd`: `missing-tools=<comma list, in check order jq,cat,grep,sed>`, `payload=invalid-json`, `refused=bare-cd`, each exit 2; a command with no bare cd exits 0 saying nothing. `pre-commit-check`: `missing-tools=<comma list, in check order jq,cat,grep>`, `payload=invalid-json`, `bypass=<the matched word, verbatim>`, `unarmed=<the directory judged>`, each exit 2; `judged=<the directory judged>` at exit 0 for the repository-moving notice; an armed repository with no bypass word exits 0 saying nothing.
- A render lands as [`../skills/AGENTS.md`](../skills/AGENTS.md) states; `tests/*` renders nowhere.
- Shell stays Bash 3.2 compatible: [`../skills/AGENTS.md`](../skills/AGENTS.md).
