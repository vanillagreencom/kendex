# pi-extensions/

Pi extension packages, one npm package per directory, each a `pi-package`.

- Every package follows the policy `package-policy.test.mjs` asserts: the Pi Node baseline, the `pi-package` keyword, optional Pi peers with `>=x.y.z` ranges, the vendored append-system helper under each package's `scripts` directory identical across packages, one vendored settings reader `package-config.ts` per package identical across packages, and TypeScript that Node's strip-only parsing accepts. Run `node --test pi-extensions/package-policy.test.mjs`.
- A package's own runtime reads of `kendex.extensionManager.config` and the project-trust registry go through its `package-config.ts`, and its extension factory calls `installSettingsCacheRefresh`. Two readers stay outside it. pi-extension-manager reads and writes through its host adapter, because that adapter also reads and writes the YAML settings documents of the Oh My Pi (OMP) host. A write path that must fail on malformed JSON rather than overwrite it, such as pi-skills-manager's `updatePackageConfig`, reads the raw file, writes it, then calls `clearPackageConfigCache`. To change the reader, edit one copy and copy it over every other `package-config.ts`. Reads, and the user directory they resolve from `PI_CODING_AGENT_DIR` and `HOME`, are memoized, so a test that rewrites a settings file or changes either variable and then reads settings calls `clearPackageConfigCache` after the change, as the manager's settings-changed event does in a session. It calls it again after it restores the file or variable, because `bun test` runs every test file of a package in one process and the memo outlives the file that filled it.
- A Pi peer floor rises to a new Pi release only after the Pi update audit (the `pi-update` skill, `.agents/skills/pi-update/SKILL.md`) records it in `pi-update.audit.md` with verdict `roll`. A `### Breaking Changes` entry that names an event or call listed in `pi-hooks/pi-contract.json` is blocking: the verdict is `hold` until the pi-hooks change for it lands, or the record names the real Pi session check that shows pi-hooks needs none. A `hold` leaves the marker in `pi-update.state.json` at the last cleared release, so the next audit reads the held release's entries again. The policy test refuses a peer floor above the release the record clears, a record that clears a release other than the state marker's, and a `roll` whose `## Verdict` section lacks the target release line in the skill's § Audit record form (version, the npm package at that version, its integrity, upstream source commit) or the full tested extension commit.
- Pi's real behaviour is read from `pi-update.audit.md` first and the mise-installed Pi second, never from a cached bundle.
- A package's CI entry point is `test:ci` when declared, else `test`; a step conditioned on a shard name `.github/workflows/skill-tests.yml` does not carry fails the policy test.
