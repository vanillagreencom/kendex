# pi-hooks development

For maintainers of the carrier. What it does for a consumer is [README.md](README.md); the mechanics live as doc comments on the functions named below, and this file holds only the invariants that span them.

## Invariants

- A guard that did not run does not stand aside. Every path that fails to reach a verdict is reported: a missing render, a timeout (read before the exit code, because a killed process still has one), a non-zero exit other than 2, a registry that exists and cannot be parsed, a matcher that will not compile. On `tool_call` the report is a refusal (`extensions/hooks.ts::toolCallVerdict`); on `tool_result`, `turn_end` and `session_start`, which gate nothing, it is a line the agent reads (`extensions/dispatch.ts::agentLine`). Only an absent registry is silent, because that is kendex having installed nothing. `extensions/dispatch.ts::runHook` and `extensions/registry.ts::readRegistry`; `tests/hooks.test.ts`, `tests/registry.test.ts`, and `tests/listener-dispatch.test.ts` hold these cases.
- The registry is the render, not a model of it. What runs is the command kendex wrote; nothing in the carrier knows a hook's name in advance, which is what lets a custom hook run at all. A hook kendex rendered is spawned at `<registry root>/hooks/<name>.sh` rather than through its command, because the command spells a project path as a walk that finds the file at run time and the registry it was read from is the anchor that walk would have to find. A command that sets an environment for that script is the exception and runs as written, since those assignments are in the command and nowhere else. `extensions/registry.ts::renderedCommand` reads a command's script and its assignments, and `renderedName` decides which commands are kendex's.
- The renderer and carrier share listener names. `crates/core/tests/pi_carrier.rs` checks real registrations and calls the carrier. `tests/listener-dispatch.test.ts` checks each delivery channel. `tests/vocab.test.ts` checks the carrier's tool and session translations. `tests/config.test.ts` checks project roots and trust.
- The project scope is read only when Pi reports the workspace trusted, for both the registry and `.pi/settings.json`; the global scope is trusted without asking because it holds the person's own files. That is why `PI_CODING_AGENT_DIR` counts only when root-anchored (`extensions/package-config.ts::piUserDir`, matching `crates/core/src/harness/pi.rs::pi_root_is_absolute_for`): a relative override would make an untrusted clone the global root.
- Every event asks for the project root, the settings and both registries. `extensions/config.ts::projectRoot` memoizes the walk per cwd for the settings window, "no project" included; `extensions/registry.ts` keeps each registry's parse while the file's inode, size and mtime are unchanged, and compiles each matcher pattern once. Only text that was read is kept: a failed read is not, since a permission change leaves the stat as it was.
- Input keying is one rename, `path` to `file_path` for `Read`, `Write` and `Edit`, with a relative path resolved against the session's working directory because Claude Code sends an absolute one; nothing else is reshaped. A guard authored against Claude Code's `Edit` payload does not see `old_string` and `new_string` under Pi.
- Refusals name the hook's label, never a custom command's text: that text is the person's and can hold a credential, and a reason is read by the model.
- Per-guard settings are a `Map` keyed by script name, and an unrecognised name runs under the master switch alone.
- The clippy check on `turn_end` reports through `pi.sendMessage` with `triggerTurn: true`, so a headless session reads it in the turn that follows. Every failing turn reports; the bound is that a turn writing no `.rs` file runs no clippy, unless the check before it was ended unfinished. The handler awaits cargo without holding Pi's thread, and passes the turn's `ctx.signal`, so a turn the person ends stops cargo and reports nothing, and its `.rs` edits stay in the set the next turn's check reads. Cargo runs through `extensions/process.ts::runCommandAsync` rather than `pi.exec`, which signals cargo alone and leaves rustc running (`extensions/cargo.ts::runCargo`). One run at a time per user holds the clippy slot, a file in the system temporary directory named with the user id (`extensions/cargo.ts::claimClippySlot`); `tests/clippy.test.ts` holds the tree kill, the slot and the thread.
- A hook's payload is built only once a hook is about to run (`extensions/dispatch.ts::runListener`), and what an event's hooks say to the agent is bounded by Pi's `truncateTail`, with the whole text saved to a file the notice names (`extensions/dispatch.ts::boundForAgent`). The bound is taken once per event: on a `tool_call` refusal's reason, and in `extensions/hooks.ts::report` for every listener Pi gives no verdict to. `tests/lazy-payload.test.ts` and `tests/output-bound.test.ts` hold them.
- The `turn_end` registry key is read on `agent_before_settle`, once per response (`extensions/hooks.ts::consultStop`). What the hooks say is appended as one `custom_message` entry after the entries earlier handlers proposed, with `continue: true`, Pi's one continuation inside the same run. The dispatch at the end of that continuation says `stop_hook_active: true`, appends what it is told and asks for nothing, so a response reaches at most two dispatches and one extra model request. `continue` is never returned `false`, which would cancel another handler's continuation, and `agent_settled` clears the state, so a continuation Pi ends early does not carry into the next response. `tests/stop-continuation.test.ts` runs this in a real Pi session; `tests/listener-dispatch.test.ts` holds the handler's answers.
- The lane mail wake (`extensions/lane-mail-wake.ts`) is its own manifest entry. Its `agent_settled` check runs after the `Stop` registrations have handed mail over, because Pi fires `agent_before_settle` first. It judges nothing itself: it runs the `lane-mail-deliver` registration's judge, the lane-mail-check hook, with the lead's session fields, so which mailbox the session reads, a lane's own or the checkout's overseer mailbox for a lead session that is no lane, what is unread and not an answer, and a subagent's stand-down are the hook's, as after a tool call. A wake whose text equals the last one's is not sent again, so a refusal or an unread halt the judge repeats at every settle starts one turn.
- Carrier diagnostics start with a stable key and its value. Hook output remains a payload from its producer. `extensions/drift-check.ts::driftMessage` controls drift report delivery in lanes. `tests/drift-check.test.ts` pins the exit and report protocol that the carrier parses.
- `pi-contract.json` lists, per extension file, the Pi events it listens on, the calls it makes on `pi` and `ctx`, the `ctx` fields it reads other than `cwd` and `hasUI`, and the exports of the Pi package it imports, each under `calls`, an export named with its package. The Pi update audit reads it to find the Breaking Changes entries that block a Pi release (`../AGENTS.md`). A change that adds or removes any of these in an extension file updates `pi-contract.json` in the same commit. `tests/pi-contract.test.ts` checks literal `pi.on` events and dotted `pi` and `ctx` accesses across the extension source files, including the shared settings reader. It ignores block comments and whole-line comments and handles optional accesses. It names a dynamic import bound to `pi` with its package. Named package exports remain a manual part of the inventory; this text check does not resolve aliases or computed accesses.

## Tests

```bash
npm test
```

`npm test` installs the Pi release the `devDependencies` pin, then runs `bun test ./tests`. `tests/lane-mail-wake.test.ts` runs a whole Pi session in process on it, with this package loaded from its manifest, a scripted model, orch's real `lane-mail` and the lane-mail hooks kendex renders for Pi, one row per rule the wake holds. Its turn before the mail ends on a speaking `Stop` hook, so it also holds the carrier to leaving the session free for a wake. `tests/stop-continuation.test.ts` runs a `Stop` hook's refusal in the same kind of session, and `tests/pi-session.ts` builds that session for both. `tests/harness.ts` builds a project with rendered registries in both scopes and a fake extension API. A new refusal path ships with the control that plants the failure it refuses, and a new copy of a kendex-side rule ships with the test that holds the two together.

A `pi` run by hand from inside a Pi subagent inherits `PI_SUBAGENT_CHILD_AGENT`, and the carrier then consults no `Stop` registration; unset it for that run. The suites clear it themselves (`tests/harness.ts::useIsolatedGitEnv`).
