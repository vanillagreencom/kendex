# pi-hooks development

For maintainers of the carrier. What it does for a consumer is [README.md](README.md); the mechanics live as doc comments on the functions named below, and this file holds only the invariants that span them.

## Invariants

- A guard that did not run does not stand aside. Every path that fails to reach a verdict is reported: a missing render, a timeout (read before the exit code, because a killed process still has one), a non-zero exit other than 2, a registry that exists and cannot be parsed, a matcher that will not compile. On `tool_call` the report is a refusal (`extensions/hooks.ts::toolCallVerdict`); on `tool_result`, `turn_end` and `session_start`, which gate nothing, it is a line the agent reads (`extensions/dispatch.ts::agentLine`). Only an absent registry is silent, because that is kendex having installed nothing. `extensions/dispatch.ts::runHook` and `extensions/registry.ts::readRegistry`; `tests/hooks.test.ts`, `tests/registry.test.ts`, and `tests/listener-dispatch.test.ts` hold these cases.
- The registry is the render, not a model of it. What runs is the command kendex wrote; nothing in the carrier knows a hook's name in advance, which is what lets a custom hook run at all. A hook kendex rendered is spawned at `<registry root>/hooks/<name>.sh` rather than through its command, because the command spells a project path as a walk that finds the file at run time and the registry it was read from is the anchor that walk would have to find. A command that sets an environment for that script is the exception and runs as written, since those assignments are in the command and nowhere else. `extensions/registry.ts::renderedCommand` reads a command's script and its assignments, and `renderedName` decides which commands are kendex's.
- The renderer and carrier share listener names. `crates/core/tests/pi_carrier.rs` checks real registrations and calls the carrier. `tests/listener-dispatch.test.ts` checks each delivery channel. `tests/vocab.test.ts` checks the carrier's tool and session translations. `tests/config.test.ts` checks project roots and trust.
- The project scope is read only when Pi reports the workspace trusted, for both the registry and `.pi/settings.json`; the global scope is trusted without asking because it holds the person's own files. That is why `PI_CODING_AGENT_DIR` counts only when root-anchored (`extensions/config.ts::rootAnchored`, matching `crates/core/src/harness/pi.rs::pi_root_is_absolute_for`): a relative override would make an untrusted clone the global root.
- Input keying is one rename, `path` to `file_path` for `Read`, `Write` and `Edit`, with a relative path resolved against the session's working directory because Claude Code sends an absolute one; nothing else is reshaped. A guard authored against Claude Code's `Edit` payload does not see `old_string` and `new_string` under Pi.
- Refusals name the hook's label, never a custom command's text: that text is the person's and can hold a credential, and a reason is read by the model.
- Per-guard settings are a `Map` keyed by script name, and an unrecognised name runs under the master switch alone.
- `turn_end` reports through `pi.sendMessage` with `triggerTurn: true`, because Pi discards the handler's return and a non-steering message is never read by a headless run that is ending. Every failing turn reports; the bound is that a turn writing no `.rs` file runs no clippy. The `turn_end` registry key is read on `agent_settled`, once per response, and the settle a steer caused dispatches again with `stop_hook_active: true` and does not steer, so a response reaches at most two dispatches. Whether the dispatch that steers waits for the run it asked for is read from `ctx.isIdle()` right after the send. Pi 0.80.4 through 0.86 start that run before the send returns and print mode disposes the runtime once its awaited `agent_settled` emit returns, so the dispatch waits for the settle the run ends in; each wait joins a set, since settles can overlap, and every exit of the next dispatch releases each wait armed before it began. Pi 0.87.0 defers the run until every `agent_settled` handler has returned and finishes it before the session reads idle, so the session still reads idle and the dispatch returns: a wait there would hold the settle open and no later prompt or triggered message would start a turn. `tests/listener-dispatch.test.ts` runs the print case on both shapes.
- The lane mail wake (`extensions/lane-mail-wake.ts`) is its own manifest entry, listed after `hooks.ts`, so its `agent_settled` check runs after the `Stop` registrations have handed mail over; `tests/lane-mail-wake.test.ts` pins the order. It judges nothing itself: it runs the `lane-mail-deliver` registration's judge, the lane-mail-check hook, with the lead's session fields, so which mailbox the session reads, a lane's own or the checkout's overseer mailbox for a lead session that is no lane, what is unread and not an answer, and a subagent's stand-down are the hook's, as after a tool call. A wake whose text equals the last one's is not sent again, so a refusal or an unread halt the judge repeats at every settle starts one turn.
- Carrier diagnostics start with a stable key and its value. Hook output and drift reports remain payloads from their producers. `tests/drift-check.test.ts` pins the exit and report protocol that the carrier parses.
- `pi-contract.json` lists, per extension file, the Pi events it listens on and the calls it makes on `pi` and `ctx`. The Pi update audit reads it to find the Breaking Changes entries that block a Pi release (`../AGENTS.md`). A change that adds or removes a Pi event listener or a call on `pi` or `ctx` in an extension file updates `pi-contract.json` in the same commit.

## Tests

```bash
npm test
```

`npm test` installs the Pi release the `devDependencies` pin, then runs `bun test ./tests`. `tests/lane-mail-wake.test.ts` runs a whole Pi session in process on it, with this package loaded from its manifest, a scripted model, orch's real `lane-mail` and the lane-mail hooks kendex renders for Pi, one row per rule the wake holds. Its turn before the mail ends on a speaking `Stop` hook, so it also holds the carrier to returning from the settle on Pi 0.87. `tests/harness.ts` builds a project with rendered registries in both scopes and a fake extension API. A new refusal path ships with the control that plants the failure it refuses, and a new copy of a kendex-side rule ships with the test that holds the two together.
