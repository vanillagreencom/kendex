# pi-tool-renderer development

For maintainers of the renderer. What it does for a consumer is [README.md](README.md); each module's doc comments hold its own mechanics, and this file holds what spans them.

## Invariants

- Rendering only. `extensions/tool-renderer/tools.ts` supplies drawing callbacks through Pi's documented `registerToolRenderer`; it registers no replacement execution definitions. Pi owns execution, argument preparation, prompt guidance and tool activation. Native resolvers follow extension load order and yield unrelated names through `next()`. `tool_batch` in `extensions/tool-renderer/batch.ts` delegates each child to Pi's `ctx.executeTool()`, so Pi owns argument validation, tool-call guards, result handlers and session metadata. `extensions/__tests__/batch-guards.test.ts` proves guard delivery with real Pi and pi-hooks, and restores direct execution in a disposable copy as its must-fail control. A change that alters what a tool does belongs in a different package.
- Install order in `extensions/tool-renderer.ts` is fixed: the stack events, the tool-execution renderer patch and live-settings refresh go in before chrome and message renderers, and tool renderers go in last, after the host agent module is imported. A patch that reads a symbol another patch installs depends on that order.
- Enabled `tool_batch` registers during factory loading, including SDK sessions that never bind extensions. Built-in searches remain discoverable, but compact drawing does not activate them. Explicit caller allowlists remain authoritative on reload; extension-owned batch retains Pi's defaultActive reload behavior. `extensions/__tests__/tool-registration.test.ts` exercises the real SDK contract.
- Every patch on a host component is guarded by a `Symbol.for("kendex.pi-tool-renderer.*")` marker so a reload does not stack a second copy. A new patch gets its own marker; a change to a patch's shape gets a new marker name, the way `installToolExecutionRendererPatch` carries `.v2`.
- Bash success or failure comes from Pi's error flag, not command output. For a failed standalone call, `commandExit` reads Pi's trailing exit-code footer; cancellation and timeout remain failures without inventing an exit code. Grouped calls use the recorded error state.
- Text reaches a line count, a preview or a clip only through `extensions/tool-renderer/text.ts::normalizeTerminalText`, which defers to `@earendil-works/pi-tui`'s `normalizeTerminalOutput` when the host exports it. A count taken from raw text disagrees with what Pi draws.
- Glyph resolution is one function, `extensions/tool-renderer/glyphs.ts::glyphStyle`: the global override wins, then the local `glyphStyle`, then the legacy `treeStyle`. The other kendex extensions read the override from this package's config id, so its key name is a cross-package contract.
- Project settings are read only after `recordProjectTrust` has seen Pi report the workspace trusted; `extensions/tool-renderer/package-config.ts::readPackageConfig` reads the user file alone until then. `PI_CODING_AGENT_DIR` counts only when root-anchored, matching `crates/core/src/harness/pi.rs::pi_root_is_absolute_for`.
- `extensions/tool-renderer/package-config.ts` is the settings reader every package in `pi-extensions/` vendors byte-identical. It serves each answer from memory for `SETTINGS_RECHECK_MS`, timed on `performance.now()` so a wall-clock step cannot stretch the window, then reads the files' text again and keeps the parsed answer when the text is unchanged. The trust answer is read on every call, so a trust change applies at once. `installSettingsCacheRefresh` drops every answer on `session_start` and on the `kendex:extension-settings-changed` event, so a manager edit applies on the next render; a hand edit to `settings.json` applies within the window. `extensions/tool-renderer/live-settings.ts` also clears on that event before it redraws, since its listener can run first.
- `extensions/tool-renderer/diff.ts::MAX_DIFF_INPUT_BYTES` caps the write diff and the edit result diff. `readDiffSnapshot` checks a file's size before it reads. `tools.ts::registerWriteDiffEvents` awaits old-file snapshots on Pi's supported `tool_call`, before execution, and adds drawing details on `tool_result` without replacing content or structured output. Its per-call state uses Pi's call identity, stays within `STACK_MAX_ITEMS`, and clears on result, execution end and existing agent/session resets; headless sessions retain none. An edit's result drawing derives its diff from Pi's unified patch without changing the original result. Call previews remain asynchronous, so a render call never waits on a file.
- Pi gives a tool row no disposal call. `extensions/tool-renderer/text.ts` keeps each pending row's blink and held resources (a write row's old-file snapshot) until its final render, `agent_end` or `session_shutdown`, whichever comes first. Pi can still redraw a row `agent_end` dropped, so that row stays settled, never blinking or holding again, until `session_shutdown`.
- `tool_batch` is one tool result, so it caps the combined child output to fit Pi's tool-result budget, head and tail preserved, after each built-in tool has applied its own truncation. A child past `batchCallTimeoutMs` is reported as timed out, never dropped.
- Images in `read` results are hidden while a floating overlay is up (`extensions/tool-renderer/overlay.ts`, through the shared modal-lock symbol) but keep their reserved rows, so the layout does not jump when the overlay closes.

## Tests

The suites under `extensions/__tests__/` run on `bun:test` and import the host packages, which are optional peers and are not installed in the tree:

```bash
cd pi-extensions/pi-tool-renderer
npm install --no-save --include=dev --include=peer --include=optional --no-package-lock --ignore-scripts --no-audit --no-fund @earendil-works/pi-agent-core@1.0.1 @earendil-works/pi-ai@1.0.1 @earendil-works/pi-coding-agent@1.0.1 @earendil-works/pi-tui@1.0.1 @earendil-works/pi-codemode@1.0.1 @earendil-works/pi-mcp@1.0.1 @earendil-works/pi-telemetry@1.0.1
npm test
```

The pinned version is the Pi release the extensions are audited against; `.github/workflows/skill-tests.yml` runs the same install. A renderer change ships with a case in the suite that draws it, and a change to a normalisation or width rule with one that measures it.
