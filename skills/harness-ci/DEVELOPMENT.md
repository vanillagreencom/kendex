# harness-ci development

Maintainer notes. Consumer docs: [README.md](README.md); the wiring rules: [SKILL.md](SKILL.md).

## Invariants

- `--no-renames` is fixed, never a flag. Rename detection emits only the post-image, so `git mv src/app.ts .agents/skills/x/app.ts` would list one harness path and nothing else, and the deletion of `src/app.ts` would go unjudged. Without it both paths are listed and the diff answers `false`.
- `pull_request` uses the merge base (`base...head`) because the base branch moves under an open PR. `push` and `merge_group` use the two endpoints (`base head`): a force-push leaves the `before` sha off the head's history, and a merge base there is a commit the push already discarded, so measuring from it reads a push that dropped product work as render-only. A merge group's base is an ancestor of its head by construction, so the two forms agree there.
- An empty changed-file set answers `false`, because it is also what a diff that read nothing looks like.
- Docs mode answers `false` when any changed path is outside the path set in `harness-only --help`. The `docs-only` suite enforces the set. It reads every changed path rather than stopping at the first outside the set, so `--outside-output` lists them all: the change-class action's lane verdicts ask the docs set about one path at a time through that list, and never spell the set a second time.
- The engine derives `.kendex-generated.json` from rendered artifact files, shared registration files, and instruction shims. It excludes in-place declarations. Pi carrier payloads do not enter the render model and remain source.
- Inventory membership is exact, never a folder prefix. A generated file adopted as source must be absent from the head inventory, which causes product checks to run. Deletions use the base inventory.
- `--mode render-candidate` permits ownership gains and the adopted caller without an inventory entry only to install render-proof prerequisites. The [caller ownership contract](SKILL.md#shared-refresh-caller-ownership) owns that exception. Its answer grants no skip. The normal harness verdict still refuses gains. The candidate suite keeps that refusal and its inverse; the real-engine rows prove an added `.agents` file and refuse a product file merely listed in the head inventory.
- A missing or invalid inventory runs every lane, including the commit that first installs the inventory. Inventory additions also run every lane before the new paths become trusted base data. A base that holds no inventory, older than the render that first wrote one, answers `cause=base-inventory-absent`; an inventory the base holds that git cannot read answers `cause=unreadable-base-inventory`, and one that does not parse `cause=invalid-generated-paths`.
- `change-class` applies its path and size rules on the `harness-only` `false` cause `cause=product-source-or-unreadable-ownership`. The adopted caller can take the render proof under the [caller ownership contract](SKILL.md#shared-refresh-caller-ownership). A `cause=generated-ownership-gain` reaches the render proof instead. The proof must pass and own every changed path, including gained paths and the inventory. A failed proof answers `standard`. Both causes keep their `harness-note:` line. `tests/change-class.test.sh` covers a refresh that adds a rendered file, a gained product path and a gained inventory without a passing owner. Its controls deny a gain access to the proof and skip coverage of the gained product path. Every other cause is a refusal to read something rather than a diff to measure, and answers `standard` carrying the cause as it stands, ahead of every path and size rule. The script's list names what may be measured, never what is refused, so `cause=invalid-generated-paths`, `cause=unreadable-base-inventory`, `cause=unreadable-head-inventory`, `cause=unreadable-changed-path`, `cause=file-lookup-failed` and every cause `harness-only` adds later are refused by the default without being named. One cause is a reading rather than a refusal: `cause=base-inventory-absent` says the base holds no inventory, so ownership at that end is not recorded, and `change-class` answers `standard` for it as a fixed rule ahead of the size rules, marked `measured=true` although no size was measured. The same diff on a base with an inventory can earn a narrower class. A long-lived branch whose merge base predates the inventory then reaches the review policy with a class rather than a refusal. The render proof has the second reading: `cause=render-retirement-unproved` is a retired render whose diff, head tree, head inventory and verify document all read, and that the document's `base_owned`, the whole files and trees the base revision's install record names, does not name as a `file` or hold under a `tree`. A document that carries no `base_owned` answers the same cause. Either answers `standard` with `measured=true` too. A retirement `base_owned` names is owned, and a diff of such retirements alone classifies `render`. It answers only after every other changed path is read, and a failed read among them, before or after the retired path, answers in its place with `measured=false`. An unowned or partially owned path is a rule verdict with `measured=true` and selects full checks. A consumer refresh that retires a render and changes no refused path is then published for full review rather than stopping.
- `aggregate-needs` accepts a skipped job only when the classifier succeeded and either its waiver is `true` and the job is in the caller's explicit skippable set, or the job is named in a `--lane` whose verdict, read out of the classifier job's outputs in the results it was handed, is `false`. An absent verdict authorizes nothing, the verdict is never a separate argument a workflow could compute wrongly, and a job named by two `--lane`s is refused rather than decided by argument order.
- `change-class` reads no diff range of its own: it calls `harness-only` for the changed-path set and for the generated-path ownership rules, and repeats that run's `changed-path:`, `base-rev:` and `head-rev:` lines as they stand and its verdict cause as a `harness-note:` line. The two revision lines are the operator's record of the range the paths came from, and the render proof's only reads of it: the proof checks out the `head-rev:` commit and hands the `base-rev:` revision to `kendex verify --base`, and resolves neither end itself. The private checkout reads the judged repository's object-store path, remote settings and partial-clone settings. It writes its own git directory and object store. It does not write the judged working tree.
- `trivial`, `micro` and `small` all need orch's line count read and are all refused by its path list, which runs ahead of the trivial decision; a plan-only `trivial` is the one that measures no ceiling against that count. The ceilings in that file are `micro`'s and `small`'s alone.
- A cross-package call into orch checks `BRANCH_GROWTH_CONTRACT` first. Each package is installed at its own revision, so the sibling can be older than the caller, and errexit is off inside `measure`: a missing function would be `command not found` on stderr and an extra argument would be dropped in silence.
- A harness instruction pointer (`CLAUDE.md`, `*/CLAUDE.md`) is refused every narrow class except `render`. Inside a diff the render proof covers it is a render like any other; anywhere else nothing re-rendered it and the shipped documentation set would take a root one for ordinary markdown.
- The `render` class needs `kendex verify --scope project --json` to report files checked and none failed, and needs every surviving changed path to be owned by a position a passing row of that document prints or by the released-caller proof in [SKILL.md](SKILL.md). A row's positions are the engine's own answer to where the installation sits, printed with the row: a file kendex owns whole, a tree it owns whole, or keys inside a shared file it writes entries in. A file position owns exactly the path it names; a tree position owns its path and the paths under it. A keys position — a hook registry, a settings file, an MCP server list — owns its path only where the row also says `foreign: unchanged`, which is kendex's own judgement that the file as the range's base held it, with kendex's edits applied over it, is byte for byte the file on disk; the classifier hands `kendex verify --base` the revision `harness-only` printed on its `base-rev:` line and parses no settings file itself. Anything else on such a file answers `standard cause=render-path-partial path=<p> foreign=<changed|unknown>`, and a surviving path neither a passing position nor the released-caller proof covers answers `standard cause=render-path-unowned path=<p>`. Deletion requirements and refusals are in `change-class --help`. Either refusal is printed under `render-coverage: named=<n>`, the count of positions the run read, which goes out ahead of the ownership pass so a refused run still says what it weighed; beside it the refusal prints verify's own rows and one `render-position: owns=<o> foreign=<f> path=<p>` line per position printed under the refused path's top-level directory, so the log names the rows an operator would otherwise re-run kendex to see. Ownership is read off rows in state `ok` alone. A clean exit alone is not proof: it also closes a run that checked nothing, so the document's `checked` count is read, and a run that checked nothing answers `standard cause=verify-counted-nothing`. The JSON document owns row, position and count evidence, version first: a kendex that rejects `--json`, which every release up to and including v5.0.1 does, exits non-zero on the flag and answers `standard cause=verify-refused`; one that accepts the flag but prints no document, or one of another `version`, answers `standard cause=verify-document-unreadable` rather than being read by guesswork, and the human rows are never parsed. On a failed verify call, the classifier reads stderr only for the stable remedy fields `verb=source operation=refresh`. Those fields select `cause=source-mirror-missing`; they grant no render waiver. Other refusals keep `cause=verify-refused`. The two files kendex keeps about itself, `.kendex-lock.json` and `.kendex-generated.json`, reach the proof as positions of the `record` and `inventory` rows that document prints, each in state `ok` only where `kendex verify` found the file as it would write it, and are granted by name to nobody. The script parses no record itself: the head record is owned from its `record` row, and the base record reaches the script only as kendex's `base_owned`. What makes those rows trustworthy is `kendex verify` itself, whose row set is closed against the scope's declarations in both directions — a recorded entry nothing declares fails its row and a declared installation the record does not hold is a gap — and whose record and inventory rows fail on an edit to either file. The classifier passes `--at-record` beside `--base`. It renders each package that follows its source and that the record can place at the commit the record names, Pi extensions included; a package with a revision of its own renders at that revision. The record row fails a held commit off the history of the revision its source resolves to now, or older than the commit the base's record names, so a render pull request the catalog moved past between its push and the writer pass is weighed on its own record rather than refused, while a branch that rewrites its record back to an older catalog commit is not a render. The document's `stale` list, one entry per source commit the record or a held package trails, comes out as one `render-stale: source=<s> recorded=<sha> resolved=<sha>` line each after `render-proof:`. A build without the flag rejects it, and the run answers `standard cause=verify-refused`; the caller must supply a build that carries it. A diff of generated files alone that fails the proof answers `standard`; it never falls through to a measured class. The de-listing chain KEN-1637 recorded closes at its first step: a commit that drops a rendered path from the inventory and its entry from the record fails the inventory row and names the gap, so it never buys the class; the hand edit cut from it still measures as product code, since the path is on the inventory at neither of its endpoints, which `tests/change-class.test.sh` pins beside the refused de-listing.
- The render proof's verifier is the `kendex` on PATH, except on a diff whose only changed path is `.kendex-lock.json` while the environment sets `HARNESS_CI_LOCK_KENDEX`. That record is written by a kendex built from the recording tree, whose registration shape the release on PATH may not know yet, so a caller may supply kendex's rolling main build there. The variable is read from the environment alone, because it names a binary on the runner. The `render-verifier: verifier=<path|lock> version=<v>` line names the verifier, and `cause=verify-refused` carries the same two fields so a refusal reads as the verifier's age. A lock path that is not executable answers `standard cause=no-verifier verifier=lock`. `tests/lock-verifier.test.sh` holds the selection.
- No shipped kendex reaches the failed-count refusal on a zero exit today, since a run with a failing row exits non-zero before the document's `failed` count is read; the refusal is the guard against a kendex that later reports failures beside a zero status, and its survival under mutation is that, not a gap.
- The `render` proof weighs the commit `--head` resolved to, never the judged checkout's working tree. `change-class` runs `git init` in its scratch directory, points the new repository's alternates file at the judged repository's object store, copies the judged clone's remote and partial-clone settings into that private git directory, checks out the `head-rev:` commit there, and runs `kendex verify` in that checkout. A partial clone fetches missing blobs into the private object store. Anything uncommitted in the judged checkout, ignored files included, never reaches the proof, and neither does the commit the checkout sits at: `references/wiring.md` § Shape 4 checks `subject` out at the pull request's merge ref, and a local caller's checkout can sit anywhere. A checkout that cannot be made, or that `git checkout` leaves short of the commit while exiting 0, as it does on a blob it cannot read, answers `standard cause=head-checkout-failed`.
- The private checkout has its own git directory because `kendex verify` runs a package's declared checker out of the tree it checks wherever kendex's arming record sits under a git directory, and that checker is a file a pull request can change. A record in the common git directory reaches every linked worktree, so a `git worktree add` of the judged repository would carry it; `git init` makes a fresh git directory, which holds no record. The whole-project scope is also what makes the proof slow and what makes unrelated drift refuse the class; the rows now carry the path-to-package map, and the proof still runs whole because the row set closed against the declarations is a whole-scope fact.
- A changed kendex configuration file refuses every narrow class, ahead of the render proof, except the byte-exact top-level `kendex.toml` schema step that `harness-only` removes from its changed-path set. A hand edit counts the same as the engine's edit: that line decides no render or classifier input, and the proof still runs `kendex verify` on the head. Other configuration changes keep the refusal, and so does `.gemini/settings.json`, which kendex generates but whose shim row weighs one key of the document. `CLAUDE.md` is refused below the render branch as an instruction pointer. An `AGENTS.md` or `SKILL.md` is not refused: it changes how every agent behaves, so a diff carrying one that earns `trivial` or `micro` answers `small`, `cause=instruction-file`, the lowest class the default review policy gives one bot round. Those globs are the `instruction` lines of orch's `narrow-change.conf`, which `item-tier` reads too, and a list carrying none is one from before the floor, refused as `cause=narrow-change-floor-missing`. The list's extglob lines sit beside the broad `path` line a `superseded` line names, which a `change-class` from before the extglob grammar still reads and refuses on, since orch and harness-ci are installed at their own revisions. The registry files a harness executes as configuration refuse every narrow class but `render`, below the render branch, one project-scope entry per structured surface the adapters under `crates/core/src/harness` name: `.claude/settings.json`, `.claude/settings.local.json`, `.mcp.json`, `.codex/config.toml`, `.codex/hooks.json`, `.agents/hooks.json`, `.agents/mcp_config.json`, `.pi/settings.json`, `.pi/kendex/hooks.json`, `opencode.json`, `opencode.jsonc`, `.cursor/hooks.json`, `.cursor/mcp.json`, `.github/copilot/settings.json`, `.github/copilot/settings.local.json`, `.github/mcp.json` and `.github/hooks/*.json`. The last is a glob because Copilot's hook registry is one file per hook named for the hook, which `engine/targets.rs` `copilot_hook` writes as `.github/hooks/<name>.json`. Their keys name the hooks that run and the MCP servers that may be started, and a harness executes them whether or not kendex wrote the file, so a hand-authored one the inventory does not carry must not fall through to the size rules. One the inventory does carry reaches the render proof first, where the owner rule for such a file is stated once, on `Owns::Keys` in `crates/core/src/engine/desired.rs`: kendex owns keys inside it and never the file, so the row owns it only with `foreign: unchanged` beside it. The two groups together cover every harness the adapters name: this list holds every one of them but Gemini, whose settings file sits in the configuration-source group above because the row kendex prints for it vouches for one key alone. A harness added later joins this list, unless its surface is one kendex only partly vouches for, which joins the configuration-source refusal instead; nothing derives either group from the adapters at run time.
- The measured classes come from orch's `branch_size_classified`, which owns the production/test split and render-mirror pairing for CI. `change-class` hands it the base endpoint the call named, so the lines are counted over the range the paths came from. The subsystem rule sets aside every path on the measurement's `BRANCH_SIZE_TEST_FILES` list and never judges a test path again: a script and its fixture under another top-level directory are one subsystem. The measurement lists every changed path, a binary file and a render copy included, where the path or its remainder past a render root is a test, and lists each end of a rename on its own; a paired render mirror is listed where its remainder is a test and its lines count as mirror lines, and every other row counts as test lines exactly when its path is listed. Only `--event pull_request` and `--event merge_group` reach a measured class; every other event answers `render` or `standard`. The size reader takes a three-dot range, which on a merge group is the same commits as the two-dot one because its base is an ancestor of its head, so the two events are measured over the range each already defines.
- The judged tree's configuration decides nothing. `change-class` reads its four measurement settings from this process's environment, else from the `[env]` tables of the settings files the commit `--base` names holds, and the repository's standard paths, queue list and selector, `HARNESS_CI_STANDARD_PATHS`, `HARNESS_CI_QUEUE_PATHS` and `HARNESS_CI_QUEUE_SELECTOR`, from those tables alone, in the ladder's order, parsed by orch's `kendex_load_settings_file` and never sourced, before `branch_growth_render_roots_from_env` fixes the render roots. That commit is the pull request's base tip or a merge group's base, never the merge base, which the author picks by choosing where to fork. Loading the judged tree's settings would let the change under judgement choose the roots its own size is scored against, and would source the file its `KENDEX_ENV_FILE` names; a settings file the branch changes is a configuration source, refused before the measurement runs.
- The queue selector is the one command `change-class` runs out of a repository, and it runs the base commit's copy in a private checkout of that commit, made as the render proof's checkout is, never the judged tree's: the branch under judgement can neither name the command nor change what it runs, while a change to the selector itself is judged by the copy it replaces. It is asked only on `pull_request` and `merge_group`, the events whose merge route it decides, and only where every path rule read `queue_only=false`, at the verdict, because the jobs a merge group runs can depend on the class: kendex's own selection, `tools/ci-job-set`, runs no shell shard on a `render` change, and on a `trivial` one only where a path the Rust source reads gives it a measured class's row.
- A glob list is split with pathname expansion off. Splitting it under the default would replace a glob naming a real directory with the files under the caller's working directory, and the list would no longer be the list.

The `change-class` suite's last section installs and refreshes a real consumer with a real `kendex` rather than a double, which is the only way its rows can say what a real refresh earns: the pure refresh is a `render`, owned from the positions its passing rows print, in an armed consumer too; the same refresh with one rendered file hand-edited is refused at the proof itself; a consumer sitting at one commit has the proof weigh the other named as `--head`, in both directions; and a commit that de-lists one render from the inventory and drops its entry from the record is refused at the proof too, the inventory row naming the de-listed path. Its last rows move the catalog and the primed mirror past the refresh: the refresh is still a `render` and names the source it trails on a `render-stale:` line, the hand edit is still refused, and a branch that puts the older install back, record and renders together, is refused against the base's record. The pure refresh row asserts that a record the catalog has not moved past prints no `render-stale:` line. It drops the fetched mirror and primes it back with `kendex source refresh` before the classify rows, which is how `references/wiring.md` § Shape 4 primes a runner, and it asserts the judged tree is unchanged across that step. Every call it makes runs through `kendex_here`, which captures the output and prints a `FAIL:` line naming the command, that output and the binary's version before the suite reports and stops: the rows after a failed install would judge a tree that was never built, and with the output discarded a runner carrying the wrong binary died at exit 2 with nothing in the log to say which call it was. Without a `kendex` on PATH the section skips itself, so `.github/workflows/skill-tests.yml` builds the checkout's own `kendex-cli` on the Linux leg of the `rest` shard and sets `HARNESS_CI_REQUIRE_KENDEX` for every Linux leg of the job, which turns that skip into a failure wherever the suite runs. Building from the checkout is what keeps the rows and the verify they read from in one commit: the contract between them is the `--json` document's `version`, pinned in `change-class` as `VERIFY_DOCUMENT_VERSION`, and a consumer copying `references/wiring.md` § Shape 4 pins a release whose `kendex verify --json` prints that version. The fixture builds its own catalog as a local git repository and fetches it into a sandbox `HOME`. The macOS leg keeps the skip: it is already that shard's slowest leg, and the rows judge the classifier rather than the platform, so one leg proves them.

`tests/lib/workflow.sh` reads a workflow's job conditions, needs, names and triggers, plants a defect in a copy, and runs `tests/lib/gh-eval.py`, which evaluates the conditions, through `gh_eval`, which turns a refusal into an answer no row expects; kendex's `tools/tests/ci-aggregate.test.sh` reads its own `skill-tests.yml` with the same two files.

`tools/bash32-lint` checks the shipped script for Bash 4+ syntax, because consumer runners include macOS system Bash 3.2.
