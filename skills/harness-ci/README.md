# harness-ci

A changed-file check for CI. It lets CI skip selected checks when a change contains only recorded generated files or only documentation files.

## Features

- Compare the files a change touched with the list of files kendex generated.
- Classify documentation-only changes.
- Run product checks for unrecorded files and uncertain results.
- Support pull requests, pushes and merge-queue events.
- Validate skipped jobs before a required-context aggregator reports success.
- Name the kind of a change: a re-rendered install, a trivial edit, a micro or small change, or anything else.
- Ship a CI workflow template that reports one `CI` check, the aggregate context every repository under the standard reports, and runs the same checks on a merge queue as on the pull request.

## Install

```bash
kendex add vanillagreencom/kendex --skill harness-ci
```

## How it works

- kendex writes a list of every file it generated, called the inventory, beside the files it installed.
- Your CI step tells the checker which GitHub event it is handling and which two commits to compare.
- The checker works out the range that event needs, then reads the inventory as it stood at each end of that range.
- Harness mode answers `true` only when every file the change touched is on the inventory at each end where that file exists.
- Docs mode answers `true` only when every changed path is in its documented path set.
- Anything it cannot prove answers `false`, and your workflow uses that answer to run or skip the product checks.
- The aggregate helper accepts a skipped job only when a successful classifier authorized that job.
- A workflow with several lanes can list, in its default branch's `.github/ci-lanes.conf`, the paths each lane reads. The change-class action then answers per lane: on a change that runs lanes at all, a lane runs where the change touches one of its paths, and every lane runs where it touches a path no lane lists that is not documentation. The list is read from the default branch, so a change cannot stand its own lanes down. A lane marked `:queue` there, a slow benchmark for example, is the one exception to that: on a pull request whose change touches its paths, it waits for the merge group, even where every other lane runs. It waits only where the classifier read that same pull request queue-only, which sends the merge through the queue, and only where the installed harness-ci of both the default branch and the pull request is new enough to read the mark; otherwise it runs on the pull request. Refresh the install, and sync the checkout you merge from, before marking a lane, and re-run CI on open pull requests after removing a mark. The other cases, a list that is missing or broken among them, are [references/wiring.md § Per-lane verdicts](references/wiring.md#per-lane-verdicts).
- The change classifier reuses that same reading of the diff and adds size and path rules, so CI, the merge route and a working agent all read one verdict instead of inventing their own.
- Beside the class, the classifier says whether the change is queue-only: a change to CI, to what the required checks read, to the shared test harness, to `kendex.toml` or to the review-bot instructions must run in the merge queue before it lands. The paths are orch's `references/narrow-change.conf` `queue` lines, which name this catalog's own CI inputs, the repository's own `HARNESS_CI_QUEUE_PATHS`, and the paths of each lane marked `:queue`. A repository whose merge group runs jobs no pull request runs can also name, in `HARNESS_CI_QUEUE_SELECTOR`, the command that selects those jobs and the output it lists them in; the classifier runs the default branch's copy of it, and a change it lists any job for is queue-only too. A harness-ci install older than the release that adds `HARNESS_CI_QUEUE_SELECTOR` ignores that key and lets such a change take the admin merge with those jobs never run, so refresh harness-ci on the default branch, and sync the checkout that runs `github.sh pr-merge`, before the setting lands there. A repository that has not set `HARNESS_CI_QUEUE_PATHS` has declared no list of its own, so every change there reads queue-only and never takes the admin merge, and the classifier prints one warning to set the key in `[env]`.
- The change-class action also asks GitHub whether a passing run of the same workflow already tested the same tree: a merge group reuses its pull request's run where the group tests the tree that run tested, and the merge queue's push to the default branch reuses the merge group's. A run leaves a small record of what it covered as an artifact, and the later run stands down only what that record covers, and only lanes you have said do the same work on every event: `covers-all-lanes: true` for a workflow with no lane list, as the template passes, or `:event-uniform` after a lane's name in `.github/ci-lanes.conf`. A lane with a job or step that runs on one event alone, or with a check over the changes since the event's base, keeps running. Every refusal prints its reason and runs the lanes. The rules are [references/wiring.md § Proof reuse](references/wiring.md#proof-reuse).
- It proves a re-rendered install by asking kendex to re-render, never by trusting the list of generated files or the install record, either of which the change itself could rewrite. It asks at the catalog commits the install record names, each of which has to be on its source's published history and no older than the commit the base branch's record names, so a refresh the catalog has moved past since it was pushed is still a render, and the log names each source commit it trails. `kendex verify --json` prints one record per thing it checked, with the files, trees and shared-file keys that thing occupies, and every changed file needs a passing record or the released caller proof in the [caller ownership contract](SKILL.md#shared-refresh-caller-ownership). A file the change deletes has no such record: it is covered only where `kendex verify --base` lists it among the files and trees the base branch's install record owned whole, and is `standard` where that list does not name it or kendex prints no list. The list reads the files each install record entry says it wrote. A record written before kendex kept those files for agents, commands and hooks names none for them, so retiring one of those answers `standard` until a later refresh's base record carries them. The two files kendex keeps about itself are records of that run like any other, each passing only where kendex found the file as it would write it, so a change that only re-runs kendex is a render and a change that edits those files by hand is not. It weighs a private checkout of the commit `--head` names, never the working tree it is pointed at, so nothing uncommitted there counts.
- A change of generated files alone whose re-render proof fails, or that touches a generated file no passing record covers, answers `standard` outright and never reaches the size rules, so only a change that touches a file kendex did not generate reaches the size rules at all.
- The files a harness itself executes as configuration are never trivial, micro or small, whoever wrote them: the settings, hook registries and MCP server lists under `.claude/`, `.codex/`, `.cursor/`, `.agents/`, `.pi/` and `.github/`, the repository root `.mcp.json` and opencode's root config file: one entry per harness kendex knows other than Gemini, whose settings file is named at the end of this bullet. Their keys decide which hooks run and which servers may be started. kendex writes entries in those files and never the whole file, so a re-render of one counts as a render only where kendex itself reports that nothing else in the file changed since the range's base; the Gemini settings file, whose record vouches for one key alone, is refused ahead of everything else as a changed configuration source.

## Setup

Commit the installed skill and generated-file inventory. The CI runner needs `jq`, a `kendex` on its PATH and a source mirror it has already fetched. The released refresh caller check also needs `python3` on PATH, per the [caller ownership contract](SKILL.md#shared-refresh-caller-ownership). Missing Python leaves an unrecorded caller at `standard`. Use review-gate's `install-latest.sh` from the trusted default branch, as [references/wiring.md](references/wiring.md) shows. It selects the latest stable release and its exact installer commit. Gate the install and mirror steps with `harness-only --mode render-candidate`; that answer permits prerequisites only and grants no CI skip. The real verifier must prove render before product jobs skip.

The installed engine must support `verify --json` with document version 1 and `verify --at-record`. An unsupported release leaves the class `standard` and runs product checks. A refresh produced by a newer unreleased engine needs a compatible release before it can get a render waiver. Local calls, including orch's `dev-validate-run` and github's `pr-merge`, use the executable on PATH. A diff whose only changed path is `.kendex-lock.json` instead uses the executable `HARNESS_CI_LOCK_KENDEX` names, where the classifier's environment sets it.

The harness and docs checkers have no project settings. The change classifier also reads repository settings. `HARNESS_CI_STANDARD_PATHS` names high-risk paths as blank-separated globs. A matching path selects `standard` before render proof and size classification, including generated files with proved ownership. The globs use the shared exclusion grammar and add to its exclusions. Unset or empty adds none. `HARNESS_CI_QUEUE_PATHS` names the repository's own queue-only paths, its CI inputs outside `.github/` such as a test harness or a CI aggregator script, as blank-separated globs; set it empty where the shipped list already names them all. It has no default: unset, every change is queue-only, with one warning per run naming the key. `HARNESS_CI_QUEUE_SELECTOR`, unset by default, is `COMMAND OUTPUT`: a repository command, as a path from the repository root, and the `name=value` output in which it writes a JSON list of the jobs a merge group runs for the change; `change-class --help` states the inputs it is given. Unset, no selector runs. The other two each have a shipped default: `HARNESS_CI_TRIVIAL_PATHS`, the repository's own low-blast allowlist as blank-separated globs (empty, the default, uses the documentation path set: `docs/`, `changelog.d/` and root Markdown files, so a root `README.md` edit under the ceiling counts as trivial while `CLAUDE.md` and every configuration source are refused ahead of it, and an `AGENTS.md` or `SKILL.md` edit that earns trivial answers `small` with `cause=instruction-file`), and `HARNESS_CI_TRIVIAL_MAX_LINES`, the line ceiling under which those paths count as trivial (default 20). The classifier reads these and the two below from `kendex.settings.toml` and `.kendex/settings.toml`, the second winning, as the commit `--base` names holds them (the pull request's base tip or a merge group's base, never the merge base), never from the branch being judged and never from the private env file. A value in its environment wins for every one but `HARNESS_CI_STANDARD_PATHS`, `HARNESS_CI_QUEUE_PATHS` and `HARNESS_CI_QUEUE_SELECTOR`, which are the base's alone. Two further inputs are orch's measurement settings: `ORCH_SIZE_RENDER_ROOTS`, the harness directories a render mirrors a source into, and `ORCH_SIZE_TEST_PATHS`, the globs that mark a file as a test rather than as product code. The classify step of [Shape 4](references/wiring.md#shape-4--one-change-class-for-every-reader) sets `ORCH_SIZE_RENDER_ROOTS`. A consumer whose test files live outside orch's default globs sets `ORCH_SIZE_TEST_PATHS` in its default branch's `kendex.settings.toml`, which CI and a lane's own classifier run both read. The CI call supplies the mode, event, and commit identifiers. A check that must apply its own policy rules to the exact changed-path set reads it from `harness-only --paths-output`, where that set is derived. Use `harness-only --help`, `change-class --help` and `aggregate-needs --help` for all arguments.
