# Continuing session

Follow this workflow when starting a continuing session, reconciling open work or transferring control.

Use [Task reconciliation](tasks.md) for incoming requests, replies, worker results and blocker changes before launching work or waiting. Run that same procedure during Start's queue reconciliation, Progress checkpoint and Succession's reconciliation.

Read each named section with `.agents/skills/jarvis/scripts/jarvis-section FILE 'Heading text'`, using its owning file and exact heading. The command includes child sections and stops before the next heading of the same or higher level. Use already loaded text when a parent read includes the requested child.

## Session command

- Start, resume and succession read published policy from the systemd user manager on Linux and from launchd's caller context on macOS. Shell-only exports do not reach a managed session. The selection list in `scripts/lib/session.py`'s `environment()` owns the supported names; extend it through a package change. A source read failure refuses launch before handover. Status and Stop remain available. Selected-account launch owners supply credentials and harness identity; Pi alone can retain the caller's explicit `CLAUDE_CONFIG_DIR` for its Claude provider.
- Before the first Start with Copilot CLI, follow [Copilot folder trust](../references/home-layout.md#copilot-folder-trust) unless the home's `JARVIS_UNATTENDED_HARNESSES` names `copilot`.
- Before the first Start with Claude Code in a home whose `JARVIS_UNATTENDED_HARNESSES` names `claude`, follow [Claude Code bypass consent](../references/home-layout.md#claude-code-bypass-consent).
- `JARVIS_UNATTENDED_HARNESSES` in the home's `kendex.settings.toml` `[env]` names, comma-separated, the start harnesses whose managed session runs with nobody at its pane. Start, resume and succession launch a named harness with the full-bypass permission words orch writes for overseers: `--dangerously-skip-permissions` on Claude Code, `--dangerously-bypass-approvals-and-sandbox` on Codex and `--allow-all` on Copilot CLI. Pi has no such word. Empty, the default, launches every harness with its native permission defaults.
- Start the controller through `.agents/skills/jarvis/scripts/jarvis-session start --home HOME --harness claude|codex|copilot|pi --account DIR --mode resume|new --origin manual`. Use the Jarvis package installed in HOME. Supply the account directory for the selected app. Both modes follow [Start](#start).
- Append `--model MODEL --effort LEVEL`, both or neither, to launch a stated model. `MODEL` accepts the model class or native model spelling the task command takes, and the pair is recorded as the session's choice. A Pi model that spends another app's account, a `pi-claude/` model, is refused. A succession that falls back to the recorded account keeps that choice. Without them, a resumed session keeps its recorded choice and a new one runs the app's own default model. A running session with another or no recorded choice starts new context, as an account change does.
- A consumer can append `--brief-file PATH` with its private instructions on one printable line. The session command delivers those instructions with Start after the harness confirms its native identity. The session record keeps the instructions, so every successor, a `succeed` retry included, receives them with its Start brief, and the consumer can remove the file once Start answers. A session started without `--brief-file` gives its successors the Start brief alone. This route starts no repository overseer workflow.
- To move a Jarvis session that runs outside this package onto it, run Start with `--mode new --origin manual --adopt-pane PANE --adopt-pid PID` from inside that session. PANE names its tmux pane and PID that pane's process. Start refuses before saving or stopping anything. It answers `name-conflict` when the home's record names a running or starting controller. It answers `selection-conflict` when PANE is missing or dead, its process is not PID, or PID runs no supported harness or two at the same nearest depth, and one `jarvis-session: adopt=refused` line names the cause. The harness nearest PID names the session, so a Pi session's codex-bridge child is not a second one. Start's own arguments select the successor's app, account, model and brief. The command then follows [Succession](#succession): it saves `state/handoff.md` and ends that process by its process identity. It closes only that pane and opens the home's `jarvis` session for the successor. Start answers `handing-over`, and status reads as for succession. A retry is `succeed`, which selects the successor through orch's walk rather than Start's arguments.
- Read `.agents/skills/jarvis/scripts/jarvis-session status --home HOME` for the recorded session. A `starting` answer means a fact Start waits for is still unconfirmed: the native identity, on Copilot CLI and Codex the end of the kickoff turn the launch submits before the brief, or the session's taking of the Start brief at its first tool call or, on Claude Code, Codex and Copilot CLI, its turn end. Pi also counts a completed turn when its pi-hooks carrier supplies the run outcome; an older carrier still needs a tool call. While a controller is live, status also prints one stderr line, `jarvis-session: attach=PATH attach --home HOME`, with PATH this `jarvis-session` script's full path and both shell-quoted; its JSON answer is unchanged. Status starts and stops nothing.
- `.agents/skills/jarvis/scripts/jarvis-session attach --home HOME` puts the caller's terminal on the live controller's session, under [Attach](../references/home-layout.md#attach). It prints nothing on stdout. A refusal exits 1 with one `jarvis-session: attach=refused cause=CAUSE` line: `no-controller`, `record-unreadable`, `tmux-missing`, `terminal-unresolved` (`xdg-terminal-exec` is not on PATH) or `terminal-launch-failed` (the terminal could not be started or watched, exited non-zero, or put no new client on the session within 5 seconds). A terminal refusal's detail follows that line, with the end of the terminal's own error output when it exited non-zero. With no live controller it starts nothing.
- `.agents/skills/jarvis/scripts/jarvis-session report-due --home HOME` reads orch's derived schedule using the controller's original session start. Succession retains that start. When adopting this checkpoint in an already running session, repeat its Start command once to establish the start floor.
- On a satellite, `jarvis-session forward --home HOME --record PATH` forwards a confirmed owner request to the main, under [Agent reach: Forward](../references/agent-reach.md#forward).
- `jarvis-session forward-drain --home HOME` retries queued forwards and reads the main's answers while one waits. The satellite's `watch-loop` runs it every 60 seconds; run it by hand only to retry at once. With no open forward it makes no SSH call, and prints only the `EVENT forward-failed` block of a forward closed as `answer-unseen` in the last 30 days.
- `jarvis-session status --home HOME --main` reads only the local outbox and settings. It starts nothing and makes no SSH call. A main answers `{"v":1,"role":"main"}`. A satellite answers `role`, `main` (the SSH destination), `reachable` and `checked_at` from the last call to the main, both `null` before any call, `cause`, `last_answer` and `requests`. Each request row names `request` (the record's request reference), `key`, `state` (`queued`, `delivered` or `read`), `cause`, `forwarded`, `queued_at` and `attempts`. A forward closes when the main's answer is read, and shows only in `last_answer` after that. With no open forward, an old `checked_at` is expected; with a queued request, it means the watch loop is not running. The default `status` answer is unchanged.
- The causes are `main-unreachable` (SSH failed or timed out), `mailbox-missing`, `overseer-absent` (no session is registered in the main home, nothing was appended), `overseer-unreadable`, `send-failed`, `read-failed`, `receipts-missed` and `setting-invalid`. `main-unread` means the main received the request and its reader has not read it. A request whose receipt was lost reads `queued` with `overseer-absent` while the main session is unregistered, although the main already holds it; the next delivery or the answer settles it, and the main lands it once while it keeps the first copy. Once the main's compaction drops that copy, a send whose receipt was lost can land a second time. A forward with no answer read within 7 days of its delivery closes as `answer-unseen`; it reaches the session once as `EVENT forward-failed` and leaves `requests`.
- Stop through `.agents/skills/jarvis/scripts/jarvis-session stop --home HOME`. An app that turns Jarvis off uses `--origin app-off`. Only `start --origin app-on` clears that Off. A boot caller uses `start --origin boot`; a repeated call in the same login does not start another session.

## Task command

- Launch a task with `.agents/skills/jarvis/scripts/task launch --home HOME --name NAME --harness claude|codex|copilot|pi --model MODEL --task-file PATH --result-file PATH`. The managed Jarvis session must be running. Use the same command for each harness. `MODEL` accepts the existing model class or native model spelling; Pi uses its provider/model spelling. Add `--effort LEVEL` when high is not the intended effort. The existing lane selector chooses the account. Add `--account DIR` to ask that selector about a named account.
- Add `--short` for a task of a few minutes when every account of the harness is past the launch limit. The selector then accepts an account with room left up to its wall (`lanes pick --max-pct 100`). The overseer seat reserve and the projected wall still apply. Full workers launch without it.
- Put the private brief in the task file. Add one `--input PATH` for each other input. The task reads that brief directly and writes its Output to the result file. This route starts no repository overseer workflow.
- Add `--cwd PATH` to start the harness in an existing directory and use its native instruction loading there. Without it, the task starts in `HOME`. Relative task, input, result and working-directory paths resolve from the caller's directory. Task records and scratch stay owned by the Jarvis home; the selected directory does not move them or the result destination. An invalid or unavailable directory refuses before task allocation.
- Add `--browser` for browser work. Each launch creates its own absolute scratch directory and browser profile beneath it. The child receives `JARVIS_TASK_SCRATCH`, `JARVIS_BROWSER_PROFILE` and `JARVIS_BROWSER_PORT=0` so Chromium allocates the profile's debugging endpoint. The record's `browser_port` keeps this allocation request; `jarvis-browser --port` reports the live port. Use that profile with the [browser guide](../references/browser.md#profile-and-tabs). Keep the result outside scratch so cleanup retains it.
- Retain the returned task id. Read its record with `task status --home HOME --id ID`; it names the task, inputs, selected model and account, result path and terminal window. Record the outcome with `task complete --home HOME --id ID --outcome succeeded|failed`. A succeeded task requires its result file. After checking the result and closing task-owned browser work, run `task cleanup --home HOME --id ID`. Cleanup closes that task's window, stops the browser running on its profile, and removes its scratch. Completion and cleanup remain on the same task record.
- A launch records a running task only once the harness can take its brief. A Claude Code account whose `.claude.json` lacks `hasCompletedOnboarding` refuses `harness-setup-pending` before the window opens. For every harness, a pane that by the end of the startup bound shows no composer or turn, or shows a dialog, a sign-in banner (Claude Code, Codex, Copilot) or a usage-limit banner (Claude Code, Codex), refuses `harness-not-ready` and prints that screen. Each refusal prints a `fix=` line naming the account. Open the harness once on that account, finish its first-run setup or the screen shown, then launch the task again.
- A launch refused after task allocation prints its task id and retains the failure cause. Read that record with `task status`; if cleanup is pending, read its `reason`, close task-owned browser work and retry `task cleanup`. Reason `browser-running` names a browser on the task's profile that could not be stopped. Task windows open in the Jarvis session, so Stop ends them with it. Once the controller has ended, Stop or Start ends a session that holds only task windows; a session of that name holding any other window stays, and Start then answers `name-conflict`. An unfinished task whose window has gone reads `failed` with reason `controller-ended`. Its scratch remains for inspection and explicit cleanup.

## Start

- Read the State, Sub-agents and Instructions in force sections of `state/handoff.md` first with `jarvis-section`, at the path in the [home layout](../references/home-layout.md). If it is absent and the user has an earlier handoff elsewhere, read those sections there. Have the user move it once to the current path. Read the [Handoff contract](../references/long-session.md#handoff) with `jarvis-section` before using it. Apply its checkpoint, staleness and recovery rules. Ask the user to set the staleness bound if none exists.
- Load only the safety core at start: the role in [persona.md](../persona.md), [Authority](../references/decisions.md#authority), [Secret transfer](../references/accounts-and-secrets.md#secret-transfer) and [Official records](../references/accounts-and-secrets.md#official-records). Use already loaded text rather than reading it again. Keep one assistant in control at a time.
- Check current holds and temporary instructions in the compact handoff sections above. Read the current owner request with its delivered context. Apply its decision boundary through Authority before choosing work.
- Check the event registration state in the handoff's State section.
- For control-host events, register and start `watch-loop` through [Control-host events](#control-host-events). For another selected event source, use its supported registration and delivery interface.
- On a satellite, read `jarvis-session status --home HOME --main` and report each open forward that has a cause. A confirmation a crash left unforwarded is forwarded by running `forward` again with the same record; a console confirmation with no reply still shows in `owner-unanswered`.
- Check the user channel and each agent's channel for unread events. Keep one communication channel per agent. Use the source's delivery order rather than sorting event ids.
- Confirm the session prerequisites under [Homes](../references/long-session.md#homes). If they are missing, take its setup route as the first decision and leave the handoff untouched. Otherwise read all open session work from the selected tracker project, through every page. Compare that list with the handoff's tracker ids; those ids are an index, not the discovery source. Reconcile the tracker queue, the open asks and the due audits through live reads of their homes. Keep a compact view of open work and due obligations for the first decision. Check what each open item waits for and why. Resume authorized work when the wait no longer applies.
- Read no other record before the first decision.
- Before taking the selected action, load its sections under [Action routes](#action-routes).
- Follow [Handoff replacement](#handoff-replacement) before writing the current handoff under the [Handoff contract](../references/long-session.md#handoff) and entering the event loop.

## Control-host events

- Read [Control-host events](../references/control-host-events.md) before starting or recovering the producer. Use the settings in the [example](../kendex.settings.toml.example). Select one absolute home path for every start and recovery command.
- From the native session's own pane, run `.agents/skills/orch/scripts/oversee register`. The session's next native hook establishes its session binding. Registration alone cannot renew presence. A satellite registers only in its own home, and its loop runs as a satellite under [Control-host events](../references/control-host-events.md#satellite).
- Set the existing orch keys `ORCH_WAKE_PROCESS` and `ORCH_WAKE_START` in the home's settings. The process pattern matches `watch-loop --home HOME` for this home. Escape regular-expression characters in HOME. The start command names this same home and its harness route below. The existing turn-end check reports an absent loop and that command. It starts no process.
- On Claude Code, run `.agents/skills/jarvis/scripts/watch-loop --home HOME` through Monitor at its maximum expiry. Keep that same loop for the session. A batch pointer means the directive is ready in the home mailbox. Read it through the installed deliver hook or `.agents/skills/mailbox/scripts/lane-mail inbox --item overseer` from HOME. Re-arm Monitor only on expiry or reported loop death.
- On Pi and Copilot, launch the same command through `.agents/skills/orch/scripts/lib/job-unit.sh launch NAME RECORD -- .agents/skills/jarvis/scripts/watch-loop --home HOME`. Use a home-specific NAME and retain RECORD with the runner's process group PID in the handoff. Pi's installed mailbox wake delivers the directive. Copilot's installed hooks deliver at their native checkpoints; this producer supplies no idle extension.
- Stop a job through `.agents/skills/orch/scripts/lib/job-unit.sh stop-job RECORD PID '*watch-loop --home HOME*'`, using its retained record and process identity. Stop the Monitor-owned command through Monitor. Retain the event log and batch state for restart. Keep the source registration, home, launch route and runner record in the handoff's State section.

## Event loop

- Read each delivered event and connect it to an open item or create that item.
- On `EVENT report-due`, follow [Progress checkpoint](#progress-checkpoint). The producer schedules this event; set no model timer and store no due row.
- Load the action's sections under [Action routes](#action-routes) before acting.
- Handle user decisions through [decisions.md:Authority](../references/decisions.md#authority). Use [communication.md:Message types](../references/communication.md#message-types) for replies, notices and scheduled reports.
- Update the item's state after each action. Keep an unresolved obligation open until its acceptance check passes.
- Run the verify pass after handling events and before waiting again. Select the checks under [Homes](../references/long-session.md#homes). Check each due box at its evidence source under [verification.md:Sources](../references/verification.md#sources). Record the outcome on the item and take the next action on failure.
- Wait through the selected event source when no authorized work or due check remains.

## Progress checkpoint

- Read [Homes](../references/long-session.md#homes), the [Handoff contract](../references/long-session.md#handoff), [Message types](../references/communication.md#message-types) and [Delivery](../references/communication.md#delivery) through `jarvis-section`.
- Capture the collection cutoff in UTC before reading live evidence. Read the tracker live through every page: Verifying counts, each item's entry time into that state, and open session checks. Read landings with merge times at or after the event's `since` cutoff and before the collection cutoff, and pending asks and their answers from the live mailboxes. Use the consumer's selected repositories and tracker project. A failed read is unavailable evidence; preserve that distinction in the report.
- Refresh changed lines in the handoff's four required sections and its checkpoint coverage. Correct the State lines `progress-log --check-state` lists under the Handoff contract in the same write. Follow Handoff replacement before converting an older handoff. Run the consumer's registered checks from its standing instructions and record their results at their owning tracker items.
- Write the summary using communication's report template. Before sending, run `.agents/skills/orch/scripts/oversee-report check-summary --summary-file SUMMARY`. Read its advisory findings and correct the summary on your judgment; findings never refuse delivery. Follow the consumer's report format and delivery settings.
- Write the report to the path `.agents/skills/orch/scripts/workflow-state progress-report-path` gives. Set the completed file's modification time to the retained collection cutoff with `TZ=UTC touch -t YYYYMMDDhhmm.SS -- PATH` before the first send. Send it once through `.agents/skills/mailbox/scripts/lane-mail notice --item overseer --to owner --attach PATH --file SUMMARY`. Follow the consumer's report format and delivery settings. Keep the file and its modification time unchanged on a failed send and retry that same attachment; do not claim delivery or advance coverage without the writer's receipt. Record an unresolved send as open work before waiting or handing over.
- Read `jarvis-session report-due --home HOME` after delivery to confirm the schedule. The next checkpoint is derived from the receipted file, and succession inherits that schedule without copying a due time. Commit changed session state under the Handoff contract.

## Handoff replacement

- After the initial reads and first decision, read every section of the predecessor handoff and its progress log. Include records in Owed and open, Context, Agent contact, Verify and Open requests when those sections exist.
- For every record outside session state, write it to its home under [Homes](../references/long-session.md#homes), or confirm that its home already retains it. Preserve its contents, durable id and recorded time. Read each destination to confirm retention before replacing the handoff or clearing the progress log. A failed destination read or write leaves the predecessor handoff and progress log untouched and stops replacement.
- Archive the predecessor's handoff and progress log in the `archive/` directory beside the current handoff, `state/archive/` in the [home layout](../references/home-layout.md), before replacing them. Then index each archived file with `.agents/skills/jarvis/scripts/progress-log --archived FILE`, adding the `--handoff PATH` that selects the current handoff when it is not the default. Use the retention rule in [accounts-and-secrets.md:Retention](../references/accounts-and-secrets.md#retention). An archive or index failure stops replacement.

## Succession

- Judge whether the remaining context permits continued work. Use the user's succession trigger when they set one.
- Follow [Handoff replacement](#handoff-replacement) and the reconciliation and update rules in the [Handoff contract](../references/long-session.md#handoff), read through `jarvis-section`.
- Wait for attached agents under the Handoff contract before calling the session command. Keep reconciliation and retention in this workflow; the command cannot read every harness's attached-agent state.
- After replacement succeeds, leave the successor's progress log empty in `state/handoff.md`. Run `.agents/skills/jarvis/scripts/jarvis-session succeed --home HOME` from the Jarvis package installed in that home.
- A caller that has positively established an account wall runs `.agents/skills/jarvis/scripts/jarvis-session succeed --home HOME --account-walled`. The command binds that wall to the recorded controller's account. It excludes that account even when its reading reports room or cannot measure it. An eligible alternative can succeed; without one, the command refuses before ending the predecessor. Ordinary context or voluntary succession omits the flag.
- The command selects a successor through orch's overseer preference walk and account pick, from the first `ORCH_OVERSEER_PREFERENCE` entry, with the recorded account and its choice last. In ordinary succession, a named entry that qualifies launches with its own model and effort, even on the recorded account's directory. The walk falls back to the recorded account, unchanged, only when no named entry has an account with room. When orch's account reading refuses it launch headroom, it is left out and the walk ends on another account of its harness; with none, succession refuses before the predecessor ends. With no preference set, an ordinary succession keeps a recorded account that still has room, or that nothing measures. A Pi session whose model names no provider skips the walk only in ordinary succession. Wall recovery tries eligible named alternatives and refuses when none qualifies. A Pi entry whose model spends no Pi account is skipped. An entry whose account reading fails refuses succession before the predecessor ends. The home and saved handoff stay with the successor.
- The walk does not read `JARVIS_UNATTENDED_HARNESSES`, and the successor carries its own harness's words only when the setting names that harness; to keep every successor unattended, name every harness the overseer preference can reach. Per-account setup, such as Claude Code bypass consent, applies to every account the preference's harnesses can pick. A missing orch dependency refuses succession before the predecessor ends; report the returned account and failure to the owner.
- Before saving or stopping the predecessor, selection leaves out a Claude Code account that has not finished first-run setup, using the task launch's shared `harness-setup-pending` check and its `fix=` line, and walks the same entries on to the next account. The command saves that handoff and opens a waiting runner in a new window of the same tmux session. It ends the predecessor by its recorded process identity before it starts the successor. Native identity confirmation precedes the successor's Start brief.
- Read `jarvis-session status --home HOME` for the transfer. A transfer in progress answers `handing-over` with reason `succession`. If a worker ends before the predecessor ends, the predecessor keeps control. If something outside the worker stops it after the predecessor ends, such as a signal or a host stop of its scope, the successor's waiting runner finishes the transfer: the record's `worker_ended` names the worker's PID and its cause, `SIGTERM` when that stopped it, else `unknown`, and `session.log` holds the matching `transfer=adopted` line. A worker that fails the transfer itself ends it as below. After the predecessor ends, a failed Start fails the unfinished tasks and closes their windows, then retries the recorded successor choice once through the same launch path and saved brief; the tasks stay failed whether or not that retry succeeds. If the retry also fails, status answers `failed` with reason `handover-failed`, and the package sends one owner notice to the home's overseer mailbox. Retry `succeed` for that home. An unfinished wall transfer keeps its original spent-account exclusion on retries, including retries without the flag. A completed transfer ends that exclusion; a new explicit wall binds the current controller's account. Boot and Start do not resume the retired predecessor.
- Keep session state in the current handoff. Never move it into memory.
