## Tests

```bash
bash skills/orch/tests/run-all.sh
bash skills/orch/tests/run-all.sh lane-host   # subset by name fragment
bash skills/orch/tests/run-all.sh open-terminal oversee       # either fragment
bash skills/orch/tests/run-all.sh '!open-terminal' '!oversee' # neither
bash skills/orch/tests/run-all.sh =lanes                     # that suite alone
```

A bare argument selects and `!name` rejects; `=name` in either place matches one whole suite name, the form `tools/guard --range` passes for the suites a diff maps to. A set of fragments and that set negated split the battery: no suite runs in both halves and none runs in neither. CI also passes `--shard` for the oversee profiles that `run-all.sh` selects by `RUNNER_OS`. `tools/tests/orch-shard-partition.test.sh` holds each platform's partition to exactly one run per suite.

Each `tests/*.sh` is self-contained: it builds its own sandbox with parametrized CLI stubs on `PATH`, prints `pass: N fail: M`, and exits 0 only when every assertion passed. `run-all.sh` discovers them at execution time, so a new suite needs no registration. It runs them `nproc` at a time, so a suite shares its host with the others and keeps every file, socket and process it makes inside its own sandbox. A suite whose fixed wall-clock window a loaded host has made it miss goes in `run-all.sh`'s `ALONE` list, and runs by itself after the others. The `run-all.sh` header states the report it prints, and `tests/run-all-parallel.sh` holds it.

Every shell suite asserts through `lib/assertions.sh`, sourced directly or through `lib/oversee-watch-harness.sh`, and defines none of its names. `tests/assertions.test.sh` holds the library, judging without it. `lane-host.sh` and `lane-host-ssh.sh` run Python suites and have no shell assertions.

Every `tests/*.sh` carries one line directly under its `set -...o pipefail`:

```bash
source "$(dirname "${BASH_SOURCE[0]}")/lib/git-env.sh"
```

That lib is where the four git environment variables are cleared, so a new suite adds the line rather than its own `unset`.

An installed skill omits its top-level `tests/`, so the runner's suites run from the catalog checkout. Byte identity and idempotence of what an apply writes are covered upstream of the installed tree, in `crates/core/tests/byte_faithful.rs`.

Run probes that import Python fixtures with `python3 -B`. Bytecode caches under the catalog become render inputs.

## Invariants the tests pin

- Relaunch ownership comes from the lane record's bound session and the home its last confirmed launch recorded, never kickoff text: the runtime's relaunch route (`runtime/src/effects/launch.rs`) resumes a session only by its fixed id, under the same harness and account, and otherwise starts fresh and names its cause. `tests/rust/effects.rs` holds the account switch and the same account's resume. The wake's session lookup, `find_relaunch_session` in `scripts/lib/lane-relaunch.sh`, serves Claude and Pi alone: it takes the newest lead transcript whose recorded working directory is the item's worktree. Copilot's resume id stays with `scripts/lib/copilot-session.sh`.
- Round-id identity. Every dev and QA delegation mints a token through the runtime's `begin-round` (a nanosecond timestamp plus a random suffix) and embeds it; `dev-return-write --round-id RID` writes `tmp/dev-return-[ISSUE]-[RID].json` with `round_id` inside, and `dev-artifact-check --round-id RID` resolves that exact path and requires the internal token to match. There is one identity model, no mtime gate and no positional mode, so a same-second re-stamp, a late-writing timed-out agent, a bundle group-A receipt consumed by group-B, and a cross-round ci-fix receipt are all unmatchable. `dev_delegated_at` is the epoch second of the round's delegation; [references/skill-rules.md § Round Closure](references/skill-rules.md#round-closure) owns its uses. Gate ordering and field rules: `dev-artifact-check --help` and [references/artifact-checks.md](references/artifact-checks.md); schemas in [schemas/](schemas/).
- Help is inert. Every orch CLI that loads project configuration answers a help form before the load. A parser reached by a dry run runs twice, so an arm that returns may only assign; an arm that prints must then exit. Held by `tools/tests/help-inert.test.sh`.
- Inherited git environment. `GIT_DIR`, `GIT_COMMON_DIR`, `GIT_WORK_TREE` and `GIT_INDEX_FILE` outrank `git -C <path>`, so a suite that inherits them builds its fixtures inside the caller's repository and still reports a clean pass. `lib/git-env.sh` clears all four at load. `git-env-isolation.test.sh` holds both halves: it runs `dev_round_gate.sh` with all four exported at a sandbox repository and pins that repository's log and index unchanged, repeating the run against a copied tree whose lib is neutralized to prove the clearing is what holds it.
- Sourced libs inherit that clearing. Every lib under `tests/lib/` that shells out to git does so with a bare `git -C` and is sandboxed only because the suite that sourced it sourced `lib/git-env.sh` first. A lib added here rests on that precondition.
- Shard coverage. CI runs the battery as shards and a shard is nothing but a `run-all.sh` name filter, so a filter that stopped matching would drop its suites out of every shard while every shard stayed green. `tools/tests/orch-shard-partition.test.sh` reads those filters out of `.github/workflows/skill-tests.yml`, replays them over the real suite names in a sandbox of empty files, and requires each suite in exactly one shard; its controls drop a shard and repeat a shard.
- Controls. `help-inert.test.sh` plants its own must-fail controls. `lanes-settings-refusal.sh` does not, so re-run it against the pre-fix file when changing what it covers.
- Waits. `tests/rust/verify.rs` drives `verify-review` through the built binary against the fixture `gh`, and `tests/rust/queue_watch.rs` drives `queue-watch`'s poll loop on the runtime's fake clock, so a deadline case cannot race a loaded runner. The mailbox skill's `lane-mail.sh` runs its `wait` rows on `lib/virtual-clock.sh`, whose `date`/`sleep` stubs make a poll budget arithmetic over a file rather than real seconds, and asserts the seconds they slept. Which repository a script reads is `lib/gh-repo.sh`'s ladder, held by `gh-repo-resolve.test.sh`.

- Detached job completion. `codex_round_wait.sh` executes the launch script from [Waiter launch](references/waiter-launch.md) with the process-owned reviewer launch from `references/codex-runtime.md` against the real artifact checkers, and reads the recorded exit. `job_unit.sh` holds the shell job runner's launch, record and stop rows. The runtime's own job launcher is held by the `controller` target's job rows.

- Secret-value pattern. `secret-value.test.sh` reads [references/secret-value.ere](references/secret-value.ere) by the reader contract in its header and runs every row through both readers the header names, `grep -aiE` in the C locale and Python's `re` with `re.I | re.M`; each row needs its verdict from both. Its control removes the `xapp-` branch and requires an app token to pass.

## Effect boundary

The runtime at `runtime/` is its own Cargo workspace; run `cargo clippy --all-targets -- -D warnings` there. Its `clippy.toml` lists the tmux, process, session, job, store, clock, wait and file primitives as disallowed methods, so that command refuses an ordinary call of one outside `src/effects/operation/` and the functions that carry an allowance. The list guards against an accidental call past the operation handle; a deliberate bypass is a code-review matter, never the list's. An allowance is one `#[allow(clippy::disallowed_methods, reason = "..")]` on a function, a trait impl's method, a test module or `mod operation`, its reason at the attribute, reviewed with the change that adds it; the inventory is those attributes. A new acting function in agent-runtime joins the list in the same change. Before building a guard here, state the goal it serves and who it is against, weigh its upkeep against the harm it prevents, and treat a constructed bypass as a defect only when ordinary code reaches it.

## GitHub auth ladder

`overseer-approve`, `dev-validate-run` and `oversee-report` share `scripts/lib/gh-auth.sh`, which wraps the GitHub skill's helpers; the GitHub skill's `scripts/gh-auth-ladder` runs the same helpers for the runtime's watch. Each candidate is probed at most once, except the timed-out env token in step 1:

1. Selected env token. `GH_TOKEN` or `GITHUB_TOKEN` set: validate with a bounded `gh api user`. A 403 naming an integration, which a GitHub App installation token gets, is validated again with a bounded `gh api installation/repositories`. A value with no known token prefix is selected only when that validation passes. A validation killed at `KENDEX_GITHUB_AUTH_TIMEOUT` (status 124) is asked once more before the keyring fallback, since the first call through an egress proxy can be the slow one, and a second killed check drops it. `tests/oversee_report.sh` holds that re-ask for `oversee-report`, and the github skill's `tests/env-first-auth.sh` holds it for `gh-auth-ladder`. One env token gets at most three checks in `oversee-report` and `gh-auth-ladder`, whose sanitize check comes first, each bounded by `KENDEX_GITHUB_AUTH_TIMEOUT`.
2. Keyring fallback. That token failing: `env -u GH_TOKEN -u GITHUB_TOKEN gh auth status` once; on success, warn on stderr and unset the stale env token.
3. Bot token. Keyring not recovering: unset the stale env tokens, then load a `GH_BOT_TOKEN` candidate from process env or project config. `op://` references resolve through `op read` only after the final source is selected. The `github.sh` router separately prefers a resolved `GH_BOT_TOKEN` over a resolved `GITHUB_TOKEN`, so bot access is not blocked by a user token.
4. No-env keyring. No env token at startup and no bot token: probe keyring auth once.
5. Hard fail. Nothing works: exit `3` with a diagnostic. Callers never poll against empty output. `oversee-report` runs steps 1 to 3 and refuses as `auth-failed` with exit `2`. `orch-runtime watch run` runs the GitHub skill's `scripts/gh-auth-ladder` once at its start, which takes steps 1 to 3 and prints its selection, then starts itself again under it, so the runtime's `gh` children inherit the selected token; a ladder that selects nothing refuses the start as `auth-failed service=github`, and the runtime's own per-read refusal is the failure path after that.

`op` CLI service-account setup is outside orch: launchers may inject resolved secrets before starting a harness, and orch preserves those values rather than clobbering them with local `op://` references.

## Git HTTPS fallback

Merge and submit workflows use targeted `origin` operations through the GitHub skill's `scripts/git-https-auth` rather than broad remote enumeration. The helper is a per-command fallback for SSH-backed GitHub remotes: it validates env-token or keyring `gh` auth, then supplies temporary `credential.helper` and `url.insteadOf` config so GitHub SSH URLs work over HTTPS. It persists nothing. Never use `git fetch --all --prune` for PR closure: a secondary remote's SSH failure must not block branch cleanup or tracker closure.

## Reviewer slot budget

`REVIEWER_SLOT_BUDGET` bounds reviewer fanout for runtimes that cap concurrent agent threads. It is the runtime's total agent-session budget counting the primary session; `0` means unlimited. When the reviewer set exceeds the available slots, review workflows run bounded waves. On surfaces with a close call, retirement releases completed threads. Codex MultiAgentV2 has no close call: every spawned thread holds its slot for the session's life, live or finished, and `interrupt_agent` releases none. The configured budget is advisory and the runtime cap authoritative: a persistent launch that hits the thread-limit error demotes to waves in place, persists the observed size, and recommends it to the user.

On the Codex collaboration runtime the cap is MultiAgentV2's configurable `features.multi_agent_v2.max_concurrent_threads_per_session`. `spawn-adapter slots` reports the effective cap, warns when only the ignored `agents.max_threads` is set, and notes that a running session keeps the cap it started with. Before each Codex spawn, read `effective_cap` from `spawn-adapter slots` and count every held thread through `list_agents`, including the primary once. At the cap, reuse eligible finished threads through `followup_task` and run waves before reporting a blocker. [references/skill-rules.md § Codex thread reuse](references/skill-rules.md#codex-thread-reuse) owns eligibility, the complete target-role delegation and V1 `close_agent` retirement. A reused thread's fixed runtime instructions must permit its new task. Review state lives in on-disk artifacts and workflow state, never in reviewer session memory.

## CI triggering

orch waits for the review result before CI verification. An armed PR still waits for GitHub's required approval and thread resolution. CI job selection belongs to the repository's workflow. The CI wait is the runtime's `verify-pr` operation, which a workflow repeats through Waiter launch while it answers `pending`, no check registered included, within `CI_WAIT_MAX_SECS`; the merge-queue wait's probe reads the head's required checks through one `verify-pr` read per probe interval, so a check not yet registered reads `pending` there too.

Reruns re-execute the workflow definition and verifier state pinned at the original triggering event, so a PR that changes gate or CI behavior only exhibits the new behavior on a fresh head. Reruns are for flakes and re-gating unchanged workflows: the workflows rerun a transient runner failure once per head through the github skill's `ci-rerun`, the item's `ci_rerun` record written before the verb runs.

## Merge route

A lane merges its own pull request: `merge-pr.md` § 5 step 1 runs `pr-merge` on the exact head, under the lanes app's installation token in a lane sandbox. `pr-merge` merges past the queue with `--admin` where the queue is all that token would bypass on the base and the change is not queue-only; otherwise GitHub queues the PR (exit `75`) and the lane waits in the runtime's `queue-watch` to a terminal verdict, where a finding that lands while the PR is queued takes it back out through `queue-watch`'s late-findings guard. The route and its causes: `pr-merge --help` § Merge route. `merge-pr.md` § 5 step 1 owns the explicit arms for `pr_approval.forced` and unresolved merge state. `submit-pr.md` § 2 step 5 owns ordinary creation arms.

The overseer's owner-credential merge, the `--force` override and the `ORCH_MERGE_BYPASS` fast path are retired; their settings are read by nothing.

## Launch lanes

The host dispatcher and static SSH provider have separate suites, `tests/lane-host.sh` and `tests/lane-host-ssh.sh`. The dispatcher suite holds the per-home bound on provider calls: under a cap of 2, a third call is refused as `lane-host-busy`, a waiting call is admitted once a slot frees, and a slot left by a killed dispatcher is reclaimed. Its call-site test finds every command under `scripts/` run with a provider verb or with its caller's whole argument list, reading an array expanded whole before the command, such as the github skill's `KENDEX_GROUP_LEADER`, as a prefix, and fails on one that does not resolve to `scripts/lane-host`, tracing a function's positional argument through its callers; planted direct calls are its controls. The provider suite executes its SSH command payloads in temporary Git repositories with an SSH transport stub. It uses the installed worktree command to check shared links and copies after clone preparation. It executes the Claude prefix and records process arguments to check that the token travels only in the environment. It also covers account bytes, repeated creation, provider failures, dirty-close refusal, and close after lane cleanup removes the worktree. The `append` cases add lines to a mailbox file, close a fragment an interrupted writer left, drop a cut transfer, create an item directory the lane has not opened with the transfer umask keeping it private, and hold the mailbox lock against a second writer, which waits for it and writes through it once the lock call is removed. Archive tests read saved records, observe the printed path before deletion, and check that transport and local storage failures preserve remote data. They cover only records still present at close. The suite does not establish live SSH connectivity. The shared provider fixture is `tests/fixtures/lane-host`; launcher and watcher integration use that protocol independently. Its `append` runs the package library that `LANE_HOST_STUB_LIB` names, the way the real provider runs the one in the remote clone it is given. The optional SSH reference uses Python's standard library to quote remote shell arguments and transfer binary files without putting credentials in arguments.

[`runtime/src/ops/accounts.rs`](runtime/src/ops/accounts.rs) owns the account listing and judge, including model windows, launch projections, overseer seats and grant ordering. Its module documentation states the measurement and refusal rules. Token renewal uses the shared credentials lock in agent-runtime; [`runtime/src/ops/accounts/renewal.rs`](runtime/src/ops/accounts/renewal.rs) owns its endpoint and Codex CLI answers.

A launch's routing and brief rules are in [lane-directive.md § Lane preference](references/lane-directive.md#lane-preference) and [§ Brief file](references/lane-directive.md#brief-file). ## Overseer session

`overseer-host` dispatches to the runtime provider `ORCH_OVERSEER_HOST` names and `overseer-host-tmux` is the included one; the protocol is `schemas/overseer-host.md`. `lib/overseer-launch.sh` holds the steps `oversee register` and `oversee-succeed` share, the record read and the session inspection, beside `oversee-succeed`'s account walk and flag words, so a control planted in one of those steps is planted in that library's copy: `tests/oversee_succeed.sh` builds its copies through `tests/lib/growth-state.sh`'s `mutant_scripts`, a tree of links to the shipped scripts with the one file a case mutates copied in. `tests/overseer-host.sh` runs the dispatcher against a fixture provider and the tmux provider against a real server on a private socket. `tests/oversee_launch.sh` runs `oversee register` against a server at the default socket under a private `TMUX_TMPDIR`, which is how a run with no `$TMUX` and `ORCH_TMUX_SESSION` set reaches the person's own server; its controls drop the permission readback of a line launched through an account executable, and the reset of a pane's native binding when it registers again. `lib/tmux-server.sh` is the one rule for which server a verb reaches and whether it holds a named session, read by `oversee`, `overseer-host-tmux`, `lane-close` and `workflow-state`, by the mailbox's `lane-mail` and Jarvis's session backend, and by every script that sources `lib/overseer-launch.sh`.

The overseer's death, wall and identity come from its own session rows, `lib/session-rows.sh`: the `session-start-row`, `session-end-row` and `stop-failure-row` hooks run `lane-mail-check row`, which appends one JSON row per event, only for the pane's top-level harness as `session_rows_top_level` judges it, to `tmp/lane-mail/overseer/session-<server>-<pane number>.jsonl` at the main checkout under the mailbox lock, and the overseer's own turn end writes a Stop at every turn end, compact except over a standing StopFailure, which it lifts; the Stop dates the turn end the watch holds the context record against. `session_rows_top_level` requires exactly one harness in the ancestry between the hook and the pane's shell. The verified direct pair of the installed Codex Node launcher and its native child counts as one harness. An additional harness or unrelated Node ancestor prevents the write. The fleet state's `overseer.session_rows` names that file, which the watch's liveness judgement reads; `oversee register` and `oversee-succeed` compute the same path through `session_rows_overseer_file`, as the hook's writer does, and the watch's context record check, which reads its turn rows for `overseer-context-stale`, reads the path the record names. Row shapes follow Claude Code 2.1.283's hook inputs, which carry no reset time as a field: the StopFailure row's `message` is the harness's text of the limit and its reset. Each row hook writes its event's row on the harnesses that `kendex show hook <name>`'s supported tools line lists as neither unsupported nor advisory: OpenCode and Cursor, which its harnesses line names, run no hooks and write none; Copilot's rows are built from its camelCase payloads, which name no event, under the event the row hook names. Codex fires SessionEnd for its main thread alone, its `reason` always `other` (Codex hooks reference, CLI 0.160.0), so its SessionEnd row is the lead session's. A harness another harness started in the same pane, such as second-opinion's `claude -p`, writes nothing, and neither does a harness that is the pane's process itself (`tmux new-window claude`, `exec claude` at the prompt, a tmux default command), since the pane's own process is where the count stops; each takes the pane fallback. A launched overseer is typed into the pane's shell and is none of these. A session whose last row names any harness but Claude Code or Pi reads `unsupported`, and the watch takes the pane. Pi's carrier says its SessionEnd reasons in Claude Code's words and names no StopFailure error kind, so a Pi StopFailure row is a wall where `lane_limit_banner` reads its `message` as the account's limit, the judge a Pi lane's rows take. A Pi row is judged only from the evidence it carries: a Pi last row that is neither a SessionEnd nor a StopFailure with a `message` reads `unsupported`, since a Pi session writes a StopFailure only where its carrier dispatches one, so its SessionStart or Stop says nothing of a wall. The pane capture is the named fallback wherever no row can judge: the watch's verdict then carries `source=pane`, and `oversee register` says so under `identity-fallback`. The successor wait never reads a row: the harness writes SessionStart before its first turn runs, so only `inspect --launch` shows the turn it waits for. A line run under `scripts/overseer-run` has the record's `exit` dropped before it runs and the harness's exit status written there once it returns; the watch reads that status as the death ahead of the rows, `source=record`, where the pane's process is a bare shell with nothing but shells under it, which covers a harness killed before its SessionEnd hook runs. A harness started again in that pane is a child of the shell, and the status reads as an earlier session's. The runtime's launch runs no such wrapper, so neither a session it opens nor a session no launcher opened has that status: its pane's process, a bare shell with nothing but shells under it, reads as `source=process`. No suite holds the wrapper. A wall its rows state, which stands unless the account judgement measures room since only a finished turn writes the row that lifts it, and a live session whose account mark is reached at value 0 (`source=account`), are succeeded in the first pass that reads them; only a pane wall keeps the `ORCH_OVERSEER_DEAD_PASSES` debounce. `tests/rust/watch_observe.rs`'s row `a_dead_overseer_is_counted_on_two_passes_and_transferred_once_with_cause_dead` judges a blank pane from its rows, and `hooks/tests/session-rows.test.sh` holds the writer; both plant their own controls.

## Container close

`container-close` owns Linear container closure and `sync-base` owns base resolution, fetch, checkout ownership and the fast-forward. Both contracts are in their own `--help`. Completion validation inside `container-close` reports facts and decides nothing: it must provide exactly one parent result, with Boolean `has_summary`, array `container_open_boxes` and `errors`, and a numeric or null `child_box`, and Boolean `ok`, `state_ok` and `has_summary` on every child result. The helper's one decision table reads those rows; it never reads `all_ok`, and never infers that a later child completion came from a parent cascade.

## Codex app worktree routing

Codex Desktop handoff starts each child thread in an app-managed worktree, often on a detached `HEAD`. Generated Codex agents must be tracked under `.codex/agents/*.toml` in the saved project branch to be visible before subagent discovery; local ignored files are not enough, because setup hooks, `WORKTREE_SYMLINKS`, and `codex-setup` all run too late. Create the app worktree from the resolved base branch rather than a controller `working-tree` snapshot, which can start the child before those agents are visible and force a `worker` fallback.

The managed lifecycle relies on committed branch diffs, so `dev-start.md`, `review-pr.md` and `submit-pr.md` reject dirty or detached worktrees before review or submission; otherwise uncommitted edits read as "no changes".

## Remaining branch measurements

`item-tier` reads the launch estimate and Expected delta to select a tier. Its branch-range mode reads changed paths only. The shared `expected_delta_read` parser remains for that estimate. Invalid or absent delta text does not refuse a tier.

`branch_size_classified` lives in change-scope's `scripts/lib/branch-growth.sh`, which `item-tier` and `dev-return-write` source from the sibling package. Harness CI reads its production, test and render counts and test paths to select CI checks and the review skip for a trivial change. `dev-validate-run` and submit reuse read that classifier for validation coverage. Review-gate consumer refresh also reads it to report the class and select checks. These uses do not gate an orch workflow on an issue allowance.

`dev-return-write` reads `branch_baseline_lines` to record additions plus deletions in an implement receipt, with paired renders counted once. The receipt reports churn; it does not authorize a round or a cut. `branch_size_numstat`, base resolution and render-root settings remain for these callers. Fix-round stamping and cut acceptance read no branch size. The review watcher reads GitHub review state only.
