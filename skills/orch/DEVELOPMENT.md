## Tests

```bash
bash skills/orch/tests/run-all.sh
bash skills/orch/tests/run-all.sh workflow_helpers   # subset by name fragment
bash skills/orch/tests/run-all.sh open-terminal oversee       # either fragment
bash skills/orch/tests/run-all.sh '!open-terminal' '!oversee' # neither
bash skills/orch/tests/run-all.sh =lanes                     # that suite alone
```

A bare argument selects and `!name` rejects; `=name` in either place matches one whole suite name, the form `tools/guard --range` passes for the suites a diff maps to. A set of fragments and that set negated split the battery: no suite runs in both halves and none runs in neither. CI also passes `--shard` for the oversee profiles that `run-all.sh` selects by `RUNNER_OS`. `tools/tests/orch-shard-partition.test.sh` holds each platform's partition to exactly one run per suite.

Each `tests/*.sh` is self-contained: it builds its own sandbox with parametrized CLI stubs on `PATH`, prints `pass: N fail: M`, and exits 0 only when every assertion passed. `run-all.sh` discovers them at execution time, so a new suite needs no registration. It runs them `nproc` at a time, so a suite shares its host with the others and keeps every file, socket and process it makes inside its own sandbox. A suite whose fixed wall-clock window a loaded host has made it miss goes in `run-all.sh`'s `ALONE` list, and runs by itself after the others. The `run-all.sh` header states the report it prints, and `tests/run-all-parallel.sh` holds it.

Every shell suite asserts through `lib/assertions.sh`, sourced directly or through `lib/md.sh` or `lib/oversee-watch-harness.sh`, and defines none of its names. `tests/assertions.test.sh` holds the library, judging without it, and fails on any suite or lib under `tests/` that defines one of those names. `lane-host.sh` and `lane-host-ssh.sh` run Python suites and have no shell assertions.

Every `tests/*.sh` carries one line directly under its `set -...o pipefail`:

```bash
source "$(dirname "${BASH_SOURCE[0]}")/lib/git-env.sh"
```

That lib is where the four git environment variables are cleared, so a new suite adds the line rather than its own `unset`. The position is the rule, not the presence: `git-env-isolation.test.sh` names any file whose line is absent or sits anywhere but directly under the `set`.

Every test the runner discovers ships with the installed skill and must pass in a downstream project with no access to the kendex source checkout. Byte identity and idempotence of what an apply writes are covered upstream of the installed tree, in `crates/core/tests/byte_faithful.rs`.

Run probes that import Python fixtures with `python3 -B`. Bytecode caches under the catalog become render inputs.

## GitHub auth ladder

`approval-wait`, `ci-wait` and `queue-wait` share `scripts/lib/gh-auth.sh`, which wraps the GitHub skill's helpers. Each candidate is probed at most once, except the timed-out env token in step 1:

1. Selected env token. `GH_TOKEN` or `GITHUB_TOKEN` set: validate with a bounded `gh api user`. A 403 naming an integration, which a GitHub App installation token gets, is validated again with a bounded `gh api installation/repositories`. A value with no known token prefix is selected only when that validation passes. A validation killed at `KENDEX_GITHUB_AUTH_TIMEOUT` (status 124) is asked once more before the keyring fallback, since the first call through an egress proxy can be the slow one; `queue_wait.sh` holds both rows. One env token gets at most two checks in a waiter and at most three in `oversee-watch` and `oversee-report`, whose `orch_sanitize_gh_env` check comes first, each bounded by `KENDEX_GITHUB_AUTH_TIMEOUT`.
2. Keyring fallback. That token failing: `env -u GH_TOKEN -u GITHUB_TOKEN gh auth status` once; on success, warn on stderr and unset the stale env token.
3. Bot token. Keyring not recovering: unset the stale env tokens, then load a `GH_BOT_TOKEN` candidate from process env or project config. `op://` references resolve through `op read` only after the final source is selected. The `github.sh` router separately prefers a resolved `GH_BOT_TOKEN` over a resolved `GITHUB_TOKEN`, so bot access is not blocked by a user token.
4. No-env keyring. No env token at startup and no bot token: probe keyring auth once.
5. Hard fail. Nothing works: exit `3` with a diagnostic. Callers never poll against empty output. `oversee-watch` and `oversee-report` run steps 1 to 3 and refuse as `auth-failed` with exit `2`.

`op` CLI service-account setup is outside orch: launchers may inject resolved secrets before starting a harness, and orch preserves those values rather than clobbering them with local `op://` references.

## Git HTTPS fallback

Merge and submit workflows use targeted `origin` operations through the GitHub skill's `scripts/git-https-auth` rather than broad remote enumeration. The helper is a per-command fallback for SSH-backed GitHub remotes: it validates env-token or keyring `gh` auth, then supplies temporary `credential.helper` and `url.insteadOf` config so GitHub SSH URLs work over HTTPS. It persists nothing. Never use `git fetch --all --prune` for PR closure: a secondary remote's SSH failure must not block branch cleanup or tracker closure.

## Reviewer slot budget

`REVIEWER_SLOT_BUDGET` bounds reviewer fanout for runtimes that cap concurrent agent threads. It is the runtime's total agent-session budget counting the primary session; `0` means unlimited. When the reviewer set exceeds the available slots, review workflows run bounded waves and retire each completed session, because a completed subagent thread can keep counting against the cap until it is explicitly shut down. The configured budget is advisory and the runtime cap authoritative: a persistent launch that hits the thread-limit error demotes to waves in place, persists the observed size, and recommends it to the user.

On the Codex collaboration runtime the cap is MultiAgentV2's configurable `features.multi_agent_v2.max_concurrent_threads_per_session`. `spawn-adapter slots` reports the effective cap, warns when only the silently-ignored legacy `agents.max_threads` is set, and notes that a running session keeps the cap it started with. Retiring is safe because review state lives in on-disk artifacts and workflow state, never in reviewer session memory.

## CI triggering

orch waits for the review result before CI verification. An armed PR still waits for GitHub’s required approval and thread resolution. CI job selection belongs to the repository’s workflow. `ci-wait` tolerates dispatch latency through `CI_WAIT_NO_CHECKS_GRACE`.

Reruns re-execute the workflow definition and verifier state pinned at the original triggering event, so a PR that changes gate or CI behavior only exhibits the new behavior on a fresh head. Reruns are for flakes and re-gating unchanged workflows.

## Merge route

A lane merges its own pull request: `merge-pr.md` § 5 step 1 runs `pr-merge` on the exact head, under the lanes app's installation token in a lane sandbox. `pr-merge` merges past the queue with `--admin` where the queue is all that token would bypass on the base and the change is not queue-only, per kendex decision D016; otherwise GitHub queues the PR (exit `75`) and the lane waits in `queue-wait` to a terminal verdict, where a finding that lands while the PR is queued takes it back out through `queue-wait`'s late-findings guard. The route and its causes: `pr-merge --help` § Merge route. `merge-pr.md` § 5 step 1 owns the explicit arms for `pr_approval.forced` and unresolved merge state. `submit-pr.md` § 2 step 5 owns ordinary creation arms.

The overseer's owner-credential merge, the `--force` override and the `ORCH_MERGE_BYPASS` fast path are retired; their settings are read by nothing.

## Launch lanes

The host dispatcher and static SSH provider have separate suites, `tests/lane-host.sh` and `tests/lane-host-ssh.sh`. The dispatcher suite holds the per-home bound on provider calls: under a cap of 2, a third call is refused as `lane-host-busy`, a waiting call is admitted once a slot frees, and a slot left by a killed dispatcher is reclaimed. Its call-site test finds every command under `scripts/` run with a provider verb or with its caller's whole argument list, reading an array expanded whole before the command, such as the github skill's `KENDEX_GROUP_LEADER`, as a prefix, and fails on one that does not resolve to `scripts/lane-host`, tracing a function's positional argument through its callers; planted direct calls are its controls. The provider suite executes its SSH command payloads in temporary Git repositories with an SSH transport stub. It uses the installed worktree command to check shared links and copies after clone preparation. It executes the Claude prefix and records process arguments to check that the token travels only in the environment. It also covers account bytes, repeated creation, provider failures, dirty-close refusal, and close after lane cleanup removes the worktree. The `append` cases add lines to a mailbox file, close a fragment an interrupted writer left, drop a cut transfer, create an item directory the lane has not opened with the transfer umask keeping it private, and hold the mailbox lock against a second writer, which waits for it and writes through it once the lock call is removed. Archive tests read saved records, observe the printed path before deletion, and check that transport and local storage failures preserve remote data. They cover only records still present at close. The suite does not establish live SSH connectivity. The shared provider fixture is `tests/fixtures/lane-host`; launcher and watcher integration use that protocol independently. Its `append` runs the package library that `LANE_HOST_STUB_LIB` names, the way the real provider runs the one in the remote clone it is given. The optional SSH reference uses Python's standard library to quote remote shell arguments and transfer binary files without putting credentials in arguments.

`lanes` answers which harness account a session should launch under on a machine carrying several. The failure it exists for is account-level: when one account hits its limit mid-fleet, every session on it stalls at once.

- Headroom is `100 - max(session_5h, weekly, model_weekly)`, the binding bucket, never an average. An account at 5% session and 95% weekly has 5% headroom.
- Everything unmeasurable is refused, never assumed idle. A lane is pickable only at `status: ok` with at least one parsed window, or at `rate_limited` carrying the last figure the host holds for it; `no_credentials`, `expired`, `unreachable`, `refused`, `no_usage_data`, `error` and a `rate_limited` lane carrying no figure all yield a null headroom and are skipped. `pick` exits `3` when nothing qualifies, distinct from 1 for a real failure.
- The inventory is discovered; config is only an overlay. `ORCH_LANE_ALIASES` renames discovered lanes, `ORCH_LANE_DIRS` covers a layout discovery cannot reach for each harness it holds an entry of, `ORCH_LANE_EXCLUDE` and `ORCH_LANE_RETIRE` remove lanes by directory name or alias. An excluded or retired lane's directory is never looked inside, because an excluded account can be one agents must not touch, and `open-terminal` refuses a named `--lane` either setting covers, through `lanes check`.
- Usage figures are cached per host under the oversee-watch state directory for `ORCH_LANES_USAGE_TTL` seconds, default 300, or for the caller's own pass interval where `lanes --max-age` names a longer one, so several overseers on one machine poll each account at most once per window. A TTL of 0 fetches on every run and no caller widens it. `oversee-watch` names two of its intervals to its mark judgement, since a long pass judges once an `--interval`, counted start to start, or longer when one overruns, and the mail pass judges a standing wall at most once an interval too. The default outlasts the 240-second default of `oversee-watch --interval`, because a TTL under the watch interval has every pass find the figure expired and post again. Credentials are still read every run, so token expiry is never masked. A fetch that could not be run is never cached, and one an endpoint refused is recorded in the lane's record, beside the last figure, until its window passes.
- The refresh itself is serialized host-wide. A lane its record cannot answer takes one lock over its refresh and re-reads the record inside it, so two readers arriving together are one refresh of each account rather than two; the TTL alone cannot do that, because at expiry every caller's fetch lands in the same second. A lane the record can answer, with a fresh figure or a live refusal, never takes the lock, so `pick --lane` on a warm account never waits behind a fleet refresh. A lock that does not come free within its bounded wait is a keyed notice and the lane is refreshed anyway: refusing every lane on contention is the same host-wide wall that serving a stale figure exists to prevent. Two callers run from different checkouts with `OVERSEE_WATCH_STATE_DIR` unset share neither cache nor lock and each pay the full cost, so set it once per host.
- A usage 429 is answered from the last figure the host holds while that figure is younger than the 5-hour session window: the lane reports `rate_limited` on it, with its age in `usage_age_s`, and `pick` judges it rather than walling the fleet for a transient burst. With no such figure, the first such lane in a run retries once, after the recorded window or 5 seconds whichever is shorter, so that retry is the one request posted inside the window; a refused retry leaves the lane `rate_limited` with no windows. A later cold lane in the same run reports its refusal at once, so one run spends at most 5 seconds and one request on retries.
- In-flight launches reduce projected headroom. `open-terminal` records a claim per tmux lane it launches under a resolved lane; a claim is live while its pane is (`<server pid> <pane id>`, pruned on read). The threshold is applied first, to the projected wall: the binding bucket and the 5-hour session window each charged for the live claims, the smaller room judged, by the rule `lanes --help` states under `pick`. A weekly charge alone let a session reset stack every launch on one account until its new session walled them all. So an account whose room its live lanes will spend is dropped as a walled one is, and `pick --lane --projected`, the named-lane launch gate, refuses it on that same rule; a claim count never buys a lane past it. Plain `pick --lane` judges the reading, since its other callers ask whether an account is out of room now and a lane's own claim is among those charged. The chooser ranks qualifying accounts by the reset-weighted score in `lanes --help`. `scripts/lib/lane-model.sh` owns projection, model reading eligibility and scoring for both pick forms. Usage samples record the live claim count. The projection divides account-wide rates by that fixed sample count, floored at one, so added claims cannot dilute them. Missing counts and host rows use one. Model rates use one because claims omit models; claims on other models cannot divide that rate. `tests/lanes-pick-spread.sh` holds account-wide sharing, added-claim projection, model-rate refusal, the session window charged to its reset with one control per half, the deciding window `list` and both pick forms name, and the pick reading a one-item fleet launch and a named lane write into the lane record. The batch re-pick's record is in `tests/open-terminal-lane-pick.sh`, a preference walk's in `tests/open-terminal-preference.sh`, and a relaunch's keep and drop in `tests/open-terminal-record.sh`. `tests/lanes-pick-reset.sh` holds reset order, bounded weighting and local model eligibility, including failed reads and shared-only readings. Both suites carry inverse controls. `tests/lanes-codex-credits.sh` holds the Codex credit room rule, its floor and its rank after plan room, with its own controls. `tests/lanes-usage-pct.sh` holds the reading of a usage percentage that does not read: the whole lane is unmeasured, with its own controls.
- The bare chooser never returns an overseer seat: it omits every account `.overseer.account` names in this checkout's fleet state, or in the state of a peer fleet with a live lane in the shared claim store, before anything is measured, and names each on its exit-3 refusal. An unreadable fleet state refuses the pick. A seat stays while the record does, running overseer or not. `pick --lane` judges the account it is given, seat or not, and the overseer's own picks pass `--for-overseer`.
- An expired access token is renewed before the lane is measured, so the lane `pick` prints carries a live token and its record reads `refreshable: true`. Refreshing rotates the refresh token in a credentials file other tools on the machine share, so the write takes a flock and re-reads the credentials inside it. A lane with no refresh token stays `expired` with the cause in its detail and is never picked. A renewal the endpoint REFUSED takes the status its HTTP answer earned — `rate_limited` on 429, `unreachable` on 5xx, `expired` on anything else — because `expired` drives a re-login remedy downstream that such an account does not need. A POST that never reached the endpoint, or one a held credentials lock kept from being tried, is `unreachable`; a step this machine failed on its own, a missing OAuth client id included, is `error`. The POST carries a `claude-cli/<version> (external, cli)` User-Agent, without which the endpoint answers 429 whatever the rate. A refusal an endpoint answered is recorded in the lane's usage record, beside the last figure, and stops every caller on the host re-posting until its window, the answer's own `Retry-After` or five minutes, has passed; `--no-cache` declines a cached figure it could refresh, never that window, and never the last figure a usage 429 is answered from. The token POST is injected through `ORCH_LANES_TOKEN_CMD` for the suite. An expired Codex token, its expiry read from the access token's own `exp` claim, is renewed by the Codex CLI itself, never by a refresh-token grant of `lanes`, because a second refresher of one auth.json can revoke the login: `codex app-server` in that config dir is asked `account/read` with `refreshToken`, under the same credentials lock, and auth.json read back is the verdict. What each failed Codex renewal reads, and its remedy, is stated once, in the `lanes` script header under "Why a Codex token is renewed by the Codex CLI". Either renewal step, the CLI run or the Claude POST, runs as a background job under `set -m`, in a process group of its own, while the shell that holds the credentials lock ignores INT and TERM and waits for it. A caller's ceiling signals the caller's process group, so it cannot end a refresh in flight and leave a retired refresh token, whatever signal handlers the Codex CLI installs. The cost: the step holds the stderr of `lanes`, so a caller that reads it through a pipe waits past its ceiling for the step's own request bound. The suite stands a `codex` stub first on PATH, which exits on TERM as the CLI does.
- Two API shapes, one trap each. Claude's model-scoped weekly windows live in `limits[]` entries with `kind == "weekly_scoped"`. The legacy `seven_day_sonnet` and `seven_day_opus` fields stand in only where a response carries no such entry, and a response carrying both keeps both. Keep every scoped window under the label the response gives it: the most-consumed one names the MODEL column, and a launch on a named model is judged on the window scoped to that model. Codex's `primary_window`/`secondary_window` do not map to session/weekly by position; route each by its own `limit_window_seconds`.
- A weekly wall the endpoint does not report. A Claude harness has shown its weekly-limit banner on an account whose usage body parsed in full and read room. `lib/account-wall.sh` is the fallback: on every pass that finds a claimed lane walled, `oversee-watch` records the weekly wall the lane's harness reported, under the claimed account and until the banner's reset, and `emit_lane` holds that account's `weekly_pct` at 100 while the reset is ahead. In a pane, only a banner line opening with the prefix Claude Code draws its limit message under is recorded, never the same words a lane quotes; a Pi lane's session row carries the harness's own error, so its weekly-limit text is recorded as it stands. `tests/oversee_watch_usage_limit.sh` and `tests/oversee_watch_pi_lanes.sh` hold the writer and `tests/lanes.sh` the reading, each with its controls.
- Testing. The network layer is the only impure part and is injected through `ORCH_LANES_FETCH_CMD`, so the suite runs offline against fixed responses. Bearer tokens never reach argv; they go to curl over stdin with `-K -`.

`open-terminal` routing and command-template rules are in [lane-directive.md § Lane preference](references/lane-directive.md#lane-preference) and [§ Launch gate](references/lane-directive.md#launch-gate). A brief reaches a `--cmd` command from `--brief-file` as `{brief}`, quoted by `lane_single_quote` in `scripts/lib/lane-launch.sh`, the one quoting every launch path's shell reads back; `cmd-unbalanced-quote` and `brief-quoted`, a `{brief}` written inside a quote, judge only the caller's own template text.

## Overseer session

`overseer-host` dispatches to the runtime provider `ORCH_OVERSEER_HOST` names and `overseer-host-tmux` is the included one; the protocol is `schemas/overseer-host.md`. `lib/overseer-launch.sh` holds the launch steps `oversee launch` and `oversee-succeed` share, from the account walk and the flag words to the deciding account read, so a control planted in one of those steps is planted in that library's copy: `tests/oversee_succeed.sh` builds its copies through `tests/lib/growth-state.sh`'s `mutant_scripts`, a tree of links to the shipped scripts with the one file a case mutates copied in. `tests/overseer-host.sh` runs the dispatcher against a fixture provider and the tmux provider against a real server on a private socket, with its control dropping the swap from `stop --successor`. `tests/oversee_launch.sh` runs `oversee` against a server at the default socket under a private `TMUX_TMPDIR`, which is how a run with no `$TMUX` and `ORCH_TMUX_SESSION` set reaches the person's own server; its controls drop the liveness check, which opens a second overseer, and the `--predecessor` check, which stops a pane the fleet never recorded. `lib/watch-handover.sh` is the fleet watch handover both launchers arrange before the stop that commits a succession: `tests/oversee_launch_watch.sh` drives it through `oversee launch --predecessor`, its control dropping the handover and its last row running the real watch over a successor that dies, and `tests/oversee_succeed_watch.sh` drives it through `oversee-succeed` along with the restart helper itself. `lib/tmux-server.sh` is the one rule for which server a verb reaches and whether it holds a named session, read by `open-terminal`, `oversee-watch`, `oversee` and `overseer-host-tmux`; `lib/watch-session.sh` is the watch's own session resolution and lane check over it, a watch library because `oversee-watch` sits at its byte ceiling; the watch harness's tmux stub answers `has-session` for the caller's session and any `windows-<s>.txt` fixture. The watch's own write of the session record is `lib/watch-overseer-record.sh`, a watch library in the `pr-watch-pass.sh` shape, because `oversee-watch` sits at its byte ceiling; `tests/oversee_watch_overseer.sh` plants its merge control in that file.

The overseer's death, wall and identity come from its own session rows, `lib/session-rows.sh`: the `session-start-row`, `session-end-row` and `stop-failure-row` hooks run `lane-mail-check row`, which appends one JSON row per event, only for the pane's top-level harness, one process that is no shell between the hook and the pane's shell, to `tmp/lane-mail/overseer/session-<server>-<pane number>.jsonl` at the main checkout under the mailbox lock, and the overseer's own turn end writes a Stop at every turn end, compact except over a standing StopFailure, which it lifts; the Stop dates the turn end the watch holds the context record against. The fleet state's `overseer.session_rows` names that file, which the watch's liveness judgement reads; `oversee register`, `oversee-succeed` and the watch's context record check, which reads its turn rows for `overseer-context-stale`, compute the same path through `session_rows_overseer_file`, as the hook's writer does. Row shapes follow Claude Code 2.1.283's hook inputs, which carry no reset time as a field: the StopFailure row's `message` is the harness's text of the limit and its reset. Each row hook writes its event's row on the harnesses that `kendex show hook <name>`'s supported tools line lists as neither unsupported nor advisory: OpenCode and Cursor, which its harnesses line names, run no hooks and write none; Copilot's rows are built from its camelCase payloads, which name no event, under the event the row hook names. Codex fires SessionEnd for its main thread alone, its `reason` always `other` (Codex hooks reference, CLI 0.160.0), so its SessionEnd row is the lead session's. A harness another harness started in the same pane, such as second-opinion's `claude -p`, writes nothing, a Codex installed through npm, whose node launcher stands above the harness, writes nothing either, and neither does a harness that is the pane's process itself (`tmux new-window claude`, `exec claude` at the prompt, a tmux default command), since the pane's own process is where the count stops; each takes the pane fallback. A launched overseer is typed into the pane's shell and is none of these. A session whose last row names any harness but Claude Code or Pi reads `unsupported`, and the watch takes the pane. Pi's carrier says its SessionEnd reasons in Claude Code's words and names no StopFailure error kind, so a Pi StopFailure row is a wall where `lane_limit_banner` reads its `message` as the account's limit, the judge a Pi lane's rows take. A Pi row is judged only from the evidence it carries: a Pi last row that is neither a SessionEnd nor a StopFailure with a `message` reads `unsupported`, since a Pi session writes a StopFailure only where its carrier dispatches one, so its SessionStart or Stop says nothing of a wall. The pane capture is the named fallback wherever no row can judge: `oversee-watch` says so under `overseer-fallback` and its event carries `source=pane`, and `oversee register` says so under `identity-fallback`. The successor wait never reads a row: the harness writes SessionStart before its first turn runs, so only `inspect --launch` shows the turn it waits for. Every launch line runs under `scripts/overseer-run`, which drops the record's `exit` before the line runs and writes the harness's exit status there once it returns; the watch reads it as the death ahead of the rows, `source=record`, where the pane's process is a bare shell with nothing but shells under it, which covers a harness killed before its SessionEnd hook runs. A harness started again in that pane is a child of the shell, and the status reads as an earlier session's. A session no launcher opened has no such status, and its pane's process, a bare shell with nothing but shells under it, reads as `source=process`. `tests/overseer_run.sh` holds the wrapper. A wall its rows state, which stands unless the account judgement measures room since only a finished turn writes the row that lifts it, and a live session whose account mark is reached at value 0 (`source=account`), are succeeded in the first pass that reads them; only a pane wall keeps the `ORCH_OVERSEER_DEAD_PASSES` debounce. `tests/oversee_watch_overseer_rows.sh` judges a blank pane from its rows, and `hooks/tests/session-rows.test.sh` holds the writer; both plant their own controls.

## Container close

`container-close` owns Linear container closure and `sync-base` owns base resolution, fetch, checkout ownership and the fast-forward. Both contracts are in their own `--help`. Completion validation inside `container-close` must provide Boolean `all_ok`, exactly one typed parent result, and Boolean `has_summary`; the helper never infers that a later child completion came from a parent cascade.

## Codex app worktree routing

Codex Desktop handoff starts each child thread in an app-managed worktree, often on a detached `HEAD`. Generated Codex agents must be tracked under `.codex/agents/*.toml` in the saved project branch to be visible before subagent discovery; local ignored files are not enough, because setup hooks, `WORKTREE_SYMLINKS`, and `codex-setup` all run too late. Create the app worktree from the resolved base branch rather than a controller `working-tree` snapshot, which can start the child before those agents are visible and force a `worker` fallback.

The managed lifecycle relies on committed branch diffs, so `dev-start.md`, `review-pr.md` and `submit-pr.md` reject dirty or detached worktrees before review or submission; otherwise uncommitted edits read as "no changes".

## Remaining branch measurements

`item-tier` reads the launch estimate and Expected delta to select a tier. Its branch-range mode reads changed paths only. The shared `expected_delta_read` parser remains for that estimate. Invalid or absent delta text does not refuse a tier.

`branch_size_classified` remains in `scripts/lib/branch-growth.sh`. Harness CI reads its production, test and render counts and test paths to select CI checks and the review skip for a trivial change. `dev-validate-run` and submit reuse read that classifier for validation coverage. Review-gate consumer refresh also reads it to report the class and select checks. These uses do not gate an orch workflow on an issue allowance.

`dev-return-write` reads `branch_baseline_lines` to record additions plus deletions in an implement receipt, with paired renders counted once. The receipt reports churn; it does not authorize a round or a cut. `branch_size_numstat`, base resolution and render-root settings remain for these callers. Fix-round stamping and cut acceptance read no branch size. The review watcher reads GitHub review state only.
