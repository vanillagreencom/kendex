Hosted oversight

How one overseer supervises lanes that run on another machine: what runs where, which credential each part spends, how mail moves, and when a lane or the overseer hands off. The rules: oversee.md and oversee-events.md. The machines themselves: the fleet repository's docs/html/remote-fleet.html.

The one idea

  • An overseer runs one watch. The watch reads files and panes; it never types into a lane.
  • A lane talks to its overseer through a mailbox, two files under its worktree. Nothing else crosses between them.
  • On a hosted fleet the lane's worktree and CLI live in a sandbox. The overseer's window on the control VM is an SSH shell into it, so the pane reads the same as a local lane.
  • Every read of a hosted file goes through one provider verb. The overseer never reads a lane's transcript.
  • A lane hands off at a fixed context mark, and the item continues in a fresh session. The overseer succeeds itself the same way.

What runs where

Credentials

Three kinds of credential exist. The two logins rotate; the lane token does not. A part that spends the wrong kind, or measures through a copy that another machine also renews, fails in ways the account itself does not.

Mail

A mailbox is two append-only files under a worktree's tmp/lane-mail/<item>/: to-overseer.jsonl and to-lane.jsonl, each line one message with an id, a kind and a sender. The overseer's own inbox is the overseer item in its checkout. Every write appends one line under a lock. A plain inbox read advances the reader's cursor, so a directive handed over once is never handed over twice; inbox --peek reads without moving it. A hosted mailbox is appended through the provider's append verb and read through cat.

The watch

One oversee-watch loop per overseer, started once per session with the fleet's fixed start time and every repository the fleet has pull requests in, the items repository first, since the first repository owns the triage, lane and merged baselines. It re-reads its items file and windows file before every pass, so a lane joins or leaves by editing those files; a hosted lane's mailbox root is passed at start and needs a restart to change.

The pass interval and the number of quiet passes before a heartbeat are the watch's --interval and --max-loops; the heartbeat runs the tracker triage and the proposal backstop. The overseer handles every line of a block, and never reads a pane a second time when the tail already answers the event.

Handoff and succession

A session has a fixed context window. Past a mark, the remaining window is not enough to finish a review loop, so the work moves to a fresh session from a record on disk. The record is the whole state the successor needs: what merged, what remains, the branch, the worktree, the open pull request and the traps found.

WhoTriggerWhat happens
A laneContext past the mark oversee-events.md names, or the account's binding bucket at or under ORCH_HANDOFF_HEADROOM_PCTAt the next safe point, a landed merge or a held pull request, never mid-round or with an unpushed tree, the lane writes workflow-state set <item> handoff, sends a notice and exits. The watch reports handoff. The overseer relaunches the item, and the successor reads the record first.
A lane at a session limit with no recordThe harness banner, reported as usage-limit with the reset timeThe overseer picks another account of the same harness and resumes the same session natively under it with open-terminal --relaunch; with none, it picks another terminal harness and launches from the continuation brief. When no replacement qualifies and the banner names a reset, the window stays parked in the watch, which reports usage-limit-passed at that time, and the overseer sends the one-line continuation nudge. A banner with no reset time is reported once, so the overseer selects another account on that event.
The overseerIts own context past the mark, or headroom at or under ORCH_OVERSEER_HEADROOM_PCTAt a point with no merge in flight and no lane waiting on an answer, it rewrites the handoff file, runs oversee-succeed, and a successor opens on the account the picker names in the same window position. The watch loop outlives the window only when it was started detached, as oversee.md § 4 directs; the successor's first steps are to confirm the loop is in the process table, start it again if it is not, and arm its own monitor on the log.
The lane trigger is the overseer's: it reads each lane's context through lanes context at every event and sends the directive. That reader is blind to a hosted pane, which runs ssh, so on a hosted fleet the overseer reads the pane percentage by hand. The trigger moves into the lane's own turn-end hook, which reads the figure the harness writes into the transcript, under KEN-1543; the overseer's read becomes a backstop.
