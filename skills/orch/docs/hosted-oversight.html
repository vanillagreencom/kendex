Hosted oversight

Hosted oversight

How one overseer supervises lanes that run on another machine: what runs where, which credential each part spends, how mail moves, and when a lane or the overseer hands off. The rules: oversee.md and oversee-events.md. The machines themselves: the fleet repository's docs/html/remote-fleet.html.

The one idea

  • An overseer follows one watch. The watch reads files and panes, and types into a lane only the one line that wakes it to read unread mail.
  • A lane talks to its overseer through a mailbox, two files under its worktree. Nothing else carries the lane's words out; the overseer also reads the lane's pane, and pastes into it only when mail cannot reach the lane.
  • On a hosted fleet the lane's worktree and CLI live in a sandbox. The overseer's window on the control VM runs the lane's harness in it over SSH, so the pane reads the same as a local lane.
  • The watch reads a hosted lane's mailbox, harness status, workflow state and status file through its provider's verbs. The overseer never reads a lane's transcript.
  • A hosted lane whose pull request is armed or queued with the gate met is parked: its harness stops, its sandbox stops with its disk kept, and on the merge of its pull request the watch hands a lane with work left to the overseer, whose relaunch starts the lane again to run its own post-merge (oversee-lanes.md § Parking a merge wait).
  • A lane hands off when the shared context rule requires it, and the item continues in a fresh session. The overseer succeeds itself the same way.

What runs where

The repository's declared owner outside the control host runs refresh and verification. The control checkout receives the reviewed, committed outputs through sync-base after they merge. It never runs post-merge, including --refresh-only. Report a failed refresh workflow; synchronizing the item merge alone does not complete refresh.

Mail

A mailbox is two append-only files under a worktree's tmp/lane-mail/<item>/: to-overseer.jsonl and to-lane.jsonl, each line one message with an id, a kind and a sender. The overseer's own inbox is the overseer item in its checkout. Every write appends one line under a lock. A plain inbox read advances the reader's cursor, so a directive handed over once is never handed over twice; inbox --peek reads without moving it, except to bring down a cursor that stands past the lines the file holds, so the next message is not marked read before it arrives. A hosted mailbox is appended through the provider's append verb, and the watch reads it at each mail turn through lane-mail drain --host, which fetches each file with the provider's cat.

The watch

One watch runs per fleet state: orch-runtime watch run, claimed by its process identity. It outlives the session that started it, every succession and every recovery, and runs until orch-runtime watch stop --fleet, a signal, or a failure of its own records (watch-record) (oversee.md § 4). Each duty reads the fleet state's lane records when it runs, so a lane launch, relaunch or close needs no restart.

Handoff and succession

The shared context rule decides when work moves to a fresh session from a record on disk. It uses tokens used and effective capacity. The harness adapter resolves the actual launch overrides before stored compaction settings. An unresolved point remains unmeasured; the independent token limit still applies. Compaction controls disable automatic compaction where supported. Codex can still compact if usage crosses its cap between checks or another compaction path runs. The record is the whole state the successor needs: what merged, what remains, the branch, the worktree, the open pull request and the traps found.

The lane fires its own trigger: the lane-mail-check turn-end hook reads tokens used and effective capacity through the harness adapter and records that reading in the lane's mailbox, and reads the account the lane's own credential runs on, and refuses the turn end at either mark until the record stands. The same hook refuses the overseer's own turn end, recognising that session by the tmux server and pane the fleet state records and asking orch-runtime marks --fleet where the overseer's marks stand. A lane's turn-end reading is recorded in its mailbox. Without a recorded reading, its context use is unknown. What the hook cannot judge it reports and passes, so a hosted lane whose account has no usage endpoint still ends its turns.
