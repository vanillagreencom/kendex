Hosted oversight

Hosted oversight

How one overseer supervises lanes that run on another machine: what runs where, which credential each part spends, how mail moves, and when a lane or the overseer hands off. The rules: oversee.md and oversee-events.md. The machines themselves: the fleet repository's docs/html/remote-fleet.html.

The one idea

  • An overseer runs one watch. The watch reads files and panes; it never types into a lane.
  • A lane talks to its overseer through a mailbox, two files under its worktree. Nothing else carries the lane's words out; the overseer also reads the lane's pane, and pastes into it only when mail cannot reach the lane.
  • On a hosted fleet the lane's worktree and CLI live in a sandbox. The overseer's window on the control VM is an SSH shell into it, so the pane reads the same as a local lane.
  • Every read of a hosted file goes through one provider verb. The overseer never reads a lane's transcript.
  • A lane hands off at a fixed context mark, and the item continues in a fresh session. The overseer succeeds itself the same way.

What runs where

Credentials

Three kinds of credential exist. The two logins rotate; the lane token does not. A part that spends the wrong kind, or measures through a copy that another machine also renews, fails in ways the account itself does not.

Mail

A mailbox is two append-only files under a worktree's tmp/lane-mail/<item>/: to-overseer.jsonl and to-lane.jsonl, each line one message with an id, a kind and a sender. The overseer's own inbox is the overseer item in its checkout. Every write appends one line under a lock. A plain inbox read advances the reader's cursor, so a directive handed over once is never handed over twice; inbox --peek reads without moving it. A hosted mailbox is appended through the provider's append verb and read through cat.

The watch

One oversee-watch loop per overseer, started once per session with the fleet's fixed start time and every repository the fleet has pull requests in, the items repository first, since the first repository owns the triage, lane and merged baselines. It re-reads its items file and windows file before every pass, so a lane joins or leaves by editing those files; a hosted lane's mailbox root is passed at start and needs a restart to change.

The pass interval and the number of quiet passes before a heartbeat are the watch's --interval and --max-loops; the heartbeat carries the account roster from the last pass and runs the tracker triage and the proposal backstop. The overseer handles every line of a block, and never reads a pane a second time when the tail already answers the event.

Handoff and succession

A session has a fixed context window. Past a mark, the remaining window is not enough to finish a review loop, so the work moves to a fresh session from a record on disk. The record is the whole state the successor needs: what merged, what remains, the branch, the worktree, the open pull request and the traps found.

WhoTriggerWhat happens
A laneContext at or past ORCH_HANDOFF_CONTEXT_TOKENS, or the account's binding bucket at or under ORCH_HANDOFF_HEADROOM_PCT, both judged by the lane's own turn-end hookAt the next safe point, a landed merge or a held pull request, never mid-round or with an unpushed tree, the lane writes the record with workflow-state set <item> handoff '<json>' (the fields oversee-events.md lists) and exits. The watch reports handoff. The overseer relaunches the item, and the successor reads the record first.
A lane at a session limit with no recordThe harness banner, reported as usage-limit with the reset timeThe overseer picks another account of the same harness and resumes the same session natively under it with open-terminal --relaunch; with none, it picks another terminal harness and launches from the continuation brief. When no replacement qualifies and the banner names a reset, the window stays parked in the watch, which reports usage-limit-passed at that time, and the overseer sends the one-line continuation nudge. A banner with no reset time is reported once, so the overseer selects another account on that event.
The overseerIts own 1M-token window past the context mark, or headroom at or under ORCH_OVERSEER_HEADROOM_PCT, reaching it twice over: its own turn-end hook refuses the turn end at either mark, and the watch judges the same marks every pass, reporting a reached one as overseer-mark at the crossing and again every ORCH_OVERSEER_MARK_REPEAT passes while it standsAt a point with no merge in flight and no lane waiting on an answer, it rewrites the handoff file, runs oversee-succeed, and a successor opens on the account the picker names in the same window position. The successor starts the watch again when it is not running, as oversee.md § 4 directs. Where the succession refuses with succession still on, no lane qualifying or a launch that failed, it records the handoff on the fleet's own item with the command the refusal prints, which is what ends the turn-end refusal so the session can close. Under ORCH_OVERSEER_SUCCESSION=off there is no refusal to end, and the handoff is by hand.
An overseer whose account walledIts pane reads walled on ORCH_OVERSEER_DEAD_PASSES consecutive watch passes AND its own account is judged at or below ORCH_OVERSEER_HEADROOM_PCT by oversee-succeed --check-marks. Both readings are required: the overseer's pane is the one pane carrying the limit banners the watch relays about other lanes, so a wall its own account refutes is one of those and the pane is left alone under overseer-wall-unconfirmed.Such a session takes no turn, so it answers no lane, reads no mail and reaches none of the marks that hand a session over. The watch reports overseer-walled with the banner's own window under it, writes one notice to the fleet log and to the overseer's inbox, and opens the successor in that same window through oversee-succeed --walled-pane. That mode keeps this session's harness, model, effort and permission flags and re-picks the ACCOUNT alone, never reopening on the spent one; the command it built is on the watch's stderr under the event. A failed launch records the outcome and gets one later retry, as a death's does. A successful launch makes the single pass exit 3 and the repeat command returns 0. Where no account in the fleet qualifies, one overseer-recovery-blocked notice naming the spent account and when its binding bucket frees up reaches both channels, the retry is not taken, and the repeat command stops; start a fresh overseer by hand once an account has room.
An overseer that diedIts pane reads exited on ORCH_OVERSEER_DEAD_PASSES consecutive watch passes, judged by the watch and not by the overseer, which runs no turn to judge anythingFrom the first exited reading, the watch advances no fleet event baseline until a live replacement or successor can receive the work. The watch reports overseer-dead, writes one notice to the fleet log and to the overseer's own inbox, and opens the successor in that same window from the launch line the current watch recorded, through oversee-succeed --dead-pane. A failed launch records the outcome and gets one later retry. A successful launch makes the single pass exit 3. The repeat command returns 0 and stops because the successor runs its own watch, so no manual restart is needed. ORCH_OVERSEER_SUCCESSION=off leaves a notice for a manual replacement and launches nothing. Notice-only recovery and an exhausted retry also stop the old repeat command, so the manual replacement starts one new watch.
The lane fires its own trigger: the lane-mail-check turn-end hook reads the context figure the harness writes into the transcript and the account the lane's own credential runs on, and refuses the turn end at either mark until the record stands. The same hook refuses the overseer's own turn end, recognising that session by the tmux server and pane the fleet state records and asking oversee-succeed --check-marks where the overseer's marks stand, so the refusal and the watch's overseer-mark line cannot describe one overseer differently. The lanes context poll is the backstop, and a weak one here: that reader takes the figure off the pane, and a hosted pane runs ssh, so it reads nothing at all and the overseer would have to read the percentage by hand. What the hook cannot judge it reports and passes, so a hosted lane whose account has no usage endpoint still ends its turns.
