# Review gate and waiter reference

Load where a workflow reads the review gate, requests Copilot or waits on one pull request. The review gate is the orch runtime's `verify-review` operation, CI on one pull request its `verify-pr` operation, and the merge queue its `queue-watch` verb. The workflows route each verdict; this file holds the review call, what its reply means and the words the three share.

## Gate-mode routing

Bind `[REVIEW_BASE_CHECKOUT]` to a checkout of the target pull request's consumer base, never the catalog checkout or the pull request's updated tree. If that checkout is unavailable, stop.

The gate mode is the `mode` of [the review call](#the-review-call)'s reply. The runtime resolves it on the item's first call and records it as `pr_review.mode`; every later call reads that record, so a retarget to another base keeps the mode the first call read. It reads the consumer's `REVIEW_GATE_MODE` from the base checkout's `kendex.settings.toml`, `.kendex/settings.toml` and private env file, never from the caller's environment, and runs nothing from that checkout. `off` is the mode. `enforce`, or no value, reads GitHub's approval requirement on the base: the base's ruleset pull-request rules, then classic branch protection's required reviews. A ruleset rule that requires an approval, code-owner review, last-push approval or a team minimum, or enabled classic protection with a required-reviews object at any count, is `approval`; anything else is `off`. A failed read is an `unreadable` reply with no mode, never `off`: repeat the call, and report a second failure rather than pick a mode.

| `mode` | Meaning | Route |
|--------|---------|-------|
| `approval` | consumer policy is `enforce`, and the base's rulesets require approval or classic protection requires reviews | the review wait |
| `off` | consumer base-checkout policy is `off`, or the base's rulesets require no approval and classic protection requires no reviews | no review wait: the call requests nothing and answers `complete` with verdict `off` and records it, `pending copilot-pending` while Copilot's work in flight on the head holds it ([§ Copilot requests](#copilot-requests)), or `blocked` while a regression blocker stands ([§ Which waiter answers which state](#which-waiter-answers-which-state)); record the gate not-applicable only on `off` |

Under `off`, open review threads still stop the merge: submit-pr's gate 3 applies, and so do the readers [thread-read.md § What reads an open thread](thread-read.md#what-reads-an-open-thread) lists. Required CI checks, commit guards, exact-head checks and conflict refusal are untouched in both modes, and the merge path still refuses a `CHANGES_REQUESTED` review at its readiness check. In `approval` mode an unresolved thread holds the wait at `comments` even beside an approval, because orch's own merge gates refuse an open thread: submit-pr's gate 3 and merge-pr's thread read ([thread-read.md](thread-read.md)). A base rule refuses one too where it requires thread resolution.

The call reads its settings at its start, the caller's environment over the private env file and the settings files' `[env]`, and refuses a value outside its form as `setting-invalid key=[KEY] value=[VALUE]`. `PR_REVIEW_ON_TIMEOUT` and `ORCH_COPILOT_HOLD_SECS` are in [settings.md](settings.md); these two are this gate's alone:

| Setting | Meaning | Default |
|---------|---------|---------|
| `PR_REVIEW_WAIT_SECS` | Seconds of one review period, counted from the head's record, or from the head's last `timeout` | `900` |
| `PR_COPILOT_REQUESTS` | `on` requests Copilot on each head; `off` requests none, and the head's request falls back `cause=off` | `on` |

## The review call

Run it from the caller's checkout, `[ROOT]`: the lane's worktree, or the main checkout merge-pr runs from. `[OWNER/REPO]` is what `gh repo view --json nameWithOwner --jq .nameWithOwner` answers there, and `[STATE_KEY]` the caller's workflow state key, `[ISSUE_ID]` in a lane. `[MARK_READY]` is `true` where the step says so, which marks an open draft ready before its request under either mode, and `false` everywhere else:

```bash
jq -cn --arg repo "[OWNER/REPO]" --argjson pr [PR_NUMBER] --arg base "[REVIEW_BASE_CHECKOUT]" --argjson ready [MARK_READY] \
  '{op: "verify-review", repo: $repo, pr: $pr, base_checkout: $base, mark_ready: $ready}' \
  > "[ROOT]/tmp/verify-review-request-[STATE_KEY].json"
.agents/skills/orch/scripts/orch-runtime op --item [STATE_KEY] --request "[ROOT]/tmp/verify-review-request-[STATE_KEY].json"
```

One call reads the pull request once and reads or records the gate mode. Under `off` it requests nothing and answers `off`, `blocked` while a regression blocker stands, or `pending copilot-pending` while Copilot's work runs on the head (§ Copilot requests). Under `approval` it counts the head's open threads and reads its reviews; every head takes its Copilot request (§ Copilot requests) before its verdict, and a head with no verdict after those reads takes its review period. The call records each act it makes, the ready mark, the Copilot request and the error retry, under the head before making it, so a repeated call repeats no act it saw confirmed: a ready mark still unconfirmed while the pull request reads draft is sent again, and the request's and the error retry's one resend are § Copilot requests'. A step that needs only the mode or the request runs the call once and reads that field; on `approval`, that same call has also requested Copilot on a head Copilot has not reviewed.

The reply's fields, under `.result`:

| Field | Meaning |
|-------|---------|
| `status` | `complete`: `verdict` is recorded on the item. `pending`: the head is not judged yet, and `reason` says why. `unreadable`: a read failed, and `reason` is its cause key |
| `mode` | `approval` or `off`, present once the mode is read |
| `head` | The head this call read |
| `request` | What the head's record holds: `outcome` `requested`, `existing` or `fallback`, with `reason` or `cause`, and `recorded_now`, true on the call that wrote it |
| `copilot` | Copilot's work on the head against the hold: `state` `none`, `pending` or `expired`, with `run` and `started_at` |
| `unresolved_count` | The open threads counted on the head |
| `verdict` | With `complete`: `approved`, `changes_requested`, `comments`, `timeout`, `proceeded`, `copilot-error`, `off` or `blocked` |

A `pending` reply's `reason` is `review-pending copilot=[STATE] remaining=[SECS]` while the period runs, `request-refused exit=[N]` in its place on the call where GitHub refused the head's request, `copilot-pending run=[ID] remaining=[SECS]` while Copilot's work in flight on the head, a Copilot check with no Copilot review of the head submitted since it started or a pending Copilot request, holds a verdict that permits a merge, `approved`, `proceeded` or `off`, `request-fallback cause=draft` for a draft the call was not asked to mark ready, which starts no period, `ready-head-moved head=[SHA]` where a push landed with the ready mark, or `head-moved head=[SHA]` where the pull request's head moved between the call's reads; the next call reads either moved head as the new head. A refusal exits nonzero with its keyed line: `pr-not-open` for a closed or merged pull request, `verify-request-invalid field=[FIELD]` for a request outside its form, `setting-invalid` as above, `record-missing` for an item with no state.

**The review wait.** A step that waits on the verdict runs the call through [Waiter launch](waiter-launch.md), repeated no more often than every 30 seconds while `result.status` is `pending`; an `unreadable` reply takes the step's `unreadable` row, which repeats it within that row's bound. The period is the runtime's: `complete` with `timeout` or `proceeded` arrives once `PR_REVIEW_WAIT_SECS` has passed, so the workflow keeps no budget of its own, and a `timeout` starts the head's next period. A step that names a shorter wait runs the call as `env PR_REVIEW_WAIT_SECS=[SECS] .agents/skills/orch/scripts/orch-runtime op ...`, and a step that must never proceed on a silent reviewer as `env PR_REVIEW_ON_TIMEOUT=block ...`: the call reads its caller's environment over the settings files.

**A new head.** The record is the head's: a push starts a new record, request and period. A reply whose `head` differs from the head the step bound takes that step's moved-head route.

## Copilot requests

Under `approval` the review call requests Copilot itself on every head Copilot has not reviewed, at most twice per head as `requested` below says, before it answers the head's verdict, whatever the verdict. Every `approval` reply carries `request`, `approved` included, except one that stopped before the request: a refusal, an `unreadable` reply, `pending ready-head-moved` or `pending head-moved`. Under `off` the call requests nothing. Route the `request` before the verdict word. The reply's `request` reports what the head's record holds:

- `requested`: the call sent the request. On a later call, a request with neither Copilot work in flight on the head nor a Copilot review of the head is sent once more, whether GitHub never recorded it or its work ended with no review, its check completed or cancelled or the request removed; a second such miss falls back `cause=unconfirmed`. An `existing-run` whose run ends the same way is claimed on the next call and sent: `request` reads `requested` with `recorded_now` true, and that request takes the same one resend and fallback. A head is asked at most twice.
- `existing`: no request was needed. `reason` is `existing-run` for Copilot's work in flight on the head, which the next call follows with the request once that work ends with no review of the head (`requested` above), `existing-review` for a Copilot review standing on it, or `existing-error-retry` for a retry of Copilot's error answer standing on it.
- `fallback`: no request went out, and `cause` says why. `off`: `PR_COPILOT_REQUESTS` is `off`. `draft`: the head is a draft the call was not asked to mark ready; keep the draft. `refresh`: the consumer's base-checkout `REVIEW_GATE_REFRESH_REVIEW=overseer` declares this pull request its refresh head, which takes [copilot-head-notices.md § Fallback approval](copilot-head-notices.md#fallback-approval). `no-files`: Copilot's current-head answer says it could review no files, which takes the same Fallback approval without another request. `error`: the item already recorded an error fallback at this head. `refused` with `exit`: GitHub answered the request with a 4xx refusal; a transport failure, a 5xx or a timeout is an `unreadable` reply instead, and the request's claim stands for the next call's confirmation. `unconfirmed`: the request went out twice, and neither drew Copilot work still in flight or a Copilot review of the head. The call asks no third time. With an approval standing, the call that records the fallback answers that approval's verdict in the same reply, so the head can merge with no Copilot review while the `copilot-fallback` notice goes out.

**The fallback notice.** In a lane, a reply whose `request.outcome` is `fallback` and whose `request.recorded_now` is true sends the `copilot-fallback` notice for that head once, as [review-pr-comments.md](../workflows/review-pr-comments.md) § 7.2 sends it: first line `copilot-fallback PR #[PR_NUMBER] head [HEAD_SHA] cause=[CAUSE]`, with ` exit=[N]` after `refused`, and the lane status path as its second line, for the overseer to read. Causes `draft` and `refresh` send none. A reply with `recorded_now` false sends nothing, since the call that recorded the fallback was the cue. The approval gate stays unmet, and the step's review wait keeps running until the overseer's approval ends it. Outside a lane, report the unavailable Copilot review and keep the approval gate unmet.

**Copilot's error answer.** A Copilot review on the head that is its error sentence takes one retry: the call claims it on the head's record and sends the request once. The verdict is `copilot-error`, its `reason` `copilot-error cause=[CAUSE]`, where the retry cannot stand: `refused exit=[N]` when GitHub refused the retry's request, `error` when Copilot answered the retry with another error, `unconfirmed` when the retry went out twice with no sign of Copilot's work, `refresh` when the refresh policy held the request back. In a lane, run the body check and send the `copilot-fallback` notice through [review-pr-comments.md § 7.2](../workflows/review-pr-comments.md#72-copilot-head-route), its first line ending `cause=[CAUSE]` from the reason and its second line the lane status path. Then keep the review wait running for the overseer's approval: the head's retry record keeps later calls from retrying again. Every wait restart still uses its caller's head-budget route. Outside a lane, report the unavailable Copilot review and keep the approval gate unmet.

**Copilot's work in flight.** Under either gate mode, while a Copilot check runs on the head with no Copilot review of the head submitted since the check started, or a Copilot request stands pending on the pull request, within `ORCH_COPILOT_HOLD_SECS` of the head's record, the call holds a verdict that permits a merge, `approved`, `proceeded` or `off`, as `pending copilot-pending`. Past the bound, `copilot.state` reads `expired` and the verdict stands as read; the expiry grants no approval. A Copilot review of the head submitted while its check still runs ends the hold: the call answers its verdict with `copilot.state` `none`. The call's own request is that work from the call that sends it, so an `approved` beside a request the call made answers `pending copilot-pending` until Copilot's review of the head is submitted, its check completes, or the bound passes. A step that merges runs the call before every merge call and repeats it while it answers so ([merge-pr.md § 5](../workflows/merge-pr.md#5-execute-the-merge) step 1). The triage waits on the same work before it reads threads through `orch-runtime copilot-wait` ([review-pr-comments.md § 1](../workflows/review-pr-comments.md#1-fetch-and-parse)), a read that requests and records nothing and holds no merge call, never through this call. Under `off` the call requests nothing, so the hold reads only the work already running or requested on the head.

## Which waiter answers which state

| Waiting on | Tool |
|------------|------|
| Reviewer verdict on one PR | `verify-review` (`orch-runtime op`), [§ The review call](#the-review-call): `status` `complete` with verdict `approved`/`changes_requested`/`comments`/`timeout`/`proceeded`/`copilot-error`/`off`/`blocked`; `pending` repeated, `unreadable` routed by each step |
| CI on one PR | `verify-pr` (`orch-runtime op`) — `status` `complete` with verdict `pass`/`fail`/`none`; `pending` or `unreadable` repeated through [Waiter launch](waiter-launch.md); a `fail` verdict is rerun once per head through `github.sh ci-rerun --required-only` before ci-fix, the item's `ci_rerun` record written first ([submit-pr.md § 5.1](../workflows/submit-pr.md#51-ci-failure-recovery)); the merge state is read through `pr-merge --check` before the first call, and `CONFLICTING` takes the workflow's `conflict` route and never the wait |
| Copilot's work on one PR's head, before a triage read | `orch-runtime copilot-wait --repo [OWNER/REPO] --pr [PR_NUMBER]`: bounded by `ORCH_COPILOT_HOLD_SECS` from its own start, its reply's `status` and `state` routed by [review-pr-comments.md § 1](../workflows/review-pr-comments.md#1-fetch-and-parse)'s table |
| Merge-queue / auto-merge outcome | `orch-runtime queue-watch --item [STATE_KEY] --repo [OWNER/REPO] --pr [PR_NUMBER] --poll [SECS] --max-wait [SECS]`: one wait bounded by `--max-wait`, its reply's `status`, `verdict` and `cause` routed by [merge-pr.md § 5](../workflows/merge-pr.md#5-execute-the-merge) step 1's table |
| Many PRs, long horizon | `pr-watch.sh` — § Multi-PR watching |

Per-verdict routing lives in the workflows (`submit-pr.md` § 4 and § 5, `merge-pr.md` § 5, [merge-attempt.md](merge-attempt.md)). `verify-review`'s reply fields are § The review call's, `verify-pr`'s are in `submit-pr.md` § 5's result table, and `queue-watch`'s verdict and cause words are in `merge-pr.md` § 5 step 1's table.

`blocked` is an approval, a `proceeded` or an `off` the runtime refuses to publish, under either mode: an `escalated_items[]` entry of `kind` `regression-against-main`, a break the branch made, stands with an outcome other than `skipped`, and `reason` reads `regression-open location=[LOCATION]`. It is never a met gate. [review-pr.md § At The Cap](../workflows/review-pr.md#at-the-cap) and its [§ 7 Converged](../workflows/review-pr.md#converged) exit write the entry, and it stands until its outcome reads `skipped` or it leaves `escalated_items`.

`queue-watch` names three states on an armed head. `queued` has a merge-queue entry, and progress is read from the entry's merge-group head; `cause: progress_unobservable` means that head could not be read. `queued` has one other shape, which is no armed head at all: `cause: exit_unconfirmed` is a PR the last poll saw out of the queue and unarmed, its ejection or disarm short of its confirmation count, so nothing is armed to fire on its own. `armed_awaiting_checks` is armed, not enqueued, with no failed check at the wait's last check read: `merge-pr.md` § 5 step 1 waits again on the same head, spending no recovery cycle, until `QUEUE_WAIT_ARMED_MINUTES` (default 90) of wall clock hands it back. `armed_blocked` is armed and not enqueued when the wait ended: a failed check takes the recovery cycle, which `CI_FIX_MAX_CYCLES` bounds, and `cause: not_mergeable` is a last check read that settled as `pass` or `none` with no entry, which `merge-pr.md` § 5 step 1 reads again before it routes. The wait reads the checks through one `verify-pr` read per `QUEUE_WAIT_PROBE_INTERVAL` (default 120 seconds), and only while a poll still fits after it before `--max-wait`; an answer that arrives past that budget is no reading. A deadline cause, `checks_pending`, `checks_unread` or `not_mergeable`, is therefore the last reading before the deadline, never a check verdict.

A wait is a running waiter, never a session sitting at its prompt.

## Stacked pull requests

Under `approval` the review call requests Copilot itself on every head Copilot has not reviewed, so a stacked pull request whose base the repository's automatic-review rulesets do not target is requested like any other head; which bases those rulesets target is the github skill's [automatic-review.md](../../github/references/automatic-review.md). Merging the bottom of a stack retargets the next pull request onto the new base without moving its head: its head record and request stand, and its gate mode stays the one the item recorded. Where the new base's diff needs Copilot's review, push a new head, which takes its own request. A head is asked at most twice: a request whose Copilot work ends with no review of the head is sent once more, and a Copilot run that stood for the request and ends so is followed by the request and that one resend. When the second request's work ends the same way, the request falls back `cause=unconfirmed`, and the overseer's fallback approval decides the head.

## GitHub authentication

`verify-review`, `verify-pr` and `queue-watch` run `gh` as the calling process is authenticated, and select no token of their own beyond the github router's own order on `queue-watch`'s guard calls. A failed read is an `unreadable` reply, or `queue-watch`'s `status: error`, at once for a refused read and once its budget is spent for a transient one, never a verdict. The runtime's watch selects its token once at its start: [DEVELOPMENT.md § GitHub auth ladder](https://github.com/vanillagreencom/kendex/blob/main/skills/orch/DEVELOPMENT.md#github-auth-ladder).

## Multi-PR watching

The waits above are single-PR waits. For many PRs across a long horizon, the github skill ships `scripts/pr-watch.sh`, a needs-attention reducer; its contract is `pr-watch.sh --help`. The fleet watch, `orch-runtime watch run`, runs it once per repository per long pass; with the script missing, that duty fails each pass as `reducer-failed`. Each pass reads GitHub's review state for every open PR, its unresolved threads, `reviewDecision`, auto-merge arm and merge-queue entry, and writes nothing. The fallback without it is per-PR `verify-review` and `queue-watch`. `queue-watch` watches only the one PR it is given and only while it runs, so the fallback gives no standing view across PRs and no `awaiting-stale` report. A PR that no wait watches warrants a manual read of `gh pr view [N] --json reviewDecision,autoMergeRequest` and its queue entry.
