# Review gate and waiter reference

Full contracts behind the gate-mode summary and the `approval-wait` / `ci-wait` / `queue-wait` rows in [../SKILL.md](../SKILL.md).

## Gate-mode settings

| Setting | Semantics | Default |
|---------|-----------|---------|
| `REVIEW_GATE_MODE` | The ENGINE's one-switch per-repo gate disable, resolved FIRST by `approval-wait --resolve-mode`: exactly `off` prints mode `off` (the wait is skipped; the engine keeps the required status green with a disabled-by-settings attestation). Any other value leaves the keys below authoritative. Set in `vstack.settings.toml` — the engine does not read `.env` files. Listed here because orch consumes it even where the review-gate skill is absent | `enforce` |
| `PR_REVIEW_GATE` | Reviewer-gate mode: `approval` requires the GitHub-native approval verdict; `review` requires a non-author review of the current head plus zero unresolved threads, for commenting-only bots that never approve; `off` means a reviewer-less repo — wait skipped, gate recorded not-applicable | `approval` |
| `PR_REVIEW_CHECK` | Exact name the trusted review bot publishes on analyzed heads (e.g. `Devin Review`). In `review` mode a `success` signal of that name on the current head — a check-run conclusion or a commit-status context, whichever surface the bot publishes — is accepted as review evidence when no review object is pinned there, for bots that submit a review object only when they have findings. Matched by name alone, so name only a trusted publisher | empty |
| `PR_REVIEW_QUORUM` | Comma- or space-separated reviewer logins that must EACH have a non-dismissed review pinned to the current head — with zero unresolved threads — before any success emit, in either mode. The multi-bot enqueue gate: one bot's verdict cannot open the gate while a listed sibling has not reacted to this head. Findings hold the gate as threads/CR; prose is never parsed. The deadline and `PR_REVIEW_ON_TIMEOUT` still bound a dead reviewer | empty |
| `PR_REVIEW_ON_TIMEOUT` | Deadline behavior when no reviewer posts: `block` → `timeout` and the workflow prompts; `proceed` → `proceeded` (exit 0) recorded as a reviewer-down override, so a dead reviewer never stalls the fleet. Reachable only with zero unresolved threads (an open thread returns `comments` first); CI and comment hygiene still apply, and a `changes_requested` always blocks | `block` |
| `PR_REVIEW_NUDGE_SECS` / `PR_REVIEW_NUDGE` | After `PR_REVIEW_NUDGE_SECS` without the mode's signal for the current head — the clock restarts on every push — the poller posts the configured `PR_REVIEW_NUDGE` comment once per head SHA, or with that setting empty falls back to a GitHub-native re-review request to the PR's requested and past reviewers | `600` / empty |
| `PR_REVIEW_WAIT_SECS` | Total review-wait budget in seconds — the per-repo quiet period before the on-timeout policy applies. Read only when the caller passes no `max_wait` positional; an explicit positional always wins, so context-specific bounds stay exact | `900` |

**Legacy mapping.** `approval-wait --resolve-mode` prints the effective mode (`approval`/`review`/`off`): `PR_REVIEW_GATE` when set, else legacy `PR_APPROVAL_GATE` (`on` → `approval`, `off` → `off`), else `approval`. It is the single implementation of that derivation, and workflows read the mode only through it. Auto-detection is forbidden by design: an empty requested-reviewer list proves nothing, because review bots never appear as requested reviewers before their first review.

## `approval-wait`

`--json` returns `{status, review_decision, approvals, changes_requested, unresolved_count, elapsed_seconds}` where `status` is `approved`/`reviewed`/`changes_requested`/`comments`/`timeout`/`proceeded`/`error`. `proceeded` (exit 0) is the reviewer-down degrade; `--on-timeout block|proceed` overrides the setting.

Approval is GitHub-native only, on either signal: `reviewDecision == "APPROVED"`, or — when `reviewDecision` is empty because no required-review protection exists — at least one reviewer whose latest review is APPROVED and none whose latest is CHANGES_REQUESTED. `REVIEW_REQUIRED` never falls back to `latestReviews`. Any reviewer counts, human or bot; emoji reactions, sticky comments, and checklist prose are never parsed. `status: "comments"` is an early return when unresolved threads exist without a verdict, so callers triage instead of idling to the deadline. Every exit path emits a final stdout result.

`--mode review` waits for a formal review instead of an approval. It succeeds with `status: "reviewed"` (exit 0; JSON adds `mode`, `head_sha`, `reviews_at_head`) when a submitted review is pinned to the current head SHA — re-read every poll, so a force-push resets the wait — is not DISMISSED and not the author's own, with no non-author reviewer standing at CHANGES_REQUESTED and zero unresolved threads. Any state counts; an approval is also a review. With `PR_REVIEW_CHECK` set, a `success` signal of exactly that name on the current head also counts, and the result carries `review_evidence` (`"review"` or `"check"`) plus `review_evidence_surface` (`"check_run"` or `"status"`) for check evidence.

## `ci-wait`

`--json` returns `{status, verdict, elapsed_seconds, pending_checks, failed_checks, passed_checks}` where `status` is `complete`/`timeout`/`error` and `verdict` is `pass`/`fail`/`pending`/`none`. `verdict=none` (with `status=complete`) means the repo has no CI to wait for — no active workflows, no branch protection, and no required-check rules on the PR's base branch, each probe answering affirmatively; a probe failure falls through to the normal grace path instead. Callers treat `none` as a documented no-CI route, never as a failure needing an override.

It ignores later all-skipped dispatches when selecting the current-head substantive run, and treats an aggregate status still linked to an older run as pending while a newer substantive run has no failures. A settled failure attributable only to superseded runs is correlated against the head's Actions run list: any queued or in-progress substantive-event run on the head — including a rerun attempt of an older run, which keeps its original run id — keeps the verdict pending; a newest same-workflow run that completed successfully discards the stale failures; a failed newest run, or a cancelled run with no newer or fresher sibling, stays terminal. Current-run failures remain terminal and a missing replacement reaches the timeout rather than passing. `CI_WAIT_NO_CHECKS_GRACE` (default 180s) bounds unregistered checks.

## `queue-wait`

`--json` returns `{status, verdict, elapsed_seconds, polls, pr_state, merged_at, in_merge_queue, merge_queue_state, auto_merge_enabled, was_queued, was_in_merge_queue, progressing}` where `verdict` is `merged`/`ejected`/`disarmed`/`dequeued`/`closed`/`queued`/`not_queued`/`unknown`, plus `cause` when known (`merge_group_failed`, `check_failed`, `auto_merge_cleared`, `never_armed`, `closed_without_merge`, `late_findings`, `late_findings_dequeue_failed`, and on `queued` always `still_progressing` or `stalled`), `unresolved_count` once the late-findings guard has read threads, `transient_api_errors` when any were absorbed, and `last_poll_age_seconds` once a poll completes. Exit `0` only for `merged`; `1` for every other verdict and non-auth error; `3` on auth failure.

- `progressing`: `true` when the merge-queue entry tuple (`state`, `position`, `headCommit.oid`) or the completed check-run count on that head commit changed within the last 3 polls, OR the last successful check-run read on that commit still shows a not-completed run (`in_progress`/`queued`/`waiting`/`requested`/`pending` — a suite mid-flight is progress even when nothing completes for many polls); `false` when that was measurable, nothing moved in the window, and nothing is running; `null` when it was never observable (no head commit exposed, or every check-run read failed — a failed read is unknown, never zero). One paginated check-runs read per poll yields both counts.
- `cause` on `queued`: `still_progressing` when `progressing` is `true`, else `stalled` — the discriminator a caller needs before acting on a budget-exhausted `queued`, since re-arming a still-moving merge re-queues a healthy one.

It is the merge-pr queue watch as one command — which is what makes it usable under Codex `approval=never`, where a poll loop is a rejected shape — and the only place `WAS_QUEUED` can live, since a per-poll re-entry carries no memory and so cannot tell an ejected PR from one that was never queued. Each poll reads `gh pr view --json state,mergedAt` plus the GraphQL `isInMergeQueue`/`mergeQueueEntry { state position headCommit { oid } }`/`autoMergeRequest` fields, because `gh pr view` exposes no queue-membership field, and — when the entry exposes its head commit — the REST check-runs list on that commit for the progress signal. Default budget is `30 2400` (40 min), sized to the merge-group suite (measured runs up to ~25 min).

Ejection is `WAS_QUEUED` plus lost queue membership while still OPEN. `disarmed` is an armed-but-never-enqueued PR whose `autoMergeRequest` cleared, or whose required check failed — that half delegates to `ci-wait --json` → `verdict=fail`, rate-limited by `QUEUE_WAIT_PROBE_INTERVAL` and scoped to the armed-not-enqueued shape (`--no-check-probe` disables it). Ejection and disarm verdicts are confirmed across `QUEUE_WAIT_CONFIRM_POLLS` (default 2) consecutive polls so one eventually-consistent blip cannot trigger a recovery cycle, and a candidate seen at least once still wins at the deadline. `QUEUE_WAIT_ARM_GRACE` (default 120s) bounds a never-armed PR before `not_queued`. A deadline reached with the PR still queued reports `status: "timeout"`, `verdict: "queued"` with `cause: still_progressing` or `stalled` — the merge stays armed and fires on its own, so it is neither failure nor success.

The late-findings guard (default on; `--no-guard` opts out) exists because the queue never re-checks thread resolution once a PR is queued, so a finding posted after enqueue merges unwatched. While the PR is queued or armed, the guard reads the unresolved review-thread set on the same `reviewThreads` surface `approval-wait` uses, rate-limited by `QUEUE_WAIT_PROBE_INTERVAL` on its own clock. ANY unresolved thread observed while queued or armed triggers — pre-existing or new, no baseline: an unresolved thread in the queue is unsafe whenever it appeared (approval mode returns `approved` on the verdict alone, so enqueue does not prove threads were zero). A thread resolved while queued is fine, and the triage-then-re-enqueue route cannot churn-loop — re-enqueue follows comment triage. On trigger: armed → `disablePullRequestAutoMerge` first (closing the re-arm hole); queued → `dequeuePullRequest` (whose input field `id` takes the PR node id, unlike enqueue's `pullRequestId`); a queued-and-armed PR gets both, disarm first: `verdict: "dequeued"`, `cause: "late_findings"`, exit 1, routed to comment triage and re-enqueue. A failed mutation is loud — `cause: "late_findings_dequeue_failed"`, exit 1, the PR stated still queued — and a failed thread fetch is no evidence, never no threads: the guard keeps waiting, retries next probe, and warns after 3 consecutive failures without ever fabricating a dequeue or a quiet.

## Waiter auth ladder

All three waiters use `scripts/lib/gh-auth.sh`, wrapping the GitHub skill's shared helpers, for a bounded auth-resolution ladder (full ladder in `DEVELOPMENT.md`). Auth is env-first: already-resolved `GH_TOKEN`, `GITHUB_TOKEN`, or `GH_BOT_TOKEN` values from the parent process win before local files are read, and `op read` runs only for the final selected `op://` reference. Preflight validates selected env tokens with `gh api user`; `gh auth status` is authoritative for keyring auth only when no env token is selected. Each candidate source is probed at most once. Exit `3` on hard auth failure.

## Multi-PR watching: `pr-watch`

The waiters above are single-PR foreground waits. For many PRs across a long horizon, the review-gate skill (optional dependency) ships `scripts/pr-watch.sh`, a needs-attention reducer: exit 0 for silence or health, exit 1 with tab-separated `<pr> <head8> <kind> <detail>` lines (`threads-open` with queued-PR dequeue annotation, `changes-requested`, `gate-stale` in both mismatch directions with `--heal`'s once-per-invocation writer dispatch reported as `heal-dispatched`, `disarmed`, `awaiting-stale` past `PR_REVIEW_WAIT_SECS`, `head-moved` when a push landed mid-reduction, and per-PR `error` lines), exit 2 on read failure.

Exit 2 has two shapes: per-PR failures carry `error` lines on stdout, while GLOBAL failures (missing `GH_REPO`, a broken open-PR listing) report on stderr only with no per-PR lines — consumers must surface stderr, not just parse stdout. Orch consumes it opportunistically via an existence check on the script; the fallback is per-PR `approval-wait`/`queue-wait` polling with one stated limitation: the waiters never read `REVIEW_GATE_CONTEXT` or verify writer convergence, so they cannot detect `gate-stale`. In the fallback, a PR that reads reviewed-and-clean but sits unmerged warrants a manual gate-status check (`gh api repos/<owner>/<repo>/commits/<head>/statuses`) and a writer dispatch. The wrap-in-anything loop lives in the review-gate skill's adoption guide.
