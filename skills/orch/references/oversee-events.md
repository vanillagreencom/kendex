# Oversee events

[oversee.md](../workflows/oversee.md) § 4 applies these rules at every watch event.

## Judgement rules

The overseer owns fleet judgement, not just liveness; every `oversee.md` § 4 event is handled under these rules. The fleet log is the oversee state's `fleet_log[]` ([schemas/workflow-state.md § Oversee state](../schemas/workflow-state.md#oversee-state)), which exists before the first append per `oversee.md` § 3 Lane record; every record a rule below asks for is one append, `[KIND]` being `proposal`, `ruling`, `close`, `peer` or `use1` and `[ITEM]` the issue or repository it is about. `[ONE_LINE]` carries text the overseer did not author, so the record crosses a file and never argv ([SKILL.md](../SKILL.md) § Harness-Safe Shell): write it with the harness file-write tool, then bind the path. Append each record before replacing the file for the next one. The record carries no time: `append-file` stamps `at` from its own clock and refuses as `fleet-log-at-future` a record already dated later than it. `[ONE_LINE]` holds at most `ORCH_FLEET_LOG_ROW_BYTES` bytes, default 600, and a longer one is refused as `fleet-log-row-bytes`. The `append-file` entry in `workflow-state --help` names the rest of what it refuses on that field.

```json
{"kind":"[KIND]","item":"[ITEM]","text":"[ONE_LINE]"}
```

```bash
.agents/skills/orch/scripts/workflow-state append-file oversee fleet_log tmp/fleet-log-record.json
```

- **Lane proposals.** Record each lane's `Proposal comment:` notice in the fleet log as an authorized tracker, repository, issue, and returned comment ID or URL binding. Partition pending authorized comments by tracker and source PR repository. For each batch, launch one fresh one-shot canonical `tpm` subagent, the catalog's planning agent that owns the creation bar, priority, placement, duplicate and cancellation analysis, on the lowest-cost model the surface exposes, with the launch call, surface rule, single-return capture and retirement of the `triage` verifier under § Event kinds, naming `tpm` where that call names `maintainer`. A proposal sweep creates no carrier item and starts no `open-terminal` or hosted lane, and its TPM analysis never runs in the overseer. Send it the [proposal-sweep](../../project-management/workflows/proposal-sweep.md) workflow with a brief that supplies a checkout of the source repository on this host as its worktree, the batch tracker, tracker repository, source repository, fleet issue IDs, and authorized and resolved comment bindings. Accept the return only when it contains no other text and parses as one issue-mode audit object whose `tracker` type, and for GitHub its `repository`, equal the batch's. Its proposal rows are its `create` and `skip` rows: each carries exactly one `proposal_sources[]` entry by `index`, each entry names a distinct authorized binding of this batch, and no entry points at another row. A proposal whose source PR has not merged has no row and stays pending for the next sweep. Stop without a reply or fleet-log outcome on a launch, capture, parse, or validation failure. Write the accepted object with the harness file-write tool to `tmp/proposal-audit-[UTC_EPOCH].json` in the overseer's checkout, `[UTC_EPOCH]` fresh per batch. Check its rows against live fleet work, then invoke [audit-issues](../../project-management/workflows/audit-issues.md) from `oversee.md` § 1 as `audit-issues --analyzed tmp/proposal-audit-[UTC_EPOCH].json` under `PM_CREATE_AUTONOMY`. Its normal route parses the tracker, runs its tracker preflight and label inventory, skips TPM analysis, and continues through §§ 5-7. For Linear, reply with `.agents/skills/linear/scripts/linear.sh comments create [ISSUE_ID] --parent [COMMENT_ID] --body-file [PATH]`. For GitHub, use `gh issue comment [NUMBER] --repo [OWNER/REPO] --body-file [PATH]`; its first line is `Proposal outcome for [COMMENT_URL]:`. Each outcome carries the created issue ID or one-line decline. Record the source and outcome in the fleet log.
- **Heartbeat backstop for lane proposals.** At each `heartbeat` and before fleet close, run the Lane proposals sweep with every fleet issue in its tracker and repository batch. This catches a comment posted without another event.
- **Heartbeat backlog audit.** At each `heartbeat`, apply [Heartbeat audit](heartbeat-audit.md), independently of the lane-proposal sweep and the fleet-lane `triage` verifier.
- **Cut scope blowups.** A PR whose diff outgrows its issue's Done-when goes back to the contract: keep the oversized work on a branch, land the contract. Machinery no issue ordered — a new subsystem, scanner, or lexer — is cut, never reviewed into shape.
- **End spirals.** A round whose finding shares a root cause with one a prior round patched is dispositioned by [references/finding-disposition.md § Recurrence](finding-disposition.md#recurrence), which states the branches and their limits. Bots drip-feeding one class get the class exhausted in one audit pass, then dispositions without pushes. After five bot rounds on one PR, the lane answers the standing threads once and starts no further fix round. The review gate and the user's merge authorization still apply. The overseer never orders a blanket `Declined` across a PR's open findings: each one is dispositioned on its own mechanism, and a label-only decline violates [finding-disposition.md § Decision flow](finding-disposition.md#decision-flow).
- **Fix the source.** The same finding class on a third PR is a mechanism gap: file it and route the smallest deterministic check (a guard lane, a preflight rule, a refusing script) or one sentence in the owning skill through a lane as its own item — the overseer still implements nothing. Deterministic beats prose where it stays simple; complex or brittle machinery is worse than either. A package or workflow gap is never a harness memory or a local note: a lane's is a proposal ([skill-rules.md § Coordination, Tracked issue creation](skill-rules.md#coordination)), and the overseer's own is filed as File one item alone below states.
- **File one item alone.** One item the overseer files itself, a class under Fix the source above or an issue an `owner-note` asks for, goes through [audit-issues](../../project-management/workflows/audit-issues.md) as `audit-issues --single [FILE_PATH]`, the file holding that one item per [audit-issues-input.md](../../project-management/schemas/audit-issues-input.md) with `source: "oversee"`, `parent_issue: null` and the fleet's `tracker`. `--issues` is for a batch: its TPM run sweeps the whole backlog for cancellations.
- **Rule once for the fleet.** A ruling that answers one lane's question is sent to every lane in the same situation and recorded in the fleet log.
- **Held merges.** Under `ORCH_MERGE_AUTONOMY=ask` (`oversee.md` § 3) the lane's merge question arrives as `lane-question`. Read the gate results without reproducing them, then relay the question to the user, worded as [communication-modes.md](communication-modes.md) requires. Send `MERGE` to the lane only after the user authorizes it, or send exactly one directive the user gave. A directive may carry the authorization ("with that landed, MERGE stands"), and the lane then merges once the change is in without a second answer. Under `ask` a `disarmed` pr-watch line is not a wake.
- **Lanes merge their own pull requests.** A lane whose gates read met merges its own head by [merge-pr.md](../workflows/merge-pr.md) § 5 step 1, where `pr-merge` picks the route. The overseer runs no normal merge for a lane. Its own GitHub App acts in two cases alone: the emergency merge of a verified head whose required check cannot pass, which that step's "Who acts" names, and the head approvals [copilot-head-notices.md](copilot-head-notices.md) sets.
- **Hand off a lane before it runs out.** The `lane-mail-check` turn-end hook reads the lane's context through its harness adapter, from the transcript, or on Copilot CLI from the reading its kendex Copilot extension recorded from Copilot's `session.usage_info`, against the limit Copilot compacts at, and where none stands from Copilot's statusLine session record ([copilot-runtime.md](copilot-runtime.md#measurement)), and its account headroom on its own credential, and refuses the turn end at either mark until the record below stands, so a lane hands itself off with no directive. Copilot honours a turn-end block 8 times in a row and then ends the turn unheld; the refusal returns at the session's next turn end. What follows is the BACKSTOP for a lane whose hook refused nothing, such as one past its account mark with no turn end since. On the `oversee.md` § 1 tmux surface, at every `oversee.md` § 4 event, read each live lane's context use:

  ```bash
  .agents/skills/orch/scripts/lanes context
  ```

  The shared context rule in `../scripts/lib/lane-context.sh::lane_context_handoff_due` requires handoff at 400000 tokens used, or when strictly less than 10 percent of effective capacity remains. `ORCH_HANDOFF_CONTEXT_PCT` accepts 1 to 100 and defaults to `90`; values above `90` use `90`. A lower setting requests an earlier handoff only after usage strictly exceeds that percentage. Equality at any percentage does not trigger handoff, unless the independent token limit is reached. The token limit applies even when capacity is unknown. Below that token limit, unknown capacity remains unmeasured. Capacity means the limit before automatic compaction, or the actual window when automatic compaction is disabled; [skill-rules.md](skill-rules.md#coordination), Compaction, defines the harness controls.

  `lanes context` reports the context reading each lane's hook recorded at its last turn end, hosted lanes included, and account headroom. It sets `handoff_required` when the shared context rule requires handoff, or when the binding account bucket has headroom at or below `ORCH_HANDOFF_HEADROOM_PCT`. A Copilot lane's launch takes no `--lane`, so no claim names it: its row is read from its running lane record. Every other lane is read through its claim alone. A row reading `unrecorded` has no reading yet, which is not room. A row reading `window-unread` has unknown capacity and remains below the independent token limit: direct it to write its handoff at its next safe point. The default is `3`, so a lane whose account reaches 97 percent used is marked for the overseer's next sweep, and the hook refuses the turn end on that same setting. Both resolve it through the kendex settings ladder, the hook through `orch-env` and this poll through its own project-env load, so a settings file sets one mark for both. At each event, tell every lane the poll marks and the hook has not already stopped to write its handoff at the next safe point, as for the context mark; a lane whose record already stands is handing itself off and needs no directive. Use `oversee-lanes.md` § Talking to a lane until lane mail is installed; then send the directive through lane mail. At either mark, wait for a safe point such as a landed merge or held PR. Never interrupt a round or an unpushed tree. The lane records the fixed shape below and exits. The record carries no time: `workflow-state set` stamps `written_at` from its own clock and refuses as `handoff-written-at-future` a record already dated later than it. The `set` entry in `workflow-state --help` names the rest of what it refuses on that field. The watch reports `handoff [ISSUE_ID]` once. Relaunch the item through [lane-directive.md § Recovery relaunch](lane-directive.md#recovery-relaunch), which uses the handoff record as durable recovery state; a copilot lane's relaunch starts a fresh session on that record rather than resuming the one that handed off.

  ```bash
  .agents/skills/orch/scripts/workflow-state set [ISSUE_ID] handoff '{"merged":["[PR]"],"remaining":["[STEP]"],"branch":"[BRANCH]","worktree":"[WORKTREE_PATH]","open_pr":[PR_NUMBER_OR_NULL],"traps":["[TRAP]"]}'
  ```

  The record, the event and the relaunch are surface-independent. Surfaces 2 and 3 register no lane claim, so `lanes context` reports no worker lane there: on surface 2 read a lane's context through the harness's own session tooling and hand off at the same mark; surface 3 has no lane to hand off.

  On a hosted fleet, also run `lane-host list`: a row not `available` whose item, the last segment of repository/item, has no `running` lane record is a sandbox with no live claim; surface it to the user.

  The overseer's own case: its triggers reach it by two routes. The account triggers run on both routes through the one judgement `oversee-succeed` owns. The context mark is judged only on the reading the `lane-mail-check` hook takes, by `lane_context_handoff_due` in `scripts/lib/lane-context.sh`. From INSIDE, the rendered `lane-mail-check` turn-end hook runs that judgement at the overseer's own turn end, handing it the context reading that turn end took, and refuses it at any reached trigger, naming the succession below, with that reading, as the route; it knows this session by the tmux server and pane the fleet state records under `.overseer`, which `oversee-watch` writes before its first pass, and heals a record naming this pane that lacks its server start, harness or launch home from the session itself rather than read it as another session's. After each tool call the same hook hands a reached context mark over as context, so a mid-turn crossing is read at the next one. A judgement it could not make, one its ceiling abandoned, and one whose reading was unmeasured are reported and the turn ends: an unmeasured trigger is never read as room. From OUTSIDE, every watch pass judges the account triggers, never the context mark, which has no reading outside the hook, and reports a reached one as `overseer-mark` in [overseer-session-events.md](overseer-session-events.md), once at the crossing and again every `ORCH_OVERSEER_MARK_REPEAT` passes while it stands, so an overseer that has not ended a turn since it crossed is still told. Silent passes between those lines are the interval, never a mark that lifted. `ORCH_OVERSEER_SUCCESSION=off` turns the account-trigger refusals off along with the succession they name; the event still goes out, carrying `succession=off`. The context-mark refusal stands under that setting, since nothing else reports that mark, and the handoff record it names ends it. The `lanes context` row remains the backstop for the account: the overseer's own pane is in that report, claim or no claim, marked with a leading `*` on its lane name, and that row carries its account headroom; its context reads `unrecorded`, since only the hook's reading judges it. That row's `HANDOFF` cell reports the shared context mark and the lane headroom threshold, and never `ORCH_OVERSEER_HEADROOM_PCT`, the wall or the qualifying-accounts trigger. The overseer succeeds itself when the shared context rule requires handoff, account headroom reaches `ORCH_OVERSEER_HEADROOM_PCT`, projected wall time reaches `ORCH_OVERSEER_WALL_MINUTES`, or the `ORCH_OVERSEER_SUCCESSOR_ACCOUNTS` trigger fires by the rule `oversee-succeed --help` states. At any trigger, wait for a safe point with no `merged` event mid-handling and no lane waiting on a root answer. Write the succession progress report as `report-due` under § Event kinds states, with `--succession` on `write`, whatever `ORCH_REPORT` says. No event repeats a refused `write` here: tell the user this handover has no report and the cause its first stderr line names, put that line in the handoff file and go on, since the last report's time did not move and the successor's next report covers the same merges. Then run the prune and rewrite the overseer handoff file per `oversee.md` § 5, the handoff in the shape [communication-modes.md](communication-modes.md) § Handoff gives, then run `.agents/skills/orch/scripts/oversee-succeed --context [TOKENS:WINDOW] -- [FLAGS]` under a shell-tool timeout longer than its `--wait-secs`. `[TOKENS:WINDOW]` carries tokens used and effective capacity from the turn-end refusal's command; the context mark is judged on it alone, so at an account trigger with no refusal to copy it from, leave `--context` out. `[FLAGS]` are the permission flags this overseer runs under, plus its own model and effort flags. Those two words reach a successor opened in the caller's own harness alone, the entry the walk always ends in, which names no model or effort of its own, so they are what such a successor runs on whatever `ORCH_OVERSEER_PREFERENCE` says. A successor opened on a NAMED preference entry takes the permission flags and the model and effort that entry names: the caller's pair is spelled for the caller's harness and names a model that entry did not choose, so passing it on would hand the successor a second model and an effort flag its harness may not have. Add `--handoff [PATH]` when the fleet brief names another handoff path. It chooses the successor's lane by its own rule, which `oversee-succeed --help` owns and this file does not restate, opens the successor overseer there and closes this window. Before that close it leaves a helper, started through the orch job runner ([job-units.md](job-units.md)), that restarts the fleet watch, which served this window's pane, from the successor pane with the successor's flags and account through the same runner, and prints `watch-handover` with the helper's runner line, or prints `watch-absent` where no watch runs. The helper writes `watch-restarted pid=[PID] pane=[PANE]` with the watch's runner line, or `watch-restart-failed step=[STEP]`, to `oversee-watch.err` beside the fleet state. The restarted watch's own start stops the old one, whose pane is gone. The successor starts its watch as `oversee.md` § 4 says, with no stop by hand: that start takes over the restarted watch, or the old one where no restart ran, since its pane is gone, and prints the restart's lines and whatever the restarted watch printed. On a host where the runner can start nothing, with neither a lingering user manager nor `setsid`, the helper never starts, `watch-restart-failed step=helper` goes to stderr, and that takeover is the recovery. On `context-below-mark`, or `context-unmeasured` with `reason=window-unnamed`, no trigger is reached: keep running and run it again at a later event. On `context-unmeasured` with `reason=context-unread` the run was handed no reading: at the context mark, run the command the refusal names, which carries it. The `headroom` field on those lines reads a number where the account was measured, and `none` or `unreadable` where nothing measured it, which is not the same as having room. `no-lane-qualifies` means no lane walked has room for a successor: every `ORCH_OVERSEER_PREFERENCE` entry, counted in `entries`, and then the fleet-wide sweep of the harness `fallback` names, which the walk always ends in. `walled` and `unmeasured` are the accounts those sweeps refused and the accounts nothing could measure, so a spent fleet reads differently from a preference aimed at the wrong harness. Its `mark` field names `headroom`, `rate`, `qualifying`, or `context`. A headroom refusal also carries this overseer's account and reset time. On `succession-off`, keep running and hand off by hand: tell the user the handoff file is written and a fresh overseer session must start, in the shape [communication-modes.md](communication-modes.md) § Status report gives. At an account trigger the turn-end refusal is off under that setting, so nothing holds this session; at the context mark it stands, so record the handoff as for any other refusal below. On `no-lane-qualifies`, `launch-failed` or any other refusal, the turn-end refusal does stand, so tell the user the same thing and then record the handoff on the fleet's own item with the command that refusal prints, which is what ends it so this session can close. Write that command as it stands: beside `handoff_file` it carries a `session_id` and a `pane_key` naming this session, and no time, which `set` stamps, and the refusal ends on a record whose names are the reader's own and on no other.

  An overseer that DIES reaches none of this: it runs no turn, so it judges no mark and calls nothing. `oversee-watch` carries that case, from the session rows the overseer's own harness writes, its pane process and its recorded launch line, and reports it as `overseer-dead` in [overseer-session-events.md](overseer-session-events.md). An overseer that WALLS reaches none of it either, for the same reason and with the harness still running: the watch reads the same rows and reports it as `overseer-walled` there, recovering it on an account the pick judged rather than on the recorded line's spent one. One that WEDGES on a full context reads as `overseer-dead` `source=context`.

- **Keep the report's inputs current.** After each `oversee.md` § 2 selection, `workflow-state set oversee launch_queue '["[ITEM]",...]'` with the items not yet launched, in launch order. The queue is the order and the tracker the membership: the `heartbeat` handling below adds what the tracker says the fleet owes. A question sent to the owner is an owner ask ([communication-modes.md § Owner asks](communication-modes.md#owner-asks)), and the report's Waiting on you row reads the unresolved ones from the mailbox itself; nothing is recorded in the state for it.
- **Decide without the user.** The ask set is [communication-modes.md](communication-modes.md) § Ask set, which nothing here narrows or widens. Any other call takes the option that costs nothing and is recorded in the fleet log as that file's § Recording requires.

## Direct-push cycle records

When a lane reports a successful direct push to the base branch, record its cycle before closing it or removing its workflow state. Run from a checkout of that repository. A direct push raises no PR `merged` event. Refuse to record a push with several commits and report it in the fleet log; `oversee-cycle --help` defines the single-commit contract.

```bash
.agents/skills/orch/scripts/oversee-cycle --state-dir [OVERSEE_STATE_DIR] record --commit [PUSHED_SHA] [ITEM_KEY]
```

Use `--tier [TIER]` only for an old lane record without a launch tier. Add `--repo [OWNER/REPO]` when the lane record names no repository. Unknown fields print `-`; the verdict is `unmeasured` when classified. Report a refusal without blocking lane close.

## Event kinds

A lane's successful direct-push completion takes [§ Direct-push cycle records](#direct-push-cycle-records) before lane close.

To wake a lane below is to send it the directive and wake it per `oversee-lanes.md` § Talking to a lane, which wakes only a Claude Code or Codex lane whose send receipt reads `monitor=none`.

- `merged` → the PR is in; the owning lane finishes `merge-pr.md` § 5 on its own and a GitHub merge alone is not lane completion. A PARKED item ([oversee-lanes.md § Parking a merge wait](oversee-lanes.md#parking-a-merge-wait)) takes the `parked-merged` rule alone, which runs the cycle record below once the relaunch brings its sandbox up. For an item that is not parked, first, before any step below and while the lane's own workflow state still stands, record the lane's cycle from the overseer's base checkout, or from a checkout of the lane's repository where its `mail_root` is another repository's worktree, as `oversee.md` § 3 runs `lane-mail` for it: `.agents/skills/orch/scripts/oversee-cycle --state-dir [OVERSEE_STATE_DIR] record --pr [PR_NUMBER] --tier [TIER] [ITEM_KEY]`, `[TIER]` being what `oversee.md` § Item Tier gives the item, and `--repo [OWNER/REPO]` added for a lane whose record names none in another repository. It logs its own row. A `verdict=miss` line needs nothing more; a `repeat-miss` line is three lanes missing on one phase, and files one CI or process issue in that repository naming the phase, the lanes and the `causes` the line gives each, per [skill-rules.md § Coordination](skill-rules.md#coordination). A refusal is reported and never blocks the rest of this rule. A hosted item stays in the watch until its `lane-closed` or `lane-close-refused` event, per § Event kinds. Wake it only if it is not still inside that run, and read a reported failure there rather than advancing the item. For a PARKED item this rule ends here: the watch closes nothing on this line, and the overseer takes no further step of this rule for it, no `sync-base`, no `post-merge` and no lifecycle check. The merge of the pull request its `parked` names, in that repository, is followed by `parked-merged`, and that rule alone carries the item: it resumes the lane, and the resumed lane runs `merge-pr.md` § 5 steps 2-6 itself, as a running lane does. For an item that is not parked, on a hosted fleet the base checkout is the control host: run `.agents/skills/orch/scripts/sync-base` there, then `.agents/skills/orch/scripts/post-merge --refresh-only`, which runs `kendex refresh --scope project --yes --leave` and then, whatever they returned, its `restore` step: `git checkout -- .` and removal of the untracked paths the refresh created, so a record the refresh re-wrote stays the committed one until its rolling pull request lands and no new render blocks that landing; CI and the lane ran build and verify, so that entry runs neither. On a fleet that is not hosted, in the overseer base checkout, run `.agents/skills/orch/scripts/post-merge`, then the repo's lifecycle check. Stop on a failed step and report its status. Consumer refresh runs in each consumer's own Actions through the [refresh workflow](../../review-gate/references/adoption.md). When the fleet's LAST item completes, run the `heartbeat` triage pass before closing out, whatever the tracker; items living in Linear also get `.agents/skills/orch/scripts/reconcile-work-items` (a GitHub-item fleet skips that with a note). Report both with the close-out.
- `parked-merged [ITEM] pr=[N] repo=[OWNER/REPO]` → the pull request a PARKED record names merged in that repository, under the `merged` line for it. The watch closed nothing and the record still reads parked: nothing on the watch's side wakes a stopped sandbox, and the record carries no launch flags. Relaunch the lane through [lane-directive.md § Recovery relaunch](lane-directive.md#recovery-relaunch) with your own launch flags, the route a `pr-watch` line on a parked pull request takes: the launcher starts the sandbox first and refuses as `host-start-failed`, the record still parked, where the provider does not confirm it, and a lane that resumes on no transcript is a blocker to report, never a resumed lane. Once the sandbox is up, run the `merged` rule's cycle record for the item. The resumed lane finds its queue wait merged and runs `merge-pr.md` § 5 steps 2-6 and § 6 itself, a further pull request of the same item included, and the overseer runs none of those steps for it. Its completion notice and exit then close it as any merged hosted lane's do, through `lane-closed` or `lane-close-refused`. The watch prints the line again ahead of every `heartbeat` for as long as the record reads parked over that merge, and the relaunch rewriting the record `stopped` is what ends the repeat: a repeated line takes this same rule, so a relaunch refused, as `lane-model-walled` or `host-start-failed`, is reported and taken again at the next repeat, never dropped.
- `lane-exited` → the window is alive but the harness under it is gone (the lane's closing lines follow the event and say why; `payload-noise-only lines=N` in their place means the lane deleted its own worktree and the shell has drawn nothing since). A lane stopped by a harness session limit ("You've hit your session limit · resets 9:50am") is not dead: resume it under another auth lane (`lanes pick --harness [HARNESS] --model [MODEL]` for the model the replacement will run, then [lane-directive.md § Recovery relaunch](lane-directive.md#recovery-relaunch)), or wait for the shown reset and use Recovery relaunch on the original account. The relaunch carries its own continuation line, except on a hosted codex lane, which resumes without one and takes it by Pane paste ([lane-directive.md § Recovery relaunch](lane-directive.md#recovery-relaunch)). A lane that reported `handoff` on an earlier run is relaunched per that event, not resumed or nudged. Any other exit is the `window-gone` rule below.
- `overseer-dead`, `overseer-walled`, `overseer-context-unmeasured`, `overseer-context-stale`, `overseer-mark` → the overseer's own session: [overseer-session-events.md](overseer-session-events.md).
- `handoff` → the item's lane recorded its handoff and exited: relaunch it per § Judgement rules, Hand off a lane; the record follows the event line.
- `lane-closed` → the watch ran `lane-close` on the merged hosted lane: record the `kept=` line below in the fleet log, the provider's `kept=PATH`, or `kept=none` for no archive ([lane-host.md](../schemas/lane-host.md) `close`).
- `lane-close-refused` → `lane-close` relayed exit 3 from the provider and the sandbox stays. Surface the `path=` line that follows to the user; its value is the checkout the close stopped on, never the path that stopped it. Render-only drift is saved as a binary patch under the hosted clone's `tmp`, restored, and refreshed before close, and the provider refuses on any of several conditions. An untraced change in the checkout is the common one; a saved patch that does not carry a path the close was about to restore or remove is another. Several of them leave every changed path inside the generated inventory, so a hunt for an untraced path can find none. Inspect the directory and never force the close.
- `lane-close` refusing `stop-failed` or `exit-timeout` → the idle lane's harness did not end by signal, and the window and record stay. `stop-failed` names the failed step as `cause=`: `cause=timeout` is a harness that ignored its signal, which on a hosted lane arrives as `cause=provider` with the provider's own lines above the refusal, and `cause=cwd-reader-missing` is a host with neither `/proc` nor `lsof`, where no process's directory can be read, so install `lsof`. `cause=provider status=4` under `--keep-sandbox` is a hosted item whose worktree its own close-out removed: the stop has no directory to find the harness by, and only a full close, which prints `stop-skipped cause=worktree-removed`, closes it: its host close ends the harness where the provider's `close` ends the sandbox, and otherwise the window kill hangs up the lane's ssh session. That reading needs the provider's `stop-worktree-removed item=[ITEM]` line above the refusal; `cause=provider status=4` without it is the provider's own `4`, such as a sandbox it stopped, whose line above names it: start the sandbox, then close again. `exit-timeout processes=0` means no harness process was left in the lane's worktree to signal. `processes=` above 0 means that many harness processes were signalled and confirmed exited, yet the pane still does not read exited: inspect what the pane now runs. Report the refusal lines to the user. Never type into the pane to end the harness instead.
