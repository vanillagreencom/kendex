# Workflow State Schema

The per-item state file orch workflows read and write, and the fleet's own record under the key `oversee`. Read it when a workflow or a script's reply names a field. It outlives the session that wrote it.

**Location**: `<state-dir>/workflow-state-[ISSUE_ID].json`, `<state-dir>` the directory `ORCH_STATE_DIR` names, or `--state-dir` where the command names one; a relative path joins the main checkout.

## Keys

`[ISSUE_ID]` is the workflow-state key, never the bare GitHub issue number, in one of four per-item forms: the tracker identifier (`PROJ-123`) for a tracked issue, `issue-<N>` for a GitHub issue, the repository-local `pr-<N>` for a pull request whose branch carries no issue id, and `local-<epoch>-<pid>-<random>` for work with neither, such as a local review whose fix round needs a key, which `orch-runtime state new-local-key` mints and writes nothing for. A workflow that inits state under a local key owns that state: it passes the key to every round it stamps and removes the state when it ends. `pr-<N>` and `local-` keys name no issue. Beside them stands one fixed key, `oversee`, the fleet record [§ Oversee state](#oversee-state) describes, which the runtime addresses as `--fleet`; an item is `--item [ISSUE_ID]`. The key is stored as passed and validated by its callers: every verb puts it into the state file name exactly as given, so the spelling passed to `init` is the spelling every later command must use.

## Field Definitions

| Field | Type | Description |
|-------|------|-------------|
| `issue_id` | string | Parent issue identifier |
| `sub_issues` | string[] | Child issue IDs if bundled |
| `agent` | string | Primary dev agent type |
| `worktree` | string | Absolute path to git worktree |
| `branch` | string | Git branch name |
| `qa_labels` | string[] | QA trigger labels from dev return |
| `qa_decision` | object | The review's QA routing, `{signals, agents, rationale}`: the signals [review-pr.md](../workflows/review-pr.md) § 6 runs, the QA agent for each, and one cause per input, with `advisory`, one `{signal, agent, cause}` per performance signal recorded advisory where a `QA_PERF_RUNNER`, `QA_PERF_WORKLOAD` or `QA_PERF_BASELINE` declaration is unset, and `reviews`, one `{signal, head, performed, reason, gating, notice}` per QA review recorded, a review not performed carrying its reason and its notice to the overseer, `owed`, `sent`, `refused` or `unknown`. The `record-qa-decision` op request writes it at review-pr § 5: its `scan` step replaces the routing, judgments included, and keeps the recorded `reviews`; its `review` step records one review. Only a user skip writes it by hand |
| `near_ceiling` | string[] | `byte-ceiling` `near-ceiling` lines from the last recorded dev return, each naming a binary blob within reach of the byte ceiling. `dev-start.md` § Store Near-Ceiling Lines is the one writer, invoked by the implement and fix accept paths and by the retry path for a structurally valid artifact with a failing `validate`. It REPLACES the list, and a return whose probe did not answer (`near_ceiling: null`) leaves it as it stood: state describes the branch as the last recorded round left it, never an accumulation across rounds. The next round's delegation renders one `Near-ceiling:` line per entry |
| `child_sessions` | object | Per-agent lifecycle keyed by logical agent name: `{agent: {status, agent_id, runtime_agent_type, agent_type_fallback}}`. `status` is `"active"` while the session is live (`dev-start.md` § 2 stamps it at spawn) and `"closed"` once the caller's shutdown step retires it (`start-worktree.md` § 5.4). Reviewer slot accounting treats a record with a missing `status` field as active |
| `review_agents` | string[] | Reviewer names currently expected to stay alive across fix/re-review cycles; in wave mode (`REVIEWER_SLOT_BUDGET` exceeded) only the currently launched wave |
| `review_agent_ids` | object | Reviewer session IDs keyed by name — reuse before spawning `{"name":"id",...}` |
| `review_agent_runtime_types` | object | Reviewer runtime agent metadata keyed by logical reviewer name: `{name: {agent_type, task_name?, fallback}}`; records a Codex `worker` fallback and, when the runtime `task_name` schema forced a hyphens-to-underscores spelling, the translated `task_name` — without changing the logical keys |
| `host_launch` | object | A released launcher's saved foreground hosted preparation for a launch without a fleet, which no current launch writes or reads; [lane-host.md § Provider protocol](lane-host.md#provider-protocol) states what to do with one |
| `validate_rounds` | object[] | One `{round_id, receipt?, kind, mode, seconds, lanes?, selection?}` entry per schema-valid dev artifact with validation time, and per pushed restack run. `orch-runtime dev-return check` retains each receipt once within its real round, a failed attempt and the round's next attempt each as its own row. `receipt` is the basename; a row without it names the round's one receipt. `record-push` appends each restack run once, with `round_id` of `restack-` plus the run id, beside the run's `validate` stage. `kind` is `implement`, `fix` or `restack`. `mode` is the run mode. Optional `lanes` and `selection` carry the command's reported selection; missing selection reads as unreported. A run the runtime started is recorded twice: this row carries the checker's minutes, and the round's `validate` entry on `stages` carries the runtime's `start`, `end` and `proof`; both stand. The merge cycle counts the `full` rows as `rounds.full_mode_runs`, one per recorded run whatever its verdict (`full` is the `DEV_VALIDATE_CMD` run, which need not be the whole suite; a started run no receipt and no push recorded is not counted), and `oversee-report`'s validation-duration rows read the entries. The `lane-long` event's `validation_runs` count reads the worktree's `tmp/validation-runs` inventory instead, one line per started run, accepted or not; an inventory of any other shape is unread |
| `stages` | object[] | Stage times in epoch seconds: `{kind, round_id, start, end}`, with `outcome` once the `accept-result` request through `orch-runtime op` closed the entry. The `begin-round` request writes `dev` or `review` starts in the same locked write as the token. It closes every earlier open stage of the same kind at the new start and sets `superseded: true`. Other kinds and closed stages stay unchanged. `orch-runtime dev-return check` sets the dev entry's kind to `implement` or `fix`; it writes no end and no `validate` entry, and `orch-runtime review-artifact check` writes no stage. The runtime is the one writer of an end: `accept-result {round_id, outcome}` closes the round's own entry and `accept-result {round_id, run_dir, outcome}` the admitted `validate` entry that names the run, `outcome` one of `pass`, `fail`, `no-verdict`, `lost`, `stopped` or `no-change`, the word for a round its item permits ending with no change, required and computed by the round acceptance owner, a request without it refused as `request-invalid`; `end` is the accept time, or, with `end: {from_artifact: PATH}`, the modification time the runtime reads from that file, refused as `end-artifact-unreadable` when it cannot and as `end-out-of-range` outside `[start, now]`; [review-pr.md § 3.3](../workflows/review-pr.md#33-present) names the batch's last accepted artifact. `reconcile-round {round_id}` closes every open `validate` entry of the round whose run will not end on its own: with the run's sentinel verdict, `stopped` for an admitted directory never created, a refused or never attempted start, or a run `validate stop` ended, `lost` for a run whose recorded child is gone without its sentinel or that never recorded one and no `stop` stands; a run whose child still runs stays open, a run the runtime cannot read stays open and is reported; `validate_rounds` and every start are untouched. A repeated accept changes nothing and reports the recorded end and word; a superseded entry refuses. A round's `validate` entry is opened by the `record-validation-admission` request as `{kind: "validate", round_id, run_dir, start, end: null}` before the validation runs: without `run_dir` the runtime mints the run id and `run_dir` is `<worktree>/tmp/dev-validate-<run_id>` under the item's `worktree`, the directory `dev-validate-run --run-id` creates; the request is idempotent per round, a repeat returning the round's open admission with `admitted_now: false`, and `attempt: next` mints a further attempt beside it, as a plain request does once every admitted run of the round is closed; with `run_dir` the runner's directory is admitted as given, and the same directory again is a no-op. `record-push` writes `{kind: "validate", reason: "restack", round_id: null, run_dir, start, end, outcome, proof}` once per finished run directory: for the restacked head after a confirmed push, or for the current head through its `record-restack-validation` mode. A skipped re-test records no earlier head's run. An open stage keeps `end: null`. `orch-runtime cycle stages ITEM` reads the lane's state by its item key, then by the pull request its record waits on, then from that pull request's saved copy, and prints its `stage item=` rows sorted by start. The close's merge cycle copies the entries to `cycle.stages`, and `orch-runtime cycle report` prints the recorded rows |
| `stages[].authorization` | object | `{by, id}`, `by` one of `overseer` or `owner-directive`: who accepted the step, written at the close by `accept-result {round_id, outcome, authorization}` on the round's own entry, by the lane's own workflow and nothing else; a run's close (`run_dir` given) names none. A plain close names none: the lane's acceptance of its own round skips no ask. A `directive-[ID]` item's round names `{by: owner-directive, id: [ID]}`, the directive the change was made under, and refuses a close without it as `authorization-missing`. `{by: overseer, id}` names an act of the overseer on this lane's own question: `id` is the id of the envelope in the lane's inbox that answers the lane's `lane-question`, or of an owner's directive the overseer relayed to the lane; a launch ruling, a fleet-log row or a session id is never the id, since one of those would mark every round of the lane authorized. It is part of the acceptance's identity: a repeat naming another, or naming one on an entry closed under none, refuses `authorization-differs`. `submit-pr.md` § 4 step 1 reads it through `orch-runtime state inspect --item` and, under a recorded one, takes each ask's `auto-recommended` action |
| `stages[].body_revision` | string | The item body's `updatedAt` as the caller's own tracker read returned it, handed to `begin-round {kind, body_revision}` and recorded on the new entry. The reply's `body_moved` is `true` where it is later than the latest revision an earlier round of the kind recorded, compared as the tracker's ISO 8601 UTC text, and `false` where the request names none, no earlier round of the kind recorded one, or the revision is equal or older |
| `stages[].stop` | object | `{at}`: written by `orch-runtime validate stop --item [ISSUE_ID] --run-dir [RUN_DIR]` on an open `validate` entry before it ends the run's job. The closer reads a gone job with no sentinel as `stopped` where a `stop` stands and as `lost` where none does |
| `summary_comment` | object | `{id, at, attachments}`: the item's Completion Summary comment on the tracker, headed `## Completion Summary`, the one the acceptance created, or found through the tracker CLI's list after a crash between its create and this record, and updates in place on every later acceptance. `at` is the stamp of the last post. `attachments` is the list of `{name, url, image}` the comment's body carries as links, read from the create's answer or the found comment's body and rendered under the summary on every update, since an update replaces the body whole; absent where the comment carries none. A record carrying an `origin` word reads without it. `accept-result {summary_file, attachments}` posts after the close, one `--attach` per path where it creates, and records the id through its own repeat, refusing `summary-comment-differs` where the record holds another |
| `ci_rerun` | object | `{head, run, at}`: the one automatic rerun of a transient CI runner failure on `head`, written by the CI wait of `submit-pr.md` § 5.1, `ci-fix.md` § 5 and `merge-attempt.md` before it asks `github.sh ci-rerun`; `run` is the run that verb named, written after its answer, and `null` while it has not answered; `at` is the write time, ISO 8601 UTC. A head whose record stands is never rerun again, whatever `run` holds. Those workflows are its one writer and its readers |
| `restack_skips` | object[] | One `{head, condition, validated_head, paths}` entry per restack whose range re-test `restack-skip` skipped, upserted by its `head` ([`merge-pr-restack.md`](../workflows/merge-pr-restack.md) step 2, its one writer): the restacked head, the condition that allowed the skip, `no-conflict` or `version-only`, the HEAD recorded by the matched run, and the files the merge left conflicted, whose only differences are the version field commit-guards reads and changelog entries, empty for `no-conflict`. The lane's status file validation line names each skip, `orch-runtime read-proof` reads a head's skip as the validated run's tree, and `oversee-report`'s Validation row counts the skips apart from the runs |
| `restacks` | number | Completed guarded restacks: `record-push` adds one per restack hop it reconciles before a push, the hop a `worktree create --reuse`, `create --restack` or `restack continue\|skip` completion appended, so the count holds whatever validation route followed the restack. A hop `rebase_map` already holds whole, from a kept map file's re-run, adds none. The `lane-long` event and `orch-runtime report render`'s Rounds line read it as `restacks=`; absent reads 0 |
| `review_wave_done` | string[] | Wave mode only: reviewers whose report artifact validated (or who went unresponsive) in the current review cycle. Reset at each new cycle's first wave; the next wave launches the first budget-sized batch of `[AGENTS]` not listed here |
| `reviewer_slots_observed` | number | Effective wave size proven by the runtime when a persistent (unlimited-budget) launch hit the thread limit. While set, `review-pr.md` § 2 enters wave mode at this size even though `REVIEWER_SLOT_BUDGET` is `0` |
| `pre_delegate_sha` | string\|null | HEAD before delegation — scopes re-review diffs. review-pr § 2.2 sends it to a re-review re-entry as `Diff-range`, a boundary no reviewer can derive from its own delegation. review-pr-comments § 6.1 writes it before a fix set and sends it as the verification pass's `Diff-range` |
| `skip_qa` | boolean | Skip QA for re-cycle (cleared after routing) |
| `cycles` | number | General fix-round tally — `dev-fix.md` increments it on every fix round (review-pr § 4 and § 7, plus pre-loop review/submit rounds). It fills review-pr § 1.2's previous-cycle block and the session summaries; it decides no cap |
| `rereview_cycles` | number | § 4 → § 2 re-review cycles entered, counting entries already taken. `orch-runtime state set … /rereview_panel` raises it in the same locked write it gates, so only that re-entry spends the budget `REVIEW_MAX_CYCLES` bounds — a § 7 QA re-check (`qa_recheck_panel`), a § 2 verification pass (`verification_panel`), and any fix round do not. At a cap of 0 no entry is allowed: the review runs one blockers-only fix round, accepted on its validation, which `review_fix_round` records |
| `review_fix_round` | boolean | `true` once review-pr § 4 Fix Delegation has run, written by that step alone on every run whatever the round's items come to, and never cleared. At a `REVIEW_MAX_CYCLES` of 0, `cap --item` reads `below` until it is set and `at-cap` after, so the review runs one fix round |
| `submit_cycles` | number | Submit-PR iteration count (created-issue re-submit loops) |
| `review_delegated_at` | number | Epoch seconds of last review delegation — the freshness boundary `review-pr.md` § 3 passes to `orch-runtime review-artifact check --delegated-at` |
| `dev_delegated_at` | number | Epoch second of the round's delegation. [`../references/skill-rules.md` § Round Closure](../references/skill-rules.md#round-closure) owns its uses |
| `dev_round_id` | string | Unique per-delegation round token, minted immediately before each dev or QA delegation and embedded in it. Every dev workflow mints it with the `begin-round` request `{kind: dev}` through `orch-runtime op`. It is the completion artifact's identity ([`dev-return.md`](dev-return.md)) and, on a fix round, the delegated-item record's ([`dev-round.md`](dev-round.md)) |
| `ci_round_id` | string | CI-fix round token, minted by `orch-runtime state new-round-id --item [ISSUE] /ci_round_id` before CI cleanup, the form `begin-round` mints and no stage. It keys the CI cleanup entries in `round_prunes` |
| `review_round_id` | string | Unique token minted by the `begin-round` request `{kind: review}` through `orch-runtime op` before each review batch, wave or QA delegation. It identifies the current review entry in `stages`; it does not change reviewer artifact freshness or identity |
| `round_prunes` | object | Round id to `{action, used_pct, mark_pct, bytes}`, one entry per round the `prune-round` op request recorded, keyed by the token its `field` names, `dev` for `dev_round_id` or `ci` for `ci_round_id`; a refusal (no round token, an unreadable worktree list, owner or disk, an invalid `ORCH_ROUND_PRUNE_DISK_PCT`) records nothing. `action` is `pruning` from before the cleanup starts until its answer is read, then `pruned`, `failed`, or `unknown` where the answer was lost; `below-mark` under the disk mark, `target-elsewhere` where the Cargo target is outside the worktree, `no-worktree` where none stands. A later prune of a round still recorded `pruning` reports `previous: unknown`. `bytes` is what the prune freed, 0 below the mark or with no worktree. The request is the one writer |
| `tier` | string | The cycle the item runs, `micro`, `small` or `standard`, as `item-tier` assigned it; `set` refuses any other value as `tier-value`. [`start-worktree.md`](../workflows/start-worktree.md) § 1 writes `standard` on every entry and [`small.md`](../workflows/small.md) § 1 then writes `small`, so the record follows the run that executes. `small` holds `REVIEW_MAX_CYCLES` and `REVIEW_MAX_EXTERNAL_ROUNDS` to the tier ceilings `cap` reads, 1 and 2 ([small.md](../workflows/small.md) § 3 and § 4), and refuses a `first_panel`, `rereview_panel` or `verification_panel` with no boolean `external` as `panel-external`, or of more than three reviewers, the external lane counted, as `panel-bound`. Absent, no tier bound applies |
| `pr_order` | string | When the lane opens its pull request, and how far an early one has come. [`start-worktree.md`](../workflows/start-worktree.md) § 2.1 records the order from `pr-order`, and `review-first` where the early open failed. `open-first`, a PR open and its internal review not yet returned, has `review-pr.md` § 1 write the lane's `Review: pending` line and `submit-pr.md` § 2 arm nothing and unarm an armed PR. `review-pr.md` § 9 keeps that line and moves it to `open-first-returned` from that value alone, recording nothing on any other, which sends the next `submit-pr.md` § 2 step 1 through Copilot's thread triage before it pushes the internal review's fix round and keeps `review-pr-comments.md` § 7.2 from routing any head; once the push lands, that step writes a lane's review verdict line and, lane or not, moves it to `open-first-pushed` and routes the pushed head. `push-first` opens a draft before internal review; start-worktree § 2.1 runs the review call, which marks it ready and, under `approval`, requests Copilot and records the head. It keeps the pending review line and holds arming until internal review passes. A passing review records `push-first-returned`. Submit publishes combined fixes and runs the review call, which under `approval` requests each unrecorded head, then records `push-first-pushed`. Required CI stays pending until submit § 5 proves the exact published head. Absent, the item runs review-first |
| `first_panel` | object | `{agents: string[], reason, external?}` for review-pr § 2's first-cycle panel, recorded on a § 1 entry: the reviewers the diff and the issue's Done-when give something to read, or the caller's `agents` with reason `caller panel` |
| `recovery_round_id` | string | The round id `orch-runtime round recover` minted when a stalled round had no report, or a report the disk contradicts. That round's own failed recovery is exhausted, never re-delegated again. Beside it, `round_recovery`, `{from, to, reason}`, records the redelegation from the stalled round to the minted one, which a repeated recovery of the same round answers again |
| `rereview_panel` | object | `{agents: string[], reason, external?, domain_reasons?}` for a § 4 fix round re-reviewed by a scoped panel instead of the full set. Setting it is the § 4 → § 2 re-review re-entry. One holding every `first_panel` agent is refused as `panel-copy` unless `domain_reasons` maps each of them to a nonempty string saying why the fix diff concerns that domain |
| `qa_recheck_panel` | object | `{agents: string[], reason}` for review-pr § 7's § 7 → § 6 QA re-check |
| `verification_panel` | object | `{agents: string[], reason, external?}` for a pass over a fix diff no reviewer has seen, which no cap gates: review-pr § 7's § 7 → § 2 pass, review-pr § 4's pass once the budget is spent, and review-pr-comments § 6.1's pass before the push. The `rereview_panel` `panel-copy` rule applies |
| `verification` | object | The verification verdict for a published head, `{head, verdict, reason, source, at}`. `head` is the commit the verdict is about. `verdict` is `pass`, `fail` or `none`; `none` says the repository runs no CI for that head, and holds only with affirmative absence evidence in `reason`, never in place of a result that did not arrive. `reason` says what was read. `source` names the reader: `verify-head` for the runtime's read of a published head, `verify-pr` for its read over a pull request's current head. `at` is the UTC time of the write. The `record-verification` request through `orch-runtime op` is the one writer; `verify-head` and `verify-pr` write through it in the same call; a later write for a newer head replaces the record. submit-pr reads it before the merge step |
| `json_paths` | string[] | Accumulated review JSON file paths. review-pr § 4 Bounded Re-Review reads the reviewers named in them as the domains already reviewed |
| `fixed_items` | object[] | Blockers successfully fixed. A `commit` of the form `dropped:<sha>` marks a fix whose commit vanished in a rebase (its patch was already upstream) — publishers omit it or cite the upstream equivalent, never print it as a live SHA |
| `escalated_items` | object[] | Items dev did not apply, plus items still outstanding when review-pr's cycle cap ends the fix loop. `outcome` records the per-item decision — `"blocked"` (could not fix; the cap path always writes this) or `"skipped"` (deliberately skipped); an entry without `outcome` is treated as blocked. The audit builder maps it to a distinct `origin`. An item is never in both buckets: every dev-fix outcome write clears the item from both, matched on (location, description), before appending its own entry |

## Oversee state

A record a shell launcher wrote also carries a private `recovery` object, the choices it launched with. The model-switch recovery, `lib/lane-relaunch.sh`, composes its `launch-lane` request from the record: the checkout the launch ran from (`checkout`, else `recovery.cwd`, else `mail_root`), its harness, tracker, repository, host and kind, the model the switch recorded with the record's effort, its refresh choice, the account the recovery names, and its `permission`, else the permission word `recovery.flags` carries. It stops a local predecessor through the runtime close on the `no_landing` ground with `interrupt`, and a hosted one through `lane-host stop`, before it launches the replacement.

The `lane-mail-check` hook's `handoff_check` consumes Claude Code's `PostModelSwitch.to_model`. It compares that value with the current session's recorded launch model. Matching models change no state. A switched or unavailable reading writes `model_check` on the current lane record. The tagged outcome retains `session_id`, `launch_identity`, `launched`, `observed`, `at` and `cause`. The launch identity retains the recorded process or pane identity and launch time. The state writer stamps `at` inside its locked update. A lane's recovery records `recovery_started` when it acquires that session's action. Missing or unresolved launch identity and unreadable event identity remain unavailable. The hook hands that notice to the model once per session.

The same locked update appends one `fleet_log` entry with `kind` `model-switched` per affected session. It carries the model-check fields and the lane item. An unavailable reading uses `model-unavailable`. These entries retain their evidence across launch replacement. Repeated events for the same recorded launch cannot append a second switch or dispatch another recovery. The current model check owns duplicate suppression. Archiving old fleet log rows cannot re-arm that launch. Native resume can retain its session ID. A later affected launch retains its own switch evidence and recovery action. The emergency `handoff` retains unfinished attached agents and their known output paths. Model recovery can interrupt an unpushed round. The replacement resumes that durable workflow state.

The lane recovery dispatcher marks the switch row's `recovery` as `starting` before launch, `replaced` after success, or `failed` after failure. A later launch's mismatch also proves a pending `starting` replacement reached a live harness. The dispatcher counts successful replacements since this item's last `model-recovery-reset` row. The dispatcher reads its limit from `ORCH_MODEL_RECOVERY_LIMIT`, default 3. A refusal adds one `model-recovery-limit` row with `recoveries`, `limit` and the keyed refusal in `text`. The first Stop of the bound replacement resets the count when that launch has no mismatch. It writes `model_check.outcome` as `passed` with `session_id`, `launch_identity` and `at`, and appends one `model-recovery-reset` row. Repeated Stops retain that check. A Stop from a stale session cannot reset the current launch.

A native remote lane with no local fleet record reads its launch model from the separate JSON launch record owned by `lane-marker` (`--launch-path`). Its `identity_file` names the predecessor record written by the SSH launch prefix. The hook verifies that the callback descends from that live predecessor. It stores the model check under `model_checks[session_id]` in the item's existing workflow state. A mismatch preserves the durable handoff, adds `cause:"model-switched"` and the recorded `model`, then dispatches the existing stop owner for the verified native predecessor. A failed stop stores `handoff.stop_failure` with `cause`, the affected `pid` (null when the failure names no process), the predecessor `launch` identity, `exit`, and `at`. The detached child also writes a keyed failure to the existing recovery log. A new model handoff clears the prior stop failure. A dispatch failure reaches the callback as unavailable context. The watch reads that handoff through the provider the lane record names and reports it as `handoff`; the overseer handles it, its `stop_failure` included, as [oversee-events.md § Event kinds](../references/oversee-events.md#event-kinds) `handoff` says. No fleet watcher runs on the lane's host.

A lane without readable launch evidence stores the unavailable reading under `model_checks[session_id]` in its existing item workflow state. The hook uses the state writer's lock when that item state needs initialization. Repeated events for the same launch retain the reading and deliver no second notice. The session continues with its model identity unjudged.

### Prune

The retention duty works on the fleet state `workflow-state-oversee.json` and the directory that holds it, by default `tmp/` in the main checkout, on its cadence in the watch; no step prunes by hand. A checkout with no fleet state, where no overseer runs, takes the same pass at each item's close-out, which [§ Item close-out](#item-close-out) runs: there no lane record judges an item.

Beside the overseer mailbox's compaction (the Overseer mailbox row above), the duty removes these kinds alone:

- An item's workflow state once every lane record of the item has ended, as the Lane records row above states.
- An item's workflow state that no lane record names, last written more than `ORCH_RECORD_RETENTION_DAYS` days ago, unless it names a linked worktree that stands, by its `worktree` field or by its `branch` checked out there. The item's close-out takes that state when the item ends, and a lane closed while its item was open leaves it for a later resume.
- A closed intent's pane receipt, job request and job record, `intents/[ID].pane`, `intents/[ID].request` and `intents/[ID].job`: once both the intent's `completed_at` and the file's own last write are more than `ORCH_RECORD_RETENTION_DAYS` days old, or the file's own write alone where the intent records no `completed_at`. An open intent's files and a closed intent's `.notice` stay.
- An owner progress report, `MM-DD-HH-MM.md` or `MM-DD-HH-MM-succession.md` in the progress report directory, last written more than `ORCH_RECORD_RETENTION_DAYS` days ago.
- A session row file `session-[SERVER_PID]-[PANE].jsonl` under the main checkout's `tmp/lane-mail/overseer`, with no age test: when the tmux server answering at the ambient socket (`$TMUX`, else the default) is that pid and holds no pane `%[PANE]`. It stays where the fleet record names it (`overseer.session_rows`, `overseer.pending.session_rows`, `pending.session_rows`), where it is a link, and where that server does not answer or its panes cannot be read.
- A rotated segment of the watch's event log, `oversee-watch.log.[N]` beside the fleet state, last written more than `ORCH_RECORD_RETENTION_DAYS` days ago, the newest segment always kept. It leaves at the start of the pass, with no archive.
- Lane rows and fleet log rows, as their rows in the table above state.

Every other entry stays, whatever its age or name: a lane's files, every file under `handoffs/`, the mailboxes, the claim store, the watch's other records, every lock file and operator scratch among them. An entry [§ Item close-out](#item-close-out) names leaves at that item's close-out; any other stays until it is removed by hand.

Every kind but the segments is archived before it goes. Under the lock of each item record it selected, the one `state remove` takes, the duty reads the record again: a record that moved since its selection keeps its item for the next pass, and nothing is reported. It then writes one archive holding each path still going and `records.json`, `{"fleet_log": [...], "lanes": [...]}`, the rows it would drop, at `ORCH_ARCHIVE_ROOT/[REPO]/oversee/prune-[EPOCH]-[SUFFIX].tgz`, `[SUFFIX]` six base-36 characters. `ORCH_ARCHIVE_ROOT` also locates item close-out, mailbox compaction and SSH lane close archives. Its default, path rules and configured-root requirements are in [references/settings.md](../references/settings.md). `[REPO]` is the main checkout's directory name. The directory is `0700` and the archive `0600`. An archive it cannot build fails the pass with nothing removed but the segments: `external-failed` or `io-failed`, a `tar` past its 600 s bound as `external-failed`. The duty then drops an item's lane rows only while they equal the rows it judged, inside the fleet transition, and removes the records of the items that transition confirmed and the paths that name no item. The archive is written before the transition, so it can hold an item the transition leaves standing; the archive root's listing records what passed the re-read, which can be more than what left. When the duty cannot take a record's lock, because a writer holds it past the 10 s wait or a stale mutex stands, that record stays until a later pass. The pass goes on and says `record=[PATH] [CAUSE]` under the failure rule below. No lock file leaves by retention: the shell store locks a lock pathname without checking the inode it holds, so a removed lock would let two writers each hold it once the record is created again. A failed pass is `watch-step-failed step=retention` on the watch's stderr with its cause, and in the event log under [oversee-events.md](../references/oversee-events.md)'s repeat rule.

### Item close-out

`orch-runtime state remove --item ITEM [--archive PATH]...` closes an item out of that directory once it ends. It removes every direct entry of that directory, and every file under `handoffs/`, whose name carries the item as a whole token, whatever its age, the lane status file included; the item's lane mailbox, the record's lock file and mutex, the fleet state and the watch's own records stay. In a lane that runs in its own worktree that is the item's workflow state, which the lane writes under the main checkout, and any file under `handoffs/` named for it; the lane's `completion-summary-ITEM.md`, `dev-return-ITEM-RID-RUNID.json` and the rest land under the worktree's own `tmp/` and go with the worktree. Only an item that ran in the main checkout leaves those beside its state, and there the close-out takes them too.

Before it removes anything, `remove` writes one archive through the retention duty's archive writer, at `ORCH_ARCHIVE_ROOT/[REPO]/oversee/close-[ITEM]-[EPOCH]-[SUFFIX].tgz` on the host it runs on, private and relative to `/` as [§ Prune](#prune) describes. The archive holds every path it is about to remove, the item's lane mailbox beside them, and each `--archive PATH` that exists. `--archive` names a path the caller removes after the close-out: [merge-pr.md § 5](../workflows/merge-pr.md#5-execute-the-merge) step 6 names the worktree's `tmp/`, which holds the item's round artifacts, review artifacts, validation run directories and lane mailbox. The archive keeps each file's bytes and modification time as written. A relative `--archive` path is the caller's working directory's. `remove` holds the item record's lock across the archive and the removals, keeps the record's lock file and mutex, and refuses `lock-timeout` where a writer holds that lock past the 10 s wait. An archive it cannot build refuses as `external-failed` or `io-failed` and removes nothing; a configured root a removal would take along refuses as `archive-root-overlap`, and a relative or `~` root as `setting-invalid`. With nothing to remove and no `--archive` path standing, it writes no archive. Its reply's `result` carries `removed`, the paths that left, `kept`, the archive, or null where it wrote none, and `pruned`, the retention pass it runs where no fleet state stands, null where one stands, its `unlocked` naming each record that pass could not lock. A path it cannot remove refuses as `remove-failed kept=ARCHIVE cause=`, the archive already holding it. A lane's own run calls it at [merge-pr.md § 5](../workflows/merge-pr.md#5-execute-the-merge) step 6, and the runtime's close runs the same close-out on the fleet's state directory, before the provider's close, at a close whose ground ends the item: a terminal tracker verdict, or a terminal close of a sandbox its provider no longer lists; a removal that fails holds the close open with its cause. A `keep-sandbox` or park close, or one of an item still open, keeps the files a relaunch resumes into, its reply noting `item-files-kept cause=`. A file with no item in its name leaves only as [§ Prune](#prune) states.

The watch's own records beside the fleet state, its event log `oversee-watch.log` and the `oversee-watch.err` its launch appends to, stay whichever start launched it, and the retention duty removes only the rotated log segments [§ Prune](#prune) names. A waiter's run directory under a checkout's `tmp/` ([waiter-launch.md § Launch](../references/waiter-launch.md#launch)) stays until it is removed by hand.

## CLI

A workflow reads and writes a record through `.agents/skills/orch/scripts/orch-runtime`; `orch-runtime --help` and `orch-runtime state --help` are the contract. The `state` family addresses an item as `--item [ISSUE_ID]` and the fleet record as `--fleet`, takes the global `--state-dir` before the verb, and names a field by JSON pointer, `/pr_review/mode`. Every verb prints the runtime's JSON reply, `ok` true with the `result` the verb names, or `ok` false with `refusal.key`, the keyed line on stderr and exit 1; a caller that projects a reply holds it in a variable and runs the projection only after exit 0. Its reads are `inspect` (the whole record under the reply's `.result.state`), `get` (the value at the pointer as `.result.value`, the whole record with no pointer, `null` for an absent one), `exists`, `path`, `cap`, `findings query`, `log takeover|audit`, `progress-report-path` and `handoff-standing`; `init` creates the file exclusively and refuses a standing one, taking no lock; its other writes, each under the record's lock, are `set` and `append` (every pointer and value pair of the call in one write), `set-file`, `append-file` and `upsert` (the one JSON value read from a file, so text crosses no argv; `append-file --unique` appends nothing where the array already holds that value; `upsert` replaces every element whose `--key` field equals the value's), `merge` (a fleet lane found by its `item`, `--lane`, each field the file names replacing the lane's and its `obligation` bound once, a differing binding refused `obligation-conflict`), `bucket`, `close-all`, `increment`, `set-now`, `set-git-head`, the turn-end hook's `heal` and `model-check slot|record|reset`, and the verbs whose rule is a decision: `head-budget take`, `post-pr-stop record|record-if-empty`, `standing add|lift`, `log append` (an `append` or `append-file` at `/fleet_log` is refused as `fleet-log-append`), `findings record`, `new-round-id` (a round token at a pointer, no stage), `handoff-resume` and `remove`; `new-local-key` mints a key and writes nothing. On an item record a `set`, `set-file`, `set-now`, `set-git-head` or `new-round-id` at or under `/handoff` is refused as `handoff-route`; the `handoff` row names the record's writers. The runtime's item operations, `begin-round`, `record-validation-admission`, `accept-result`, `reconcile-round`, `record-verification`, `verify-head`, `verify-pr`, `verify-review`, `approve-head`, `record-handoff`, `resume-handoff`, `validate`, `record-queue-watch`, `record-push`, `prune-round` and `record-qa-decision`, run as `.agents/skills/orch/scripts/orch-runtime op --item [ISSUE_ID] --request [FILE]`, `[FILE]` holding one JSON object tagged by `op` with the request's fields, written with the harness file tool. For a transition the reply's `.result.report` carries the typed result; `record-push` and `prune-round` reply with their own result and exit by its outcome. `verify-head` reads GitHub before its one transition and replies differently: `.result.status` is `complete`, `pending` or `unreadable`, `.result.verdict` and the `record-verification` report at `.result.recorded.report` are present only on `complete`, and `.result.reason` carries the cause otherwise; the **Verification** step of [submit-pr.md](../workflows/submit-pr.md) routes each reply. `orch-runtime --help` is the contract.

To target a state directory from a worktree, pass the global `--state-dir <path>` flag before the subcommand; it is the one way a command line names another checkout's state. The global `--no-private-env` flag takes only `ORCH_STATE_DIR` from the project's settings files, read as data, sets no other `[env]` key and never sources its private env file, for a caller reading another checkout's state; `lane-mail peer` places a peer's `overseer` record through its own reader the same way, taking `ORCH_STATE_DIR` alone from the peer's settings files as data.

`set` and `append` values are JSON only when they look like it: a `{`/`[` prefix parses as JSON, refused as `request-invalid` when it does not parse; exactly `null`, `true` or `false` is JSON; all digits is a number. Every other value is stored as a raw string: pass plain strings bare, `set --item PROJ-123 /pr_review/mode approval`, never `'"approval"'`, which stores the quotes.

## Finding occurrences

`finding_occurrences` is optional item state, `{prior: "none"|"unknown", records: [...]}`. `init` starts it with `prior: "none"`. Absence, unavailable provenance or an unusable failed-check list keeps `prior: "unknown"`, including after later successful reads. It follows the item record's archive and remove lifetime. No total is stored. The runtime's `findings` verbs derive counts; patched and frozen records and `repeated_class_rounds` keep the disposition meaning and patched-commit units their own rows define.

### Record verified findings

This is the review-batch admission and completion contract for review producers feeding an item's fix or filing routes. Callers supply the item key and worktree, local or native identity, dry-run status, and their existing launch, acceptance and disposition routes. They keep their panels, deadlines, continuation proofs, advisory failures and round allowances.

1. **Admission, before launch.** Ensure the caller's item state exists through its existing initialization route. Mint the batch token through the runtime, writing `[WORKTREE_PATH]/tmp/orch-op-[ISSUE_ID].json` with the harness file tool as `{"op": "begin-round", "kind": "review"}`, then stamp its freshness boundary:

   ```bash
   .agents/skills/orch/scripts/orch-runtime op --item [ISSUE_ID] --request [WORKTREE_PATH]/tmp/orch-op-[ISSUE_ID].json
   .agents/skills/orch/scripts/orch-runtime state set-now --item [ISSUE_ID] /review_delegated_at
   ```

   Bind the reply's `.result.report.round_id` and the stored `review_delegated_at` boundary to this batch's assignments. A fresh wave or QA delegation is a batch. A confirming local pass takes fresh admission under its existing bound. A proved original-batch continuation keeps its original binding instead of stamping again. Under dry-run, make neither write and keep round provenance unavailable.

2. **Acceptance.** Check each assigned report through the existing acceptance owner:

   ```bash
   .agents/skills/orch/scripts/orch-runtime review-artifact --text check --file [ARTIFACT_PATH] --worktree [WORKTREE_PATH] --delegated-at [BOUND_REVIEW_DELEGATED_AT] --issue [ISSUE_ID]
   ```

   Under dry-run, omit the unavailable boundary and `--issue` to avoid recording a stage. The caller keeps its specialized acceptance checks and failure route. Only accepted evidence supplies findings. Retain its original path, batch token, boundary, array and index through disposition, even after another batch starts. A native report's `qa_metadata.review_round_id` must match its assigned token; dry-run reports use `null`. A missing original binding stays unknown, never today's mutable token. A failed or unavailable advisory review supplies no finding or clean pass.

3. **Completion, before routing away.** Apply the caller's existing finding-disposition pass, Step 0 first. Write the batch file below with the harness file tool from every accepted source before display deduplication. Complete this step before any fix delegation, issue filing, empty-result exit or return, including reply-only and bounded confirming passes. Record verified true findings that survived Step 0, including findings tracked instead of fixed. False claims, questions and Step 0 exclusions add no record. An accepted clean batch has `records: []`. Under dry-run, report proposed observations and unavailable provenance without writing state. A failed or unbound observation follows the unknown-coverage rule below before a later query can claim completeness.

```json
{"records":[{"kind":"review","location":"src/x.rs (`f`)","owner":"src/shared.rs (`rule`)","source":{"round_id":"R","artifact":"tmp/review-reviewer-correctness-T.json","array":"blockers","index":0,"identity":["artifact","tmp/review-reviewer-correctness-T.json","blockers",0]}}]}
```

Omit absent `owner`. Set `source.round_id` from the retained original batch token. For original local reviews identity is `["artifact", original_path, array, index]`; for inline/PR-level copies it is `["native", source_type, original_id]`, preferring the original comment ID and using a thread-only ID conservatively once. A body entry uses `["native", "review-body", original_review_or_comment_id, entry_token]`; bare `file:line` supplies no native identity. Copied native findings never fall back to local artifact identity. An unavailable round, class or native binding sets `unknown: true` and omits that observation; keep any other bound records in the batch. With none bound, this is `{"unknown":true,"records":[]}`. Outside dry-run, record through the existing state writer:

```bash
.agents/skills/orch/scripts/orch-runtime state findings record --item [ISSUE_ID] [BATCH_FILE]
```

The recorder retains the first source provenance. Same-identity/class reads add nothing, even after a new round stamp or native retriage. A changed class under that identity refuses without rewriting it. A nonzero record result is unread coverage: preserve it through the existing design route and record an unknown batch before any later query can claim complete coverage. A failed unknown write remains unread; it supplies no zero/one count.

`orch-runtime dev-return check` records validation refusals in its recording step for a schema-valid receipt, including a failed original and its recovery separately. It splits the receipt's `FAILING: check1,check2` list, trims outer whitespace, and deduplicates exact names within one receipt. Each row is `{kind:"validation", check, source:{round_id, receipt, identity:["receipt", round_id, receipt, check]}}`. Empty names retain unknown coverage. Pass, pending CI, no-verdict, missing/invalid receipts and run-live supply no refusal. Runner logs remain evidence; this interface claims no unpublished check identities. A stage-recording failure's existing advisory diagnostic leaves occurrence coverage unread too; it never proves complete recording.

### Query and admission

Write requests as an array of `{kind:"review", location, owner?}` copied from the proposed fix's source finding, or `{kind:"validation", check}` copied EXACTLY from the failed source receipt. Never derive a validation name from review-item prose. `orch-runtime state findings query --item [ISSUE_ID] [REQUEST_FILE]` answers `{prior, classes:[{class, observed_count, prior, sources}]}` as the reply's `result`. Without the request file it reports all known classes. Review matching takes a request and a record that share a location or owner cause key, with no transitive aliases; validation matches exact check names. A request with no usable key reports `observed_count: null` and `prior: "unknown"`. Unknown prior coverage makes a numeric count a known lower bound; two attributable sources still establish recurrence. Query failure remains unread.

Both direct fix owners read that result before stamping, pruning or changing delegation time, under [design-review.md](../references/design-review.md). Carry the reply's unchanged `result` in the existing ask/status and next delegation, and give the file holding it to `orch-runtime round stamp --finding-occurrences-file`. No observation interrupts active work, changes a disposition, or grants another round or validation start.
