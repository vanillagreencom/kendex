# tools/

This repository's own scripts and the exclusion lists its commit guards read. Nothing here is catalog content: these run in this repository's commit chain and in CI, never on a consumer's machine.

- A script's suite belongs at `tests/<n>.test.sh`, where the `guards-tools` shard of `../.github/workflows/skill-tests.yml` runs it; `release-channel-point` is the one script with none, exercised from [`../crates/cli/tests/release_workflow/`](../crates/cli/tests/release_workflow/) instead. `tests/orch-shard-partition.test.sh` belongs to no script in this directory: it reads [`../.github/workflows/skill-tests.yml`](../.github/workflows/skill-tests.yml) and judges every seam that sends a suite to one shard — the orch name filters, the shell shards' file rosters, the cargo legs' `--test` target rosters and their doc-test request, and the shard names tracked prose cites — and must run outside the orch battery whose suites those filters partition. `ci-job-set` and `ci-aggregate` share one suite, `tests/ci-class-job-set.test.sh`, which reads that workflow with the harness-ci package's workflow readers and expression evaluator under `../skills/harness-ci/tests/lib/`, for the contract the two scripts and it hold together. `tests/change-class-action.test.sh` belongs to no script here either: it is the suite of `../.github/actions/change-class/classify`.
- `ci-job-set` turns the change class and the changed paths into one `<lane>=true|false` line per gated lane of that workflow, and `ci-aggregate` holds each required context open over the lanes a class stood down. Neither decides a class: `.github/actions/change-class` reads it once from the shipped classifier and publishes it. `guard --full` asks it for a selection from the class, docs verdict and changed paths `dev-validate-run` hands over, so completion validation stands a lane down only where CI does.
- An exclusion list is `<n>-excludes`, read by the one commit-guards lane named in its own header; the row format and what may be excluded are [`../skills/commit-guards/SKILL.md`](../skills/commit-guards/SKILL.md).
- `guard` and `setup` are described in the root [`../AGENTS.md`](../AGENTS.md) § Commands; `guard` is where a repo-specific rule is added, one lane per rule.
- `lane-setup` is the executable body behind [`../.fleet-setup`](../.fleet-setup). It installs clone dependencies before the fleet creates a worktree. On a fleet sandbox it also owns two files: `.cargo/config.toml` in the clone's parent directory, which every checkout beside the clone reads, and sccache's own config when the fleet's cache endpoint is set and sccache is installed. It refuses either file when it did not write it. With `FLEET_WARM=1` and sccache wrapping rustc it then compiles the workspace tests at HEAD in a temporary worktree at the hosted lane path, `worktree path --hosted`, which it removes afterwards, so the shared cache holds a built main under the source path every hosted lane builds in; with no wrapper it only fetches the registry. The script's comment states the sandbox rule, each setting and the choice of build. Its suite is `tests/lane-setup.test.sh`.
- `test-roster` holds every file under a harness crate's `tests/` to a `[[test]]` root that declares it, the rule [`../crates/AGENTS.md`](../crates/AGENTS.md) states; `guard` runs it at commit time and the Linux cargo job of `../.github/workflows/skill-tests.yml` at merge.
- `rust-reads` prints the repository paths the Rust source under `crates/` names in two shapes, `include_str!` and `include_bytes!` literals and literal chains joined onto `CARGO_MANIFEST_DIR`, and the build inputs cargo reads. Its header names the reads it does not follow. `ci-job-set` runs the lint and Windows compile lanes only where a build or include path changed, and gives a `trivial` diff that changes a path it names the measured row. `guard` takes the build rows outside `crates/` as the shared compiler inputs, and `guard --full` takes the include rows to decide whether the cross-target checks and cargo doc run.
- `bash32-lint` and `bash32-parse` hold this directory and the shell the catalog ships to Bash 3.2; where each runs is [`../skills/AGENTS.md`](../skills/AGENTS.md).
- `release-digests` and `release-channel-point` belong to the release feed, which [`../docs/architecture/updates.md`](../docs/architecture/updates.md) covers.
- `check-aur-sync` and `publish-aur` are the AUR side of [`../packaging/README.md`](../packaging/README.md) § Publishing: the first holds each `packaging/arch/<name>/` PKGBUILD to its `.SRCINFO` (and, with `--remote`, to the AUR), the second pushes them from `.github/workflows/publish-aur.yml`, and its `--check-key` proof of the AUR key has its own suite, `tests/publish-aur-check-key.test.sh`. `check-aur-sync` is Python, the one script here that is; its suite is beside the others. `publish-homebrew` is the tap side: it copies `packaging/homebrew/` into `vanillagreencom/homebrew-kendex` from `.github/workflows/publish-homebrew.yml`, deferring a recipe that still pins a placeholder, and its suite holds the must-fail control for that guard.
- `harness-smoke` answers whether each harness on the machine loads what kendex installed for it, and what reaches a lane when a directive is sent to its mailbox, on every harness the `lane-mail-check` row of `../hooks/README.md` gives a delivery mechanism: through that hook's event where the harness runs it, and through the harness's own listing of the wait-point instruction where it runs no hooks; on Claude Code and Pi it also asks whether a lane idle at its prompt is woken for the directive by its own mailbox monitor; it runs installed CLIs against scratch projects and writes nothing to the repository.
