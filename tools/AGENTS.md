# tools/

Repository scripts and commit-guard exclusion lists. These run in the commit chain and CI, not on a consumer's machine.

- A script's suite belongs at `tests/<n>.test.sh`, run by `../.github/workflows/skill-tests.yml`. Exceptions: `release-channel-point` runs through [`../crates/cli/tests/release_workflow/`](../crates/cli/tests/release_workflow/); `lock-record` runs through [`../crates/cli/tests/lock_record.rs`](../crates/cli/tests/lock_record.rs). `tests/orch-shard-partition.test.sh` judges suite partitioning in that workflow and must run outside the orch battery it partitions. `tests/ci-class-job-set.test.sh` and `tests/ci-aggregate.test.sh` share `tests/lib/ci-job-set-world.sh`. `tests/change-class-action.test.sh` and `tests/change-class-proof.test.sh` hold `../.github/actions/change-class/classify` and its `proof`.
- `ci-job-set` turns the class, the changed paths and the event into one `<lane>=true|false` line per gated lane, the shard list and its runner list, less what a `proof_record`'s run ran; `ci-aggregate` holds each required context open over the lanes a class stood down. Neither decides a class: `.github/actions/change-class` reads it once and publishes it. `guard --full` asks it for the pull request's selection from what `dev-validate-run` hands over, so completion validation stands a lane down only where CI does.
- An exclusion list is `<n>-excludes`, read by the one commit-guards lane named in its own header; the row format and what may be excluded are [`../skills/commit-guards/SKILL.md`](../skills/commit-guards/SKILL.md).
- Add repo-specific rules to `guard`, one lane per rule.
- `guard --range` runs, of each touched skill and of `hooks/`, only the suites its changed files reach, and prints `guard-note: suites=<n>/<total> reason=mapped tree=<tree>` for the narrowed run or `suites=all` with its reason where it runs the whole set; the header comments of `guard::mapped_suites`, `guard::path_role` and, for a reference, `guard::reference_readers` are the one statement of the rule. `--full` and the other trees run whole sets.
- `lane-setup` is the executable body behind [`../.fleet-setup`](../.fleet-setup). It installs clone dependencies before the fleet creates a worktree, and gitleaks through [`../skills/commit-guards/scripts/install-gitleaks`](../skills/commit-guards/scripts/install-gitleaks) where no gitleaks on PATH can run the secrets lane's `dir` scan; on a fleet sandbox it also owns the shared `.cargo/config.toml` and sccache config, refusing either file it did not write, and under `FLEET_WARM=1`, where sccache wraps rustc, it warms sccache with a build of main at the hosted lane path, and otherwise only fetches the registry.
- `shipped-refs` holds what a catalog package ships to the rule [`../skills/AGENTS.md`](../skills/AGENTS.md) states: no decision citation the package does not ship a record for, and no relative markdown link into a package it does not require. `guard` runs it and hands it the skill entries no render carries.
- `test-roster` holds every file under a harness crate's `tests/` to a `[[test]]` root that declares it, the rule [`../crates/AGENTS.md`](../crates/AGENTS.md) states; `guard` runs it at commit time and the Linux cargo job of `../.github/workflows/skill-tests.yml` at merge.
- `rust-reads` prints the repository paths the Rust source under `crates/` names in two shapes, `include_str!` and `include_bytes!` literals and literal chains joined onto `CARGO_MANIFEST_DIR`, and the build inputs cargo reads. Its header names the reads it does not follow. `ci-job-set` runs the lint and Windows compile lanes only where a build or include path changed, and gives a `trivial` diff that changes a path it names the measured row. `guard` takes the build rows outside `crates/` as the shared compiler inputs, and `guard --full` takes the include rows to decide whether the cross-target checks and cargo doc run.
- `bash32-lint` and `bash32-parse` hold this directory and the shell the catalog ships to Bash 3.2; where each runs is [`../skills/AGENTS.md`](../skills/AGENTS.md).
- `release-digests` and `release-channel-point` belong to the release feed, which [`../docs/architecture/updates.md`](../docs/architecture/updates.md) covers. `release-installer-check` takes each Linux and macOS installer a release lane built apart and runs the `kendex` command inside it; `release-installer-check.ps1` installs and uninstalls the Windows setup for real, PATH edit included. It is the one PowerShell script here, with no suite: nothing on a Linux or macOS host runs an NSIS setup, so the release lane is its proof.
- `check-aur-sync` and `publish-aur` are the AUR side of [`../packaging/README.md`](../packaging/README.md) § Publishing: the first holds each `packaging/arch/<name>/` PKGBUILD to its `.SRCINFO` (and, with `--remote`, to the AUR), the second pushes them from `.github/workflows/publish-aur.yml`, and its `--check-key` proof of the AUR key has its own suite, `tests/publish-aur-check-key.test.sh`. `publish-homebrew` is the tap side: it copies `packaging/homebrew/` into `vanillagreencom/homebrew-kendex` from `.github/workflows/publish-homebrew.yml`, deferring a recipe that still pins a placeholder. `publish-npm` publishes a `pi-extensions` package from `.github/workflows/publish-npm.yml`, per `../docs/RELEASING.md` § Pi packages on npm; its suite and `publish-homebrew`'s hold a must-fail control per guard.
- `lock-record` records this repository's install record on `main` after a merge and lands it through one rolling pull request; `.github/workflows/lock-record.yml` runs it, and the rule a branch follows is [`../skills/AGENTS.md`](../skills/AGENTS.md).
- `harness-smoke` asks each harness on the machine whether it loads what kendex installed, and what reaches a lane sent a directive; [`../DEVELOPMENT.md`](../DEVELOPMENT.md) § The commit chain states its rows, and it writes nothing to the repository.
- `catalog-release-check` runs the strict check, a fresh install and, with `--prior`, an upgrade install. `../crates/cli/tests/catalog_check.rs` tests it with the built CLI and mutant controls.
