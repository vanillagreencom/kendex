# tools/

Repository scripts and commit-guard exclusion lists. These run in the commit chain and CI, not on a consumer's machine.

- A script's suite belongs at `tests/<n>.test.sh`, run by `../.github/workflows/skill-tests.yml`. Exceptions: `release-channel-point` runs through [`../crates/cli/tests/release_workflow/`](../crates/cli/tests/release_workflow/); `lock-record` runs through [`../crates/cli/tests/lock_record.rs`](../crates/cli/tests/lock_record.rs). `tests/orch-shard-partition.test.sh` judges suite partitioning in that workflow and must run outside the orch battery it partitions. `tests/ci-class-job-set.test.sh` and `tests/ci-aggregate.test.sh` share `tests/lib/ci-job-set-world.sh`. `tests/change-class-action.test.sh` holds `../.github/actions/change-class/classify`.
- `ci-job-set` turns the class, the changed paths and the event into one `<lane>=true|false` line per gated lane, the shard list and its runner list; `ci-aggregate` holds each required context open over the lanes a class stood down. Neither decides a class: `.github/actions/change-class` reads it once and publishes it. `guard --full` uses the pull request selection `dev-validate-run` supplies. Configured completion runs a range.
- An exclusion list is `<n>-excludes`, read by the one commit-guards lane named in its own header; the row format and what may be excluded are [`../skills/commit-guards/SKILL.md`](../skills/commit-guards/SKILL.md).
- Add repo-specific rules to `guard`, one lane per rule.
- `guard --range` and `guard --full` map changed repository files to suites across skills, `hooks/`, `refresh/` and `tools/`. They print `guard-note: suites=<n>/<total> reason=mapped tree=<tree>` for a mapped run or `suites=all` with its reason for a whole set. The header comments of `guard::mapped_suites`, `guard::path_role` and, for a doc, `guard::doc_readers` own the reach rule. Pi-package trees run their declared suites.
- `lane-setup` is the executable body behind [`../.fleet-setup`](../.fleet-setup). It installs clone dependencies before the fleet creates a worktree, and gitleaks through [`../skills/commit-guards/scripts/install-gitleaks`](../skills/commit-guards/scripts/install-gitleaks) where no gitleaks on PATH can run the secrets lane's `dir` scan; on a fleet sandbox it also owns the shared `.cargo/config.toml` and sccache config, refusing either file it did not write, and under `FLEET_WARM=1`, where sccache wraps rustc, it warms sccache with a build of main at the hosted lane path, and otherwise only fetches the registry.
- `shipped-refs` holds what a catalog package ships to the rule [`../skills/AGENTS.md`](../skills/AGENTS.md) states: no decision citation the package does not ship a record for, and no relative markdown link into a package it does not require. `guard` runs it and hands it the skill entries no render carries.
- `test-roster` holds every file under a harness crate's `tests/` to a `[[test]]` root that declares it, the rule [`../crates/AGENTS.md`](../crates/AGENTS.md) states; `guard` runs it at commit time and the Linux cargo job of `../.github/workflows/skill-tests.yml` at merge.
- `rust-reads` prints Rust source reads and Cargo build inputs. Its header owns the row contract and its limits. `ci-job-set` reads the workspace rows for compile lanes and the `--cli-smoke` rows for catalog and smoke. It gives a `trivial` diff that names a Rust read the measured row. `guard` reads the default workspace build and include rows for compiler checks and cargo doc, and manifest rows for local tests.
- `bash32-lint` and `bash32-parse` hold this directory and the catalog's shell to Bash 3.2; where each runs is [`../skills/AGENTS.md`](../skills/AGENTS.md). `bash32-lint` refuses `"${4:-{\}}"`.
- `exec-bits` holds every tracked skill script, skill test and hook test, less libs and controls, to mode 100755 in the index; `guard` runs it at commit time and the `guards-scans` shard of `../.github/workflows/skill-tests.yml` at merge.
- `release-digests` and `release-channel-point` belong to the release feed, which [`../docs/architecture/updates.md`](../docs/architecture/updates.md) covers. `release-installer-check` takes each Linux and macOS installer a release lane built apart and runs the `kendex` command inside it; `release-installer-check.ps1` installs and uninstalls the Windows setup for real, PATH edit included. It is the one PowerShell script here, with no suite: nothing on a Linux or macOS host runs an NSIS setup, so the release lane is its proof.
- `check-aur-sync` and `publish-aur` are the AUR side of [`../packaging/README.md`](../packaging/README.md) § Publishing: the first holds each `packaging/arch/<name>/` PKGBUILD to its `.SRCINFO` (and, with `--remote`, to the AUR), the second pushes them from `.github/workflows/publish-aur.yml`, and its `--check-key` proof of the AUR key has its own suite, `tests/publish-aur-check-key.test.sh`. `publish-homebrew` is the tap side: it copies `packaging/homebrew/` into `vanillagreencom/homebrew-kendex` from `.github/workflows/publish-homebrew.yml`, deferring a recipe that still pins a placeholder. `publish-npm` publishes a `pi-extensions` package from `.github/workflows/publish-npm.yml`, per the npm-deploy skill § Publish, tag, refresh, verify; its suite and `publish-homebrew`'s hold a must-fail control per guard.
- `lock-record` records this repository's install record on `main` after a merge and lands it through one rolling pull request; `.github/workflows/lock-record.yml` runs it, and the rule a branch follows is [`../skills/AGENTS.md`](../skills/AGENTS.md).
- `harness-smoke` asks each harness on the machine whether it loads what kendex installed, and what reaches a lane sent a directive; [`../DEVELOPMENT.md`](../DEVELOPMENT.md) § Test states its rows, and it writes nothing to the repository.
- `catalog-release-check` runs the strict check, a fresh install, the released reader over shipped manifest schemas and, with `--prior`, an upgrade install. `../crates/cli/tests/catalog_check.rs` tests installation with the built CLI; `tests/catalog-release-check.test.sh` holds the schema refusal and its control.
