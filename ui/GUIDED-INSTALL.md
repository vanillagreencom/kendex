# The guided install, and what a write leaves behind

The `ui/` rules for how an install is asked and where it lands, and for what runs behind a write that reaches a project. `AGENTS.md` points here.

- One guided install, `src/stores/install-flow.ts` plus `src/components/install/install-dialog.tsx`, mounted once in `App.tsx`: every Install anywhere opens it with an ask, and nothing else builds a `marketplaceInstall` request. It asks what and where; the tools question is asked only for a single place, and only a personal subscription may be redirected into a project.
- A subject carrying a `template` installs that whole saved selection instead of walking its groups: a template's members span marketplaces and its own copies, which is more than one `marketplaceInstall` carries, so the flow sends it to `templateInstall` once per place. It is the only subject with no groups, and it answers the same what and where questions as every other.
- A place a browse was begun for travels as `nav.ts`'s `installInto`, stated by the caller and cleared by every navigation that is not a browse; the flow opens on it. A named place the install cannot reach opens on nothing rather than on another place: the errand was for that one.
- Whether a place can be written to is `src/lib/reachable-projects.ts`, answered from the reading rather than from its absence — with no scan landed nothing is offered, because the folders an empty missing list would clear are the ones nobody has looked at. Every surface offering a write reads it: a project card's actions and empty state, and the destinations here, both arms of them. The answer is taken again where the write happens, since a scan landing behind an open dialog can take a folder away.
- A folder that stops being a project — reconnected elsewhere, or removed — is marked in `src/lib/forgotten-roots.ts`. A store holding something per project drops it and asks there, so a read still out cannot land it back; asking about a folder again is what unmarks it.
- Registering a project and reading what it holds are separate answers: `settings-projects.ts` answers the registry write, `project-setup.ts` carries the read's checking and unchecked states, and no surface shows zero as a checked result before that read lands.
- One reader action can run `writingRepo` many times — the guided install writes per place and per marketplace — so anything behind it appends, refreshes or reports once for the run, never assumes a single write. `src/lib/rescan.ts` holds that rule.
- A write reads the tracked projects before it runs, through `src/lib/rescan.ts::beforeWriting`, so the offer after it is about what that write did rather than about everything pending. The first reading of each project stands until that project's question is answered, which is what makes one reader action one action. A write that spells `rescanEverything` out for itself calls `beforeWriting` too, inside its own busy window.
- What each project has waiting for a commit is a passive read, `src/stores/project-changes.ts`, on the same refresh path as the rest: it draws the project card's line, the project view's line and the review page, and it opens nothing.
- Every question a write leaves behind is asked in the order `src/lib/asks-first.ts` states, and that file is the only place stating it: a dialog that adds a condition of its own is how two modals end up on screen together. A question's own failure surface is part of it.
- A read behind a committed write cannot refuse it. `marketplaceInstall` reads the subscription and the repository effects back after the plan lands, so a failure there answers as what could not be read, beside the place it is about, and the rows the caller had stay put.
